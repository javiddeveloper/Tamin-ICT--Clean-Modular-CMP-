## 1. Editing a draft never calls the update endpoint — High

**Files:** `feature/workshops/src/commonMain/kotlin/com/tamin/taminhamrah/feature/workshops/ui/workshopRecentlyAddedMembers/WorkshopRecentlyAddedMembersViewModel.kt:376-391`,
`core/core-network/src/commonMain/kotlin/com/tamin/taminhamrah/apiService/WorkShopsApiService.kt:217-221`

```kotlin
/** Creates the registration. `employers`, as the old app posts it. */
@POST("employers")
suspend fun createNewMemberRegistration(
    @Body request: NewMemberRegistrationDTO,
): BaseDTO<NewMemberRegistrationResultDTO>
```

There is exactly one submit path, and it is always a `POST`. `submitRegistration()` calls it whether
or not the form is a fresh entry or a re-opened draft (`edit()` populates `form.personalId` from an
existing `WorkshopNewMemberPR`, and `submitRegistration()` passes that same `form.personalId` through
as a field on the POST body — but never switches the HTTP method).

`old_android` has two distinct calls for exactly this fork:

```kotlin
// ServicesService.kt
suspend fun postNewInsuredInfo(...)          // new person

@PUT("employers/{requestId}")
suspend fun updateNewInsuredInfo(requestId: Long?, dataModel: NewInsuredUserInfoReq?)   // existing draft
```

```kotlin
// InsuredRegistrationFragment.kt:437-447
if (isNewPerson) {
    mViewModel.postNewInsuredInfo()
} else {
    mViewModel.updateNewInsuredInfo(mViewModel.mldInsuredUserInfo.value?.data?.request?.id)
    // or, when resuming from the recently-added-members list:
    mViewModel.updateNewInsuredInfo(mViewModel.mldRecentlyAddedMemberInfo.value?.personal?.id)
}
```

There is no `PUT`/update method anywhere in `WorkShopsApiService.kt`, `WorkShopsRemoteDataSource.kt`,
or `WorkShopsRepository.kt` in the new code — only `createNewMemberRegistration`. Unless the backend
happens to treat a `POST` that carries a `personalId` as an implicit upsert (unconfirmed, and legacy
clearly didn't rely on that — it used a separate `requestId`-keyed `PUT` route for the update case),
re-opening and re-submitting a draft from the "recently added members" list will create a second
`employers` record rather than updating the first.

> **سناریوی بیزینسی نیازمند تایید:** وقتی کاربر یک درخواست نام‌نویسی پیش‌نویس (ثبت‌نشده) را از لیست
> «افزوده‌شدگان اخیر» باز می‌کند و دوباره ارسال می‌کند، نسخه‌ی جدید همیشه با متد ایجاد (POST) به سرویس
> `employers` درخواست می‌فرستد — درست مثل حالت «کاربر کاملاً جدید». نسخه‌ی قدیمی برای این حالت یک متد
> جدا (PUT روی `employers/{requestId}`) داشت که رکورد موجود را به‌روزرسانی می‌کرد، نه اینکه رکورد تازه
> بسازد. اگر سرویس بک‌اند این تفاوت را در نظر نگیرد، نتیجه این می‌شود که هر بار ویرایش یک پیش‌نویس، به‌جای
> تکمیل همان درخواست، یک درخواست ثبت‌نام تکراری برای همان کارگر در همان کارگاه ایجاد می‌کند.

**Suggested change:** confirm with the backend whether `POST employers` with a `personalId` present
is actually treated as an update. If not, add an update path (mirroring legacy's `PUT
employers/{requestId}`) and branch on it the way `InsuredRegistrationFragment` does.

## 2. The "already registered" gate moved to the last step — Medium, needs confirmation

**File:** `feature/workshops/src/commonMain/kotlin/com/tamin/taminhamrah/feature/workshops/ui/workshopRecentlyAddedMembers/WorkshopRecentlyAddedMembersViewModel.kt:360-374`

```kotlin
private fun submitRegistration(): Flow<PartialState> = flow {
    ...
    val isNew = checkNewMemberIsNew(form.nationalId)
    if (!isNew && form.personalId == null) {
        ...
        sendEvent(ShowMessage(Res.string.abs_form_err_already_known))
        return@flow
    }
    val result = createNewMemberRegistration(...)
    ...
}
```

This check now runs as the very last thing before creation — after identity, place/job, **and**
documents have all been filled in — and the person record is only created at that point.

`old_android` creates the person record right after step 1's local field checks pass
(`InsuredRegistrationFragment.kt:430-451`, before any document upload), which is why the legacy
"recently added members" list can show and let the user resume a draft that never got past step 1.
Its own `checkUserIsNew` call happens afterward but its result is never actually branched on in the
fragment — the legacy "is-new" gate is effectively inert, so this isn't a case of the new code
skipping a check legacy enforced; it's the new code adding a **real** enforcement of a check legacy
only pretended to make, but doing so much later in the flow.

Two concrete behavior changes from this reordering, worth confirming are intentional:

1. A user who abandons the form after step 1 or 2 leaves nothing behind server-side — no resumable
   draft appears in "recently added members" the way it would in the legacy app.
2. A user who completes the entire form, including uploading documents, can still be rejected at the
   very last step with «قبلاً ثبت شده» — after having already done all the work — where legacy would
   have (if its check had actually been wired up) rejected them right after step 1.

> **سناریوی بیزینسی نیازمند تایید:** در نسخه‌ی قدیمی، رکورد فرد بلافاصله بعد از تکمیل مرحله‌ی اول فرم
> (قبل از بارگذاری مدارک) در سرور ساخته می‌شد، به همین خاطر اگر کاربر فرم را نیمه‌کاره رها می‌کرد، یک
> پیش‌نویس در لیست «افزوده‌شدگان اخیر» باقی می‌ماند که می‌شد بعداً ادامه‌اش داد. در نسخه‌ی جدید، این
> رکورد فقط بعد از تکمیل کامل فرم (شامل بارگذاری مدارک) و رد شدن از بررسی «قبلاً ثبت نشده»، ساخته
> می‌شود؛ یعنی اگر کاربر فرم را نیمه‌کاره رها کند، هیچ پیش‌نویسی برایش باقی نمی‌ماند، و اگر بعد از پر
> کردن کل فرم مشخص شود که قبلاً ثبت شده، کل کاری که انجام داده هدر می‌رود.

**Suggested change:** not necessarily a bug — confirm with the developer/product whether moving both
the create call and the is-new gate to the end was a deliberate design choice (it does correctly fix
a legacy check that was never enforced) or should be moved earlier to preserve the "resumable draft"
behavior.

## 3. Duplicate document-type selection is no longer prevented — Medium

**Files:** `feature/workshops/src/commonMain/kotlin/com/tamin/taminhamrah/feature/workshops/ui/components/WorkshopFormParts.kt:818-858` (`WorkshopDocumentTypeSheet`),
`.../workshopRecentlyAddedMembers/RegistrationFormPage.kt:567-568`

```kotlin
// RegistrationFormPage.kt
WorkshopDocumentTypeSheet(
    ...
    types = RegistrationDocumentTypes,   // full, unfiltered list, every time the sheet opens
    ...
)
```

`WorkshopDocumentTypeSheet` renders whatever `types` list it's given with no check against
`form.attachments` for a type already picked. `old_android` explicitly guarded against this:

```kotlin
// InsuredRegistrationFragment.kt:604-613
mViewModel.tempUserInfoModel.imageFileList?.forEach {
    if (it.imageName == itemResult.title) {
        duplicatePic = true
        showAlertDialog(..., getString(R.string.error_select_repeat_pic))
    }
}
if (!duplicatePic) { /* open picker */ }
```

A user can currently attach two files under the same category (e.g. two «تصویر پرسنلی») and never
fill in one of the required document categories, with no warning at any point.

**Suggested change:** filter `RegistrationDocumentTypes` against `form.attachments.map { it.type }`
before passing `types` to the sheet, or show an error the way legacy did if a duplicate type is
picked.

## 4. Request-status filter has no UI control — Low

**File:** `feature/workshops/src/commonMain/kotlin/com/tamin/taminhamrah/feature/workshops/ui/workshopRecentlyAddedMembers/WorkshopRecentlyAddedMembersScreen.kt`

The plumbing for filtering by request status is all there and correct — `NewMemberRequestStatus`
mirrors legacy's 7 status codes, and `loadPage()` passes `requestStatus = search.status` through to
the query — but nothing in `WorkshopRecentlyAddedMembersScreen.kt` ever sets
`NewMemberSearch.status`; the search card only renders a national-ID text field. `old_android`'s
equivalent (`WRecentlyAddedMemberSDialogFragment`) let the user pick one of the 7 statuses. The
filter is implemented end-to-end except for the one control that would let a user reach it.

**Suggested change:** add a status picker to the search card (a dropdown or bottom sheet listing
`NewMemberRequestStatus`'s labels), matching the legacy search dialog.

## 5. Confirm and Delete fire with no "are you sure?" dialog — Medium

**File:** `feature/workshops/src/commonMain/kotlin/com/tamin/taminhamrah/feature/workshops/ui/workshopRecentlyAddedMembers/WorkshopRecentlyAddedMembersScreen.kt:257-268`

```kotlin
val onConfirm = remember(member, onIntent) {
    { onIntent(WorkshopRecentlyAddedMembersIntent.Confirm(member)) }
}
val onDelete = remember(member, onIntent) {
    { onIntent(WorkshopRecentlyAddedMembersIntent.Delete(member)) }
}
```

Both fire their intent directly from the button's `onClick`. `old_android` wrapped both in a warning
dialog with a cancel option — «آیا مطمئن هستید که می‌خواهید این کاربر را تایید کنید؟» for confirm
(`WRecentlyAddedMemberListFragment.kt:170-195`) and the equivalent delete-confirmation text for
delete (`:235-261`). Confirming a registration is not reversible from this screen, and deleting a
draft discards whatever the user has already filled in — both are exactly the kind of action this
codebase's own convention (and legacy) gates behind a confirmation dialog.

**Suggested change:** add a confirmation dialog before dispatching `Confirm`/`Delete`, matching the
existing dialog pattern used elsewhere in this module (e.g. the objection-submission dialog in
`ObjectionableDebitScreen.kt`).

## 6. ViewModel-level flows have no test coverage — Medium

**File:** `feature/workshops/src/commonTest/kotlin/com/tamin/taminhamrah/feature/workshops/ui/RegistrationFormRulesTest.kt`

All 9 tests exercise `RegistrationFormState`'s pure computed properties (`isStepComplete`, `error`,
`isLastStep`, `fullName`) — none touch `WorkshopRecentlyAddedMembersViewModel` itself. Untested,
business-relevant behavior:

- `submitRegistration()`'s create-call construction and the `isNew`/`personalId` gate (items 1 and 2
  above — tests here would have caught or at least documented the current behavior).
- `edit()`/`resolveDraftLabels()` — re-opening a draft and resolving city/job codes back to display
  labels.
- `Confirm`/`Delete` intent handling and their guard conditions (`member.canConfirm`, `member.isDraft`).
- The search/status query construction (`loadPage`, `NewMemberSearch`).

> **سناریوهای بیزینسی جاافتاده:** تمام تست‌های موجود فقط منطق ساده‌ی فرم (مثل کامل بودن هر مرحله یا
> اعتبار کد ملی) را بررسی می‌کنند. هیچ تستی برای ارسال واقعی درخواست ثبت‌نام (و تفاوت حالت «کاربر جدید»
> با «ویرایش پیش‌نویس»)، بازکردن دوباره‌ی یک پیش‌نویس برای ویرایش، یا عملیات «تایید» و «حذف» روی لیست
> افزوده‌شدگان اخیر وجود ندارد — دقیقاً همان بخش‌هایی که در این ریویو مشکل داشتن.

**Suggested change:** add ViewModel-level tests for the submit/edit/confirm/delete flows, at minimum
one test per scenario listed above.

## What was done well

- **The national-ID field now gets real checksum validation** (`isValidIranianNationalId`, reusing
  the existing shared, already-tested `core-domain` validator) where legacy only checked for
  blankness — a genuine improvement, and it correctly reuses an existing validator rather than
  reinventing one, per rule 7.
- **Status codes are properly enum-backed.** `NewMemberRequestStatus` matches legacy's 7 status codes
  exactly and is used instead of magic strings anywhere the status is compared or displayed.
- **No hardcoded Persian display strings anywhere in the diff** — all UI text goes through
  `strings.xml`; the only Persian literals found are in `@Preview` fixture data and test assertions,
  the accepted exception already established in prior reviews.
- **The perf/cleanup commits are correct and well-targeted.** `mutableStateMapOf` → `mutableMapOf` for
  `ObjectionableDebitViewModel`'s `debtsByNumber` is a real improvement, not a behavior change — that
  field is a private lookup structure read only inside ViewModel logic, never observed directly by
  Compose (the actual UI-facing state goes through `uiState`), so it never needed to be a Compose
  observable snapshot map. The `Navigation.kt` route/composable deduplication removes what was
  genuinely duplicated code with no leftover duplicates (verified — each route/action defined once).
- **`.catch {}` on `Flow`, not raw `try/catch(e: Exception)`, is used consistently** in the new
  ViewModel — the recurring `CancellationException`-swallowing bug found in several other MRs this
  cycle does not apply here.
- **The 3-step wizard's field requirements per step are a faithful, careful port** of legacy's
  `hasValidData()` checks (identity fields, city/job/start-date, and the final confirmation tick),
  correctly ordered to match the old fragment's step gating.
