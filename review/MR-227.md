## 1. Swallowed `CancellationException` — High

**File:** `feature/contractsAndPaymentAffair/src/commonMain/kotlin/com/tamin/taminhamrah/feature/contractaffair/ui/premiumPayment/ContractPremiumPaymentViewModel.kt`

Round 1 found this at the `pay()` site (then line 164): catching `Exception` broadly without
rethrowing `CancellationException` breaks structured concurrency — if the ViewModel is cleared
mid-request, the resulting cancellation gets reported as a user-facing error instead of propagating.

> **Round 2 — ✅ fixed, at all three sites.** `if (e is CancellationException) throw e` was added not
> only in `pay()` but also in `loadInitialData()`/`calculate()` (the same `catch (e: Exception)`
> pattern appears three times in this file) — broader than what round 1 flagged. A new test,
> `` `Pay intent does not emit ShowError when operation is cancelled via CancellationException` ``,
> confirms the fix at the `pay()` site directly.

## 3. `systemType` hardcoded to `"03"` regardless of premium type — High

**File:** `feature/contractsAndPaymentAffair/src/commonMain/kotlin/com/tamin/taminhamrah/feature/contractaffair/ui/premiumPayment/ContractPremiumPaymentViewModel.kt:136`

```kotlin
private fun pay(): Flow<PartialState> {
    val debit = uiState.value.debit ?: return emptyFlow()
    val systemType = "03"
    return flow {
        ...
        val params = InsurancePaymentParamsDN(
            systemType = systemType,
            ...
```

`systemType` is a fixed literal, but this same `pay()` — and the whole
`ContractPremiumPaymentViewModel` — serves **every** `ContractPremiumType`: the ViewModel itself
branches on `premiumType != ContractPremiumType.OPTIONAL` two lines above (`isFreelance`, line 75),
so optional-insurance payments genuinely flow through this exact code path, not a separate one.

`old_android`'s `EnumInsuranceType.kt:8-13` ties `systemType` to the insurance type, and it is **not**
the same value for all of them:

```kotlin
TYPE_STUDENT("دانشجویی", "01", "03"),
TYPE_FREELANCE("حرف و مشاغل آزاد", "01", "03"),
TYPE_OPTIONAL("اختیاری", "02", "01"),
TYPE_WOMAN("زنان خانه دار", "01", "03"),
TYPE_FRACTION("تکمیل سوابق کسری از ماه", "38", "04"),
```

`"03"` is correct only for freelance (and student/woman, which this MR's `ContractPremiumType` enum
doesn't cover). For `ContractPremiumType.OPTIONAL` it should be `"01"`, and for
`ContractPremiumType.FRACTION` it should be `"04"`. Every other use case in this feature threads
`premiumType` through to pick the right endpoint/variant
(`GetContractDebitUseCase`/`GetContractLastPaymentUseCase`/`DownloadContractReportUseCase`/
`GetPaymentCalculationDetailsUseCase` all take `premiumType` as a parameter) — `pay()` is the one
place that doesn't, which is what makes this read as an oversight rather than a considered
simplification.

`systemType` is exactly the parameter the SEP gateway/backend is documented (in this MR's own
`SpecialInsuredPaymentVerifier` KDoc) to use for routing the post-payment status check
(`sep/online-payment-widthout-back`) — so an optional-insurance or fraction-contract user paying
through this screen would have their payment ticket built with the wrong system routing value, which
risks the payment succeeding at the gateway while the backend either rejects it or records it against
the wrong system.

> **سناریوی بیزینسی جاافتاده:** وقتی کاربری قرارداد «بیمه اختیاری» یا «تکمیل سوابق کسری از ماه» داره
> و از همین صفحه می‌خواد حق بیمه‌ش رو پرداخت کنه، مقدار `systemType` که به سرویس پرداخت فرستاده
> می‌شه همیشه «۰۳» است — درحالی‌که طبق نسخه‌ی قدیمی، برای بیمه اختیاری باید «۰۱» و برای تکمیل سوابق
> باید «۰۴» فرستاده بشه. این یعنی ممکنه پرداخت از نظر درگاه موفق باشه ولی سیستم بک‌اند نتونه اون رو
> درست ثبت کنه یا حتی ردش کنه، چون کد سیستم فرستاده‌شده با نوع قرارداد واقعی هم‌خوانی نداره.

No test currently exercises `systemType`'s value for `OPTIONAL`/`FRACTION` — the only
`OPTIONAL`-related assertion in `ContractPremiumPaymentViewModelTest.kt` checks
`lastLastPaymentPremiumType`, unrelated to this parameter.

**Suggested change:** derive `systemType` from `premiumType`, mirroring `EnumInsuranceType`'s table
(e.g. a `ContractPremiumType.systemType` property or a `when` in `pay()`:
`FREELANCE -> "03"`, `OPTIONAL -> "01"`, `FRACTION -> "04"`), and add a test asserting the value sent
for each of the three premium types.

> **Round 3 — ✅ fixed, exactly as suggested.** `pay()` now derives `systemType` with
> `when (premiumType) { OPTIONAL -> "01"; FRACTION -> "04"; else -> "03" }`, matching
> `EnumInsuranceType`'s table precisely. Two new tests —
> `` `Pay intent sends correct systemType 01 for optional insurance` `` and
> `` `Pay intent sends correct systemType 04 for fraction insurance` `` — load each premium type
> through the real `Calculate`/`Pay` flow and assert the value that actually reaches
> `PaymentRequestDN.verifierReference`, not just an internal variable.

## 4. Hardcoded Persian fallback error message — Low

**File:** `feature/contractsAndPaymentAffair/src/commonMain/kotlin/com/tamin/taminhamrah/feature/contractaffair/ui/premiumPayment/ContractPremiumPaymentViewModel.kt:164`

```kotlin
val message = payment.responseMessage ?: "خطا در دریافت شناسه پرداخت"
```

**Suggested change:** add e.g. `contract_premium_payment_ticket_error` to `strings.xml` and use
`getString(...)`, matching the pattern already established elsewhere in this file
(`ContractAffairsEvent.ShowError`/`ShowWarning` callers upstream all source their text from
resources).

> **Round 3 — ✅ fixed.** `contract_premium_payment_ticket_error` was added to `strings.xml` with the
> original text, and the fallback now reads `getString(Res.string.contract_premium_payment_ticket_error)`.

## What was done well

  `NavigateToPayment`/`SpecialInsuredPaymentVerifier` follow MR !222's documented contract
  (`docs/vault/Payments.md`) exactly — a ticket and verifier key/reference are handed to
  `:feature:payment`, with no gateway URL built locally and no payer-type logic duplicated here.
- **`CancellationException` handling was fixed everywhere in the file**, not just at the one site
  round 1 flagged, and the fix that matters most (`pay()`) has a direct regression test.
- **The loading-state fix reused the existing `LoadingButton` component** instead of hand-rolling a
  second state on top of `TaminPrimaryButton`, which is the right call per `CLAUDE.md` rule 5.
- **Every other premium-payment use case correctly threads `premiumType` through** to pick the right
  endpoint variant, which is exactly what makes item 3 stand out as the one inconsistency rather than
  a systemic gap.
