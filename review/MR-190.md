## 2. `getPersonalInfo(refreshRemote = true)` silently serves stale data when the forced refresh fails — High

**File:** `core/core-data/src/commonMain/kotlin/com/tamin/taminhamrah/data/repository/personal/PersonalRepositoryImpl.kt:38-58`

```kotlin
override fun getPersonalInfo(refreshRemote: Boolean): Flow<PersonalInfoDN?> = flow {
    val localInfo = personalDao.getPersonalInfo().first()
    if (!refreshRemote) {
        emit(localInfo?.toDomain())
    }

    try {
        val response = personalRemoteDataSource.getPersonalInfo()
        val remoteInfo = response?.toDomain()
        if (remoteInfo != null) {
            personalDao.upsertPersonalInfo(remoteInfo.toEntity())
        }
    } catch (e: Exception) {
        if (localInfo == null) {
            throw e
        }
    }

    emitAll(personalDao.getPersonalInfo().map { it?.toDomain() })
}.distinctUntilChanged()
```

`refreshRemote` is a new parameter added in this MR specifically so `GirlSurvivorViewModel.loadPersonalInfo()` can request up-to-date address/phone/national-ID for an official commitment document (`getPersonalInfoUseCase(refreshRemote = true)`). But the `catch` block only rethrows `if (localInfo == null)` — it does not distinguish "no refresh requested, cache is fine" from "refresh was explicitly requested and failed." If a stale local cache already exists and the network call fails (timeout, server error, expired token), the exception is swallowed and the flow re-emits the old cached `PersonalInfoDN` from the DB with no error surfaced anywhere.

**Failure scenario:** the user opens the girl-survivor form; the forced refresh silently fails (poor connectivity); the screen shows old cached address/phone/national-ID as if it were current, with no error or staleness indicator. The user fills in and submits an official commitment form based on data they believe is current but isn't, and `submitRequest()` has no way to know the refresh never actually happened.

**Suggested change:** when `refreshRemote` is true and the network call fails, propagate the error (or at minimum emit a distinct "stale" signal) instead of silently falling back to cache — this repository method is now used for a legal submission flow, not just a display list.

## 3. Viewing the commitment PDF always triggers a redundant second network download — Medium

**File:** `feature/girlSurvivor/src/commonMain/kotlin/com/tamin/taminhamrah/feature/girlSurvivor/ui/GirlSurvivorViewModel.kt:173-226`, `core/core-ui/src/commonMain/kotlin/com/tamin/taminhamrah/ui/components/TaminPdfViewer.kt:80-90`

```kotlin
// GirlSurvivorViewModel
private suspend fun FlowCollector<PartialState>.downloadAndViewForm() {
    ...
    checkGirlSurvivorConditionsUseCase(...).collect {
        ...
        downloadReportPdf()   // fetches the PDF and sets state.viewerPdf, then sends OpenPdfViewer
    }
}
```

```kotlin
// TaminPdfViewer
LaunchedEffect(fileName) {
    val saved = saver.load(fileName)
    if (saved == null) {
        awaitingDownload = true
        requestDownload()   // always called on first open, regardless of whether `pdf` is already non-null
    } else { ... }
}
```

`downloadAndViewForm()` already fetches the PDF and populates `state.viewerPdf` before `sendEvent(OpenPdfViewer)` opens `TaminPdfViewer`. But `TaminPdfViewer`'s mount effect decides whether to call `onRequestDownload()` purely based on whether a file is cached **on disk** under `fileName`, not on whether `pdf` was already passed in non-null. On first open there's no cached file yet, so it unconditionally calls `onRequestDownload()`, wired to `GirlSurvivorIntent.RetryPdfDownload -> downloadReportPdf()`, which immediately does `emit(PartialState.ViewerPdfChanged(null))` — wiping the just-fetched PDF — and re-fetches the same report from the network a second time.

**Failure scenario:** every successful "Download and view form" tap costs two network round-trips for the same PDF and produces a visible loading flicker even though the data was already in hand a moment earlier. Compare with the established pattern elsewhere in the app (e.g. pensioner payroll PDF viewing), which opens `TaminPdfViewer` with `pdf = null` from the start and lets the viewer's own `onRequestDownload` be the single fetch.

**Suggested change:** either don't eagerly fetch in `downloadAndViewForm()` and let `TaminPdfViewer`'s own `onRequestDownload` do the one fetch, or have `TaminPdfViewer`'s mount effect skip `requestDownload()` when `pdf` is already non-null.

## 4. `PlainTextErrorResponsePlugin` installed globally changes the error message for several unrelated existing endpoints — Medium

**File:** `core/core-network/src/commonMain/kotlin/com/tamin/taminhamrah/di/NetworkKoinModule.kt` (installed on `createHttpClient`, `createHealthHttpClient`, `createAuthHttpClient`)

The plugin's own documentation (`PlainTextErrorResponsePlugin.kt:7-11`) says it exists to work around legacy endpoints that "answer failed requests with a bare Persian string instead of the usual `BaseDTO` JSON envelope" — apparently needed for one or more of the girl-survivor/personal endpoints added in this MR. It is installed unconditionally on all three app-wide HTTP clients, so every non-2xx response from every endpoint in the app now runs through `call.save()` + `bodyAsText()` before Ktorfit's normal JSON deserialization — including endpoints whose error bodies are already well-formed JSON and worked correctly before this MR.

Separately (and more concretely user-facing): consolidating several existing endpoints' error handling into the new shared `errorParser.safeCall` helper changes their fallback error from the generic "خطا / مشکلی پیش آمده است" (`ErrorUri.UNKNOWN`) to "لطفا اتصال اینترنت خود را بررسی کنید" (`ErrorUri.NO_CONNECTION_ERROR`) on any non-network exception — affecting `getDisabilityDependentInfo`, `confirmSurvivorsList`, `submitFinalSurvivorPension`, `getFinalSurvivorPensionPDF`, `saveSurvivorInfo` (`PersonalRemoteDataSourceImpl.kt`) and `pensionerPayRollPDF`/`getEdictReportPDF` (`PensionRemoteDataSourceImpl.kt`) — none of which belong to the girl-survivor feature.

**Failure scenario:** a JSON-parsing failure, a null-pointer in mapping, or any non-network exception on any of the affected pre-existing endpoints now incorrectly tells the user to check their internet connection even when connectivity is fine and the real problem is server-side — sending them down the wrong troubleshooting path, and changing behavior on code this MR didn't intend to touch.

**Suggested change:** scope the plugin to the specific HTTP client/route that actually needs plain-text error handling rather than all three global clients, and keep the pre-existing generic-`UNKNOWN` fallback for endpoints whose error handling wasn't meant to change in this MR.

**File:** `feature/girlSurvivor/src/commonMain/kotlin/com/tamin/taminhamrah/feature/girlSurvivor/ui/GirlSurvivorViewModel.kt:188-193, 233-238`

state.confirmPayload?.copy(

This exact overlay appears independently in both `downloadAndViewForm()` and `submitRequest()`.
