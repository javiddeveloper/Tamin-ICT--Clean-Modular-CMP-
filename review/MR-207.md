## 1. Minimum retirement age raised from 42 to 50 — High, needs confirmation

**File:** `feature/retirementPension/src/commonMain/kotlin/.../ui/RetirementPensionViewModel.kt:699,322-325`

```kotlin
/** Statutory minimum, below which the service refuses the request. */
const val MIN_RETIREMENT_AGE_YEARS = 50
...
isAgeEligible = years == null || years >= MIN_RETIREMENT_AGE_YEARS,
```

`old_android`'s equivalent gate (`RetirementPensionFragment.onUserInfoResponse:493`) is:

```kotlin
if (yearsAge < 42) {
    // error_user_age_pension_request, then back to previous
}
```

The new code refuses anyone under 50; `old_android` refuses anyone under 42. If 42 is the correct
statutory floor (early/special retirement categories exist under Iranian social security law —
e.g. hazardous-job retirement, women with 20 years' service, etc. — which can legally retire well
before the general old-age minimum), this change silently blocks every applicant aged 42–49 from
ever reaching the form, with a comment ("Statutory minimum") that asserts correctness rather than
flagging a deliberate change from the ported value.

> **یافته‌ی بیزینسی (فارسی):** در نسخه‌ی قدیمی، حداقل سن برای ثبت درخواست بازنشستگی ۴۲ سال بود. در
> پیاده‌سازی جدید این عدد بدون هیچ توضیحی به ۵۰ سال تغییر کرده. اگه ۴۲ سال واقعاً حداقل سن قانونی
> (مثلاً برای بازنشستگی زودتر مشاغل سخت و زیان‌آور یا مشابه) بوده، این تغییر باعث می‌شه بیمه‌شده‌های
> ۴۲ تا ۴۹ ساله که واقعاً واجد شرایط ثبت درخواست هستند، اصلاً نتونن وارد فرم بشن — بدون هیچ پیام
> توضیحی که چرا رد شدن.

**Suggested change:** confirm with whoever owns the retirement-eligibility business rule whether
42 or 50 is correct today (rules can genuinely change over time, so 50 may be intentional and
current — but the comment gives no indication either way). If 42 was correct and got typo'd/
misremembered as 50, fix the constant. Either way, leave a comment explaining *why* it differs
from `old_android`'s 42, the way this same file already does elsewhere (see the `0015`
status-code fix in `RetirementStage.kt`).

## 2. Rules step shows a paraphrase instead of the actual regulations document — High, needs confirmation

**Files:** `feature/retirementPension/src/commonMain/kotlin/.../ui/components/RetirementDialogs.kt:63-70`,
`.../ui/components/RetirementRulesStep.kt`

`old_android` (`RetirementPensionFragment.initRulesStep:670-697`) opens the actual bundled
`rulesAndRegulationsHtmlFile/rules_retirement.pdf` in a PDF viewer when the applicant taps
"مشاهده ضوابط و مقررات" — the same pattern this project uses elsewhere (e.g. MR !199's
pregnancy-pay rules PDF, MR !196's pension-survivor rules PDF, both confirmed bundled and wired in
their own reviews).

This MR's version of that same link instead opens a short in-app dialog with one paraphrased
paragraph (`retirement_pension_dialog_rules_body`) and an "متوجه شدم" button — no PDF, no full
regulations text anywhere in this diff (confirmed: no `rules_retirement.pdf` or equivalent asset
exists under `feature/retirementPension` or `core/core-ui`). The consent checkbox itself
(`RetirementFormError.Consent`) still gates correctly — the applicant still has to check a box —
but they're now attesting to having read regulations they were only ever shown a summary of.

> **یافته‌ی بیزینسی (فارسی):** در نسخه‌ی قدیمی، دکمه‌ی «مشاهده ضوابط و مقررات» متن کامل آیین‌نامه
> رسمی بازنشستگی (یک فایل PDF واقعی) رو به کاربر نشون می‌داد. در پیاده‌سازی جدید این دکمه فقط یک
> پاراگراف خلاصه‌شده و بازنویسی‌شده در یک دیالوگ کوچیک نشون می‌ده — هیچ فایل PDF یا متن کامل مقررات
> جایی وجود نداره. کاربر تیک «قبول می‌کنم» رو می‌زنه بدون اینکه واقعاً متن رسمی مقررات رو دیده
> باشه، که از نظر حقوقی/انطباق (compliance) ممکنه مشکل‌ساز باشه.

**Suggested change:** either bundle the actual `rules_retirement.pdf` (or its current-version
equivalent) and open it the same way the pregnancy-pay/pension-survivor rules steps do, or confirm
with product/legal that a short in-app summary is an accepted replacement for the full document —
and if so, say so in a comment so a future reviewer doesn't re-raise this.

## 3. Pension estimate caps credited years at 35 — Medium, needs confirmation

**File:** `feature/retirementPension/src/commonMain/kotlin/.../ui/RetirementHistoryCalculator.kt:35,92-107`

```kotlin
/** Contribution years past which extra service no longer raises the multiplier. */
private const val MAX_CREDITED_YEARS = 35.0
...
val creditedYears = min(contributionYears, MAX_CREDITED_YEARS)
```

`old_android`'s `Utility.calculateDayAndWageOfHistory` uses `premiumPaymentYear` (the applicant's
actual contribution years) directly, with no such cap. For an applicant with more than 35 years of
service, the new code will display a materially lower estimated monthly pension than `old_android`
would have for the exact same inputs — this is only a *displayed estimate* (the real eligibility
decision is made server-side by the branch), so the blast radius is smaller than item 1, but it's
still a number the applicant sees and may act on.

**Suggested change:** confirm whether 35 years is a real statutory cap on credited service that
`old_android` simply never implemented (in which case this is a genuine improvement — worth a
comment saying so), or an assumption that crept in; if the latter, remove the cap.

## 4. Address validity check not ported — Medium

**File:** `feature/retirementPension/src/commonMain/kotlin/.../ui/RetirementValidation.kt:52-63`

`old_android`'s identity-step address validation (`RetirementPensionFragment.kt:958-967`) runs
three checks: non-blank, length ≥ 10, and `Utility.checkInputIsValidAddress()` — which rejects an
address containing Latin letters or the character set `` $&+:;=?@#|/'<>.^*()%! ``. `identityError()`
here reproduces the first two but not the third, so an address with Latin characters or those
symbols now passes validation and gets submitted to the server, where `old_android` would have
blocked it client-side.

**Suggested change:** port `checkInputIsValidAddress`'s character-set rule as a fourth check in
`identityError()` (with a test in `RetirementValidationTest.kt`), or confirm the server now
validates/sanitizes this itself and the client-side check is deliberately dropped.

## 5. No test for `RetirementPensionViewModel` itself — Medium

**File:** `feature/retirementPension/src/commonMain/kotlin/.../ui/RetirementPensionViewModel.kt`
(742 lines)

The pure logic this ViewModel depends on is well tested — `RetirementValidationTest.kt` (13
tests), `RetirementHistoryCalculatorTest.kt` (10 tests), `RetirementStageTest.kt` (5 tests) — but
there is no `RetirementPensionViewModelTest.kt` covering the ViewModel's own orchestration: step
transitions, OTP request/verify, document upload, the age/history gate dialogs, and
`toForm()`/final submission assembly. This is the same "logic extracted and tested, but the
ViewModel wiring itself untested" gap, just less severe than MR !198's original finding since the
highest-risk business rules here already live in tested pure functions.

**Suggested change:** at minimum, a test asserting `toForm()` builds the exact request payload
described in this review (all fields populated, `status` defaulted correctly), plus the OTP
verify/`ticketNotFound` path and the age-gate dialog trigger.
