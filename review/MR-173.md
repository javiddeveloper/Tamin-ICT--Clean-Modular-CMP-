## 1. Duplicate `securityModule` registration in Koin — High

**File:** `shared/src/commonMain/kotlin/com/tamin/taminhamrah/di/Koin.kt:22-23,53-58`

```kotlin
import com.tamin.taminhamrah.feature.addDependent.di.addDependentModule
import com.tamin.taminhamrah.feature.addDependent.di.addDependentModule   // duplicate import
import com.tamin.taminhamrah.feature.userRequest.di.userRequestModule
...
        myInboxModule,
        securityModule,
        addDependentModule,
        settingsModule,
        userRequestModule,
        securityModule            // <- securityModule listed a second time
    )
```

This diff (introduced by this MR, visible as `+` lines against the merge-base) leaves `securityModule` in the `sharedModules` list twice and imports `addDependentModule` twice. This looks like a leftover from a bad merge/rebase rather than an intentional change — nothing in this MR's actual feature work (userRequest) needs `securityModule` touched at all.

Duplicate imports are at best a compiler warning, but a module registered twice in the list passed to `modules(sharedModules)` is a real risk: depending on the Koin version/definition kind in `securityModule`, starting Koin can throw at app startup (`Koin: definition already exists` / `A Koin Application has already been started`-style errors for non-factory singles), or at minimum silently doubles definitions that shouldn't be doubled.

**Suggested change:**

```kotlin
import com.tamin.taminhamrah.feature.addDependent.di.addDependentModule
import com.tamin.taminhamrah.feature.userRequest.di.userRequestModule
...
        myInboxModule,
        securityModule,
        addDependentModule,
        settingsModule,
        userRequestModule
    )
```

## 2. Pregnancy request detail is fully implemented but unreachable — High

**File:** `feature/userRequest/src/commonMain/kotlin/com/tamin/taminhamrah/feature/userRequest/ui/UserRequestsScreen.kt:240-246`

```kotlin
onViewDetails = {
    if (request.requestTypeId == UserRequestTypeIds.PREGNANCY) {
        onIntent(UserRequestsIntent.ShowInfoDialog(demoDetailsMsg))
    } else {
        onIntent(UserRequestsIntent.ViewDetails(request))
    }
},
```

`demoDetailsMsg` resolves to the string `user_request_demo_details_dialog`:

> «در نسخه نهایی، این دکمه شما را به صفحه جزئیات همین درخواست با کد پیگیری %s منتقل می‌کنند.»
> ("In the final version, this button will take you to the details page of this request with tracking code %s.")

So for `PREGNANCY` requests, tapping "مشاهده درخواست" shows this placeholder dialog instead of navigating — even though `UserRequestDetailScreen.kt:430-509` already has a complete, correctly-fielded `REQUEST_TYPE_PREGNANCY` branch (insured name, insurance number, mobile, branch, start/end date, childbearing date, doctor name/id, rest days, status/type description — matching old_android's `getPregnancyDaysInfo()` field set), and the repository (`UserRequestRepositoryImpl.getShortTermDetails`) already fetches and resolves pregnancy status/type codes exactly like `ShowRequestInfoViewModel` in old_android does. The whole vertical slice is built; only the list screen's click handler blocks it.

> در نسخه‌ی قدیمی (old_android)، وقتی کاربر روی دکمه‌ی «مشاهده درخواست» یک درخواست غرامت بارداری (کمک‌هزینه بارداری) با وضعیت مناسب می‌زد، به صفحه‌ی جزئیات همان درخواست با اطلاعات واقعی (نام بیمه‌شده، شماره بیمه، تاریخ شروع/پایان، نام پزشک و...) منتقل می‌شد. در نسخه‌ی جدید این مسیر عمداً مسدود شده و به‌جای صفحه‌ی جزئیات (که کاملاً پیاده‌سازی شده و آماده است)، فقط یک پیام «در نسخه نهایی این قابلیت اضافه می‌شود» به کاربر نشان داده می‌شود. یعنی کاربرانی که درخواست بارداری ثبت کرده‌اند، عملاً نمی‌توانند جزئیات درخواستشان را ببینند، در حالی که کاربران انواع دیگر درخواست می‌توانند.

**Suggested change:** remove the `PREGNANCY` special case and route it through the normal `ViewDetails` intent like every other type — the guard and the placeholder string/dialog can be deleted once this is done (unless there's a known server-side gap for pregnancy specifically, in which case say so explicitly rather than leaving a silent demo message in production code).

## 3. Empty request-errors result opens an empty sheet instead of the old "nothing to show" message — Medium

**File:** `feature/userRequest/src/commonMain/kotlin/com/tamin/taminhamrah/feature/userRequest/ui/UserRequestsViewModel.kt:84-92`

```kotlin
private fun handleLoadErrors(requestId: Long, title: String): Flow<PartialState> = flow {
    emit(PartialState.LoadingErrors(true))
    try {
        val errors = getUserRequestErrorsUseCase(requestId).toErrorPresentation()
        emit(PartialState.ErrorsLoaded(errors, title))   // opens the sheet unconditionally
    } catch (e: Exception) {
        emit(PartialState.Error(e.message))
    }
}
```

`RequestErrorsBottomSheet.kt` has no empty-state branch either — if `items` is empty it renders a header, an empty `LazyColumn`, and a close button.

> در نسخه‌ی قدیمی، وقتی کاربر روی «نمایش خطاها» می‌زد و لیست خطاها از سرور خالی برمی‌گشت، اپ به‌جای باز کردن صفحه‌ی خطاها، یک پیام «اطلاعاتی برای نمایش موجود نیست» به کاربر نشان می‌داد. در نسخه‌ی جدید این حالت در نظر گرفته نشده و اگر لیست خطاها خالی باشد، باتم‌شیت خطاها همچنان باز می‌شود ولی چیزی داخلش نیست؛ کاربر با یک پنجره‌ی خالی و گیج‌کننده مواجه می‌شود.

**Suggested change:** mirror the `handleLoadSmartGuide` pattern already used a few lines above it — when `errors.isEmpty()`, emit `PartialState.LoadingErrors(false)` + `PartialState.InfoDialogToggled(...)` with an appropriate "no errors to show" string instead of `ErrorsLoaded`.

## 4. Reject reason is fetched and mapped end-to-end but never rendered — Medium

**File:** `feature/userRequest/src/commonMain/kotlin/com/tamin/taminhamrah/feature/userRequest/ui/screens/UserRequestDetailScreen.kt`

`rejectReason` is threaded all the way through the pipeline:
- `ShowRequestInfoDTO.kt:10` — `@SerialName("rejectReson") val rejectReason`
- `ShowRequestInfoMapper.kt:26,30,34,36` and `UserRequestRepositoryImpl.kt:149` — populated on `UserRequestDetailsDN`
- `UserRequestDetailsPR.kt:14` and `UserRequestMapper.kt:62` — carried into the presentation model

...but `UserRequestDetailScreen.kt` never reads `request.details.rejectReason` anywhere (`grep rejectReason` inside this file returns nothing). In old_android (`ShowShortTermRequestFragment.kt:160-173`), when the latest status entry has a non-blank `rejectReason`, it's shown as a subtitle under the toolbar ("دلیل رد: …", string `reason_rejection_request`) — this is how a rejected short-term request (ill day / pregnancy / orthotics-prosthesis) communicates *why* it was rejected.

This is a business-relevant discrepancy: for a rejected request, the new screen shows the same layout as an approved one, with no reason surfaced anywhere.

**Suggested change:** render `request.details?.rejectReason` (when non-blank) near the top of the detail screen, similar to old_android's toolbar-subtitle placement.

## 5. Submitted-document list/preview/download has no equivalent; the new use case is unused — Medium

**File:** `feature/userRequest/src/commonMain/kotlin/com/tamin/taminhamrah/feature/userRequest/ui/screens/UserRequestDetailScreen.kt`, `core/core-domain/.../useCases/userRequest/DownloadUserRequestDocumentUseCase.kt`

`DownloadUserRequestDocumentUseCase` is added by this MR and registered in `DomainModule.kt`, but has no consumer anywhere in `feature/userRequest` (or elsewhere) — it's dead code as it stands.

In old_android, the short-term request detail wizard (`ShowShortTermRequestFragment`) has a dedicated step that lazily fetches the uploaded-document list (`getDocumentList(requestType)`) and lets the user preview/download each one (`downloadDocument()`, with `getDocumentTitle()` resolving Persian titles per document type). `UserRequestDetailScreen.kt` has no document section at all for any request type.

> در نسخه‌ی قدیمی، در صفحه‌ی جزئیات درخواست‌های کوتاه‌مدت (ایام بیماری، بارداری، اروتز و پروتز)، یک بخش مجزا وجود داشت که مدارک آپلود شده توسط کاربر (مثل گواهی پزشکی یا فاکتور خرید) را نشان می‌داد و امکان دانلود/پیش‌نمایش آن‌ها را می‌داد. در نسخه‌ی جدید این بخش کلاً وجود ندارد؛ کاربر نمی‌تواند مدارکی که برای درخواستش ارسال کرده را در صفحه‌ی جزئیات ببیند یا دانلود کند.

**Suggested change:** either wire `DownloadUserRequestDocumentUseCase` + a document list into the detail screen (matching old_android's step), or, if this is intentionally deferred to a follow-up MR, say so in the MR description and remove/mark the currently-dead use case so it isn't reviewed as finished work.

## 7. Detail-load failure is silently swallowed — Low, needs confirmation

**File:** `feature/userRequest/src/commonMain/kotlin/com/tamin/taminhamrah/feature/userRequest/ui/screens/UserRequestDetailViewModel.kt:37-45`

```kotlin
val showInfo = runCatching {
    getShowRequestInfoUseCase(referenceId, intent.requestTypeId)
}.getOrNull()

emit(
    PartialState.Loaded(
        fallbackRequest(intent, referenceId).copy(details = showInfo).toPresentation()
    )
)
```

If `getShowRequestInfoUseCase` throws (network error, parsing error, etc.), the exception is swallowed and the screen renders the bare fallback request (title/refCode only, no `details`) as if it loaded successfully — `PartialState.Error` is never emitted, so `UserRequestDetailContent`'s `error != null && request == null` branch never triggers. In old_android, an empty/failed detail payload triggers `MessageOfRequestDialogFragment` with `MessageType.ERROR` (`error_recive_data`) and forces the user back to the previous screen (`DismissType.BACK_TO_PREVIOUS`) — a much more visible failure than a silently near-empty screen.

I'm flagging this as `needs confirmation` rather than a definite bug because showing *something* rather than a hard error might be an intentional, more forgiving UX choice for this rewrite. Worth confirming with the developer/product owner whether a silent partial render is acceptable here, or whether a failure should surface to the user the way it did in old_android.
