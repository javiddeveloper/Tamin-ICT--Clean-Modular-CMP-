## 1. A feature-specific keyboard-inset fix also changed the app's shared navigation shell — Medium

**File:** `shared/src/commonMain/kotlin/com/tamin/taminhamrah/ui/navigation/TaminHamrahNavGraph.kt:264-333`

```kotlin
bottomBar = {
    if (isBottomBarVisible) {           // was: AnimatedVisibility(visible = ..., enter = slideInVertically(...), exit = slideOutVertically(...))
        Box(...) { FloatingGlassNavigationBar(...) }
    }
},
...
Box(
    modifier = Modifier
        .fillMaxSize()
        .padding(top = paddingValues.calculateTopPadding())
        .consumeWindowInsets(paddingValues)   // new
        .safeHazeSource(...)
) {
    NavHost(...) { /* every screen in the app, including Home and all other tabs */ }
}
```

Commit `bc9f282c0` ("fix: stop IME insets stacking under the deferred installment bar") explains
the reasoning clearly in its message — the previous `AnimatedVisibility`-wrapped `bottomBar` kept
an IME-sized slot reserved in `Scaffold` even while hidden, and consuming the parent insets in the
shared `NavHost` was the fix. That's a real, well-diagnosed root cause, not a hack.

The scope is what stands out: `TaminHamrahNavGraph` is the single top-level `Scaffold` +
`NavHost` for the entire app (`isBottomBarVisible = currentTab != BottomTab.OTHER`) — it hosts
`Route.Home` and every other feature's screen, not just `deferredInstallmentScreen`. Two effects
of this change reach every screen in the app, not just this MR's new one:

- The main bottom navigation bar (`FloatingGlassNavigationBar`) no longer slides in/out
  (`slideInVertically`/`slideOutVertically`, 300ms) when switching between a bottom-bar tab and a
  full-screen route — it now appears/disappears with a hard cut on every tab transition,
  everywhere in the app.
- `consumeWindowInsets(paddingValues)` on the shared `NavHost` wrapper changes what insets every
  other feature's screen receives from its parent, not just `deferredInstallmentScreen`'s.

I don't have a way to visually verify every other screen and tab transition from a diff alone, and
there's no test or documented manual check confirming the rest of the app was verified against this
change. Given the severity legend's "impact outside this MR's scope" is literally what this is, I'm
flagging it at Medium rather than treating the underlying fix itself as wrong — the diagnosis reads
correct, but a fix landing in a piece of shared/global navigation code that every screen depends on
deserves a note in the MR description (and ideally a look at whether the slide animation can be
restored, e.g. with a fade, rather than dropped silently) so the next person touching this file
isn't surprised by an unexplained animation loss that traces back to an unrelated feature's MR.

**Suggested change:** call out this shared-file change explicitly in the MR description with what
was verified elsewhere in the app (at minimum: Home tab ↔ another tab transition, and one other
full-screen feature that hides the bottom bar), and consider re-adding a lighter-weight transition
(e.g. `fadeIn`/`fadeOut`) instead of the hard `if` cut, if the slide specifically was what caused
the insets bug rather than `AnimatedVisibility` itself.

## 2. No tests anywhere in the feature — Low

**File:** `feature/deferredInstallment/`

This MR ports a non-trivial set of validation rules from `old_android` — required fields split
across two steps, the "guarantee for others" conditional required-field group (name/national
ID/birth date), the numeric floors/ceilings (≥500,000 rial per installment, 12–240 installment
count), the auto-computed repayment (`amount × count`) and minimum-guarantee (`repayment × 1.2`)
amounts, and the cross-field check that the user-editable guarantee amount can't be set below that
computed minimum — but ships with zero test files (`find feature/deferredInstallment -iname
"*Test*"` returns nothing).

I verified the ported logic itself is faithful to `old_android` while reading it (the 500,000/12/240
constants, the `+ it/5` = ×1.2 guarantee floor, and the cross-field guarantee-amount gate all match
`old_android`'s `checkValidInput`), so this isn't a "logic is wrong" finding — it's that none of it
is protected against a future regression.

## What was done well

- The business logic itself is a careful, faithful port: the 500,000-rial floor, the 12–240
  installment-count range, the repayment/guarantee auto-calculation (`amount × count`, then
  `× 1.2`), and — notably — the cross-field "guarantee amount must cover the computed minimum"
  check are all present and correctly wired to a real field error, an improvement over
  `old_android`'s silent `return false` with no user-facing message for that same case.
- `garanteeType`'s legacy naming quirk is preserved consistently through to the pre-existing
  `DeferredInstallmentRequestDN`, and the birth-date-to-ISO conversion reproduces `old_android`'s
  specific TZ-safety offset (`70_200_000L`) with a comment explaining why, rather than dropping it.
- `KeyboardInsets.kt`'s two new modifiers (`taminFormImeHost`, `taminStickyBottomBarInsets`) are a
  clean, reusable, well-documented addition to `core-ui` rather than a one-off local hack — the
  next feature with a sticky bottom bar over a form can reuse them directly.
- DI (`deferredInstallmentModule` in `sharedModules`) and navigation (callback-based, no direct
  cross-feature import) both follow the project's established conventions.
- The success/confirmation dialog flow (confirm → submit → success dialog with `refCode` →
  acknowledge → navigate back) matches `old_android`'s behavior, including falling back to a
  generic success message when the server doesn't return a tracking code.
