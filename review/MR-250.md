## 2. Header gradients are not RTL-aware — Low, needs confirmation

**Files:** `feature/pensionStatusInquiry/.../ui/components/PensionStatusCard.kt:158-165`,
`feature/profile/.../ui/activeRelation/components/ActiveRelationItemCard.kt` (`topHeaderGradient`)

```kotlin
Brush.horizontalGradient(
    colors = listOf(
        if (isActive) colors.greenBg else colors.dangerBorder.copy(alpha = 0.12f),
        colors.bgSurface,
    ),
)
```

`Brush.horizontalGradient` always runs left to right in pixel space. `TaminPrimitives.kt` already has
`startToEndGradient(colors)` for this — its KDoc says the stops are reversed under RTL «to land the
first color on the start edge». Both new gradients list the status tint first and the surface second, so
in this RTL app the tint sits on the *left* (the end side), while the status icon and label are on the
right (the start side). I cannot tell from code which side the design wants the tint on; the previews
are RTL, so the developer will have seen the result.

**Suggested change:** if the tint should start at the reading edge, use `startToEndGradient(...)` (inside
the same `remember` key set, with the layout direction added); otherwise leave a one-line comment that the
left-to-right sweep is intended.

## 3. Shared `TopAreaState` change is only partly tested — Low

**Files:** `core/core-ui/src/commonMain/.../ui/toparea/TopAreaState.kt`,
`core/core-ui/src/commonTest/.../ui/toparea/TopAreaStateTest.kt`

`TopAreaState` drives the collapsing header on many screens, so the change reaches well beyond
girl-survivor: `onPreScroll` and `onPostScroll` now return early for any source other than `UserInput`,
`onPreFling` was rewritten around a new public `settleToNearestEdge`, and `collapseFully` is new. The two
added tests exercise only `onPreScroll` with `NestedScrollSource.SideEffect`. Not covered: the same filter
in `onPostScroll`, `collapseFully()` (including the no-op when already collapsed), `settleToNearestEdge`
at the midpoint and with a fling velocity, and that a normal user drag followed by a fling still snaps to
an edge.

The filter also changes what a fling does: fling frames are not `UserInput`, so they no longer move the
header — it now folds only under the finger and snaps on release. That is the intent, but it is worth a
quick check on a device that a fast flick from the fully expanded state still ends collapsed.

> **سناریوی بیزینسی:** کاربر صفحه‌ای را که هدر جمع‌شونده دارد سریع به بالا «فلیک» می‌کند. باید هدر
> کامل جمع شود یا کامل باز بماند؛ نه اینکه وسط راه گیر کند. فقط یکی از مسیرهای تغییرکرده تست دارد و
> بقیه (فلیک، کیبورد، جمع‌شدن کامل) بدون تست‌اند، در حالی که این کلاس در صفحه‌های زیادی استفاده می‌شود.

**Suggested change:** add tests for `onPostScroll` with a non-user source, `collapseFully`,
`settleToNearestEdge` (below/above the midpoint, with velocity above the threshold) and a drag-then-fling
sequence.

## What was done well

- **MR !239's back-handling survived a 246-line rewrite of `GirlSurvivorScreen`.** Checked against the
  merge-base: one shared `handleBack` still feeds both `BackHandler` and the header's back button (step 1
  opens the abandon dialog, the commitment step goes back a step), and ✕ still opens the dialog. The
  most likely regression in this kind of restructure did not happen.
- **The keyboard fix targets the actual cause.** The header used to end up mid-fold when the IME scrolled
  the content; ignoring non-user scroll sources and adding an explicit `collapseFully()` on IME open removes
  the source of that state, rather than patching the symptom, and the test names the scenario.
- **Skeletons replace bare spinners consistently**, with Compose previews for the loaded, loading, empty and
  error states of the pension-status screen, and an a11y/brush-stability follow-up commit.
- **Brushes are built inside `remember` keyed on the colours they use**, so they are not rebuilt on every
  recomposition.
- **No hardcoded Persian strings in production code** — the only new literals are sample data inside
  `@Preview` composables, and the sample person is the team's existing test persona.
- **`docs/vault/TopArea-System.md` was updated** with the new behaviour, as the project asks.
- **No error-handling, data or navigation changes**, so nothing in this MR can introduce the recurring
  `CancellationException` problem.
