## 2. Header gradients are not RTL-aware — ✅ fixed (round 2)

**Verified** (`190fe2026`): both `PensionStatusCard.kt` and `ActiveRelationItemCard.kt` now build
their header gradient with `startToEndGradient(listOf(...))` instead of `Brush.horizontalGradient`,
so the tint lands on the reading-start edge under RTL as intended.

<details>
<summary>Round 1 (original finding)</summary>

### Header gradients are not RTL-aware — Low, needs confirmation

**Files:** `feature/pensionStatusInquiry/.../ui/components/PensionStatusCard.kt:158-165`,
`feature/profile/.../ui/activeRelation/components/ActiveRelationItemCard.kt` (`topHeaderGradient`)

```kotlin
Brush.horizontalGradient(
    colors = listOf(
        if (isActive) colors.greenBg else colors.dangerBorder.copy(alpha = 0.12f),
        colors.bgSurface,
    ),
)
```

`Brush.horizontalGradient` always runs left to right in pixel space. `TaminPrimitives.kt` already has
`startToEndGradient(colors)` for this — its KDoc says the stops are reversed under RTL «to land the
first color on the start edge». Both new gradients list the status tint first and the surface second, so
in this RTL app the tint sits on the *left* (the end side), while the status icon and label are on the
right (the start side). I cannot tell from code which side the design wants the tint on; the previews
are RTL, so the developer will have seen the result.

**Suggested change:** if the tint should start at the reading edge, use `startToEndGradient(...)` (inside
the same `remember` key set, with the layout direction added); otherwise leave a one-line comment that the
left-to-right sweep is intended.

</details>

## 5. `ContractFlowViewModel` has no test coverage — ✅ fixed (round 4)

**Verified** (`1aea33779`): `ContractFlowViewModelTest` now exists with the three scenarios asked
for — cached eligibility does not enable «بعدی» until both refreshes complete
(`isRegistrationGateLoading` true, `canGoNext` false, then true after both are released), a failed
all-contracts refresh closes the gate with the failure message, and a stale `preflightGateError`
clears once the next check finds no block. The tests run because `getString` is now injected as
`resolveString` (stubbed in the test), and `ContractsModule` registers the ViewModel explicitly so
Koin does not try to resolve that parameter. The gate itself was reworked: it now decides from
`preflightFacts` kept in the producers instead of reading `uiState`, which is not yet reduced when a
`merge`d producer reads it — a fix for a real ordering hazard, documented in `MVI-Pattern.md`.
`:feature:contracts:testDebugUnitTest` passes. One follow-up on the new facts: item 8.

<details>
<summary>Round 2–3 (original finding)</summary>

### `ContractFlowViewModel` has no test coverage — Medium

**File:** `feature/contracts/src/commonMain/kotlin/com/tamin/taminhamrah/feature/contracts/flow/ui/ContractFlowViewModel.kt`
(no `ContractFlowViewModelTest.kt` exists anywhere in the repo)

Commit `03d775d5c` ("Fix contract registration gate showing cached eligibility before API refresh")
fixes a real race: `emitPreflightGateIfReady()` used to run its checks as soon as
`hasLoadedTypedContracts`/`hasLoadedAllContracts` were set — which happened on the *first* emission
of each contracts flow, including a cache hit that fires before the network call has even started.
A user could see the registration step's eligibility gate open (green "allowed" state, "Next" button
enabled) for a moment before the network answer arrives and possibly closes it again. The fix adds
`hasCompletedTypedContractsRefresh`/`hasCompletedAllContractsRefresh`, set only in each flow's
`finally` block, and a `isRegistrationGateLoading` derived flag that keeps the gate (and the "Next"
button) waiting until both underlying flows have actually finished, not just started. I traced
`getContractsUseCase()`'s underlying `flow { }` builder in `ContractsRepositoryImpl` and confirmed it
always completes on its own (cache emission, then a network attempt that either emits or falls back
to cache, then returns) — so the new gating can't get stuck waiting for a `finally` that never runs.

The fix itself reads correct, but there is no ViewModel test file for this class at all, so nothing
pins the fixed behaviour (or would catch a regression of it): not the race itself, not the
`isRegistrationGateLoading` transition, not the "Next" button staying disabled while a request is
in flight, and not the case where a stale `preflightGateError` needs to clear once the gate re-opens
(the `block?.let { ... }` change from an early `return`).

> **سناریوی بیزینسی مهمی که تست ندارد:** کاربری که می‌خواهد قرارداد جدید ثبت کند وارد مرحله‌ی
> «ثبت‌نام» می‌شود. سیستم باید تا وقتی پاسخ واقعی سرور درباره‌ی واجد شرایط بودن او نرسیده،
> دکمه‌ی «بعدی» را غیرفعال نگه دارد — نه اینکه بر اساس داده‌ی کش‌شده‌ی قدیمی اجازه‌ی ادامه بدهد
> و بعد، وقتی پاسخ واقعی رسید، کاربر را وسط فرآیند با خطا مواجه کند. این سناریو (و حالت مشابهش
> برای پاک‌شدن خطای قبلی وقتی وضعیت دوباره مجاز می‌شود) الان فقط با خواندن دستی کد تایید شده،
> نه با تست خودکار.

**Suggested change:** add `ContractFlowViewModelTest.kt` covering at minimum: cached eligibility
alone does not enable "Next" until both refresh flows complete; a failed all-contracts refresh still
completes the gate (with the failure message) rather than leaving it loading forever; and a
previously-set `preflightGateError` clears once a later check finds no blocking condition.

</details>

## 8. Registration-gate facts are not reset on a repeated load — Low, needs confirmation

**File:** `feature/contracts/.../flow/ui/ContractFlowViewModel.kt:294` (`preflightFacts`) and the
`hasCompletedTypedContractsRefresh` / `hasCompletedAllContractsRefresh` reducers at `:1222-1227`

```kotlin
private var preflightFacts = PreflightFacts()   // never reassigned to a fresh value
...
PartialState.TypedContractsRefreshCompleted -> currentState.copy(hasCompletedTypedContractsRefresh = true)
```

`handleLoadInitialData()` starts the producers again but nothing puts the "refresh completed" facts
back to `false` — neither the private `preflightFacts` nor the state flags. If the screen sends
`LoadInitialData` a second time on the same ViewModel (the screen does so from an effect at
`ContractFlowScreen.kt:133`, which runs again whenever that composition is re-entered), the first
cache emission of the new load finds both refreshes already marked complete and can evaluate the gate
from the previous load's contracts before the new network answer arrives — the same cache-before-refresh
window the round-2 fix was written to close, in the second-load case. The added test reloads once but
with the refresh already released, so it does not exercise this window. I cannot tell from code whether
the ViewModel is ever reused across a re-entry in practice.

> **سناریوی بیزینسی:** کاربر مرحله‌ی ثبت‌نام را باز می‌کند، به صفحه‌ی قبل برمی‌گردد یا صفحه دوباره
> ساخته می‌شود و دوباره وارد همین مرحله می‌شود. تا رسیدن پاسخ تازه‌ی سرور، دکمه‌ی «بعدی» باید دوباره
> منتظر بماند و بر اساس نتیجه‌ی بارگذاری قبلی باز یا بسته نشود.

**Suggested change:** reset `preflightFacts` (keeping a new `generation`) and dispatch a partial that clears
the two `has…RefreshCompleted` flags at the start of `handleLoadInitialData()`; add a test that reloads
with `holdRefresh = true` and asserts `isRegistrationGateLoading` is true again.
