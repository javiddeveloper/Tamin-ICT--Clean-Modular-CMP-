## 1. A first-load network failure looks identical to "nothing to show" — Medium

**Files:** `shared/src/commonMain/kotlin/com/tamin/taminhamrah/ui/home/HomeViewModel.kt:81-87`,
`core/core-data/src/commonMain/kotlin/com/tamin/taminhamrah/data/repository/HistoryRepositoryImpl.kt:57-73`

```kotlin
// HomeViewModel.kt
private suspend fun loadHistorySummary(): HistorySummaryPR? = try {
    getTalfighInfosUseCase().list?.toPresentation()?.toHistorySummary()
} catch (e: CancellationException) {
    throw e
} catch (e: Exception) {
    null
}
```

The `CancellationException` handling here is correct. But `HistoryRepositoryImpl.getTalfighInfos`
already falls back to a local Room cache on a remote failure, and only rethrows if that cache is
*also* empty — so the exception that reaches `HomeViewModel` is specifically "the network/API call
failed **and** there's no prior successful load cached," e.g. the user's first time opening the app,
or a person who has never opened سوابق before. In that exact case, a genuine connectivity/server error
is caught here and treated exactly the same as the legitimate business case ("این کاربر بیمه‌ای ندارد،
پس چیزی برای نمایش نیست") — the card is just left out, silently, with no retry offered anywhere on
Home.

Since there's no legacy screen to compare this against, this isn't a business-flow discrepancy — it's
a UX/quality gap worth fixing on its own: a person with a real connectivity problem on first launch
sees no indication anything went wrong and has no way to retry short of navigating into سوابق directly
(which does its own fetch).

**Suggested change:** distinguish the "no data" case from a genuine fetch failure — e.g. have
`loadHistorySummary()` propagate (or a sibling partial-state carry) enough information to show a
small retry affordance on the card's spot when the failure was a real error, rather than collapsing
both outcomes to `null`.

## 2. No test coverage for the new `HomeViewModel` logic — Low

**File:** `shared/src/commonMain/kotlin/com/tamin/taminhamrah/ui/home/HomeViewModel.kt` (no
`HomeViewModelTest.kt` exists in the repo)

The pure mapping logic is well-tested — `HistorySummaryPRTest.kt` covers the empty-list case, the
current-year split into registered/unpaid/upcoming, summing days across multiple rows sharing a year,
and a past year where every month has elapsed. But the ViewModel layer this MR adds to
(`loadHistorySummary()`'s success/failure paths, `LoadHistorySummary` running alongside `LoadMenu`
rather than after it, `OnHistorySummaryClick` routing to `FeatureFlag.WAGE_AND_HISTORY`) has zero
test coverage, because `HomeViewModel` has no test file at all yet.

**Suggested change:** add `HomeViewModelTest.kt` covering at least: a successful history-summary load
populates `historySummary` and clears `isHistorySummaryLoading`, a failed load also clears the loading
flag but leaves `historySummary` null, and `OnHistorySummaryClick` fires the expected navigation.

## What was done well

- **Correctly diagnosed as having no legacy precedent** rather than assumed to need a parity check —
  confirmed by searching `old_android`'s dashboard fragment and layouts directly; nothing there
  references a history/talfigh summary on the home screen.
- **`CancellationException` is rethrown before the general catch** in `loadHistorySummary()` — the
  recurring bug found in nearly every other MR reviewed this cycle does not appear here.
- **No hardcoded Persian strings** — all new copy is in `strings.xml` (`history_summary_*` block),
  including the pluralized "X از Y ماه سپری‌شده ثبت شده" and unpaid-warning strings.
- **`toHistorySummary()` is a clean, well-documented pure function** — counts are held as typed data
  (`HistoryMonthStatusPR` enum) rather than as pre-formatted strings, so the card can't drift from the
  numbers it derives from; the "newest year, not current year" and "-1 means already-elapsed" design
  decisions are both explained in doc comments and directly covered by tests.
- **Recomposition-conscious wiring in `TaminHamrahNavGraph.kt`** — the shared card-tap lambda is
  hoisted with `remember(viewModel)` instead of being rebuilt inline, and the padding modifier is a
  top-level `val` instead of a fresh instance per recomposition, with both choices explained in
  comments.
- **No commented-out code, no TODOs left in the new files.**
