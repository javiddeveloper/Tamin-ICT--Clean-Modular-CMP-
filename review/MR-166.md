## 1. Non-Persian server messages are dropped with no specific fallback copy — High

**File:** `core/core-network/src/commonMain/kotlin/com/tamin/taminhamrah/tools/BaseDTO.kt:141-151`

```kotlin
private fun <T> BaseDTO<T>.getServerMessage(): String? {
    val fromData = when (val d = data) {
        is ErrorCarrier -> d.message
        is JsonObject -> d["message"]?.jsonPrimitive?.contentOrNull
        else -> null
    }
    return (fromData ?: problemMessage ?: reason).takeIf { it.isPersian() }
}
```

Old_android's equivalent (`old_android/.../BaseRemoteDataSource.kt`, all 4 call sites around
lines 294, 392, 487, 652) never leaves the user with nothing: when
`ValidationUtil.isProbablyArabic(message)` is false, it substitutes a specific, hand-written
Persian fallback string (e.g. a long explanatory message for a 500/`INTERNAL_SERVER_ERROR`, or
"کاربر گرامی با عرض پوزش اختلالی در سیستم رخ داده است..." for 502).

Here, when the message isn't Persian, `getServerMessage()` returns `null`, and
`ErrorParserImpl.parseGeneralError` falls through to its generic per-`ErrorUri` copy. Since
every server error status collapses through `handleCommonErrors()` into
`ErrorUri.fromString("$errorPrefix: $reason")`, anything not literally matching a known
`ErrorUri` name resolves to a generic `UNKNOWN` message ("خطا" / "مشکلی پیش آمده است").

**Suggested change:** confirm with product whether the old per-status specific copy is still
required; if so, port it as the fallback used when `isPersian()` is false, instead of falling
through to the generic message.

> **مغایرت بیزینسی:** در نسخه‌ی قدیمی، وقتی پیام خطای سرور فارسی/عربی نبود، به‌جای نمایش پیام
> خام، یک پیام فارسی مشخص و متناسب با نوع خطا (مثلاً برای خطای ۵۰۰ توضیح کامل درباره‌ی احتمال
> قطعی اینترنت یا ترافیک بالا، یا برای ۵۰۲ پیام «اختلال در سیستم») به کاربر نشان داده می‌شد. در
> کد جدید وقتی پیام سرور فارسی تشخیص داده نشود، این پیام‌های خاص جایگزین نمی‌شوند و به‌جایش یک
> پیام خیلی کلی («خطا» / «مشکلی پیش آمده است») نمایش داده می‌شود که اطلاعات کمتری به کاربر
> می‌دهد.

## 2. Status-code-specific business rules from old_android are gone — High

**File:** `core/core-network/src/commonMain/kotlin/com/tamin/taminhamrah/tools/BaseDTO.kt:131-139`

```kotlin
private fun <T> BaseDTO<T>.handleCommonErrors(): Nothing {
    val errorPrefix = when (status) {
        in 400..499 -> "CLIENT_ERROR"
        in 500..599 -> "SERVER_ERROR"
        else -> "UNKNOWN_ERROR"
    }
    throw TaminErrorUriException(ErrorUri.fromString("$errorPrefix: $reason"), serverMessage = getServerMessage())
}
```

Old_android's `getErrorResult`/`handleError` branch on the exact HTTP status and apply distinct
business rules with no equivalent here:

- **403** → a dedicated VPN/proxy message ("دسترسی به سرویس مورد نظر مقدور نمی‌باشد؛ در صورت
  استفاده از هرگونه VPN یا پروکسی...") **and** `isBackToPrevious = true` (auto pop-back
  navigation). Nothing in `BaseDTO.kt` wires 403 to this.
- **500** → several substring-matched business rules ahead of the generic Persian check:
  missing-bank-account message, `sso.to.sa.connection.exception`,
  `pension.request.current.request.open`, `pension.survivor.request.survivor.already.saved`,
  and a `data?.cause == "ProxyProcessingException"` passthrough. None are ported.
- **502/503/504** → distinct fixed Persian messages. New code treats all of 500-599 identically.
- **401** → old code triggers a token-refresh flow on 401; nothing here distinguishes 401 from
  other 4xx statuses.

**Suggested change:** at minimum confirm with product/backend whether these rules are still
needed; if so, port them keyed off the actual HTTP status.

> **مغایرت بیزینسی:** در نسخه‌ی قدیمی، بسته به کد وضعیت خطا (مثلاً ۴۰۳، ۵۰۰، ۵۰۲، ۵۰۳، ۵۰۴)
> پیام‌ها و رفتارهای متفاوتی وجود داشت؛ برای مثال خطای ۴۰۳ پیام مخصوص «احتمال استفاده از VPN یا
> پروکسی» را نشان می‌داد و کاربر را خودکار به صفحه‌ی قبل برمی‌گرداند، و برخی پیام‌های سرور (مثل
> «شما فاقد شماره حساب بانکی هستید» یا «درخواست شما در حال بررسی است») بر اساس محتوای پیام سرور
> شناسایی و با متن راهنمای دقیق‌تر نمایش داده می‌شدند. در کد جدید همه‌ی کدهای وضعیت ۴۰۰ تا ۴۹۹ و
> ۵۰۰ تا ۵۹۹ یکسان مدیریت می‌شوند و هیچ‌کدام از این قوانین خاص وجود ندارد؛ یعنی کاربر اطلاعات
> کمتر و کم‌دقیق‌تری درباره‌ی علت واقعی خطا دریافت می‌کند.

## 3. `extractTypedData()` bypasses the new `isPersian()` filter — Medium

**File:** `core/core-network/src/commonMain/kotlin/com/tamin/taminhamrah/tools/BaseDTO.kt:189-204`

```kotlin
fun <T> BaseDTO<JsonElement?>.extractTypedData(json: Json, deserializer: DeserializationStrategy<T>): T {
    return when {
        ...
        status in 400..599 -> {
            val serverMessage = (data as? JsonObject)?.get("message")?.jsonPrimitive?.contentOrNull
            throw TaminErrorUriException(uri = ..., serverMessage = serverMessage)
        }
        ...
    }
}
```

This function (used by `UserRemoteDataSourceImpl`, the change-mobile Kong gateway path) reads
`data.message` directly, without the `isPersian()` guard this MR introduces everywhere else in
the same file. If the gateway ever returns a raw English/technical message, it is shown to the
user verbatim through this path while every other path now filters it.

**Suggested change:** route `extractTypedData` through `getServerMessage()`/`isPersian()` too,
for consistency with the rest of the file.

## 5. `.gitignore` broadened to ignore all DB schema folders; active schema file untracked — Medium

**Files:** `.gitignore`, `core/core-database/schemas/com.tamin.taminhamrah.data.local.TaminXDatabase/2.json`

The `.gitignore` change narrows the ignore path from
`core/core-database/schemas/com.tamin.taminhamrah.data.local.TaminXDatabase/` to
`core/core-database/schemas/` — i.e. it now ignores **all** schema folders, for every database.
Combined with this diff, `2.json` (the current Room schema for `TaminXDatabase` v2, 2521 lines)

schema folder and that file must be committed — this MR resolves that requirement in the wrong
direction (untracking instead of keeping it tracked).

**Suggested change:** revert the `.gitignore` broadening and restore `2.json` to git tracking.

## 8. `ErrorCarrier` interface added but never implemented — Low

**File:** `core/core-network/src/commonMain/kotlin/com/tamin/taminhamrah/tools/BaseDTO.kt:16-19`

```kotlin
interface ErrorCarrier {
    val message: String?
    val cause: String? get() = null
}
```

No DTO in the repo implements `ErrorCarrier` — it's referenced only in `getServerMessage()`'s
`is ErrorCarrier -> d.message` branch, which is therefore always dead code (the `is JsonObject`
branch is what actually fires). `cause` is also unused (old_android's
`data?.cause == "ProxyProcessingException"` check, see finding 2, has no equivalent here).

**Suggested change:** wire at least one error DTO to implement it, or drop the interface until
it's needed.

## 10. `isPersian()` is a misleading name for what it actually detects — Low

**File:** `core/core-network/src/commonMain/kotlin/com/tamin/taminhamrah/tools/NetworkUtils.kt:8-14`

```kotlin
fun String.isPersian(): Boolean {
    val persianRegex = Regex("[؀-ۿﭐ-﷿ﹰ-﻿]")
    return persianRegex.containsMatchIn(this)
}
```

This uses the exact same three Unicode ranges as old_android's `ValidationUtil.isProbablyArabic()`
— functionally correct and matches old business logic, but the new name claims Persian
specificity it doesn't have (it matches any Arabic-script character, Persian or not). Old_android's
own name is more accurate for what the check is used for (readability heuristic, not language
detection).

**Suggested change:** rename to something like `looksLikeArabicScript()` or match old_android's
`isProbablyArabic()`.
