## 2. Payment verifier drops the `ticket` parameter — Medium, needs confirmation

**File:** `feature/taminServices/src/commonMain/kotlin/com/tamin/taminhamrah/feature/taminServices/verifier/ConstructionWorkersPaymentVerifier.kt:18-20`

```kotlin
override suspend fun verify(reference: String): String =
    inspectWorkersPaymentTicketUseCase(ticket = null, paymentInfo = reference)
```

`old_android`'s equivalent confirmation call always sent **both** values, not just one:

```kotlin
// PaymentViewModel.kt:82-90 (updateWorkersPaymentStatus)
val ticket = repository.getWorkerPayTicket() ?: ""
val info = repository.getWorkerPayInfo() ?: ""
repository.inspectTicket(ticket, info)
```

— and `workers/inpectTicket`'s API signature (`WorkersPaymentApiService.kt:29-33` here, matching
`old_android`'s `ServicesService.kt:1352-1357`) still accepts both `ticket` and `paymentInfo` as
independent query params. The new code always passes `ticket = null`.

This isn't simple plumbing negligence — the real ticket **is** available earlier in the flow
(`WorkersPaymentViewModel.kt`'s `payItem()` puts it in `PaymentRequestDN.ticket`), but the shared
`PaymentVerifier.verify(reference: String)` contract (from the already-reviewed MR !222) only forwards
a single string to each registered verifier, and this implementation chose to carry `paymentInfo`
through that one slot rather than encode both values into it. So the root constraint is architectural
(the shared interface), not a mistake local to this file — but the result is still a real deviation
from the only confirmed-working legacy call shape, and it's locked in by a test rather than flagged as
a gap: `ConstructionWorkersPaymentVerifierTest.kt:31-39` asserts
`repository.lastInspectTicketParams == (null to "WRK-TOKEN-123")`, i.e. it pins the missing ticket as
expected behavior.

One point in favor of this being harmless: `paymentInfo` is documented as an **encrypted** token
(`WorkersPaymentModelsDN.kt:54`, `// wire list[3]`, "encrypted paymentInfo"), which suggests it may
already be self-sufficient for the backend to identify the payment record without a separate ticket —
in which case `old_android` sending both was likely just leftover redundancy, not a requirement.
That can't be confirmed from the client code alone.

> **سناریوی بیزینسی نیازمند تایید:** برای تایید نهایی پرداخت حق بیمه کارگران ساختمانی، نسخه‌ی قدیمی
> همیشه هم `ticket` و هم `paymentInfo` رو با هم به سرویس `inspectTicket` می‌فرستاد. پیاده‌سازی جدید
> فقط `paymentInfo` رو می‌فرسته و `ticket` رو همیشه `null` می‌ذاره — نه به این خاطر که این مقدار در
> دسترس نیست، بلکه چون قرارداد مشترک تایید پرداخت (که در یک MR دیگه طراحی شده) فقط جا برای یک مقدار
> داره. اگه سرویس بک‌اند واقعاً به `ticket` نیاز داشته باشه (نه فقط `paymentInfo`)، این تایید پرداخت
> ممکنه شکست بخوره یا نتیجه‌ی اشتباه بده. باید با تیم بک‌اند تایید بشه که `paymentInfo` به‌تنهایی
> برای شناسایی و تایید پرداخت کافیه.

**Suggested change:** confirm with whoever owns the `workers/inpectTicket` endpoint whether
`paymentInfo` alone is sufficient. If yes, this can be marked accepted (and the encrypted-token
reasoning above is worth writing down in the verifier's KDoc so the next reader doesn't have to
re-derive it). If `ticket` is actually required, this needs a fix at the shared-interface level
(e.g. `PaymentVerifier.verify` taking a small struct instead of one string, or encoding both values
into the single `reference` string and decoding them in the verifier) — which is a decision that
affects MR !222's shared module, not something to patch locally in this feature alone.

> **Round 3 — ✅ fixed, via exactly the "encode both into the reference string" option this item
> suggested.** `WorkersPaymentViewModel.kt`'s `payItem()` now builds
> `verifierReference = "$ticket|${result.paymentInfo.orEmpty()}"`, and
> `ConstructionWorkersPaymentVerifier.verify()` splits on `"|"` (limit 2) to recover both values,
> falling back to `null to reference` when no delimiter is present (covered by a dedicated test
> alongside the new delimited-parsing test). This closes the gap without touching the shared
> `PaymentVerifier` interface from MR !222 — a local, self-contained fix. The `ticket` now really does
> reach `inspectWorkersPaymentTicketUseCase`, matching `old_android`'s `updateWorkersPaymentStatus()`
> call shape.

## 3. `paymentInfo` now falls back to `list[2]` — Medium, needs confirmation

**File:** `core/core-data/src/commonMain/kotlin/com/tamin/taminhamrah/data/mapper/workersPayment/WorkersPaymentMapper.kt:58`

```kotlin
internal fun WorkersPayDebitDTO.toDomain(): WorkersPayDebitResultDN = WorkersPayDebitResultDN(
    paymentUrl = list.getOrNull(0),
    ticket = list.getOrNull(1),
    paymentInfo = list.getOrNull(3) ?: list.getOrNull(2),
)
```

The same commit that fixed item 2 also changed this mapper, unprompted. Before this round,
`paymentInfo` was strictly `list.getOrNull(3)`, matching `old_android`'s accessor exactly
(`WorkersPaymentInfo.kt:35`: `fun paymentInfo() = list.elementAtOrNull(3)`, with index 2 always
present but unused — round 1's own "what was done well" section noted this precise parity). Now, if
the wire response has only 3 elements, index 2 is read as `paymentInfo` instead.

Nothing in `old_android` does this — there is no fallback, no code path that reads index 2 as
`paymentInfo`, and no comment in the new code explaining what a 3-element response means or why
index 2 would hold the same data index 3 normally does. The accompanying test
(`WorkersPaymentRepositoryImplTest.kt`, `` `payWorkersDebit reads paymentInfo from list index 3`
`` next to it) only proves the *code* does what it's written to do, not that a real 3-element
response from the service actually puts `paymentInfo` at index 2 — that's an assumption about the
wire format with no legacy precedent to check it against.

If a 3-element response is a real shape this endpoint sends (and index 2 genuinely is `paymentInfo`
in that case), this is a legitimate defensive fix. If it isn't — if a 3-element list just means the
service omitted `paymentInfo` entirely for some other reason, or index 2 is a different, unrelated
field in that shape — this silently sends the wrong value into `verifierReference`, which (per item
2's fix) is now also carrying the `ticket`, so a wrong `paymentInfo` here reaches the same
money-verification call that item 2 was fixing.

> **سناریوی بیزینسی نیازمند تایید:** این تغییر می‌گه اگه پاسخ سرویس پرداخت کارگران فقط ۳ عنصر داشته
> باشه (به‌جای ۴ عنصر همیشگی)، مقدار سوم (index 2) به‌عنوان «اطلاعات پرداخت» در نظر گرفته بشه. این
> رفتار نه توی نسخه‌ی قدیمی وجود داره و نه هیچ توضیحی توی کد برای این‌که چرا و در چه شرایطی سرویس
> فقط ۳ مقدار برمی‌گردونه نوشته شده. اگه این فرض اشتباه باشه، یعنی وقتی این حالت واقعاً اتفاق بیفته،
> اطلاعات اشتباهی برای تایید نهایی پرداخت به سرویس ارسال می‌شه — دقیقاً همون سرویسی که مورد ۲ هم
> بهش وابسته‌ست.

**Suggested change:** confirm with the backend/API owner whether the service ever legitimately
returns only 3 list elements for this endpoint, and if so, what index 2 means in that case. If
confirmed, add a comment recording that fact (the same way the existing `list[3]`/index-2-skipped
comment already documents the 4-element shape). If it can't be confirmed, consider reverting to the
strict `list.getOrNull(3)` and letting a missing `paymentInfo` surface as `null` (already handled
downstream) rather than guessing at a fallback.

## What was done well

- **The pay-debit request and response mapping match `old_android` exactly.** Amount (payable +
  fines), dates, and `fromToDate` are built identically to `WorkersPaymentInfo.makePayDebitRequest()`,
  and the response's positional-array mapping (`list[0]`=url, `list[1]`=ticket, `list[3]`=paymentInfo,
  index 2 skipped) matches the legacy client's own field accessors field-for-field — the same kind of
  detail that's easy to get subtly wrong in a rewrite, and it isn't here.
- **The redirect URI change is a deliberate architectural improvement, not a slip.** Using the shared
  `NetworkConstants.PAYMENT_RETURN_URI` ("mytamin://payment_callback") instead of `old_android`'s
  construction-specific `"mytamin://workers_payment_callback"` is exactly what MR !222's centralized
  payment-callback design calls for.
- **List/debt business rules match legacy** — payable items are still derived from the same
  status fields the old adapter used to show/hide its pay button, and totals are passed through from
  the server rather than recomputed client-side, consistent with the backend-driven totals
  `old_android` also relied on.
- **No hardcoded strings or magic-value comparisons anywhere in production code** — all UI text is in
  `strings.xml` (39 new `workers_payment_*` keys), and status/type fields from the server are
  displayed as opaque strings without branching on them, matching `old_android`'s own behavior.
- **`WorkersPaymentViewModelTest.kt` directly asserts the pay-debit parameter building** (`amount`,
  `dates`, `fromToDate`, `redirectUrl`) and the resulting `PaymentRequestDN`, not just that a call
  happened — this is exactly the level of test that would have caught item 2 if it had also asserted
  on the ticket value reaching the verifier.
- **Round 3: item 2's fix is a genuinely good solution**, not a workaround that trades one problem
  for another — encoding both values into the existing single-string `reference` slot closes the gap
  without touching the shared `PaymentVerifier` interface other MRs also depend on, and both the
  delimited and non-delimited parsing paths are directly tested.
