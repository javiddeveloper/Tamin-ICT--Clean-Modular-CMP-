## 1. Debug `println` left in production — High

**File:** `feature/history/src/commonMain/.../ui/HistoryViewModel.kt:363`

```kotlin
is PartialState.HistoryLoaded -> run {
    println("TOTALDBG years=${partialState.years.size} total=${partialState.careerTotal} merged=${partialState.hasCombinedRecords} wage=${partialState.hasWageRecords}")
    currentState
}.copy(...)
```

`println` in `reduceState` runs on every successful history load for every user session.
On Android it surfaces in logcat as `System.out` even in release builds. It also forces
`careerTotal` — a potentially sensitive financial figure — into the log stream of every
device that opens the history screen.

**Suggested fix:** Delete the `println`. The `run { … }.copy(…)` wrapper was only needed
to accommodate it; after removal the block collapses to the normal `currentState.copy(…)`.

## 2. DB schema changed without version bump — High

**File:** `core/core-database/src/commonMain/.../data/local/TaminHamrahDatabase.kt`

The database was at `version = 2` before this MR. This MR adds two new Room entities
(`HistoryYearEntity`, `HistoryWageRowEntity`) and two new tables, but leaves the version
number at `2`.

Room validates its schema with a stored hash at startup. On any device that already has the
`version = 2` database with the old schema (i.e. without the two history tables), Room finds
a hash mismatch and throws:

```
IllegalStateException: Room cannot verify the data integrity.
Looks like you've changed schema but forgot to update the version number.
```

`fallbackToDestructiveMigration(dropAllTables = true)` only activates when the version
*number* changes (e.g. 2 → 3 without a provided migration). It does not protect against a
version that stays the same while the schema changes — Room raises the hash error before
migration logic runs.

**Suggested fix:** Bump to `version = 3`. Because `fallbackToDestructiveMigration` is
already in place no migration function is needed; Room will recreate the database on upgrade.

## 3. Hardcoded Persian string in ViewModel companion — Medium

**File:** `feature/history/src/commonMain/.../ui/HistoryViewModel.kt:449`

```kotlin
private companion object {
    /** Used only when the service confirms without wording of its own. */
    const val DEFAULT_SEND_SUCCESS = "درخواست شما با موفقیت ثبت شد."
}
```

User-visible strings must live in `composeResources/values/strings.xml` so they can be:
- Translated later without code changes.
- Tested via `Res.string.*` (strings in companion objects are invisible to the Compose
  resource system and excluded from screenshot tests that verify text).

The same MR already adds `strings.xml` under `feature/history` for other messages — this
string belongs there too.

**Suggested fix:** Add `<string name="history_send_success_default">…</string>` to the
feature's `strings.xml` and replace the constant with
`Res.string.history_send_success_default`. Emit `HistoryEvent.ShowToast` with a
`StringResource` (the same pattern already used for `ConfirmSendNotice`'s error path).

## What was done well

- **Parallel data fetching** in `load()` with `coroutineScope { async { … } }` — both the
  year and wage calls run concurrently. The deliberate ordering (`years.await()` before
  `wages.await()`) ensures a page failure never also fires the wage toast. This is a subtle
  but correct design that the tests pin explicitly.
- **`loadInFlight` guard** comment is accurate: set before the first suspension point, so a
  fast second tap on «تلاش دوباره» is blocked without reading `isLoading` from the state
  (which only becomes true after a channel hop).
- **Cache-then-network pattern** in `HistoryRepositoryImpl` is correctly implemented: the
  cache is only written when the service returns non-empty rows, the second wider-limit
  request is guarded by `MAX_HISTORY_LIMIT = 500` to avoid asking for an implausible number
  of rows, and `preferLonger` picks the first response if the speculative retry came back
  shorter — so a regression in the backend cannot lose rows already received.
- **`CancellationException` is rethrown** everywhere it can appear — `downloadReport()`,
  `orNull()`, and the wage `async` block. None of the `catch (e: Exception)` blocks silently
  swallow a cancellation.
- **`NetworkUtils.toErrorUri()`** distinguishes transport failures (`IOException`) from
  deserialization failures (`SerializationException`) and maps them to different error URIs
  — the fix from "check your internet" to "server error" is correct.
- **`HistoryEvent.ShowToast` carries `StringResource`**, not a resolved `String` — the
  right pattern for KMP ViewModels where resolving resources requires a composition context.
- **Test coverage** is solid: `HistoryViewModelTest` covers concurrent loading timing, year
  merge, wage failure isolation, wage toast suppression on page failure, access denial, and
  the «اعلام» idempotency guard. `SplitCandidatesTest` and `YearHistoryTest` cover the
  domain models independently.
