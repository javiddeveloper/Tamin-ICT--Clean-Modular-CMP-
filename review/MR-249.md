before the general catch. `getAllManager` does it with an explicit catch rather than `errorParser.safeCall`,
which is fine and consistent with the five older functions in the same file.

### 2. ✅ Fixed

The screen no longer switches paging off while a filter is applied, and a `LaunchedEffect` keeps
loading the next page whenever the filter matches nothing and pages remain; while it does, a skeleton is
shown, and «موردی یافت نشد» appears only once `inspectionsEndReached`. I read the loop for runaway
requests: it re-fires only when the loading flag drops, stops on a paging error and at the last page.

Remaining note, not blocking: a filter that matches *some* loaded rows does not keep paging on its own —
`OnLoadMore` fires only when the end of the list first comes into view — so a second match on a later
page appears only after further scrolling. For a search by inspection or workshop number that is
acceptable. The paging rule lives in the composable, so it has no unit test.

for a blank mobile and for an 11-digit non-mobile), and the banner now says to correct «the editable
fields». Still open, none of them changed in this round:

## 7. The double-submit guard does not hold — Medium

**Files:** `feature/taminServices/.../workshopInspection/ui/WorkshopInspectionViewModel.kt:190-194`,
`feature/taminServices/src/commonTest/.../workshopInspection/WorkshopInspectionViewModelTest.kt:222`

```kotlin
private fun handleSubmitRequest(intent: ...): Flow<PartialState> = flow {
    if (uiState.value.isLoading) return@flow   // ← the guard
    emit(PartialState.Loading(true))
    ...submitInspectionUseCase(intent.request)
```

`BaseViewModel` runs each intent's flow inside `flatMapMerge` and applies the emitted partial states in a
separate collector. `uiState` is only updated once that collector runs, so a second `SubmitRequest`
that starts before it still reads `isLoading == false`. (MR !248 hit the same limitation and its ViewModel
documents it: "the reduced state cannot be consulted for this".) The new test passes only because it runs
on `UnconfinedTestDispatcher`, which executes every step eagerly.

I checked this by running the same scenario — two `SubmitRequest` intents in a row, the first held in
flight — on a `StandardTestDispatcher`, which orders work like a real main thread: the repository
received **2** submit calls, not 1. (The scratch test was removed; nothing extra is in the commit.) The
disabled «ثبت» button makes this hard to hit, but a double tap inside one frame is exactly the case the
guard was added for, and the result is two objections filed for one inspection.

> **سناریوی بیزینسی:** کاربر دکمه‌ی «ثبت اعتراض» را خیلی سریع دو بار لمس می‌کند. انتظار این است که فقط
> یک اعتراض ثبت شود و کاربر یک کد رهگیری بگیرد؛ ولی در شرایط واقعی هر دو درخواست به سرور می‌رسد و دو
> اعتراض برای یک بازرسی ثبت می‌شود. تست فعلی این حالت را نمی‌گیرد چون در محیط تست همه‌چیز پشت‌سرهم و
> بدون تأخیر اجرا می‌شود.

**Suggested change:** keep the guard in a plain field of the ViewModel that is set *before* the first
suspension, e.g. `private var isSubmitting = false`, checked and set at the top of `handleSubmitRequest`
and cleared in a `finally`. Then run the double-submit test on a `StandardTestDispatcher` so it would fail
without the field.
