## 1. `CancellationException` swallowed at three new sites — Medium

**Files:** `feature/taminServices/.../workshopInspection/ui/WorkshopInspectionViewModel.kt:194,206`,
`core/core-network/.../dataSource/inspection/InspectionRemoteDataSourceImpl.kt` (`getAllManager`)

```kotlin
private fun handleSubmitRequest(intent: ...): Flow<PartialState> = flow {
    emit(PartialState.Loading(true))
    try {
        val result = submitInspectionUseCase(intent.request)
        emit(PartialState.SubmitSuccess(result.id))
    } catch (e: Exception) {
        emit(PartialState.Loading(false))
        sendEvent(WorkshopInspectionEvent.ShowToast(e.toSingleLineMessage()))
    }
}
```

`handleSubmitRequest` and `handleDownloadReportPdf` catch broadly with no `CancellationException`
rethrow; the new `getAllManager` copies the same shape from its neighbours, turning a cancelled call
into a fake «no connection» error. Nothing in the new code mentions `CancellationException`. A user who
leaves the wizard while the submit is in flight gets an error toast and a reset state for a request
that may still have gone through. (The other five catch sites in `InspectionRemoteDataSourceImpl` are
the same pattern and predate this MR, but that file is being edited now.)

`ErrorParser.safeCall(tag)` in `NetworkUtils.kt` already does this correctly and could replace the
hand-written try/catch in the data source.

**Suggested change:** add `catch (e: CancellationException) { throw e }` before the general catch at the
two ViewModel sites, and use `errorParser.safeCall(...)` for `getAllManager`.

## 2. Search only covers the loaded pages — Medium, needs confirmation

**Files:** `WorkshopInspectionContract.kt:20-30,74-80`, `WorkshopInspectionViewModel.kt:213-222`

`ApplySearch` only stores a `WorkshopInspectionFilter`; `filteredInspections` then filters
`inspections` — the rows loaded so far — by `contains`. The code documents why: the
`get-all-manager` endpoint has no confirmed filter support and legacy called it with `filter = "[]"`.
Legacy had no search on this list at all, so this is new behaviour, and the comment calls it «the honest
behaviour». But the result screen does not say it is partial: with 10 rows per page, a search for an
inspection that is on page 3 finds nothing and shows the «no result» state.

> **سناریوی بیزینسی:** کارفرمایی که چند بازرسی دارد، شماره‌ی یک بازرسی قدیمی را جستجو می‌کند. اگر آن
> بازرسی هنوز بارگذاری نشده باشد (چون کاربر تا آن صفحه اسکرول نکرده)، صفحه «نتیجه‌ای یافت نشد» نشان
> می‌دهد؛ کاربر تصور می‌کند بازرسی وجود ندارد در حالی که فقط بارگذاری نشده.

**Suggested change:** either load the remaining pages when a filter is applied, show that the search is
limited to what has loaded (and offer «بارگذاری بیشتر»), or confirm with the backend team whether the
endpoint can filter — then send the filter as a query.

## 3. The objection form differs from legacy — Medium, needs confirmation

**Files:** `WorkshopInspectionContract.kt:83-89`, `WorkshopWorkshopInfoStep.kt:153-250`,
`WorkshopInspectionViewModel.kt:156-168`, `WorkshopRequestDescriptionStep.kt:64-76`

Compared with `SubmitInspectionRequestFragment` / `SubmitInspectionRequestViewModel`:

- **Mobile is required, and only its length is checked.** The contract says it deliberately requires
  a mobile «unlike the insured-side flow». Legacy treated it as optional and checked `^09\d{9}$`. The new
  check is `isPhoneNumberValid`, which is just `length == 11`, so `12345678901` passes while a user with
  no mobile on their profile can no longer submit.
- **Workshop name and branch are read-only, but the banner says «در صورت نیاز ویرایش کنید»** («edit
  if needed»). Legacy let the user edit them and pick the branch from a list. Here only employer name,
  workshop phone, address, job and dates can be changed, and step 2 is valid only when name and branch
  code are non-blank — so a row the server returns without either leaves the user unable to continue.
- **Email is not pre-filled and mobile is not locked.** Legacy locked mobile and email when the profile
  had them; the new form fills only name, national code and mobile, and leaves them editable.
- **Payload.** Legacy always sent `inspectionNumberOld = ""` and `insuranceId = ""`. The new request sends
  the real inspection number and insurance number of the tapped row. That is arguably more correct, but
  it is a change in what the server receives, so someone should confirm the backend accepts it.

> **سناریوی بیزینسی:** در نسخه‌ی قدیمی شماره‌ی موبایل اختیاری بود و فقط الگوی «۰۹ و ۹ رقم» بررسی
> می‌شد؛ کارفرمایی که موبایل ثبت‌شده در پروفایل ندارد هم می‌توانست اعتراض بدهد. در نسخه‌ی جدید موبایل
> اجباری است و هر عدد ۱۱ رقمی (حتی غیرموبایل) پذیرفته می‌شود. نام و شعبه‌ی کارگاه هم قابل ویرایش
> نیست ولی متن بالای صفحه می‌گوید ویرایش کنید؛ و اگر این دو مقدار از سرور خالی برسند، کاربر نمی‌تواند
> از مرحله‌ی دوم رد شود.

**Suggested change:** confirm the required mobile and the read-only workshop fields are intended; if so,
change the banner text, validate the mobile with the `09` pattern legacy used, and pre-fill the email if
the profile has one. Confirm the payload change with the backend team.

## 4. No entry point for requesting a new inspection — Medium, needs confirmation

Legacy had a second screen, `ListOfInspectionsPerformedFragment`, with an «درخواست بازرسی» button that
opened the same request form with no source inspection and nothing pre-filled. The new module only offers
«ثبت اعتراض» from a row (`WorkshopInspectionRequestScreen` is documented as «always an objection
request»). I could not establish from legacy which of the two screens an employer actually reached from
the menu — its routing points at both — so it is possible that this button was never live for
employers.

> **سناریوی بیزینسی:** اگر در نسخه‌ی قدیمی کارفرما می‌توانست از همین بخش «درخواست بازرسی» جدید ثبت
> کند، در نسخه‌ی جدید فقط «ثبت اعتراض» به بازرسی‌های انجام‌شده وجود دارد و راهی برای درخواست بازرسی
> تازه نیست.

**Suggested change:** confirm with product whether employers should be able to request a new inspection
here; if so, it needs its own entry point.

## 5. Step files copied from the insured-side flow — Low

**Files:** `workshopInspection/ui/steps/{WorkshopIdentityContactStep, WorkshopWorkshopInfoStep,

**Suggested change:** extract the shared step composables and parameterise the differences (read-only
fields, mobile required, the «شرح اعتراض» label) instead of copying them.

## 6. Tests miss the failure paths and the multi-page search — Low

**File:** `feature/taminServices/src/commonTest/.../workshopInspection/WorkshopInspectionViewModelTest.kt`

The ten ViewModel tests cover the first page, its error toast, the pre-fill, the job search, retry, a
successful submit, a successful PDF download and the search filter state. The contract tests cover the
step validation and `filteredInspections`. Nothing tests a *failed* submit or PDF download, a repeated
submit, or applying a search while more pages remain (item 2).

> **سناریوی بیزینسی:** اگر ثبت اعتراض با خطای سرور روبه‌رو شود، باید پیام خطا نشان داده شود و دکمه
> دوباره فعال شود تا کاربر بتواند دوباره تلاش کند؛ و اگر کاربر دو بار سریع روی «ثبت» بزند نباید دو
> اعتراض ثبت شود. هیچ‌کدام از این دو سناریو تست ندارد.

**Suggested change:** add a submit-failure test, a PDF-failure test, and one that fires `SubmitRequest`
twice in a row.

## What was done well

- **The list is a faithful port**: same endpoint and page size, same row fields, the same two actions
  and the same `objectable == "1"` gate, with the legacy footnote about objecting only to the last
  inspection kept as a string resource.
- **Step-2 and step-3 rules match legacy** — landline pattern when filled, required address, employer
  name, job and both dates, end date not before start date, description longer than 10 — and each has a
  contract test, including the same-day boundary.
- **Deviations from the insured flow are written down where they occur**: the required mobile, the
  read-only workshop, and the client-side search each carry a comment saying they differ from the
  source and why, which is what made items 2 and 3 quick to check.
- **Error handling elsewhere is safe**: `fetchUserProfileForRequest` and the pagers use `Flow.catch`, which
  never intercepts cancellation.
- **No hardcoded Persian strings in production code**; every label goes through `strings.xml`, and the
  only literals are `@Preview` sample rows and comments.
- **The shared `TaminStyledTextField` change is sound**: restricting the click overlay to the field means
  the label and the error text no longer open a picker when tapped, and the error line no longer sits
  inside the tappable area.
- **The submit button is disabled while a request is in flight** (`primaryEnabled = ... && !uiState.isLoading`),
  and the wizard has an exit-confirmation dialog that legacy lacked.
- **Build and the whole test suite pass** across the affected modules.
