## 1. Pension calculation skips the oldest wage-history year — High ✅

> **Round 2:** fixed and verified. The loop now reads `list.lastIndex downTo 0`, matching
> `old_android`. The test that had locked in the wrong behavior
> (`` `skips first wage history row` ``) was replaced with
> `` `includes oldest wage history year in two-year average` ``, which places different wages at
> the oldest and newest of a 2-entry list and asserts both are counted
> (`assertEquals(1500L, result.averageSalaryLastTwoYears)` — the average of both years' wages, not
> just the newest). I ran the suite myself rather than trusting the diff:
> `:core:core-domain:testDebugUnitTest --tests "...CalculateWagePensionUseCaseTest"` →
> `BUILD SUCCESSFUL`, all 4 tests pass, 0 failures.

**File:** `core/core-domain/src/commonMain/kotlin/com/tamin/taminhamrah/useCases/calculateWagePension/CalculateWagePensionUseCase.kt:55-64`

```kotlin
for (i in list.lastIndex downTo 1) {
    for (detail in list[i].wageDetails.asReversed()) {
        val month = detail.month
        val wage = detail.wage
        if (month != null && wage != null) {
            listDays.add(month)
            listWages.add(wage)
        }
    }
}
```

The loop starts at `list.lastIndex` and stops at `1`, so `list[0]` — the oldest year in the wage
history — is never visited at all, no matter how much of it would be needed to reach the 730-day
(two-year) window the average is supposed to be computed over.

`old_android`'s equivalent, `internalCalc()` in `CalculateWagePensionFragment.kt:211`, walks every
index: `(list.size - 1 downTo 0).forEach { i -> ... }` — index 0 included. I checked the domain
model this MR itself introduces
(`core/core-domain/.../model/history/DastmozdInfoDN.kt`, and the DTO→DN mapper in
`core/core-data/.../mapper/HistoryMapper.kt`): `DastmozdInfoItemDN` at every index has the exact
same shape (`wageDetails`, `hisyear`, etc.) — unlike the *separate* `TalfighInfoDN` list, whose
index 0 legitimately holds aggregate totals (`sumHistoryYears`, `historyYears`, ...) and is
correctly treated differently via `firstOrNull()` a few lines above in this same use case. There is
no structural reason found anywhere in this MR, the DTO, or `old_android` for the wage list's index
0 to be treated as special — it looks like the "skip the totals row" pattern that's correct for
`talfigh` was carried over to `dastmozd` by mistake, where every row (including index 0) is real
per-year wage data.

This isn't accidental in the new code — it's asserted on purpose by a test in this same MR,
`CalculateWagePensionUseCaseTest.kt:46` (`` `skips first wage history row` ``), which places a
year with wage `999999` at index 0 and asserts it contributes nothing to
`averageSalaryLastTwoYears`.

**Concrete failure scenario:** a user whose total wage history is short — say two or three years on
record — opens this calculator. `old_android` sums days/wages starting from the newest year down
through every year on record, including the oldest, until it reaches 730 days. The new code stops
one year short of the end of the list, so if the two most recent years don't themselves add up to
730 days (they typically fall just short, at ~720-724 days for two 12-month years, depending on
month-length data), the calculation needs a few days from the third-oldest-or-earlier year to
complete the window — but if that need lands on `list[0]` specifically (a common case for someone
early in their career, where the wage list itself only has 2-3 entries), those days are silently
never added. `sumDays` ends up under 730, `sumWages` under-counted, and both
`averageSalaryLastTwoYears` and `eligibleAmountPension` come out lower than `old_android` would
have computed for the same person.

> **مغایرت بیزینسی:** در نسخه‌ی قدیمی، برای محاسبه‌ی میانگین حقوق دو سال اخیر، تمام سال‌های
> موجود در سابقه‌ی بیمه‌ای فرد بررسی می‌شدند — از جدیدترین تا قدیمی‌ترین سال، بدون استثنا — تا
> مجموع روزها به ۷۳۰ روز (دو سال) برسد. در نسخه‌ی جدید، قدیمی‌ترین سال موجود در لیست همیشه از
> محاسبه کنار گذاشته می‌شود. برای کاربری که سابقه‌ی بیمه‌ای کوتاهی دارد (مثلاً فقط ۲ یا ۳ سال
> سابقه ثبت‌شده)، همین قدیمی‌ترین سال ممکن است دقیقاً همان سالی باشد که برای تکمیل بازه‌ی ۷۳۰
> روزه لازم است؛ در نتیجه مبلغ «میانگین حقوق دو سال اخیر» و «مبلغ مستمری قابل‌دریافت» که به کاربر
> نمایش داده می‌شود، کمتر از مقدار واقعی محاسبه می‌شود.

**Suggested change:** change the loop to `list.lastIndex downTo 0` to match `old_android`, unless
there's a confirmed reason (from backend/product) that the oldest row in this specific list should
be excluded — in which case a comment explaining why would prevent the next reader from having the
same question, and the test name should say why, not just that it happens.

## 2. `MultipleWorkshopResultDN` overloads one field for two unrelated meanings — Low

**File:** `core/core-domain/src/commonMain/kotlin/com/tamin/taminhamrah/model/calculateWagePension/CalculateWagePensionDN.kt:9-14`

```kotlin
data class MultipleWorkshopResultDN(
    val result: Int
) {
    val isMultiple: Boolean get() = result == MULTIPLE_WORKSHOPS_YES
    val pensionAmount: Long get() = result.toLong()
}
```

The same type is returned by both `isMultipleWorkshops()` (where `result` is really a `0/1` flag)
and `calculateMultipleWorkshops()` (where `result` is really a Rial amount), and callers pick
whichever computed property matches the endpoint they called. This mirrors `old_android`'s
`MultipleWorkShopResponse`/`MultipleWorkShopModel`, which does the same thing, so it's not a
regression — just carried-forward ambiguity. Since this MR is already introducing new DN/DTO types
for this feature, it would have been a natural point to split it into two distinct types (e.g.
`MultipleWorkshopEligibilityDN(isMultiple: Boolean)` and `MultipleWorkshopPensionDN(amount: Long)`)
so a caller can't accidentally read `.isMultiple` off a `calc` response or `.pensionAmount` off an
`is-multiple` response.

**Suggested change:** optional — split into two purpose-specific DN types if there's appetite for
it in this MR or a follow-up; not blocking given it faithfully matches the existing API contract
and `old_android`'s own modeling of it.

  follows the existing registration patterns exactly — nothing is left unregistered.

  `*PR.kt`, `*Mapper.kt` in their expected modules).

  the mapper/repository/API-service layers, including an error-path test
