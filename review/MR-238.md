## 1. Home-screen request cards always show the wrong status color — High

**Files:** `core/core-data/src/commonMain/kotlin/com/tamin/taminhamrah/data/repository/home/HomeRepositoryImpl.kt:100`,
`shared/src/commonMain/kotlin/com/tamin/taminhamrah/ui/home/HomeScreen.kt:274-288`

The status *code* is dropped when the request list is cached for the home screen:

```kotlin
// HomeRepositoryImpl.kt:95-102
val requestEntities = requests?.take(3)?.map { req ->
    RequestEntity(
        id = req.id.toString(),
        title = req.title ?: "",
        date = req.creationTime?.toString() ?: "",
        status = req.status?.requestDesc ?: "",   // only the description text is kept
        refCode = req.refCode ?: ""
    )
} ?: currentContent?.requests
```

`HomeContentDN.RequestDN` (`core/core-domain/.../model/home/HomeContentDN.kt`) has no status-code
field at all — only `status: String`. Then, when `HomeScreen.kt` maps the cached row back into the
shared `UserRequestPR` model for rendering:

```kotlin
// HomeScreen.kt:284-285
statusCode = "",
requestTypeId = 0L,
```

`HomeLastRequestsSection.kt:190` calls
`UserRequestWorkflowStatus.fromCode(request.statusCode)` to pick the badge's color — exactly the
project's own enum-based pattern rule 7 asks for, and it works correctly on the full "user requests"
list screen. But `fromCode` is:

```kotlin
fun fromCode(statusCode: String): UserRequestWorkflowStatus? {
    val parsed = statusCode.toIntOrNull() ?: return null
    return entries.find { it.code == parsed }
}
```

`"".toIntOrNull()` is always `null`, so `fromCode` always returns `null` for every home-screen
request card, regardless of the request's real status — it silently falls through to whatever the
`null` branch of the color `when` defaults to. The text label (`requestDesc`) is still correct; only
the color/icon is wrong. This won't show up reading either side of the pipeline in isolation — only
by tracing the status field from network → cache → UI mapping.

> **سناریوی بیزینسی جاافتاده:** رنگ نشان وضعیت (badge) کارت‌های «آخرین درخواست‌ها» در صفحه‌ی اصلی
> همیشه به رنگ خنثی/پیش‌فرض نمایش داده می‌شود، نه رنگ واقعی متناظر با وضعیت درخواست
> (تاییدشده/ردشده/خطا و...)، چون کد وضعیت (`requestCode`) در مسیر ذخیره‌سازی آفلاین دور ریخته
> می‌شود و در نمایش هم به‌صورت رشته‌ی خالی جایگذاری می‌شود؛ در نتیجه enum تشخیص وضعیت که در بقیه‌ی
> اپ درست کار می‌کند، برای این کارت‌ها همیشه نتیجه‌ی خالی برمی‌گرداند.

**Suggested change:** carry `requestCode` through `RequestEntity`/`HomeContentDN.RequestDN`, and set
`statusCode`/`requestTypeId` from the real cached values in `HomeScreen.kt` instead of hardcoding
them.

## 2. Cached campaigns/quickAccess/specialServices are never read by the UI — Medium

**Files:** `core/core-data/src/commonMain/kotlin/com/tamin/taminhamrah/data/repository/home/HomeRepositoryImpl.kt` (sync logic, lines 133-147),
`shared/src/commonMain/kotlin/com/tamin/taminhamrah/ui/home/HomeScreen.kt:247,258,268`

`syncHomeContent()` fetches the main menu, builds `CampaignEntity`/`QuickAccessEntity`/
`SpecialServiceEntity` placeholder rows, and writes them to Room; `getHomeContent()` maps them back
out. But `HomeScreen.kt` renders all three sections from a **different** source entirely:

```kotlin
// HomeScreen.kt
campaigns = uiState.campaigns.toPresentation(),          // from menu.visibleCampaigns() in LoadMenu
sections = uiState.menuItems.toQuickAccessSections(),     // from GetMainMenuUseCase, a second call
services = uiState.menuItems.featuredServices(),          // same
```

`uiState.homeContent?.campaigns` / `?.quickAccess` / `?.specialServices` are never referenced
anywhere in `HomeScreen.kt`. So this MR fetches the main menu **twice** per home load (once inside
`syncHomeContent()`, once via `HomeIntent.LoadMenu`), and the sync's placeholder-building/caching
work for these three fields is computed and persisted for no benefit.

> **سناریوی بیزینسی جاافتاده:** بخش زیادی از داده‌ی «آفلاین-فرست» که برای «دسترسی سریع» و «خدمات
> ویژه» ساخته و در دیتابیس کش می‌شود، اصلاً جایی در رابط کاربری استفاده نمی‌شود — رندر واقعی این دو
> بخش از یک منبع کاملاً جدا (فراخوانی مستقیم منوی اصلی) می‌آید. یعنی یک فراخوانی شبکه‌ی اضافه (منوی
> اصلی، دوبار در هر بار باز شدن صفحه‌ی اصلی) و منطق ساخت/کش‌کردن داده‌ای انجام می‌شود که کسی
> نمایشش نمی‌دهد.

**Suggested change:** either wire `HomeScreen.kt` to actually read `homeContent.campaigns`/
`.quickAccess`/`.specialServices` (removing the redundant `LoadMenu` call), or remove the unused
sync/cache work for these three fields if `LoadMenu` is meant to stay the source of truth.

## 3. `CancellationException` swallowed in the new home sync — High

**Files:** `core/core-data/src/commonMain/kotlin/com/tamin/taminhamrah/data/repository/home/HomeRepositoryImpl.kt:71-91`,
`shared/src/commonMain/kotlin/com/tamin/taminhamrah/ui/home/HomeViewModel.kt:46-56`

```kotlin
// HomeRepositoryImpl.kt — 6 sites, one shown
val identityDeferred = async { runCatching { userRepository.getIdentityInfo().take(2).lastOrNull() }.getOrNull() }
```

The comment above this block explains `runCatching` is there "to avoid cancelling the scope on
failure" — true for ordinary failures, but `runCatching` also catches `CancellationException`
without rethrowing it, so a real cancellation (the coroutine scope itself being torn down, not just
one call failing) is silently converted into a `null` result at each of the 6 sites, and
`syncHomeContent()` proceeds to build/write `HomeContentEntity` from whatever partial results it has
instead of stopping.

```kotlin
// HomeViewModel.kt:46-56
viewModelScope.launch {
    tokenStoreManager.tokenValidFlow()
        .distinctUntilChanged()
        .collectLatest {
            try {
                syncHomeContentUseCase()
            } catch (e: Exception) {
                // Ignore sync errors and fallback to cached data
            }
        }
}
```

This one is inside `collectLatest`, which relies on `CancellationException` being thrown into the
in-flight block to cancel it when a new value arrives (e.g. a rapid login/logout/token refresh).
Catching plain `Exception` without rethrowing cancellation risks swallowing `collectLatest`'s own
cancellation signal for the previous sync — the textbook shape of this codebase's recurring bug.

> **سناریوی بیزینسی جاافتاده:** در چند نقطه از منطق همگام‌سازی جدید (`HomeRepositoryImpl.syncHomeContent`
> و `HomeViewModel.init`) از `runCatching{}` یا `catch (e: Exception)` بدون رهاسازی مجدد
> `CancellationException` استفاده شده — همان الگوی تکراری باگی که در این چرخه‌ی ریویو بارها دیده
> شده؛ می‌تواند باعث شود لغو (cancel) شدن کوروتین‌ها به‌درستی منتشر نشود.

**Suggested change:** replace the `runCatching { }` calls with explicit
`try { ... } catch (e: CancellationException) { throw e } catch (e: Exception) { null }`, and do the
same in `HomeViewModel.init`'s `catch (e: Exception)` block.

## 4. Hardcoded fallback strings, and a dead, already-written correct implementation — Medium

**Files:** `core/core-data/src/commonMain/kotlin/com/tamin/taminhamrah/data/repository/home/HomeRepositoryImpl.kt:107-108,111`,
`core/core-ui/src/commonMain/kotlin/com/tamin/taminhamrah/mapper/home/HomeHeaderMapper.kt`

```kotlin
// HomeRepositoryImpl.kt:106-108
val fullName = identity?.let {
    listOfNotNull(it.firstName, it.lastName).joinToString(" ").takeIf { str -> str.isNotBlank() } ?: "کاربر تامین"
} ?: currentContent?.userInfo?.fullName ?: "کاربر تامین"
```

Two hardcoded Persian literals ("کاربر تامین" — "Tamin user"), shown directly to the user as a
fallback display name, not sourced from `strings.xml`.

Separately, the "is the user covered by Darman" check is reimplemented inline with a raw string
literal:

```kotlin
// HomeRepositoryImpl.kt:110-112
val hasDarmanCoverage = darmanCoverage?.firstOrNull()?.let { main ->
    val refusal = main.finalDesc?.takeIf { it.isNotBlank() } ?: main.message?.takeIf { it.contains("عدم استحقاق") }
    refusal == null
} ?: currentContent?.userInfo?.hasDarmanCoverage
```

This exact logic already exists in this same MR's own diff, properly named and documented:

```kotlin
// HomeHeaderMapper.kt — added by this MR, never called from production code
private const val NOT_ENTITLED_PHRASE = "عدم استحقاق"

fun List<DeservedTreatmentDN>.toDarmanCoveredOrNull(): Boolean? {
    val main = firstOrNull() ?: return null
    val refusal = main.finalDesc?.takeIf { it.isNotBlank() } ?: main.message?.takeIf { it.contains(NOT_ENTITLED_PHRASE) }
    return refusal == null
}
```

`toDarmanCoveredOrNull()` is well-documented (including a note on why it can't import the equivalent
`feature/treatment` constant, a genuine module-boundary constraint) and has its own test
(`HomeHeaderMapperTest.kt`), but is never invoked anywhere outside that test — the repository
computes the same thing over again with a bare literal instead of calling it.

**Suggested change:** move "کاربر تامین" into `strings.xml`. Have `HomeRepositoryImpl` call
`toDarmanCoveredOrNull()` instead of duplicating its logic inline (adjusting the module dependency
if `core-data` can call into `core-ui`, or moving the shared function to a module both can reach).

## 5. Dead navigation parameter — Low

**File:** `feature/userRequest/src/commonMain/kotlin/com/tamin/taminhamrah/feature/userRequest/Navigation.kt:28-33`

```kotlin
fun NavController.navigateToUserRequests(
    refCode: String? = null,
    requestTypeId: String? = null,
) {
    navigate(UserRequestRoute.List(refCode = refCode))   // requestTypeId never used
}
```

`UserRequestRoute.List` has no `requestTypeId` field, so this parameter can never reach the
destination screen. No call site in the repo currently passes it (`TaminHamrahNavGraph.kt` bypasses
this helper and calls `navigate(UserRequestRoute.List(refCode = refCode))` directly), so this is
dead rather than live-broken today — but it's a public function with a parameter that silently does
nothing, which invites a real bug the next time someone tries to use it as documented.

**Suggested change:** either add `requestTypeId` to `UserRequestRoute.List` and forward it, or
remove the unused parameter until it's actually wired up.

## What was done well

- **The `TaminHamrahNavGraph.kt` extraction is a genuine architecture improvement, not churn.** The
  ~250 lines of previously-inline home UI (menu grid, campaign carousel, story rail, role dropdown)
  are pulled out into their own `HomeScreen.kt` composable, correctly wired through callbacks per
  rule 4 — Home was previously not extractable, previewable, or testable in isolation at all, and now
  is. No correctness issues found in the restructuring itself; most of the remaining diff noise is
  import resorting.
- **The new request-type picker bottom sheet is a faithful, arguably cleaner port** of legacy's
  generic `MenuDialogFragment`-based type picker in the "user requests" search flow.
- **"Quick access" is correctly treated as new UX, not a port** — no legacy equivalent exists
  anywhere in `old_android`, and the code doesn't pretend otherwise.
- **`HomeHeaderMapper.kt`'s Darman-coverage check is thoughtfully documented**, including an explicit
  note on why it can't reuse the `feature/treatment` module's identical constant (a genuine module
  dependency-graph constraint) — even though it ended up unused (item 4), the function itself is a
  model of how to explain a non-obvious constraint.
- **No hardcoded Persian strings in the newly-added UI components** — the two literals in item 4 are
  confined to the data layer, the rest of this large diff correctly routes through `strings.xml`.
