This diff deletes nine fully-working screens (`EmployerAgreementScreen`, `ManagementDebitScreen`,
`ObjectionableDebitScreen`, `PaymentSheetsScreen`, `WorkshopDebitScreen`,
`WorkshopDebtInquiryScreen`, `WorkshopMembersScreen`, `WorkshopRecentlyAddedMembersScreen`,
`WorkshopStackholdersScreen` — each a pure deletion in the diff, not a move) and their
ViewModels/DI registrations (`GetAllEmployerAgreementByNationalIdUseCase`,
`GetAllPaymentSheetsUseCase`, `GetWorkshopDebitUseCase`, etc. are all removed from
`DomainModule.kt` and no longer referenced by `WorkshopsModule.kt`, which now registers only
`WorkshopsViewModel`). `workshopsScreen(...)` was already reachable from the main nav graph before
this MR (`TaminHamrahNavGraph.kt` already called it), so `کارگاه‌های کارفرما` is not new, unreached
surface — it is a live entry point.

In their place, `WorkshopDetailScreen`'s own doc comment still says "the eight services it can be
taken to" and renders `WorkshopAction.entries.forEach { ... }` under a «عملیات این کارگاه» header —
but with zero enum entries, that section renders empty for every workshop, and tapping a workshop
row can go nowhere. The domain/data layer and a shared form-component library for four of those
services (Article 16, debit objection, debit payment, new-member registration) are added in this
same diff, but no screen composable consumes them yet — `git log` on this branch shows commits
that did build them ("implement Article 16 and debt objection forms in workshops", "implementing
adding a new member to a workshop"), and this final squashed commit is explicitly titled
"EM-2598 کارگاه‌های کارفرما **(صفحات اصلی)**" — main pages only — so this looks like a deliberate
scope cut for this specific MR rather than an oversight.

**Suggested change:** this is not necessarily wrong — it may be a deliberate first step of a
staged rollout where the follow-up MRs (adding each `WorkshopAction` row + its screen) are queued
to merge immediately after. Before merging, please confirm explicitly:
- whether this MR is meant to reach `develop`/a release build on its own, or only together with
  the follow-up screens landing in the same release window, and
- if it can reach `develop` alone, whether the workshops entry point should be hidden/flagged off
  until at least the highest-traffic actions (workshop debt, members) are back, rather than
  shipping a detail screen with an empty action list.

### Author's confirmation

Yes — deliberate, and the follow-ups are already written.

**Is this meant to reach a release on its own?** No. It is the first of nine MRs, one per Jira
task under the same parent, and they are meant to land in one release window:

| task | branch | own diff |
|---|---|---|
| EM-2598 صفحات اصلی | `Feature-EM-2598-workshops-main` | this MR |
| EM-2599 برگ پرداخت‌ها | `Feature-EM-2599-payment-sheets` | 6 files |
| EM-2600 گردش حساب بدهی | `Feature-EM-2600-debt-turnover` | 10 files |
| EM-2601 استعلام بدهی | `Feature-EM-2601-debt-inquiry` | 6 files |
| EM-2602 اعتراض به بدهی | `Feature-EM-2602-debt-objection` | 8 files |
| EM-2603 نام‌نویسی غیرحضوری | `Feature-EM-2603-member-registration` | 8 files |
| EM-2604 ماده ۱۶ | `Feature-EM-2604-article-sixteen` | 8 files |
| EM-2605 کارکنان | `Feature-EM-2605-workshop-members` | 7 files |
| EM-2606 ذینفعان | `Feature-EM-2606-workshop-stakeholders` | 7 files |

Each of the eight exists as a commit today, chained off this one, and each passes
`testDebugUnitTest testDirectDebugUnitTest` on the whole project. They are held back only so each
Jira task gets its own reviewable MR; they will be pushed and merged in order as this one lands.

Each restores exactly one service — its screen, its `WorkshopAction` row, its route and
destination, and its ViewModel registration — so the nine deleted screens come back one MR at a
time rather than being lost. The `when` in `WorkshopAction.route()` is exhaustive on purpose: an
action cannot be added without a destination, so a menu row that goes nowhere is a compile error
rather than something to notice in review.

**Should the entry point be hidden if it can reach `develop` alone?** If `develop` were released
between this MR and EM-2606, then yes — your reading is right, and the empty «عملیات این کارگاه»
list would be a straight regression for کارفرما users. Two ways to prevent it, and the choice is
the team's rather than ours:

1. **Do not cut a release from `develop` until EM-2606 has merged.** Preferred: the eight are
   small, already green, and reviewable quickly.
2. If a release may go out mid-chain, hide کارگاه‌های کارفرما behind its `FeatureFlag` for that
   release and turn it back on once the actions are back.

We have not flagged it off in this MR, because doing so unconditionally would also hide it in the
normal case where the chain completes first. Say which you want and we will push the change.

## What was done well

- The ported business constants that *were* checked line-by-line against `old_android` all match:
  the 31/21-day objection filing windows (`WorkShopDebtDN.kt`'s `ObjectionKind`), the ماده ۱۶
  `objectionType = "3"` hardcode (`WorkshopMapper.kt`), and the members-vs-stakeholders
  filter-key naming quirk (documented directly in `WorkshopQueries.kt`).
- Several latent bugs in `old_android` are fixed here and explicitly documented as such in code
  comments rather than silently changed — e.g. `ObjectionKind.wireLabel()` notes the legacy client
  "always sent `FILED`'s label... because it read a constant field that shadowed the computed
  kind," and `WorkshopNewMemberQuery` notes the old branch-code key mismatch that made that
  screen's search silently never fire a request.
- `WorkshopsViewModel`/`WorkshopsScreen` (the part of this MR that *is* wired up end-to-end) is
  clean, has 14 tests in `WorkshopsViewModelTest.kt`, and does not swallow
  `CancellationException` anywhere (it consistently uses `Flow.catch { }` rather than a raw
  `try/catch`, unlike the pattern flagged on MR !191 and MR !201).
- Good data-layer test coverage for the new features despite no UI yet consuming them
  (`WorkshopUseCasesTest.kt`, `WorkShopsApiServiceTest.kt`, `FakeWorkShopsRepository.kt`).
- `NewMemberRegistrationDN`'s field set matches `old_android`'s `InsuredRegistrationFragment`
  (same 8 required fields), though since no form UI exists yet to enforce them, this is only a
  shape check — the actual field-level validation (blank checks, ordering) can't be verified until
  that screen ships.
