## 1. String concatenation without delimiter in key — Low

**File:** `feature/workshops/src/commonMain/kotlin/com/tamin/taminhamrah/feature/workshops/ui/assignerContracts/AssignerContractsScreen.kt:180`

```kotlin
key = { it.card.workshopId + it.contractRow + it.contractSequence },
```

String concatenation without delimiters can collide (`"12"+""+"3"` and `"1"+"2"+"3"` both give
`"123"`), and Compose's `key` must be unique per item to track recomposition correctly.

> **Round 2 — ✅ fixed** (`011bd36b7`). The key is now
> `"${it.card.workshopId}_${it.contractRow}_${it.contractSequence}"` — delimited, no collision risk.

## 3. Computational-base document grouping is broader than legacy's — Low, needs confirmation

**File:** `core/core-ui/src/commonMain/kotlin/com/tamin/taminhamrah/mapper/workshop/WorkshopUiMapper.kt:182-186`

`old_android`'s "مدارک تصاویر نامه" (letter-image documents) section filters on **two** fields
together (`ContractInfoViewModel.kt:171-172`):

```kotlin
attachmentList = dataDetail?.filter { it.documentType == "1" && it.documentCode == "1" }
```

— so a document with `documentCode == "1"` but `documentType` other than `"1"` (i.e. a PDF, not an
image) was silently **dropped from every section** in the legacy UI (none of the other three
sections match `documentCode == "1"` either). The new mapper groups purely by `categoryCode`
(`documentCode`), independent of `documentType` — so that same document now surfaces, correctly
rendered as a PDF, under the "letter" heading instead of disappearing.

This is arguably a bug fix rather than a regression (nothing should be silently dropped), but it's
still new behavior beyond what's being ported, on a document-visibility rule. Flagging so it's a
deliberate call, not an accidental side effect of grouping by one field instead of two.

**Suggested change:** confirm with whoever owns this data that a "letter" document is correctly
identified by `documentCode` alone regardless of `documentType`, i.e. that the legacy `documentType`
check was dead-code-shaped filtering rather than an intentional exclusion. If confirmed, this can be
marked accepted as a deliberate improvement.

## 4. No mapper-level test for the money-relevant amount distinction — Low

**Files:** `core/core-ui` mapper tests (no `AssignerContractMapperTest`/`ComputationalBaseMapperTest`
equivalent at the presentation layer)

`ComputationalBaseDN.amount: Long?` is documented as "null and zero are different answers — see the
mapper" (`ComputationalBaseDN.kt`), and `AssignerContractPR`/the `toPresentation()` mapper is where
that distinction becomes display text. `AssignerContractsViewModelTest.kt` (709 lines) is thorough at
the ViewModel level, but nothing directly tests the presentation mapper's zero-vs-null formatting or
`BaseDocumentCategory.fromCode`'s grouping — both money- or visibility-relevant, and both currently
exercised only indirectly through the ViewModel test rather than pinned at the level where the
formatting logic actually lives.

**Suggested change:** a small `ComputationalBaseDN.toPresentation()` test with `amount = null` vs
`amount = 0L` asserting the two render differently, alongside a `BaseDocumentCategory.fromCode`
coverage table.

## What was done well

- **Business-flow parity is otherwise solid.** Both list filter params (`workshop.workshopId`/
  `workshop.branchCode`/`contractRow` as `EQ` clauses) and the computational-base query
  (`workshopId`/`brchCode`/`contractRow`/`contractSequence`) match `old_android`'s
  `ContractInfoViewModel` field-for-field, and the detail screen's three field groups match the
  legacy `createKeyValue*` sets exactly.
- **The two-sided contract model is deliberately guarded against a real mix-up.**
  `AssignerContractDN`'s KDoc and the mapper both call out that `assigner` (the signed-in employer's
  own کارگاه) and `employer` (the پیمانکار) must never be swapped, since the wrong one on a card
  would send the bases call looking for someone else's records — documented in place, not left
  implicit.
- **Document-kind routing is enum-driven, not string-compared.** `BaseDocumentKind.fromType()` and
  `BaseDocumentCategory` (with `StringResource` titles) replace `old_android`'s raw
  `documentType`/`documentCode` string comparisons entirely — exactly what `CLAUDE.local.md` rule 7
  asks for, and no magic-value comparison was found anywhere in this diff.
- **`AssignerContractsViewModelTest.kt` (709 lines) is genuinely thorough** — pagination,
  stale-request discarding across two different contracts' bases, quick-pick de-duplication,
  document open/fail/missing/retry states, and the blank-workshop-id validation error are all
  covered, not just the happy path.
- **The four-key guard on computational-base navigation is correct and tested.** A پیمان missing any
  of the four keys the bases endpoint needs is recognized before navigation (`canOpenBases`), with
  the button disabled and a reason shown, rather than opening a screen that would return someone
  else's records or nothing at all.
- **`WorkshopSheetParts.kt` is a legitimate, documented dedup** of three feature-local bottom sheets
  that drew the same header, not a duplicate of `core-ui`'s existing `TaminSearchableListSheet`.
