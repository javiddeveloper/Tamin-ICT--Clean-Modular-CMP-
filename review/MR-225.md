## 1. `core-network` does not compile — High, blocking

**File:** `core/core-network/src/commonMain/kotlin/com/tamin/taminhamrah/dataSource/workshopsSource/WorkShopsRemoteDataSourceImpl.kt`

```

```

`WorkShopsRemoteDataSourceImpl.kt` — the file that should contain
`internal class WorkShopsRemoteDataSourceImpl(...) : WorkShopsRemoteDataSource { ... }` — currently
contains, instead, a second full copy of the `WorkShopsRemoteDataSource` *interface* declaration
(233 lines, an exact duplicate of `WorkShopsRemoteDataSource.kt`'s content). The actual
implementation class no longer exists anywhere in the file.

Traced via `git log` and `git show`: the file was correct as of commit `849f323ff` ("Add Article 38
settlement certificate APIs..."). The very next commit that touches it, `c954956f9` ("Merge
remote-tracking branch 'origin/develop' into Feature-EM-2618-vagozarkonandegan"), lists this exact

resolution is broken — the implementation body was lost.

The result: `:core:core-network` fails to compile, which means every module that depends on it
(`:core:core-data`, `:feature:workshops`, and transitively the whole app) cannot be built or tested.
None of the other findings in this report could be build/test-verified this round because of this —
only source-level reading was possible past this point.

**Suggested change:** restore the actual `WorkShopsRemoteDataSourceImpl` class body (the pre-merge
version at `849f323ff` is a good reference point, combined with whatever new methods `develop` added
to the interface in the meantime — check `WorkShopsRemoteDataSource.kt`, which resolved correctly,
for the full current method set to implement). Re-run the full build after fixing before pushing.

## 2. Computational-base workflow status is dropped entirely — Medium

**Files:** `core/core-domain/src/commonMain/kotlin/com/tamin/taminhamrah/model/workshop/AssignerContractDN.kt:49-61` (`ComputationalBaseDN`),
`core/core-network/.../model/workshop/AssignerContractDTO.kt` (`ComputationalBaseDTO`),
`feature/workshops/.../ComputationalBaseDetailScreen.kt`

Legacy's `ComputationalBaseResponse.kt` carries a `status` field ("01"–"17") and maps it to a
17-state workflow description, shown **bold** as the first row of the detail view:

```kotlin
// old_android — ComputationalBaseResponse.kt:377-398 (excerpt)
private fun statusDescription(): String = when (status) {
    "01" -> "ارسال پيامک"
    "02" -> "ثبت مباني محاسباتي توسط واگذارنده"
    "03" -> "تاييد و ثبت در اطلاعات تکميلي پيمان"
    "04" -> "عدم تاييد"
    // ... through "17" — up to صدور/ابلاغ مفاصاحساب (settlement certificate issued)
}
// createKeyValue(): keyValueList.add(KeyValueModel("وضعیت", statusDescription(), _isValueBold = true))
```

The new domain model has no equivalent field at all:

```kotlin
// AssignerContractDN.kt:49-61
data class ComputationalBaseDN(
    val letterNumber: String = "",
    val sendDate: Long? = null,
    val amount: Long? = null,
    val startDate: Long? = null,
    val endDate: Long? = null,
    val documents: List<BaseDocumentDN> = emptyList(),
    // no status field
)
```

Confirmed `ComputationalBaseDTO` never decodes a `status` field from the wire response either, and
neither `ComputationalBasesScreen.kt` (list) nor `ComputationalBaseDetailScreen.kt` (detail) render
any status/workflow-stage information anywhere. Unlike the settlement-request deviations in item 3
(which are explicitly documented as intentional), nothing in the code acknowledges this omission.

> **سناریوی بیزینسی جاافتاده:** واگذارنده‌ای (کارفرما) که برای یک پیمان مبانی محاسباتی ثبت کرده، در
> نسخه‌ی جدید هیچ راهی برای دیدن اینکه درخواستش در کدام مرحله از فرآیند بررسی/محاسبه‌ی بدهی/صدور
> مفاصاحساب قرار داره نداره — اطلاعاتی که نسخه‌ی قدیمی به‌صورت برجسته (بولد) نشون می‌داد. مثلاً
> کاربر نمی‌تونه بفهمه درخواستش رد شده، در انتظار محاسبه‌ی بدهیه، برگه‌ی بدهی قطعی صادر شده، یا
> مفاصاحساب نهایی براش صادر شده.

**Suggested change:** add `status` to `ComputationalBaseDTO`/`ComputationalBaseDN`, and render the
17-state description in `ComputationalBaseDetailScreen.kt` (an enum, per rule 7, rather than a raw
string `when`).

## 3. Four settlement-request validation rules are stricter than legacy — Low, needs confirmation

**File:** `feature/workshops/src/commonMain/kotlin/com/tamin/taminhamrah/feature/workshops/ui/assignerContracts/settlement/contract/SettlementRequestContract.kt:50-54,268-360`

Checked per-subject against `MafasaHesabRegisterFragment.lastStepIsValid()`/
`setUiVisibilityCordingContractSubject()`. The rules match, with four documented deviations (in the
code's own KDoc):

1. The "پیمانکار جزء" (subcontractor) yes/no question is now required — legacy never validated it,
   just defaulted to "0" (no).
2. Subjects 01 and 29 now require their condition image — legacy never checked `subjectimageId` for
   either.
3. Subject 11's four cost fields now may not sum past the gross amount — legacy only required each
   field non-blank, with no sum check.
4. The minimum letter-number length (5 characters) is now a blocking validation — legacy only showed
   a live text-field error without gating overall form validity on it.

These read as deliberate improvements, not oversights, and are documented as such in the code. But
they do change what a user can successfully submit compared to the currently-shipped legacy app, so
worth an explicit confirmation this was agreed with product/design rather than assumed.

**Suggested change:** confirm with product/design that these four stricter rules are intended. If
so, no code change needed — this can be marked accepted.

## What was done well

- **The settlement-request wire format is an unusually faithful, well-documented port**, including
  details only visible in the legacy *data-source* layer (not the fragment/ViewModel) — e.g.
  `mafasaStatus`/`contractNumber` being hardcoded `"-"` regardless of what's passed in, correctly
  reproduced in `WorkShopsApiService.kt:155-163` with a comment explaining why. The TT-joined id, the
  fixed `T19:30:00.000Z` date stamp, and the `subjectamount2` JSON-type-follows-subject quirk are all
  preserved and directly tested in `WorkShopsRepositorySettlementTest.kt`.
- **No `CancellationException`-swallowing anywhere in the new/touched code.** Every error-handling
  path in `SettlementRequestViewModel.kt` and `AssignerContractsViewModel.kt` uses `Flow.catch {}`
  consistently (not raw `try/catch (e: Exception)` or `runCatching`) — the recurring bug found in
  nearly every other MR reviewed this cycle does not appear here.
- **No hardcoded Persian strings in production code** — all copy routes through `strings.xml`; the
  only literal Persian strings found are `@Preview`-only sample data.
- **Subject-code string comparisons in `SettlementTermsForm.of()` are not a rule-7 violation** —
  there's no pre-existing project enum for these server-driven subject codes, and this mapping *is*
  the (well-documented) enum-equivalent definition being introduced, not a magic-string `when` layered
  on top of an enum that already exists.
- **`AssignerContractsViewModel`'s certificate-lookup caching faithfully mirrors legacy's
  Clause38 two-call (list → detail) pattern**, with the same safe `Flow.catch` error handling.
