## 3. Four settlement-request validation rules are stricter than legacy — Low, needs confirmation

**File:** `feature/workshops/src/commonMain/kotlin/com/tamin/taminhamrah/feature/workshops/ui/assignerContracts/settlement/contract/SettlementRequestContract.kt:50-54,268-360`

Checked per-subject against `MafasaHesabRegisterFragment.lastStepIsValid()`/
`setUiVisibilityCordingContractSubject()`. The rules match, with four documented deviations (in the
code's own KDoc):

1. The "پیمانکار جزء" (subcontractor) yes/no question is now required — legacy never validated it,
   just defaulted to "0" (no).
2. Subjects 01 and 29 now require their condition image — legacy never checked `subjectimageId` for
   either.
3. Subject 11's four cost fields now may not sum past the gross amount — legacy only required each
   field non-blank, with no sum check.
4. The minimum letter-number length (5 characters) is now a blocking validation — legacy only showed
   a live text-field error without gating overall form validity on it.

These read as deliberate improvements, not oversights, and are documented as such in the code. But
they do change what a user can successfully submit compared to the currently-shipped legacy app, so
worth an explicit confirmation this was agreed with product/design rather than assumed.

**Suggested change:** confirm with product/design that these four stricter rules are intended. If
so, no code change needed — this can be marked accepted.

**Round 2:** unchanged — still present exactly as before, still documented in the same KDoc on
`SettlementRequestUiState` ("made binding where it only printed an error... as the design asks"), and
still no recorded product/design confirmation. Not a defect on its own, just still open pending that
confirmation.

## What was done well

- **The settlement-request wire format is an unusually faithful, well-documented port**, including
  details only visible in the legacy *data-source* layer (not the fragment/ViewModel) — e.g.
  `mafasaStatus`/`contractNumber` being hardcoded `"-"` regardless of what's passed in, correctly
  reproduced in `WorkShopsApiService.kt:155-163` with a comment explaining why. The TT-joined id, the
  fixed `T19:30:00.000Z` date stamp, and the `subjectamount2` JSON-type-follows-subject quirk are all
  preserved and directly tested in `WorkShopsRepositorySettlementTest.kt`.
- **No `CancellationException`-swallowing anywhere in the new/touched code.** Every error-handling
  path in `SettlementRequestViewModel.kt` and `AssignerContractsViewModel.kt` uses `Flow.catch {}`
  consistently (not raw `try/catch (e: Exception)` or `runCatching`) — the recurring bug found in
  nearly every other MR reviewed this cycle does not appear here.
- **No hardcoded Persian strings in production code** — all copy routes through `strings.xml`; the
  only literal Persian strings found are `@Preview`-only sample data.
- **Subject-code string comparisons in `SettlementTermsForm.of()` are not a rule-7 violation** —
  there's no pre-existing project enum for these server-driven subject codes, and this mapping *is*
  the (well-documented) enum-equivalent definition being introduced, not a magic-string `when` layered
  on top of an enum that already exists.
- **`AssignerContractsViewModel`'s certificate-lookup caching faithfully mirrors legacy's
  Clause38 two-call (list → detail) pattern**, with the same safe `Flow.catch` error handling.
