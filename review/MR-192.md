## 1. Field-validation error messages are hardcoded in the ViewModel instead of using `strings.xml` — Medium

**File:** `feature/pensioner/src/commonMain/kotlin/com/tamin/taminhamrah/feature/pensionInquiry/ui/issuanceCertificate/IssuanceCertificateViewModel.kt:113-126`

```kotlin
private fun validateFields(): PartialState.ValidationFailed? {
    val state = uiState.value
    val pensionerIdError = if (state.selectedPensionerId.isNullOrBlank()) {
        "شماره مستمری را انتخاب کنید"
    } else null
    val recipientError = if (state.selectedRecipient == null) {
        "گیرنده را انتخاب کنید"
    } else null
    val branchNameError = when {
        state.branchName.isBlank() -> "نام شعبه را وارد کنید"
        INVALID_BRANCH_NAME_CHARS_REGEX.containsMatchIn(state.branchName) ->
            "نام شعبه شامل کاراکتر غیر مجاز است"
        state.branchName.length < 2 && !NUMERIC_REGEX.matches(state.branchName) ->
            "نام شعبه نمی‌تواند کمتر از دو کاراکتر باشد"
        else -> null
    }
    ...
```

Per `CLAUDE.local.md` rule 7, user-facing Persian text must come from `composeResources/strings.xml`,
not be a literal in code. This MR itself adds matching string resources for two of these three
messages — `issuance_certificate_error_select_pensioner`, `issuance_certificate_error_select_recipient`,
`issuance_certificate_error_enter_branch_name` (`core/core-ui/.../strings.xml`, new "Issuance Wage
Certificate" section) — with text identical to the hardcoded literals above, but the ViewModel never
references them. The other two branch-name error messages ("نام شعبه شامل کاراکتر غیر مجاز است" /
"نام شعبه نمی‌تواند کمتر از دو کاراکتر باشد") have no string resource at all.

`IssuanceCertificateContract.kt` declares these as plain `String?` fields, and
`IssuanceCertificateScreen.kt` renders them verbatim via `FieldErrorText(state.xxxError)` — so the
literal travels untouched from ViewModel to screen.

**Failure scenario:** any future localization pass or copy review that greps `strings.xml` for
user-facing text will miss all five of these validation messages entirely, since three of them
already have unused sibling resources sitting right next to them (easy to assume they're wired up
when they aren't) and two aren't in `strings.xml` at all.

**Suggested change:** resolve the three already-added resources via `getString(Res.string.xxx)`
(this file is already inside `handleGoToNextStep`/`handleSubmitRequest`'s `flow { }` builders, so a
suspend `getString` call is available the same way `IssuanceCertificateViewModel.handleInit()`
already uses it elsewhere in this file), and add the two missing resources for the branch-name
character/length errors.

## 2. Identity-info fetch failure is silently swallowed and untested — Low

**File:** `feature/pensioner/src/commonMain/kotlin/com/tamin/taminhamrah/feature/pensionInquiry/ui/issuanceCertificate/IssuanceCertificateViewModel.kt:63-71`

```kotlin
private fun handleInit(): Flow<PartialState> = flow {
    emit(PartialState.Loading(true))
    getIdentityInfoUseCase()
        .catch { }
        .collect { identity ->
            val fullName = listOfNotNull(identity.firstName, identity.lastName)
                .joinToString(" ")
            emit(PartialState.FullNameLoaded(fullName))
        }
    getPensionerIdUseCase()
        .catch {
            sendEvent(IssuanceCertificateEvent.ShowToast(it.toSingleLineMessage()))
            emit(PartialState.Loading(false))
        }
        ...
```

The pensioner-ID fetch right below it correctly surfaces failures via `sendEvent(ShowToast(...))`,
but the identity-info fetch's `.catch { }` is empty — no toast, no log, nothing. `fullName` is shown
on the confirm step (`issuance_certificate_detail_full_name`) as part of the summary the user
reviews before submitting an official certificate request, so a failure here leaves that field
silently blank with no indication anything went wrong, and there is nothing in the code (`Logger.e`
or similar) that would even show up in a bug report.

> سناریوی بیزینسی که تست ندارد: اگر واکشی اطلاعات هویتی کاربر (نام و نام خانوادگی) با خطا مواجه شود،
> این خطا در هیچ‌جا مدیریت نمی‌شود — نه به کاربر پیامی نمایش داده می‌شود و نه حتی برای دیباگ ثبت
> می‌شود. کاربر در مرحله‌ی «بازبینی و تأیید» فیلد نام و نام خانوادگی را خالی می‌بیند بدون این‌که
> بداند چرا، و می‌تواند بدون این اطلاعات درخواست گواهی رسمی را نهایی کند.

**Suggested change:** at minimum log the failure (`Logger.e { ... }`, matching the pattern used
elsewhere in this codebase, e.g. `NetworkUtils.safeCall`); consider whether a blank name on an
official certificate request should actually block submission or show a non-blocking toast, and add
a test covering the identity-fetch-fails-but-pensioner-ids-still-load case.

## What was done well

- The branch-name validation is a faithful, exact port of `old_android`'s `Utility.checkInputIsValidBranch`
  regex (`[a-zA-Z$&+،,:;=\\?@#|/'<>.^*()%!-]`) and the `length < 2 && !isNumericString()` exception —
  including the same auto-prefix-with-"شعبه"-if-missing behavior (`formatBranchName`), carried over
  field-for-field.
- The single-pension-ID UX detail from `old_android` (`if (size <= 1) hideDrawable()`) is correctly
  reproduced as `canSwitch = state.pensionerIds.size > 1` gating the picker.
- `HealthMutationResult`-style reuse: this MR's recipient-search UX (fetch once, filter client-side)
  deliberately mirrors the already-established pattern in `ActiveRelationViewModel` (same
  `GetRecipientsUseCase`, same `.filter { it.name.contains(query) }` shape) rather than inventing a
  third variant — consistent with the rest of the codebase, not a regression from `old_android`'s
  server-side paginated search (that precedent was already set before this MR).
- Good test coverage: `IssuanceCertificateViewModelTest.kt` (466 lines) covers both validation paths,
  step transitions, submit success/failure, and the pensioner-id/recipient selection flows.
- DI (`GetWageCertificateReportUseCase`/`GetIdentityInfoUseCase` registered in `DomainModule.kt`) and
  navigation (`onGoHome` threaded through as a callback, popping to `Route.Home` rather than a direct
  cross-feature import) both follow project convention.
