## 1. Mobile number became a required field in Step 1 — Medium

**File:** `feature/taminServices/src/commonMain/kotlin/com/tamin/taminhamrah/feature/taminServices/inspection/contract/InspectionContract.kt:79-82`

```kotlin
val isRequestStep1Valid: Boolean
    get() = ValidationUtils.isPhoneNumberValid(identityContact.mobile) &&
        ValidationUtils.isLandlineValid(identityContact.landline) &&
        ValidationUtils.isEmailValid(identityContact.email)
```

`ValidationUtils.isPhoneNumberValid(phone) = phone.length == 11` has no "blank is valid" exception
(unlike `isLandlineValid`/`isEmailValid`, both used right next to it in this same expression, which
explicitly return `true` on blank). `IdentityContactStep.kt:142` also marks the field
`isRequired = true`. `identityContact.mobile` is prefilled from `GetUserProfileUseCase` (`profile.mobile.orEmpty()`)
but is editable and can be blank if the profile has none — nothing else in the wizard prevents the
user from reaching Step 1 with a blank mobile.

> در نسخه‌ی قدیمی (`SubmitInspectionRequestFragment.kt`، متد `checkValidInputIdentityInfoStep()`)،
> شماره موبایل، تلفن ثابت و ایمیل هر سه **اختیاری** بودند — فقط در صورتی که کاربر مقداری وارد
> می‌کرد، فرمت آن بررسی می‌شد (`mobile.isNotBlank() && checkValidMobile != 0`). در کد جدید، فیلد
> موبایل الزامی شده (`isRequired = true`) و بدون یک شماره‌ی موبایل معتبر و کامل، کاربر اصلاً نمی‌تواند
> از قدم اول عبور کند — حتی اگر بخواهد صرفاً با تلفن ثابت یا ایمیل قابل تماس باشد، همان‌طور که در
> نسخه‌ی قدیمی امکانش بود.

**Failure scenario:** a user whose profile has no mobile number on file (or whose mobile field was
cleared) reaches Step 1 with a blank, editable mobile field. Unlike `old_android`, they cannot
proceed past Step 1 at all without typing a valid 11-digit mobile number — even though landline and
email are both still correctly optional right next to it.

**Suggested change:** either drop the mobile requirement from `isRequestStep1Valid` (validate the
same way as landline/email — format-only, blank allowed) if this was unintentional, or confirm with
product that requiring a mobile number is a deliberate tightening for this specific request type.

## 2. Employment end date must now be strictly after the start date — Medium

**File:** `core/core-ui/src/commonMain/kotlin/com/tamin/taminhamrah/util/ValidationUtils.kt:82-85`

```kotlin
fun isDateRangeValid(startTimestamp: Long?, endTimestamp: Long?): Boolean {
    if (startTimestamp == null || endTimestamp == null) return true
    return endTimestamp > startTimestamp
}
```

> در نسخه‌ی قدیمی (`SubmitInspectionRequestFragment.kt`)، فقط زمانی خطا نمایش داده می‌شد که
> «تاریخ پایان» *قبل از* «تاریخ شروع» باشد (`endDate < startDate`) — یعنی انتخاب یک روز یکسان برای
> شروع و پایان دوره‌ی اشتغال (یک بازرسی یک‌روزه) مجاز بود. در کد جدید، پایان باید *دقیقاً بعد از*
> شروع باشد (`endTimestamp > startTimestamp`)، پس اگر کاربر برای شروع و پایان یک تاریخ یکسان انتخاب
> کند، فیلد به‌عنوان نامعتبر علامت می‌خورد و دکمه‌ی «مرحله‌ی بعد» غیرفعال می‌ماند — بدون این‌که خطای
> روشنی نشان دهد چرا (چون همان تاریخ به‌نظر منطقی می‌رسد).

**Failure scenario:** a user reporting a single-day inspection period picks the same Jalali date for
both "شروع اشتغال" and "پایان اشتغال" — a case `old_android` explicitly allowed. The end-date field
shows an error and Step 2's "next" button stays disabled with no obvious reason why, since the two
dates the user picked don't look wrong to them.

**Suggested change:** change the comparison to `endTimestamp >= startTimestamp` to match
`old_android`'s "only reject *before*" rule (this helper is also documented as shared/general-purpose,
so double-check no other future caller actually wants the strict version before changing it globally).

## 3. Request description's minimum-length requirement was dropped — Medium

**File:** `feature/taminServices/src/commonMain/kotlin/com/tamin/taminhamrah/feature/taminServices/inspection/contract/InspectionContract.kt:96`

```kotlin
val isRequestStep3Valid: Boolean get() = requestDescription.isNotBlank()
```

> در نسخه‌ی قدیمی (`SubmitInspectionRequestFragment.kt`، قدم سوم)، دکمه‌ی نهایی ثبت درخواست فقط
> زمانی فعال می‌شد که طول متن توضیحات بیش از ۱۰ کاراکتر باشد (`text.length > 10`). در کد جدید این
> محدودیت به‌کلی حذف شده و فقط بررسی می‌شود که فیلد خالی نباشد — یعنی کاربر می‌تواند با یک یا دو
> کاراکتر (مثلاً فقط یک حرف) یک درخواست بازرسی رسمی را ثبت کند، در حالی که نسخه‌ی قدیمی این را
> مسدود می‌کرد.

> **سناریوی بیزینسی که تست ندارد:** هیچ تستی برای این‌که توضیحات کوتاه‌تر از حداقل طول مورد انتظار
> (یا فقط یک کاراکتر) باید مانع از فعال‌شدن دکمه‌ی ثبت درخواست شود وجود ندارد — نه در سطح
> ViewModel/Contract و نه در تست‌های موجود این فیچر.

**Failure scenario:** a user opens the description step, types a single non-space character, and the
submit button becomes enabled — the request is sent to the backend with an effectively-empty
description, something `old_android` structurally prevented.

**Suggested change:** restore a minimum-length check (confirm the exact number with product/business
— `old_android`'s was 10) in `isRequestStep3Valid`, mirroring how `requestDescription` is displayed
elsewhere, and add a test covering the too-short-description-blocks-submit case.

## 4. Workshop code is now required and must be exactly 10 digits — Medium, needs confirmation

**File:** `feature/taminServices/src/commonMain/kotlin/com/tamin/taminhamrah/feature/taminServices/inspection/contract/InspectionContract.kt:86`

```kotlin
val isRequestStep2Valid: Boolean
    get() = workshopInfo.workshopName.isNotBlank() &&
        workshopInfo.workshopCode.length == 10 &&
        ...
```

> در نسخه‌ی قدیمی (`SubmitInspectionRequestFragment.kt`، متد `checkValidInputWorkShopInfoStep()`)،
> فیلد «کد کارگاه» (`inputWorkShopCode`) اصلاً در لیست فیلدهای بررسی‌شده وجود نداشت — نه الزامی بود
> و نه محدودیت طول داشت؛ مقدارش هرچه بود مستقیماً به درخواست اضافه می‌شد. در کد جدید این فیلد الزامی
> شده و باید دقیقاً ۱۰ رقم باشد.

I couldn't determine from the diff alone whether this is a deliberate new backend requirement
(perhaps the server always expected a 10-digit code and `old_android` simply never validated it
client-side, silently failing server-side on a bad value) or an unintended new restriction copied
from a different field's convention (national ID is also validated as exactly 10 digits elsewhere in
this codebase). Flagging as `needs confirmation` rather than a definite regression.

**Suggested change:** confirm with product/backend whether workshop codes are always exactly 10
digits; if so this is a legitimate, welcome client-side strengthening and no change is needed beyond
noting it in the MR description so it isn't mistaken for a bug in a later review round.

## What was done well

- The per-source error-tracking design (`InspectionRequestErrorSource.USER_INFO`/`BRANCHES`/`JOBS`,
  a `Map<InspectionRequestErrorSource, String>` in state) correctly lets `RetrySource` re-issue only
  the one failed call instead of reloading the whole wizard — branches and jobs load concurrently and
  independently, and the retry logic respects that (`WorkshopInfoStep.kt`'s `onRetry` checks each
  key separately rather than always retrying both).
- The objection flow (`OpenRequestFlow(item = ...)`) correctly prefills and locks
  (`readOnly = isPrefillLocked`) exactly the fields that came from the inspection being objected to
  (workshop name/code/branch), while leaving job/dates/address open — matches the conceptual split
  between "what you're objecting about" (fixed) and "your input" (editable) implied by
  `old_android`'s separate objection-vs-fresh-request paths.
- Good, broad test coverage across every new layer — mapper, repository, API service, remote data
  source, and every use case each have their own test file, plus a real `InspectionViewModelTest.kt`
  for the list/wizard flow (though see finding #3 for the one gap in that coverage).
- DI (`TaminServicesModule.kt`) and navigation (`FeatureNavigation.kt`/`TaminHamrahNavGraph.kt`, no
  direct cross-feature import) both follow project convention, and the feature reuses existing shared
  components (`TaminStyledTextField`, `TaminJalaliDatePicker`, shimmer skeletons) rather than
  reinventing them.
- No hardcoded Persian strings found in the ViewModel/Contract layer — all 89 new `strings.xml`
  entries are actually wired up via `stringResource(...)`, including the "optional" labels
  (`_landline_optional`, `_email_optional`, `_workshop_phone_optional`) that correctly signal which
  fields don't block the step.
