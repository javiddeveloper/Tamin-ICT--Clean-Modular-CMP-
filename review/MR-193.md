## 1. The measured header passed to `rememberMeasuredTopAreaState` includes an infinitely-animating component — Medium

**File:** `feature/profile/src/commonMain/kotlin/com/tamin/taminhamrah/feature/profile/ui/activeRelation/ActiveRelationScreen.kt:99-108`

```kotlin
val topArea = rememberMeasuredTopAreaState { state ->
    ActiveRelationHeader(
        activeCount = uiState.activeCount,
        inactiveCount = uiState.inactiveCount,
        lastCheckTime = uiState.lastCheckTime,
        topAreaState = state,
        onBackClicked = {},
    )
}
```

`rememberMeasuredTopAreaState`'s own doc comment (`TopAreaConnectors.kt:51-56`) is explicit about
the contract for the `header` lambda passed in:

> `[header]` is composed twice, off-screen and unplaced, purely to measure its natural height at
> each extreme — so it must be side-effect-free ... no `LaunchedEffect` tied to first composition,
> no analytics fired from the composable body.

`ActiveRelationHeader` includes `AnimatedRingHeaderIcon` (`GlassIconTile.kt`), which renders two
`RippleRing`s, each backed by `rememberInfiniteTransition().animateFloat(..., infiniteRepeatable(...))`
— an animation that keeps requesting animation frames for as long as its composition is alive, with
no natural stopping point. This is exactly the class of side effect the doc above says the probe
header must not have, and it's not a hypothetical: `ActiveRelationHeader` is the system's one and
only real-world consumer today, so it's already happening.

**Failure scenario:** every time `ActiveRelationScreen` composes (first visit, and again on any
width change such as rotation, since `rememberMeasuredTopAreaState` re-probes when `constraints.maxWidth`
changes), two extra, fully off-screen `AnimatedRingHeaderIcon` instances — four `RippleRing`
animations total — start running via `SubcomposeLayout`'s `Expanded`/`Collapsed` probe slots, on
top of the two ring animations the real, visible header already runs. None of this is ever drawn
(the probe's `layout(0, 0) {}` never places its content), so it's pure wasted animation-clock
work — continuous recomposition/frame requests for content nobody sees, for at least as long as
those probe slots stay composed. Whether `SubcomposeLayout` disposes those slots promptly on the
next remeasure or keeps them alive for the screen's lifetime, the header handed to this API today
violates the contract the API's own documentation states, and the first thing a future header adopts
from `ActiveRelationHeader` as a "solid template to copy" (per `docs/vault/TopArea-System.md`'s own
description) inherits the same problem.

**Suggested change:** either (a) make `AnimatedRingHeaderIcon` conditional on the header actually
being live/placed (e.g. gate it behind a parameter the probe states can set to `false`), or (b)
extract a variant of `ActiveRelationHeader` for the measurement probe that swaps
`AnimatedRingHeaderIcon` for a static, same-sized placeholder — the goal is just matching layout
size, not a running animation. Whichever is chosen, it's worth adding a line to
`docs/vault/TopArea-System.md`'s "Gotchas" section calling out infinite-animation children
specifically, since "side-effect-free" alone didn't stop this from happening on the first real use.

## What was done well

- The core arithmetic (`TopAreaState.collapseBy`/`expandBy`/`connection`) is genuinely well-designed:
  folding from the drag itself via `onPreScroll` (not a separate scroll-offset listener) means the
  header moves under the finger with zero lag, and `contentCanScrollForward()` gating means a short
  list that can't scroll at all still keeps the header fully expanded with no separate special case.
  `onPreFling`'s fire-and-forget spring (not suspended on directly) is explained with a concrete,
  correct reason — awaiting it would hold the driven scrollable's fling mutex and could silently drop
  a fast follow-up touch.
- `TopAreaStateTest.kt` covers exactly the part that's easy to get quietly backwards — the
  scroll-delta sign convention, both clamping edges, and the "canScrollForward gates folding" rule —
  with one assertion per behavior rather than one giant end-to-end test.
- `rememberMeasuredTopAreaState`'s measure-the-real-header approach (vs. hardcoded `Dp` guesses) is
  a real, well-motivated improvement over the old `rememberCollapsingHeaderState`/fixed
  `HeaderCollapseDistance` it replaces — the fold budget can no longer silently drift out of sync
  with a copy or font change.
- `docs/vault/TopArea-System.md` is thorough and specific: a mental model, a building-blocks table,
  a step-by-step trace of how a drag actually flows through `onPreScroll`/`onPostScroll`/`onPreFling`,
  and — notably — it explicitly flags the pre-existing, still-in-use `ScrollMotionState` system and
  tells future readers not to silently migrate the three screens still on it. Documenting the
  overlap instead of pretending it doesn't exist is exactly the right call for a partial migration.
- The `Box` overlay (vs. `Scaffold` top bar) is explained with a concrete reason (edge-to-edge
  header behind the status bar vs. `Scaffold`/`TaminTopAppBar` inset double-counting) rather than
  left for a reader to reverse-engineer.
