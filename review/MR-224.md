## 1. Premium-payment "Pay" button is a silent no-op — High

**File:** `feature/contractsAndPaymentAffair/src/commonMain/kotlin/com/tamin/taminhamrah/feature/contractaffair/ui/premiumPayment/ContractPremiumPaymentViewModel.kt:55-58`

```kotlin
ContractPremiumPaymentIntent.Pay -> {
    // TODO: SEP online-payment — intentionally deferred, no logic wired here.
    emptyFlow()
}
```

The class-level KDoc says this is intentional ("the SEP online-payment call is intentionally left
out"), and I'm not disputing the scope cut itself — but the button that triggers it is fully live in
the UI: `ContractPremiumPaymentScreen.kt:191-192` wires `enabled = uiState.canPay` (`canPay = debit !=
null` — true as soon as the user calculates their premium) and `onPay = {
onIntent(ContractPremiumPaymentIntent.Pay) }`. A user who reaches this screen, picks a month count,
taps «محاسبه», sees a real payable amount, and taps «پرداخت» gets **no feedback at all** — no toast,
no navigation, no disabled state, nothing. They can't tell whether the tap registered, whether payment
is coming, or whether the button is broken. For a primary, money-related call-to-action this is worse
than simply hiding the button.

**Suggested change:** until the SEP integration lands, either disable the Pay button with a "به‌زودی"
tooltip/label, or route it to `ContractAffairsEvent.ShowToast`/a "not yet available" message — anything
that gives the user feedback instead of a silent dead end.

## 2. "Edit Contract" operation is a silent no-op — Medium

**File:** `feature/contractsAndPaymentAffair/src/commonMain/kotlin/com/tamin/taminhamrah/feature/contractaffair/ui/ContractAffairsScreen.kt:139`

```kotlin
is ContractAffairsEvent.NavigateToEditContract -> Unit // TODO(ui): edit-contract flow
```

`operationsFor()` (`ContractAffairsViewModel.kt:188-209`) adds `ContractOperation.EDIT_CONTRACT` to
the operations sheet for every active, non-fraction contract, and `ContractOperationsSheet.kt` gives it
a full icon, label (`Res.string.contract_affairs_edit_contract`), and styled row — nothing in the UI
suggests it's unfinished. Tapping it just closes the sheet with no further action.
`ContractAffairsViewModelTest.kt:131` only asserts the operation *appears* in the list for an eligible
contract; nothing exercises what happens after the tap (understandably — it's a screen-level
navigation gap, not something a ViewModel test would catch).

**Suggested change:** same as item 1 — either remove `EDIT_CONTRACT` from `operationsFor()` until the
edit flow exists, or wire `NavigateToEditContract` to at least a "coming soon" toast so the menu item
doesn't look broken.

## 3. Cancelled-status styling via substring match on freeform text — Medium

**File:** `core/core-ui`... — actually
`feature/contractsAndPaymentAffair/src/commonMain/kotlin/com/tamin/taminhamrah/feature/contractaffair/ui/components/ContractAffairsItemCard.kt:452-470`

```kotlin
private fun statusContainerColor(item: ContractPR): Color {
    val colors = LocalTaminColors.current
    return when {
        item.statusCode == ACTIVE_STATUS_CODE -> colors.greenBg
        item.statusDesc.contains("ابطال") -> colors.dangerBorder
        else -> colors.orangeBg
    }
}
```

Two things here:

1. `old_android`'s equivalent (`ContractListAdapter.kt:45-63`) only has a **binary** green/orange split
   on `selfIsuContStatCode == 1` — there is no third "cancelled/red" visual state in the legacy list at
   all. This MR adds one, which may well be a deliberate, reasonable design improvement — but it's worth
   confirming with design/product that a third status color is intended, since it's new behavior beyond
   what's being ported.
2. However it's detected, `item.statusDesc.contains("ابطال")` matches CLAUDE.local.md rule 7's pattern
   almost exactly: a freeform, localized server description string is substring-matched instead of
   using a structured field. `ContractPR.statusCode: Int?` already exists and is used one line above for
   the active check — if the backend has a distinct code for "ابطال شده", it should drive this branch
   too, rather than text-matching a description that could change wording, be empty, or come back in a
   different phrasing without warning.

**Suggested change:** confirm the intended "cancelled" `statusCode` value (or add one if it doesn't
exist) and branch on that instead of `statusDesc.contains(...)`; if this third visual state is not
actually wanted (parity with legacy's binary state), drop it.

## 4. Housewife icon selection via substring match on display text — Medium

**File:** `feature/contractsAndPaymentAffair/src/commonMain/kotlin/com/tamin/taminhamrah/feature/contractaffair/ui/components/ContractAffairsItemCard.kt:472-478`

```kotlin
private fun contractIcon(premiumTypeCode: String, title: String): ImageVector = when {
    title.contains("خانه‌دار") -> Icons.Outlined.Home
    premiumTypeCode == "01" -> Icons.Outlined.WorkOutline
    premiumTypeCode == "02" -> Icons.Outlined.HealthAndSafety
    premiumTypeCode == FRACTION_PREMIUM_TYPE_CODE -> Icons.Outlined.CalendarMonth
    else -> Icons.Outlined.Description
}
```

`premiumTypeCode` alone can't distinguish housewife from student/freelance — all three share code
`"01"` (confirmed in `old_android`'s `EnumInsuranceType`: `TYPE_STUDENT("01","03")`,
`TYPE_FREELANCE("01","03")`, `TYPE_WOMAN("01","03")`), which is presumably why this branches on the
localized display `title` text instead. But `ContractPR.freeJobCode` is already on the model and
already used two lines away in `operationsFor()` for the exact same "is this a housewife contract"
distinction, via `ContractFreeJobCode.WOMEN_CONTRACT_CODE` (`"099785"`, matching `old_android`'s
`Constants.WOMEN_CONTRACT_CODE`, already ported correctly in this same file). Matching `title` instead
is fragile — a wording change to `insuranceType`/`contract_housewife_insurance_type` (half-space
variant, "بیمهٔ" prefix added/dropped, etc.) silently breaks the icon with no compile-time or
runtime signal.

**Suggested change:**
```kotlin
private fun contractIcon(premiumTypeCode: String, freeJobCode: String): ImageVector = when {
    freeJobCode == ContractFreeJobCode.WOMEN_CONTRACT_CODE -> Icons.Outlined.Home
    premiumTypeCode == "01" -> Icons.Outlined.WorkOutline
    ...
}
```
matching the code-based check already used for the red-crescent/medical-student gating in this file.

## 6. `ACTIVE_STATUS_CODE` duplicated across three files — Low

**Files:** `ContractAffairsItemCard.kt:86`, `ContractOperationsSheet.kt:64`,
`ContractAffairsViewModel.kt:427`

```kotlin
private const val ACTIVE_STATUS_CODE = 1          // ContractAffairsItemCard.kt
private const val ACTIVE_STATUS_CODE = 1          // ContractOperationsSheet.kt
private const val ACTIVE_CONTRACT_STATUS_CODE = 1 // ContractAffairsViewModel.kt
```

Same magic number (`1` = active, matching `old_android`'s `selfIsuContStatCode == 1`), redefined three
times under two different names instead of one shared constant. Not a correctness bug — all three
currently agree — but it's the kind of duplication that silently drifts if the value or its meaning
ever needs a second look.

**Suggested change:** hoist to a single `const val` (e.g. next to `ContractPremiumType`/
`ContractStateChange` in `core-domain`, or a small `ContractAffairConstants` object) and reuse it.

## What was done well

- **The two riskiest pieces of this MR — the positional-array field mappings for payment history and
  payment-calculation-detail — are verified byte-for-byte correct.** `ContractAffairRemoteDataSourceImpl.kt:199-227`
  (`toPaymentHistoryItem()`: indices 1,2,3,5,6,7,8,9,10,11,12; `toPaymentCalculationRow()`: indices
  0-5) match `old_android`'s `ServiceRepository.getContractsPaymentsListFreelance` (`ServiceRepository.kt:1398-1414`)
  and `getPaymentCalculationDetailList` (`ServiceRepository.kt:1433-1444`) field-for-field, including
  the same skipped indices (0 and 4 in the payment-history row). This is exactly the kind of silent,
  hard-to-catch bug a rewrite could easily introduce, and it's correct.
- **Endpoint routing and job-code gating are correctly ported.** The freelance-vs-optional endpoint
  split (cancel, debit, last-payment, report, payment-details all have two variants) is consistently
  applied via `ContractPremiumType`, and the red-crescent/medical-student operation gating
  (`ContractAffairsViewModel.kt:198-207`) matches the documented legacy rule
  (`ContractFreeJobCode.kt:28-31`) exactly — red-crescent members can't pay premium or deactivate,
  medical students can't pay premium.
- **Unusually thorough test coverage** — repository, both mapper directions, both use-case groups, the
  remote data source (including the positional-array parsing itself), and all four ViewModels all have
  dedicated test files. This is a marked improvement over the create-contract-wizard MRs reviewed
  earlier in this series.
- **Cross-feature navigation correctly uses callbacks** (`onNavigateToService: (FeatureFlag) -> Unit`,
  etc. in `Navigation.kt`), not direct imports, per project rule 4.
- **Extensive, accurate inline documentation** — nearly every non-obvious mapping (PDF endpoint per
  contract type, positional-array indices, the `rulesCopy`-style cross-references) carries a comment
  naming the exact `old_android` class/method it was ported from, which made this review substantially
  faster and is worth calling out as a practice to keep.
