## 1. Rules bottom sheet hardcoded to student content — High

**File:** `core/core-ui/src/commonMain/kotlin/com/tamin/taminhamrah/ui/contractFlow/ContractRulesBottomSheet.kt`

```kotlin
fun ContractRulesBottomSheet(
```

## 2. Guardian form data is collected but never submitted — High

**Files:** `feature/contracts/src/commonMain/kotlin/com/tamin/taminhamrah/feature/contracts/flow/ui/ContractFlowViewModel.kt:874-936` ·
`core/core-ui/.../model/contractFlow/GuardianFormPR.kt`

`old_android` treats "buying optional insurance on behalf of a ward" as a materially different
submission. `OptionalContractFragment.kt:657-660`:

```kotlin
if (mViewModel.dataModel.guardianShip == GuardianType.FOR_GUARDIAN)
    mViewModel.makeOptionalContractByGuardian(
        ...,
        OptionalContractByGuardian(mViewModel.dataModel),
    )
```

— a separate request carrying the guardian's name, national ID, guardianship-letter number/date,
and the uploaded guardianship-letter document guid.

This MR adds the UI for exactly that: `GuardianFormPR` (new), a full form in
`ContractApplicantStepContent.kt` (national ID, letter number, full name, letter date, document
upload), and it correctly *gates* the Next button on it —
`ContractFlowContract.kt:104`: `contractApplicantType == ContractApplicantType.GUARDIAN && guardianForm.isValid`.
The document upload even round-trips through the real `uploadImageUseCase`
(`ContractFlowViewModel.kt:536-557`).

But `handleSubmitContract()` (`:874`) always calls `makeContractUseCase` via
`buildMakeContractParams()` (`:905-936`), which builds only `FreelanceMakeContractRequestDN`
(`brchCodeNew`, `cityCode`, `cntDrmn`, `cntFreeJobCode`, `guid`, `guidName`, `premiumRateCode`,
`provinceCode`) — no reference anywhere to `guardianForm` or `contractApplicantType`. The
pre-existing `MakeOptionalContractByGuardianUseCase` (already in the repo, already registered in
`DomainModule.kt:368`, unrelated to this MR) is never injected into `ContractFlowViewModel` and never
called.

> **سناریوی بیزینسی جاافتاده:** وقتی کاربر برای ثبت بیمه اختیاری، حالت «قیم» رو انتخاب می‌کنه و فرم
> قیم (نام، کد ملی، شماره و تاریخ نامه قیم‌نامه) رو کامل پر می‌کنه و مدرک قیم‌نامه رو هم آپلود می‌کنه،
> دکمه‌ی ادامه درست فعال می‌شه — ولی موقع ثبت نهایی قرارداد، هیچ‌کدوم از این اطلاعات به سرور ارسال
> نمی‌شه. درخواستی که برای سرور ساخته می‌شه دقیقاً همون درخواستیه که برای حالت «شخصاً» (بدون قیم) ساخته
> می‌شه؛ یعنی از نگاه سرور، این قرارداد اصلاً توسط قیم ثبت نشده. کل مسیر «ثبت قرارداد بیمه اختیاری توسط
> قیم» که در نسخه‌ی قدیمی برنامه وجود داشت، در نسخه‌ی جدید عملاً کار نمی‌کنه — کاربر فکر می‌کنه کارش
> تموم شده، ولی قراردادی که ثبت شده از نظر قانونی به نام قیم نیست.

**Suggested change:** in `buildMakeContractParams()`/`handleSubmitContract()`, branch on
`contractApplicantType`: when it's `GUARDIAN`, inject `MakeOptionalContractByGuardianUseCase` and
call it with the guardian's data instead of (or alongside, per whatever the API actually expects)
`MakeContractUseCase`.

## 3. Guardian letter-number validation is weaker than legacy — Medium

**File:** `core/core-ui/src/commonMain/kotlin/com/tamin/taminhamrah/model/contractFlow/GuardianFormPR.kt:20-26`

```kotlin
val isValid: Boolean
    get() = nationalId.length == 10 &&
        letterNumber.isNotBlank() &&
        ...
```

`old_android`'s `ContractBaseFragment.kt:531-534` rejects a guardianship-letter number shorter than
10 digits (`etGuardianShipNumber.getValue(false).length < 10`, `R.string.error_guardianship_number`).
The new `isValid` only checks `letterNumber.isNotBlank()` — a 1-digit letter number passes here and
would previously have been rejected client-side, pushing the failure to the server (or, worse, being
accepted if the server doesn't re-validate length).

**Suggested change:** add `letterNumber.length >= 10` (or whatever the real minimum is — matching
`nationalId`'s existing `== 10` check style) to `isValid`, and surface a matching field-level error
in `ContractApplicantStepContent.kt` the way `nationalId` presumably already does.

## 5. Hardcoded Persian string sent to the backend — Low

**File:** `feature/contracts/src/commonMain/kotlin/com/tamin/taminhamrah/feature/contracts/flow/ui/ContractFlowViewModel.kt:548`

```kotlin
val request = UploadImageRequestDN(
    fileName = fileName,
    bytes = bytes,
```

A Persian literal, not a `strings.xml` resource — same file already does this correctly two lines up
(`getString(Res.string.contract_upload_jpeg_only_error)`). It's a backend-only `description` field
rather than displayed UI text, so this is the mild version of `CLAUDE.local.md` rule 7, but it's
still a literal that should be a named resource/constant per the project's convention.

**Suggested change:** move it to `strings.xml` alongside the other `contract_guardian_*` entries (or
a plain `private const val` if it's genuinely never shown to a user), consistent with how the rest of
this file sources its strings.

  `checkGuardianshipInput()` behaviour even though the other half (item 3) is weaker.

  matching `old_android`'s `EnumOptionalContractStep` (no treatment-support or upload-image step
  exists for optional insurance there either) — the shared step-content files were not force-fitted
  onto a flow that doesn't need them.
- **No stray `review/MR-205.md` or other MR's review report** committed on this branch, and no
  commented-out code found anywhere in the ~8,000-line diff.
