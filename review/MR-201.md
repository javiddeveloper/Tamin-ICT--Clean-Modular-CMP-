## 1. `CancellationException` swallowed by raw `try/catch(e: Exception)` — High

**File:** `feature/workshops/src/commonMain/kotlin/.../completeEmployerInfo/CompleteEmployerInfoViewModel.kt:143-189`

```kotlin
private fun loadUserAndWorkshops(): Flow<CompleteEmployerInfoPartialState> = flow {
    emit(CompleteEmployerInfoPartialState.Loading(true))
    try {
        getUserProfileUseCase().collect { userProfile -> emit(/* ... */) }
    } catch (e: Exception) {
        sendEvent(CompleteEmployerInfoEvent.ShowToast(e.toSingleLineMessage()))
    }
    try {
        val agreements = getAllEmployerAgreementUseCase(emptyList())
        emit(CompleteEmployerInfoPartialState.WorkshopsLoaded(/* ... */))
    } catch (e: Exception) {
        emit(CompleteEmployerInfoPartialState.Error(e.toSingleLineMessage()))
    }
    emit(CompleteEmployerInfoPartialState.Loading(false))
}

private fun loadProvinces(): Flow<CompleteEmployerInfoPartialState> = flow {
    try {
        getProvincesUseCase().collect { provinces -> emit(/* ... */) }
    } catch (e: Exception) {
        sendEvent(CompleteEmployerInfoEvent.ShowToast(e.toSingleLineMessage()))
    }
}
```

Both `getUserProfileUseCase()` and `getProvincesUseCase()` are, per this file's own comment, flows
"that never complete" (a reactive local-DB read), collected via `merge(loadUserAndWorkshops(),
loadProvinces())` in `handleLoadInitialData()` for the life of the screen. `CancellationException`
is a subtype of `Exception` in Kotlin coroutines — when this collection is cancelled (the user
navigates away from the screen while it's still loading, or the ViewModel is cleared), the raw
`catch (e: Exception)` here catches that cancellation instead of letting it propagate, and reacts
to it as if it were a real failure. In `loadUserAndWorkshops` this can fire a `ShowToast` event or
emit an `Error` state during teardown; in both places it breaks structured concurrency by not
rethrowing cancellation, which is exactly the pattern already flagged as a High finding on MR !191
(`RepositoryFlowHelpers.kt`'s `cacheFirst`).

**Suggested change:** re-throw cancellation, e.g.:

```kotlin
} catch (e: Exception) {
    if (e is CancellationException) throw e
    sendEvent(CompleteEmployerInfoEvent.ShowToast(e.toSingleLineMessage()))
}
```

or restructure to use `Flow.catch { }` instead of a raw `try/catch` around `.collect { }`, which
rethrows cancellation automatically (as the rest of this same ViewModel already does everywhere
else it consumes a use-case `Flow`).

## 2. Repeated "loading → catch → collect" shape could be one shared helper — Low

**File:** `feature/workshops/src/commonMain/kotlin/.../completeEmployerInfo/CompleteEmployerInfoViewModel.kt`

`handleChangeLegalNationalId`, `handleChangeCeoNationalId`, `handleSelectCeoBirthDate`,
`handleSelectProvince`, and `handleSelectCity` (lines 191-274) all repeat the same shape: emit a
"loading" partial state, call a use case, `.catch { emit error state; emit loading(false); toast }
.collect { emit result state; emit loading(false) }`. The five copies differ only in which
`PartialState` subtypes and use case get plugged in.

**Suggested change:** extract a small private helper, e.g.

```kotlin
private fun <T> FlowCollector<CompleteEmployerInfoPartialState>.loadingCollect(
    source: Flow<T>,
    onLoading: (Boolean) -> CompleteEmployerInfoPartialState,
    onResult: (T) -> CompleteEmployerInfoPartialState,
    onError: (Throwable) -> CompleteEmployerInfoPartialState,
) = flow { /* ... */ }
```

so each call site becomes one expression instead of a 10-line block. Not required for correctness,
but the current shape is copy-pasted five times in one file and a sixth callback anywhere in this
class is likely to copy it a sixth time.
