## 1. Unused national-ID checksum validator — Low

**File:** `core/core-domain/src/commonMain/kotlin/com/tamin/taminhamrah/model/common/NationalId.kt`

`isValidIranianNationalId()` implements the real Iranian national-code checksum algorithm and has
its own dedicated test (`NationalIdTest.kt`), but nothing in this MR calls it — the CEO national ID
field (`ceoNationalId`, the one field in this feature that is actually a personal کد ملی) is only
length-checked (`== 10` digits) in `CompleteEmployerInfoContract.kt:141`. This is not a regression
against `old_android` (which never checksum-validated either), so it does not block the flow, but
as delivered the function is dead code with no caller.

**Suggested change:** either wire `isValidIranianNationalId()` into `legalBlockingError`'s CEO-ID
check (rejecting a code that is 10 digits but fails the checksum before it ever reaches the
CEO-lookup network call), or drop the unused function/test if it was left over from an earlier
draft.

> **Round 2 response (user, 2026-08-31):** confirmed not a problem, no change needed. Marked
> ➖ rejected (with reason).

## What was done well

- Both flows (real workshop code+branch, legal CEO+company-type) match `old_android`'s field
  requirements, OTP request payloads, and submit payloads closely: workshop-code length (10),
  legal national ID length (11), the `"tamin@tamin.ir"` fallback email for the real-path OTP
  request, and the 5-minute (300s) OTP countdown all line up with the legacy fragment.
- The CEO-info inquiry is actually more robust than `old_android`: the legacy code's text-watcher
  trigger for `getLegalWorkshopCEOInfo` was commented out (dead code), leaving only the date-picker
  path; this MR triggers the lookup from *either* input (national ID reaching 10 digits, or a
  birthdate being picked), whichever completes the pair second.
- The unrelated but useful cleanup applied consistently across sibling workshop Contract files
  (`EmployerAgreementContract`, `ManagementDebitContract`, `ObjectionableDebitContract`,
  `WorkshopMembersContract`, etc.) — converting plain `class` UI states to `data class` with
  `ImmutableList` — is correctly explained with a comment about why the old code silently
  recomposed on every emission.
- Good test coverage: `CompleteEmployerInfoViewModelTest`, `EmployerInfoRepositoryImplTest`,
  `EmployerInfoUseCasesTest`, plus the data-layer mapper/API-service/remote-data-source tests.
