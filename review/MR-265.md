## 1. Guide/error load failures toast the raw exception message — Low

**File:** `feature/userRequest/src/commonMain/kotlin/com/tamin/taminhamrah/feature/userRequest/ui/UserRequestsViewModel.kt:141,143,163,165`

```kotlin
} catch (e: Exception) {
    emit(PartialState.Error(e.message))
    sendEvent(UserRequestsEvent.ShowToast(e.message ?: loadErrorMessage()))
}
```

This MR newly makes a failed guide/errors load surface as a toast (previously it silently fell
into `state.error`, which this screen never renders — the finding this commit itself fixes). But
the toast text is the exception's own `.message`, not the mapped, single-line message every other
`catch` block in the codebase produces via `Throwable.toSingleLineMessage()` (see
`ProfileViewModel`, `ActiveRelationViewModel`, `RetirementPensionViewModel`). A raw
`SocketTimeoutException`/serialization message is technical and in English; the user sees that
instead of the app's normal "no connection" / "server error" copy. `state.error` at line 122 (a
pre-existing, untouched line) has the same shape, so this isn't a new pattern in this file, but the
newly-added toast is the first time this raw text is actually shown to a user rather than sitting
unused in state.

**Suggested change:** `sendEvent(UserRequestsEvent.ShowToast(e.toSingleLineMessage()))`, matching
the rest of the codebase's error-to-toast convention.

## What was done well

- **`a7efd9f2a` fixes a real, easy-to-miss starvation bug.** `getUserRequestsUseCase` never
  completes (it ends in the Room cache flow), and `BaseViewModel` runs intents through
  `flatMapMerge` with a concurrency cap of 16 — every `InitFilters`/search left one more
  collection running, and after 16 opens of the screen no further intent (including the guide
  button) was ever handled again. The fix (cancel the previous list job before starting a new one)
  is correct and comes with two tests that reproduce the exact starvation scenario before
  asserting the fix.
- **`CancellationException` is now rethrown, not swallowed**, in the two `catch` blocks this MR
  touches — matches the project's stated Kotlin/coroutine convention.
- **`db02305f8`'s `isPublic` fix is a clean, minimal, well-tested change** for a field the server
  sends as `"1"`/`"0"` rather than a JSON boolean; not a type-code case (rule 7 doesn't apply — this
  is a binary flag, not one of several named states), so parsing the two literal values is
  appropriate rather than needing a new enum.
- **`2f69804a6`'s `ensureSuccess()` fix is a real, well-tested business-flow correction** — a
  `200` with `data: null` on delete/license calls was being thrown as an error, so those actions
  always looked like they failed even though the server accepted them.
- **The Room schema v5 export is the generated file**, not a hand-edit; no schema drift with the
  entity definitions found.
- No hardcoded user-facing strings and no commented-out code.
