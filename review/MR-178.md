## 1. Dark-mode toggle can never reach/return to "follow system" — now duplicated across two screens — High

**File:** `feature/settings/src/commonMain/kotlin/com/tamin/taminhamrah/feature/settings/ui/SettingsScreen.kt:179-182`, `feature/settings/src/commonMain/kotlin/com/tamin/taminhamrah/feature/settings/ui/SettingsViewModel.kt:41-47`

```kotlin
// SettingsScreen.kt
Switch(checked = isDark, onCheckedChange = { onIntent(SettingsIntent.ToggleNightMode(it)) })

// SettingsViewModel.kt
private fun handleToggleNightMode(isDark: Boolean): Flow<PartialState> {
    viewModelScope.launch {
        val config = if (isDark) DarkThemeConfig.DARK else DarkThemeConfig.LIGHT
        setThemeUseCase(config)
    }
    return emptyFlow()
}
```

`DarkThemeConfig.FOLLOW_SYSTEM` already exists (`core/core-domain/.../model/DarkThemeConfig.kt`,
pre-existing, unchanged) and is the app's actual default
(`MainUiState.darkThemeConfig = DarkThemeConfig.FOLLOW_SYSTEM`), but this binary switch never
sets it. Old_android's equivalent, `SettingsFragment.kt:85-119` (`setupThemeRow`), has a real
3-way `MaterialButtonToggleGroup` (light / dark / "خودکار" follow-system).

This isn't only a new gap — `feature/profile/.../ProfileViewModel.kt:175-181`
(`handleToggleTheme`) already had the same binary-only mapping before this MR, via a sun/moon
icon button already present in `ProfileScreen.kt`. What this MR adds is a **second, independent
control for the exact same persisted setting**, without consolidating or removing the
pre-existing one. After this MR there are two disconnected UI surfaces (Profile's icon toggle,
Settings' switch) that can each silently overwrite `DarkThemeConfig`, neither able to express or
return to "follow system."

**Failure scenario:** a user on the default follow-system theme taps either toggle once — from
then on there is no path back to "follow system" from either screen, and the two toggles can
disagree about what state they're showing since they both derive their initial display from the
currently-rendered colors rather than the actual persisted `DarkThemeConfig`.

**Suggested change:** consolidate to one theme control (ideally in Settings, matching
old_android's single settings-screen home for this), implemented as a 3-way selector like
old_android, and remove the duplicate control from Profile.

> **مغایرت بیزینسی:** به‌جای یک انتخاب سه‌حالته‌ی تم (روشن / تاریک / خودکار مطابق سیستم) که در
> نسخه‌ی قدیمی وجود داشت، دو کلید جداگانه‌ی روشن/خاموش برای تم تاریک در دو صفحه‌ی متفاوت
> (پروفایل و تنظیمات) گذاشته شده که هیچ‌کدام حالت «خودکار» را پشتیبانی نمی‌کنند. کاربر بعد از
> اولین لمس هرکدام از این دو کلید، دیگر هیچ راهی برای برگشتن به حالت خودکار ندارد، و چون دو محل
> جدا برای همین یک تنظیم وجود دارد ممکن است کاربر گیج شود که کدام کلید واقعی است.

## 2. Security screen silently drops the "Change Password" and "2FA" menu rows — High

**File:** `feature/security/src/commonMain/kotlin/com/tamin/taminhamrah/feature/security/ui/SecurityScreen.kt:170-207`

Before this MR, `SecurityContent`'s `ListGroupView` had three entries: Change Password, 2FA
(with a "تست" badge), and Fingerprint. After this MR it has **only** the fingerprint/biometric
entry — the other two `ListItemData` entries were removed entirely:

```kotlin
// removed by this MR:
ListItemData(
    title = stringResource(Res.string.security_change_password),
    ... onClick = { /* Navigate to change password */ }
),
ListItemData(
    title = stringResource(Res.string.security_2fa),
    badge = ListItemBadge(text = "تست", ...),
    ... onClick = { /* Navigate to 2FA */ }
),
```

This MR is scoped to a Settings feature (font size + dark mode) and adopting the shared
`TaminSwitchButton`. Removing two pre-existing, visible menu rows from an unrelated screen
(Security) is a functional change bundled in with no apparent connection to the MR's stated
purpose. The two rows were placeholder navigations, but they were visible/clickable UI
communicating that those features exist or are coming — removing them silently, with nothing in
the diff explaining why, is exactly the kind of out-of-scope change worth flagging even though
the underlying `TaminSwitchButton`/biometric-auth-challenge logic itself was correctly preserved
in the same diff (the biometric re-auth-before-toggle flow moved up a composable level but is
functionally intact).

**Suggested change:** if removing these rows was intentional (e.g. product decided to hide
unfinished features), split it into its own commit/MR with a stated reason; otherwise restore
them.

## 4. No test for `SettingsViewModel`'s intent/state branching — Medium

**File:** `feature/settings/src/commonMain/kotlin/com/tamin/taminhamrah/feature/settings/ui/SettingsViewModel.kt`

Only `SetFontSizeUseCase` has a unit test (`SetFontSizeUseCaseTest.kt` — adequate, covers
persist/overwrite/default-MEDIUM). Nothing tests `SettingsViewModel` itself: whether
`handleToggleNightMode` calls `setThemeUseCase` with the right config for both switch
directions, whether `handleSelectFontSize` calls the use case and `PartialState.SetFontSize` is

`observeFontSize → UpdateFontSize` state-sync path.

**Suggested change:** add a `SettingsViewModelTest` covering both toggle directions and the
font-size selection/reduction path.

## What was done well

- **Font-size feature is implemented cleanly end-to-end**: `FontSizeOption` → `UserData.fontSize`
  → `UserPreferencesRepository`/`Impl` (DataStore-backed, follows the exact same pattern as the
  pre-existing `darkThemeConfig` field) → `SetFontSizeUseCase` (tested) → `SettingsViewModel` →
  `MainViewModel`/`MainContract` → `TaminHamrahTheme(fontSizeOption = ...)`, which overrides only
  `Density.fontScale` (keeping the ambient `density`) via `LocalDensity provides scaledDensity` —
  the correct, app-wide, typography-only scaling approach, not confined to the Settings screen.
  Old_android has no equivalent feature, so this is genuinely new value, not a ported regression.
- **The build-logic change is a legitimate consolidation, not scope creep**:
  `kotlinx-collections-immutable` moved from 5 separate `feature/*/build.gradle.kts` files into
  `TaminHamrahKmpFeaturePlugin.kt`'s shared dependencies block, with the now-redundant per-module
  lines correctly removed everywhere.
- New feature is wired correctly per the architecture rules: `settingsModule` registered in
  `sharedModules`, navigation added via callback (`onNavigateToSettings`), not a direct
  cross-feature import.
- `TaminSwitchButton` is not a new component (pre-existing) — this MR extends it with an optional
  `showThemeIcon` sun/moon animation, and both Security and Settings consume the same component
  rather than duplicating a hand-rolled `Switch`.
- `ListGroupView`'s new `footerContent`/`footerContentPadding` params are a sensible, minimal
  extension of an existing `core-ui` component rather than a bespoke one-off.
- The biometric re-authentication-before-toggle flow in `SecurityScreen.kt` (challenge via
  `biometricAuthenticator.authenticate`, only committing the new switch state on success) is
  correctly preserved through this MR's refactor of that screen, matching old_android's intent.
