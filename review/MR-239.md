## 2. Hardware/gesture back and chevron didn't match ✕'s abandon-confirmation — High

**Files:** `feature/girlSurvivor/src/commonMain/kotlin/com/tamin/taminhamrah/feature/girlSurvivor/ui/GirlSurvivorScreen.kt`,
`feature/contracts/src/commonMain/kotlin/com/tamin/taminhamrah/feature/contracts/flow/ui/ContractFlowScreen.kt`

Round 2's fix (`BackHandler { showAbandonDialog = true }`, unconditional) stopped the silent
hardware-back exit round 1 found, but introduced two new problems on both screens, confirmed by
reading the round-2 code directly:

1. **Hardware back could no longer step backward inside the wizard** — pressing back on step 2+
   now always showed the abandon dialog instead of returning to the previous step, since the
   `BackHandler` didn't check `currentStep`.
2. **The visible chevron button on step 1 was untouched** and still called `onBack()` /
   `handleNavigateBack()` directly, exiting with no dialog — the exact failure mode item 2 was
   originally opened for, just on a different control than the one round 1 tested.

Round 3's fix (`e426d8b35`) unifies both controls behind one handler on each screen:

```kotlin
// ContractFlowScreen.kt
val handleNavigateBack: () -> Unit = {
    when {
        state.isEditMode -> onIntent(ContractFlowIntent.GoToPreviousStep)
        steps.isFirstStep(state.currentStep) -> showAbandonDialog = true
        else -> onIntent(ContractFlowIntent.GoToPreviousStep)
    }
}
BackHandler(onBack = handleNavigateBack)
// ...chevron's onClick = handleNavigateBack
```

```kotlin
// GirlSurvivorScreen.kt
val handleBack: () -> Unit = {
    if (state.currentStep == GirlSurvivorStep.Details) {
        showAbandonDialog = true
    } else {
        onIntent(GirlSurvivorIntent.GoToPreviousStep)
    }
}
BackHandler(onBack = handleBack)
// ...chevron's onClick = handleBack
```

Both the `BackHandler` and the chevron's `onClick` now call the exact same function — first step
shows the abandon dialog, later steps step back through the wizard, and ✕ (unchanged, separate
handler) still always shows the dialog. This matches `DeferredInstallmentScreen`'s already-correct
shape from round 2.

**Round 3 — ✅ fixed, verified.**

## 5. `HistoryObjectionStepperScreen`'s `STEP_BRANCH` exit had no confirmation on 3 of its 4 exit
controls — High

**File:** `feature/history-objection/src/commonMain/kotlin/com/tamin/taminhamrah/feature/historyobjection/ui/stepper/HistoryObjectionStepperScreen.kt`

Not named in round 1 (only 3 of the 9 wired screens were individually checked then) — found this
round by auditing every screen this MR wires `TaminFormAbandonDialog` into, not just the ones
already flagged. This MR changed ✕ from `onNavigateHome()` to `showAbandonDialog = true`, but left
every other exit control (`BackHandler`, top-bar chevron, both bottom-bar chevrons) still dispatching
`OnBackClicked` directly:

```kotlin
// before this round's fix
HistoryObjectionStepperIntent.OnBackClicked -> flow {
    if (uiState.value.currentStep == STEP_BRANCH) {
        sendEvent(HistoryObjectionStepperEvent.NavigateBack)  // no dialog
    } else {
        emit(PartialState.StepChanged(step - 1))
    }
}
```

So on `STEP_BRANCH` (the step where legacy's own equivalent screen would lose the most work),
hardware back and both visible chevrons left with no warning, while only ✕ asked. Same bug class as
item 2.

**Round 3 — ✅ fixed, verified** (`e426d8b35`). A shared `handleBack` now backs both the
`BackHandler` and all chevron `onClick`s: at `STEP_BRANCH` it sets `showAbandonDialog = true`
(tracking `abandonToHome = false` so the dialog's "leave" action correctly calls `onNavigateBack()`
rather than `onNavigateHome()` for this entry point — ✕ still sets `abandonToHome = true` and goes
home); at any other step it still dispatches `OnBackClicked` as before. This correctly distinguishes
"abandon via ✕" (go home) from "abandon via back on the first step" (go back), rather than collapsing
both into one destination.

## What was done well

- **The consolidation itself is clean and reduces duplication.** `RetirementDialogs.kt` and
  `DisabilityPensionScreen.kt` both replace a hand-rolled `TaminConfirmationDialog` instance with the
  new shared component, each removing 20-30 lines of near-duplicate dialog-building code with no
  behavior loss.
- **`OccurrenceScreen`/`InspectionScreen` were correctly left alone** — their existing
  ViewModel-intent-driven confirmation (`STEPS_REQUIRING_EXIT_CONFIRMATION`) already routed hardware
  back through the same gate as the close button, so only the dialog's visual component needed
  swapping, and that's all that changed.
- **Round 3's fix pattern is consistent across all three screens it touches** — one shared handler
  function backing both the `BackHandler` and every chevron, rather than three separate patches —
  and each screen correctly preserves its own specific "abandon destination" semantics (home vs. back
  vs. previous-step) instead of applying one generic shape everywhere.
- **No hardcoded Persian strings anywhere in the diff.**
- **All affected modules build and pass their test suites.**
