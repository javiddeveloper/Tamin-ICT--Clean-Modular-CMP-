**File:** `feature/workshops/src/commonMain/kotlin/com/tamin/taminhamrah/feature/workshops/Navigation.kt`

The MR adds four `legalRepresentative` imports and `composableWithFadeTransitions` in a new block
near the top of the file, while identical declarations already existed lower down (carried over from
earlier MRs). All five are now present twice in the file, confirmed by grep:


Kotlin compiles duplicate imports without error, but every Kotlin toolchain (IDE, detekt, ktlint)

the import block was not reviewed before the commit — the same kind of oversight can hide a real
conflict in a non-import hunk.

**Suggested change:** Delete the five redundant declarations added by this MR. Only
`ObjectionableDebitScreen` and the new `@Serializable ObjectionableDebitRoute` additions are net-new.

## 2. `mutableStateMapOf` used as internal ViewModel cache — Medium

**File:** `feature/workshops/src/commonMain/kotlin/com/tamin/taminhamrah/feature/workshops/ui/objectionableDebit/ObjectionableDebitViewModel.kt:46`

```kotlin
private val debtsByNumber = mutableStateMapOf<String, WorkShopDebtDN>()
```

`mutableStateMapOf` is from `androidx.compose.runtime`. It registers the map with Compose's
snapshot system, which expects reads and writes on the Main thread (inside a composition or a
`withMutableSnapshot` block). The ViewModel writes to this map inside `flow { }` blocks
(`loadPage`, lines 95–96) that run on whatever dispatcher `BaseViewModel` uses — not necessarily
Main. Accessing Compose snapshot state from a background coroutine without `withMutableSnapshot`
is a threading violation that can silently produce stale reads or, in a Compose-snapshot crash,
an `IllegalStateException`.

The map is a purely internal cache; nothing in the UI observes it directly.

**Suggested change:**

```kotlin
private val debtsByNumber = mutableMapOf<String, WorkShopDebtDN>()
```

## 3. Confirmation dialog before submit removed — Medium

**File:** `feature/workshops/src/commonMain/kotlin/com/tamin/taminhamrah/feature/workshops/ui/objectionableDebit/ObjectionableDebitViewModel.kt:179`

In `old_android`, `DebitObjectionFragment.onClick()` (lines 248–289) required the user to pass
**three gates** before the API call was made:

1. At least one uploaded document (non-blank guid).
2. Confirmation checkbox (`cbSubmit.isChecked`).
3. **Explicit confirmation dialog** — `MessageOfRequestDialogFragment.MessageType.CONFIRM` with
   message `R.string.message_debit_objection_confirmation`; the API was called only after the user
   pressed "Confirm" in that modal.

The new code enforces (1) and (2) in `submitObjection()`, but gate (3) — the modal — is absent.
`ObjectionableDebitIntent.FormSubmit` submits to the server immediately once both checks pass.

> **بررسی تطابق رفتار با اندروید قدیم:**
> در اندروید قدیم پیش از ارسال اعتراض یک دیالوگ تأیید نمایش داده می‌شد و کاربر باید صراحتاً
> «تأیید» می‌زد. در نسخه جدید این مرحله حذف شده و بعد از تیک چک‌باکس، ارسال مستقیم به سرور
> انجام می‌شود. اگر این تغییر عمدی است — مثلاً چک‌باکس تأیید به تنهایی کافی تلقی شده — لطفاً
> در ریجکشن این آیتم توضیح دهید.

If the removal is intentional, mark `➖ rejected` with a brief note.
If not, the fix is to emit a `ObjectionableDebitEvent.ConfirmSubmit` (or similar) from
`submitObjection()` before the API call, and let the screen show the dialog and re-send
`FormSubmit` only when the user confirms.

## 4. Test file implements full `ContractsRepository` for a no-op uploader — Low

**File:** `feature/workshops/src/commonTest/kotlin/com/tamin/taminhamrah/feature/workshops/ui/objectionableDebit/ObjectionableDebitViewModelTest.kt:219`

```kotlin
private object NoUploads : ContractsRepository {
    private fun notUsed(): Nothing =
        error("not used by ObjectionableDebitViewModel tests")
    // … 20+ method stubs for contracts, branches, premium rates, insurance payments …
}
```

`WorkshopAttachmentUploader` is wired via `UploadImageUseCase(ContractsRepository)`.
`ContractsRepository` is a wide interface unrelated to workshops; any test that only needs to
inject a no-op uploader must stub all 20+ of its methods. This couples `feature/workshops` tests
to the contracts domain at test-compile time.

This is a pre-existing design issue (check whether `DemandDocumentsViewModelTest` has the same
problem) that this MR surfaces but did not introduce. A narrower `ImageUploadPort` interface, or
a shared `FakeWorkshopAttachmentUploader`, would eliminate it across all workshop tests.
Fixing it in this MR alone may not be the right scope — flagging for awareness.
