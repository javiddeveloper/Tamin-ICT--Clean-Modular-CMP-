## 1. The submit guard does not hold — Medium

**File:** `feature/profile/src/commonMain/kotlin/com/tamin/taminhamrah/feature/profile/ui/editPhoto/EditProfilePhotoViewModel.kt:78-81`

```kotlin
private fun submit(): Flow<PartialState> = flow {
    val state = uiState.value
    // flatMapMerge runs intents concurrently: a second tap must not queue a second request.
    if (state.isSubmitting) return@flow
    ...
```

The comment states the intent correctly, but the guard reads `uiState.value`, which is only updated once
`BaseViewModel`'s collector applies the `Submitting` partial state — a step later than this check. A
second `Submit` intent sent before that update still reads `isSubmitting == false`. This is the same
defect found in MR !244 and MR !249, where the fix was a plain field set synchronously before the first
suspension, not a read of the reduced state.

I confirmed it: with a temporary test firing two `Submit` intents in a row on a `StandardTestDispatcher`
(which orders work like a real main thread, unlike the file's `UnconfinedTestDispatcher`, which runs every
step eagerly and cannot see the race), the fake repository received **2** calls, not 1. The scratch test
was removed; the worktree is clean. In the UI, `LoadingButton` disables its own click once `isLoading`
(i.e. `isSubmitting`) is `true`, but that disabling itself depends on the same delayed state update, so a
fast double-tap can still land both taps before the button visually disables.

> **سناریوی بیزینسی:** کاربر روی دکمه‌ی «ثبت درخواست» دو بار پشت‌سرهم لمس می‌کند. انتظار این است
> که فقط یک درخواست تغییر عکس ثبت شود؛ ولی در شرایط واقعی هر دو درخواست به سرور می‌رسد و دو درخواست
> یکسان برای تغییر تصویر پروفایل ثبت می‌شود.

**Suggested change:** replace the guard with a plain class field (`private var isSubmitting = false`)
checked and set at the very top of `submit()`, cleared in a `finally`. Add a test that fires two `Submit`
intents on a `StandardTestDispatcher` so it fails without the field, the same pattern used to verify this
fix in MR !249.

## 2. New entry point bypasses the feature's own menu flag — Low, needs confirmation

**Files:** `feature/profile/src/commonMain/kotlin/com/tamin/taminhamrah/feature/profile/ui/ProfileScreen.kt:417`,
`core/core-network/src/commonMain/kotlin/com/tamin/taminhamrah/dataSource/commonSource/MockMenuData.kt:72`

```kotlin
// MockMenuData.kt
MainServiceDto(id = 4, sorting = 36, name = "ویرایش تصویر", showRole = listOf(1), icon = "camera", status = MenuServiceStatus.DISABLED),
```

`FeatureFlag.EDIT_IMAGE(4)` has existed since the menu-id rework (MR !247) but was never used anywhere to
gate a screen — this MR is the first to implement the feature that row names, and its entry point
(the camera badge on the avatar, `onClick = onNavigateToEditProfilePhoto`) navigates unconditionally, with
no `featureManager.getFeatureStatus(FeatureFlag.EDIT_IMAGE)` check. The row for it is currently
`DISABLED` in the mock data this app currently serves. This is consistent with how the rest of the
Profile screen's own sub-items work today — `BANK_ACCOUNT_LIST` and `ACTIVE_RELATION` aren't gated from
inside `ProfileViewModel.OnItemClick` either, only from the Home quick-access cards — so this is not a
regression unique to this MR, but it is the one row whose name and id line up exactly with the feature
being added here.

> **سناریوی بیزینسی:** ردیف «ویرایش تصویر» در منو فعلاً `DISABLED` است، ولی از صفحه‌ی پروفایل با
> لمس روی آیکن دوربین کنار عکس، کاربر مستقیم به فرم تغییر تصویر می‌رسد و هیچ‌جا وضعیت غیرفعال بودن
> این سرویس بررسی نمی‌شود. اگر تیم بخواهد این قابلیت را موقتاً از سمت سرور خاموش کند، این راه ورودی
> از آن تبعیت نمی‌کند.

**Suggested change:** confirm with product/backend whether the profile screen's own sub-items are meant
to bypass the menu gate entirely (as they do today) or whether this specific one — being brand new —
should check `FeatureFlag.EDIT_IMAGE` before navigating. If the latter, wire it the way `HomeViewModel`
does for the quick-access cards.

## 3. `sendImageRequest`'s data source does not rethrow cancellation — Low

**File:** `core/core-network/src/commonMain/kotlin/com/tamin/taminhamrah/dataSource/userSource/UserRemoteDataSourceImpl.kt:87-102`

```kotlin
override suspend fun sendImageRequest(
    branchCode: String,
    filter: List<ApiFilterDN>
): String {
    return try {
        val response = userApiService.sendImageRequest(branchCode, queryBuilder.buildFilterJson(filter))
        response.extractMessage()
    } catch (e: TaminErrorUriException) {
        throw errorParser.parseGeneralError(e)
    } catch (e: Exception) {
        throw errorParser.parseGeneralError(TaminErrorUriException(ErrorUri.NO_CONNECTION_ERROR))
    }
}
```

No `catch (e: CancellationException) { throw e }` before the general catch, so a user leaving the screen
mid-request surfaces a fake «no connection» error instead of the request being silently cancelled. This
predates this MR (only the response type and extraction call changed here), but the function was edited
in this diff, so it was carried forward rather than introduced.

**Suggested change:** add `catch (e: CancellationException) { throw e }` before the general catch, or
route through `errorParser.safeCall(...)` the way newer data sources in this codebase do.

## What was done well

- **Legacy's odd validation order is preserved and explained**: the serial number is required in *both*
  modes (even though a dependant's request sends their national code instead), matching
  `EditProfileImageFragment`'s "serial blank always wins" check — and the KDoc says so, so it doesn't
  read as an oversight.
- **The `data: null` response is handled at the right layer**: `BaseDTO<String>` (which throws when
  `data` is null) was replaced with `BaseDTO<JsonElement?>` and a new `extractMessage()` that falls back
  to `reason`, with a service test built from the real response shape (`"data":null`).
- **The shared `SegmentedInputField`** got one new, well-documented parameter
  (`formatAsPersianDigits`) instead of a forked copy, and the new `alphanumericOnly()` filter (with a
  dedicated test) correctly folds Persian/Arabic-Indic digits to ASCII before uppercasing Latin
  letters — needed because the smart-card serial is printed in Latin, unlike every other numeric field
  in the app.
- **No hardcoded Persian strings in production code** — every label goes through `strings.xml`; the only
  literals are `@Preview` sample data.
- **Solid ViewModel test coverage** — 13 cases: both validation errors together (with the correct
  priority), each alone, the main-user and dependant submit paths (checking exactly what's sent), a
  server error, dialog dismissal for both outcomes, and back navigation.
- **The dependants load is independent of the relation load** (two separate intents in `init`), so a
  failed relation lookup can't take the dependants list down with it — and the dependants fetch itself
  falls back to an empty list on error rather than leaving the picker stuck loading.
