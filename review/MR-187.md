## 1. iOS camera-permission callback fires off the main thread — High

**File:** `core/core-ui/src/iosMain/kotlin/com/tamin/taminhamrah/util/CameraPermission.ios.kt:16-20`

```kotlin
override fun request(onResult: (Boolean) -> Unit) {
    AVCaptureDevice.requestAccessForMediaType(AVMediaTypeVideo) { isGranted ->
        onResult(isGranted)
    }
}
```

`AVCaptureDevice.requestAccessForMediaType`'s completion handler runs on an arbitrary background queue per Apple's documentation — it is not guaranteed to be the main thread, unlike Android's `ActivityResultLauncher` callback (which is always main-thread). The call site in `Step6DocumentSubmitStep.kt` does `cameraPermission.request { granted -> cameraLauncher.launch(...); onIntent(...) }` directly inside this callback.

**Failure scenario:** the first time an iOS user taps "camera" to attach an accident-scene photo and the OS permission prompt appears, the completion handler (and everything chained off it — launching the camera UI, dispatching a Compose intent) can run off the main thread. Since UIKit/Compose UI operations must happen on the main thread, this can crash or silently fail to present the camera on iOS, while the identical flow works fine on Android.

**Suggested change:** dispatch `onResult(isGranted)` back onto the main queue (e.g. via `dispatch_async(dispatch_get_main_queue()) { onResult(isGranted) }` or the Kotlin/Native equivalent) before invoking the callback.

## 2. No file-size/type validation on uploaded documents, despite the test suite's own doc comment claiming it exists — High

**File:** `feature/taminServices/src/commonMain/kotlin/com/tamin/taminhamrah/feature/taminServices/occurrence/components/steps/Step6DocumentSubmitStep.kt` (`handlePicked()`)

`OccurrenceViewModelTest.kt`'s own class doc comment states: "the JPEG/size/duplicate validation that orotez-protez does in its ViewModel happens in Step6DocumentSubmitStep before the intent is sent." The sibling feature `OrotezProtezViewModel.kt` does enforce `isJpegFileName()` and a `MAX_DOCUMENT_SIZE_BYTES` (2MB) cap before upload. `handlePicked()` here only reads the picked file's bytes and immediately dispatches `UploadDocument(...)` — no size or type guard exists anywhere in the occurrence flow (`FileKitType.Image` allows any image format, unbounded size).

**Failure scenario:** a user picks a large PNG/HEIC photo straight from the gallery (multi-MB, common for modern phone cameras). It uploads unrestricted — risking an out-of-memory crash reading the `ByteArray` on lower-end devices, and/or a backend rejection with no client-side warning telling the user why.

**Suggested change:** port `OrotezProtezViewModel`'s `isJpegFileName()`/size-cap checks (or the equivalent) into `handlePicked()` before dispatching the upload intent.

## 3. Workshop list item `id` is the bare `workshopCode`, not guaranteed unique — High

**File:** `core/core-data/src/commonMain/kotlin/com/tamin/taminhamrah/data/mapper/occurrence/OccurrenceMapper.kt:37`

```kotlin
id = workshopCode.orEmpty(),
```

`Step2WorkshopStep.kt` resolves the tapped bottom-sheet option via `step.workshops.first { it.id == option.id }`. If a national code has two workshop registrations that share the same `workshopCode` but differ by `branchCode` (the same employer registered through two branch offices — a real, known case for this endpoint), both list entries get the same `id`, and `first { ... }` always resolves to the first match regardless of which row the user tapped.

`old_android`'s equivalent (`OccurrenceReportViewModel.kt:134-147`) deliberately used the list index as the id specifically to avoid this collision — it never assumed `workshopCode` alone was unique.

**Failure scenario:** a worker registered at the same employer through two branches picks the second workshop entry in the list; the app silently binds the first one instead — wrong branch, wrong employer address/phone prefilled into the rest of the form, with no error shown.

**Suggested change:** use a composite key (`"$workshopCode|$branchCode"` or the list index, matching `old_android`) as the item id instead of the bare `workshopCode`.

## 4. No cross-field check that work end time is after work start time — High

**File:** `feature/taminServices/src/commonMain/kotlin/com/tamin/taminhamrah/feature/taminServices/occurrence/contract/OccurrenceContract.kt:147-150`

```kotlin
val isStep4Valid: Boolean
    get() = ... &&
        workHours.workStartTime.isNotBlank() &&
        workHours.workEndTime.isNotBlank() &&
        ...
```

`old_android`'s `OccurrenceSubmitUseCase.validate()` explicitly rejected the payload with "ساعت پایان کار باید بعد از ساعت شروع کار باشد" when `workEnd <= workStart`. Neither `isStep4Valid` nor `OccurrenceViewModel.submitOccurrence()` performs this comparison in the new code — only blank-checks exist.

**Failure scenario:** a user picks work start = 18:00 and work end = 08:00 (a nonsensical range for the accident day); the step accepts it and the report is submitted to the backend as-is.

**Suggested change:** add a comparison in `isStep4Valid` (or a dedicated error state) requiring `workEndTime > workStartTime`, mirroring the old validation message.

**File:** `feature/taminServices/src/commonMain/kotlin/com/tamin/taminhamrah/feature/taminServices/occurrence/contract/OccurrenceContract.kt:158`

## 6. `reporterType` hardcoded to self-filed instead of derived from the worker's nationality — High

**File:** `feature/taminServices/src/commonMain/kotlin/com/tamin/taminhamrah/feature/taminServices/occurrence/OccurrenceViewModel.kt:35, 315`

```kotlin
/** The legacy "occurence" submit endpoint's reporterType for a self-filed report — this flow has no reporter-type picker. */
...
reporterType = REPORTER_TYPE_SELF,
```

In `old_android`, `reporterType` is **not** "who is filing the report" — it encodes the injured worker's **nationality**: `dataModel.reporterType = if (nation.nationCode == "01") "1" else "2"` (Iranian = "1", non-Iranian = "2"), set from the workshop-specification lookup. The new code always sends `"1"` regardless of `state.jobDetails.nationalityCode`, which is fetched and carried in state but never read for this field — the comment above suggests the field's actual meaning (nationality, not filer identity) was misunderstood during the port.

**Failure scenario:** a non-Iranian insured worker's accident report is submitted with `reporterType = "1"` instead of `"2"`, which the backend previously used to distinguish nationality — this can misroute or misprocess the report server-side.

**Suggested change:** set `reporterType` from `Gender`-style code mapping on `state.jobDetails.nationalityCode` (`"01"` → `"1"`, else `"2"`), matching `old_android`, instead of a hardcoded constant.

## 7. Phone validation loosened for two fields — Medium

**File:** `feature/taminServices/src/commonMain/kotlin/com/tamin/taminhamrah/feature/taminServices/occurrence/components/steps/Step2WorkshopStep.kt`, `OccurrenceContract.kt:141`

Two related regressions from `old_android`:

- **Employer phone** (`bossMobileNumber`) is validated with `ValidationUtils.isPhoneNumberValid` (11-digit length only). `old_android` required it to match an Iranian mobile pattern (`^09\d{9}$`). A user can now type any 11-digit number, including a landline-formatted one, into a field specifically meant to capture the employer's *mobile* number.
- **Workshop phone** (`workshopTelephone`) is validated with the same `isPhoneNumberValid` (required, 11 digits). In `old_android` this field was optional (`required = false`) — a workshop without a landline could still submit. `ValidationUtils.isLandlineValid` (which explicitly allows blank) already exists in the same file and appears to have been intended for this field but isn't used here.

**Failure scenario:** (a) an employer phone number that isn't actually a mobile number passes validation; (b) a user whose workshop genuinely has no landline is permanently blocked from completing Step 2, where the old app allowed leaving it blank.

**Suggested change:** use a mobile-specific validator (`ValidationUtils.validateMobileNumber`/a `09\d{9}` check) for employer phone, and switch workshop phone to `ValidationUtils.isLandlineValid` (optional) as its name already implies it was meant to be used for.

## 8. `android:windowSoftInputMode="adjustResize"` changed app-wide, not scoped to this feature — Medium

**File:** `androidApp/src/main/AndroidManifest.xml` (added on the single `MainActivity`)

This is a single-Activity app, so this attribute change affects keyboard-resize behavior for **every** existing screen, not just the new occurrence wizard.

**Failure scenario:** any existing screen that already handles the keyboard itself (e.g. manually applying `imePadding()`/`WindowInsets.ime` padding, or relying on content staying put while a bottom sheet/dialog is open) can now double-apply resize/padding or shift layout unexpectedly the next time the keyboard opens — on screens with nothing to do with occurrence reporting.

**Suggested change:** if `adjustResize` is genuinely only needed for the occurrence wizard's own layout, apply it more narrowly (e.g. via `WindowCompat`/per-screen inset handling) rather than as a global manifest attribute; otherwise, regression-test the keyboard behavior of other screens that already do their own IME padding before merging.

## 9. Hardcoded Persian strings in new shared `core-ui` components — Medium

**File:** `core/core-ui/src/commonMain/kotlin/com/tamin/taminhamrah/ui/components/TaminStyledTextField.kt:3480, 3492`, `core/core-ui/src/commonMain/kotlin/com/tamin/taminhamrah/ui/components/topbars/TaminStepTopAppBar.kt` (`contentDescription = "بازگشت"`, `"بستن"`, default `stepLabel = "مرحله ${current} از ${total}"`)

Per `CLAUDE.local.md` rule 7, user-facing Persian text must come from `strings.xml`. These two components are documented as shared infrastructure ("reused by occurrence reporting and health self-declaration" per their own doc comments), so the violation isn't isolated to one screen — every current and future caller ships these un-externalized, untranslatable strings.

**Failure scenario:** any future localization pass or copy review misses these strings entirely since they're invisible to `strings.xml` tooling, and they multiply across every feature that adopts these new shared components.

**Suggested change:** move `"معتبر"`, `"خطا"`, `"بازگشت"`, `"بستن"`, and the `"مرحله %d از %d"` template into `strings.xml` and resolve via `stringResource(...)`.

## 10. `selectWorkshop()` awaits two network calls sequentially, and a mid-chain failure leaves half the prefill silently applied — Medium

**File:** `feature/taminServices/src/commonMain/kotlin/com/tamin/taminhamrah/feature/taminServices/occurrence/OccurrenceViewModel.kt` (`selectWorkshop()`, around line 168-210)

`getWorkshopSpecUseCase` is awaited, then `getPersonalInfoUseCase` is awaited — the second call needs only the already-selected workshop's code/branch and `userInfo` already in state, not the first call's result, so there's no data dependency forcing sequential execution. Contrast with `loadInitialData()` just above it, which correctly runs its independent calls concurrently via `merge()`.

Additionally, both calls are wrapped in one try/catch: if `getWorkshopSpecUseCase` succeeds (committing employer name/address/phone prefill to state) but the subsequent `getPersonalInfoUseCase` throws, the user sees the workshop-derived fields already filled in with only a toast error — Step 3's `fullName`/`gender`/`nationality` prefill (which depends on the same selection) is silently missing, with no indication of *which* half of the prefill failed.

**Failure scenario:** on a slow connection, every workshop selection pays the sum of both round-trips instead of the max; if the second call specifically fails, the user proceeds to Step 3 with some fields blank and no clear signal why.

**Suggested change:** run both calls concurrently (`coroutineScope { async { ... } }`, awaiting both, similar to `loadInitialData()`'s `merge()` pattern), and consider surfacing which specific prefill failed rather than one generic toast.

## 11. Document thumbnail encoding and duplicate-file check run on the main dispatcher — Medium

**File:** `Step6DocumentSubmitStep.kt:249, 264` (thumbnail `Base64.Default.encode`), `OccurrenceViewModel.kt:212` (duplicate check)

Two related performance issues in the document-upload path:

- Each document card's thumbnail is base64-encoded synchronously inside the composable body, and — since the encoding happens in a `forEach` over the full uploaded-document list — it **re-encodes every previously uploaded document's bytes** on every list change, not just the new one.
- The duplicate-file check (`current.uploadedDocuments.any { it.bytes?.contentEquals(intent.fileBytes) == true }`) does a full byte-by-byte comparison against every existing upload, on `viewModelScope` (which `BaseViewModel` itself flags with a `// todo check IO dispatcher` comment) — i.e. likely the Main dispatcher.

**Failure scenario:** camera/gallery photos are commonly 2–8MB. With 2-3 documents already uploaded, adding another one blocks the main thread first for the duplicate-byte-compare, then re-triggers a full re-encode of every thumbnail — visible jank/dropped frames right as the upload-success animation should play.

**Suggested change:** move both operations off the main dispatcher (`Dispatchers.Default`), and/or compute each thumbnail once at upload time and cache it instead of re-deriving it from raw bytes on every recomposition.

## 12. Six wizard steps duplicate their scaffold and field-state boilerplate; a new step-progress bar duplicates the existing `StepIndicator` — Low

**File:** `Step1PersonInfoStep.kt` through `Step6DocumentSubmitStep.kt`, `TaminStepTopAppBar.kt` (`TaminStepProgressBar`)

Two related reuse gaps:

- The `Scaffold { topBar = TaminStepTopAppBar; bottomBar = TaminBottomActionBar } { OccurrenceErrorWrapper { Column.verticalScroll... } }` skeleton (~15-20 lines) is copy-pasted identically across all six step files, and the per-field "touched/focused" `rememberSaveable` boolean-pair boilerplate is copy-pasted 5-6 times per file (already inconsistent between `Step2` and `Step4` — one keeps a `HasFocused` companion flag the other drops).
- `TaminStepTopAppBar` introduces a brand-new segmented step-progress bar (`TaminStepProgressBar`) instead of reusing `core-ui`'s existing `StepIndicator` — the established multi-step-wizard component already used by `orotez-protez`, `addDependent`, `change-mobile`, `girlSurvivor`, `studentInsuranceContract`, and `sendHistoryToInstitutions`. The occurrence wizard is now the only stepper in the app with a visually different "step X of Y" design.

**Failure scenario:** any future fix to shared step-scaffold behavior (e.g. insets, loading overlay) or to touched-state semantics has to be manually repeated across six files/many field blocks and will drift, as it already has between Step2 and Step4; and the app now shows two different visual languages for step progress depending on which wizard the user is in.

**Suggested change:** factor a shared `OccurrenceStepScaffold(...)` composable and a `rememberFieldTouchState()` helper; evaluate whether `TaminStepProgressBar` should be replaced with the existing `StepIndicator` for visual consistency (or document why occurrence intentionally diverges).
