## 1. Red Crescent day-20 rule reads the API response instead of today's Jalali date — High

**File:** `feature/contractFlow/src/commonMain/kotlin/com/tamin/taminhamrah/feature/contractFlow/ui/ContractFlowViewModel.kt:394-415`

```kotlin
FreelanceSpecialJobCode.RED_CRESCENT_CODE -> {
    try {
        val day = checkRedCrossStatusUseCase().first().toIntOrNull()
        if (day == null || day > 20) {
            emit(PartialState.Error(getString(Res.string.contract_error_red_crescent_day_limit)))
            return@flow
        }
        …
```

In `old_android` these are two separate things (`InsuranceContractFragment.kt:688-700`):

```kotlin
RED_CRESCENT_CODE -> {
    val day = PersianDate.today().shDay      // ← today's day of the Jalali month
    if (day > 20) { showAlertDialog(…error_redCrescentCode_select_job_title); return }
    mViewModel.checkRedCrossStatus()          // ← a separate eligibility service
}
```

`checkRedCrossStatus` is an eligibility check whose payload the legacy app reads as a boolean
(`RedCrossStatusResponse(val data: Boolean? = true)`, handled as `result.isSuccess && result.data == true`).
Here its response string is parsed as a day number, so `toIntOrNull()` returns `null` for anything
that is not a bare integer — including the `"ok"` the project's own fakes emit — and the branch
takes the `day == null` path every time.

**Failure scenario:** a freelance applicant picks «هلال احمر» from the job list on the 3rd of the
month. The service answers positively, `toIntOrNull()` yields `null`, and the user is told the job
can only be chosen up to the 20th. The job can never be selected, on any day.

> **مغایرت بیزینسی:** در نسخه‌ی قدیمی دو شرط جدا وجود دارد: اول اپلیکیشن **تاریخ روز شمسی** را
> می‌خواند و اگر روز ماه بزرگ‌تر از ۲۰ باشد، انتخاب شغل «هلال احمر» را همان‌جا رد می‌کند؛ بعد اگر
> تاریخ مشکلی نداشت، سرویس بررسی وضعیت هلال احمر صدا زده می‌شود و پاسخ آن (بله/خیر) تعیین می‌کند
> که کاربر مجاز است یا نه. در کد جدید شرط تاریخ حذف شده و به‌جای آن **پاسخ همان سرویس** به‌عنوان
> «روز ماه» تفسیر شده است. نتیجه این‌که کاربر هیچ روزی از ماه نمی‌تواند شغل هلال احمر را انتخاب کند.

**Suggested change:** keep the two checks separate — read the current Jalali day from the project's
date utilities for the `> 20` gate, and treat the service response as the yes/no eligibility answer
it is.

> **Round 2 — ✅ fixed.** The two checks are now separate exactly as suggested:
> `val (_, _, jalaliDay) = PersianDateFormatter.today(); if (jalaliDay > RED_CRESCENT_DAY_LIMIT)`
> reads today's date for the day gate, and `checkRedCrossStatusUseCase().first()` is checked
> separately (`isRedCrossEligible(status)`) as the yes/no eligibility answer.

## 2. Locked premium rate uses the percentage, not the rate code — High

**File:** `core/core-domain/src/commonMain/kotlin/com/tamin/taminhamrah/model/contracts/FreelanceSpecialJobCode.kt:6-7`

```kotlin
const val RED_CRESCENT_PREMIUM_RATE = "18"
const val MEDICAL_STUDENT_PREMIUM_RATE = "14"
```

These values are fed into `PartialState.LockedPremiumRateChanged`, and from there into
`FreelancePremiumRangeParams.spcRateCode` and `FreelanceMakeContractRequestDN.premiumRateCode`
(`ContractFlowViewModel.kt:501-514, 602-608`). Both fields are `spcrateCode` values —
`SpcPremiumRateOptionMapper.kt:6` maps `code = spcrateCode` and keeps the percentage separately in
`insurancePercent`.

`old_android` sets the code and the percentage label as two different values
(`InsuranceContractFragment.kt:1134-1145`):

```kotlin
if (tempCntCode == RED_CRESCENT_CODE) {
    mViewModel.dataModel.premiumRateCode = "03"
    mViewModel.dataModel.selectedPercentDesc = "18 درصد"
} else if (tempCntCode == MEDICAL_STUDENT_CODE) {
    mViewModel.dataModel.premiumRateCode = "02"
    mViewModel.dataModel.selectedPercentDesc = "14 درصد"
}
```

**Failure scenario:** once item 1 is fixed and a Red Crescent applicant gets through, the premium
range is requested for `spcRateCode = "18"` and the contract is registered with
`premiumRateCode = "18"` — a code the server does not know. The applicant either sees a wrong
premium band or the registration is rejected outright.

> **مغایرت بیزینسی:** برای «هلال احمر» و «دانشجوی علوم پزشکی»، نرخ حق بیمه در نسخه‌ی قدیمی با
> **کد نرخ** («۰۳» و «۰۲») روی قرارداد ثبت می‌شود و «۱۸ درصد» / «۱۴ درصد» فقط متنی است که به کاربر
> نشان داده می‌شود. در کد جدید همان درصد به‌جای کد نرخ برای سرویس محاسبه و برای ثبت قرارداد ارسال
> می‌شود، یعنی نرخ حق بیمه‌ی این دو گروه اشتباه ثبت خواهد شد.

**Suggested change:** store `"03"` / `"02"` as the rate codes, and if the percentage is needed for
display take it from `SpcPremiumRateOptionPR.insurancePercent` of the matching option.

> **Round 2 — ✅ fixed.** `FreelanceSpecialJobCode.kt` now defines `RED_CRESCENT_PREMIUM_RATE = "03"`
> and `MEDICAL_STUDENT_PREMIUM_RATE = "02"` — the actual rate codes, matching
> `InsuranceContractFragment.kt:1134-1145` exactly.

## 3. Uploaded document is never attached to the contract request — High

**File:** `feature/contractFlow/src/commonMain/kotlin/com/tamin/taminhamrah/feature/contractFlow/ui/ContractFlowViewModel.kt:612-641`

```kotlin
return FreelanceMakeContractParams(
    …
    guid = DEFAULT_APPLICANT_GUID,          // "00"
    guidName = DEFAULT_APPLICANT_GUID_NAME, // "00"
    …
)
```

In `old_android`, `guid` / `guidName` are not constants — they are the identity of the document the
user uploaded in the «بارگذاری مدارک» step
(`data/remote/models/services/concludingStudentInsuranceContract/ContractRequest.kt:22-23`):

```kotlin
data.imageFile?.guid ?: "00",
data.imageFile?.imageName ?: "00",
```

`"00"` is only the fallback for *no* document. Here the upload does happen —
`state.uploadedDocuments` holds `UploadImagePR(imageId, fileName, description)` and `canGoNext`
refuses to leave the step until it is populated (`ContractFlowContract.kt:79-80`) — but the
resulting `imageId` is then dropped.

**Failure scenario:** a student applicant photographs the required document, waits for the upload,
completes the flow, and the contract is registered on the server with no document attached. The
branch has no evidence for the request and the applicant has to start over.

The constant names are also misleading — `DEFAULT_APPLICANT_GUID` is the *image* guid, not anything
to do with the applicant.

> **مغایرت بیزینسی:** در مرحله‌ی «بارگذاری مدارک» کاربر مجبور است سند را آپلود کند و تا وقتی آپلود
> نشود دکمه‌ی مرحله‌ی بعد فعال نمی‌شود، ولی شناسه‌ی همان سند در زمان ثبت نهایی قرارداد به سرور
> فرستاده نمی‌شود و به‌جای آن مقدار ثابت «۰۰» می‌رود. در نسخه‌ی قدیمی «۰۰» فقط برای حالتی است که
> اصلاً سندی آپلود نشده باشد. نتیجه این‌که قرارداد بدون مدرک ثبت می‌شود.

**Suggested change:** take `guid` / `guidName` from `uiState.value.uploadedDocuments.firstOrNull()`
(`imageId` and `fileName`), falling back to `"00"` only when the list is empty.

> **Round 2 — ✅ fixed.**
> `val uploaded = uiState.value.uploadedDocuments.firstOrNull(); guid = uploaded?.imageId ?:
> DEFAULT_IMAGE_GUID, guidName = uploaded?.fileName ?: DEFAULT_IMAGE_GUID_NAME` — exactly the
> suggested change, and the constant was also renamed from the misleading `DEFAULT_APPLICANT_GUID`
> to `DEFAULT_IMAGE_GUID`.

## 4. Housewife/Student premium range queried with the wrong job code — High

**File:** `feature/contractFlow/src/commonMain/kotlin/com/tamin/taminhamrah/feature/contractFlow/ui/ContractFlowViewModel.kt:500-514`

```kotlin
val lookupCode = when {
    config.requiresFreeJob -> uiState.value.selectedFreeJobCode.orEmpty()
    else -> uiState.value.registrationInfo?.insuranceId.orEmpty()
}
…
return FreelancePremiumRangeParams(…, freeJobCode = lookupCode)
```

Only the freelance flow has `requiresFreeJob = true`. For housewife and student the `else` branch
sends the applicant's **insurance number** as the free-job code, while the *contract registration*
for the same two flows correctly sends the fixed job code (`resolveCntFreeJobCode()` →
`config.fixedFreeJobCode`, i.e. `WOMEN_CONTRACT_CODE` / `STUDENT_CONTRACT_CODE`). The two calls
therefore describe two different contracts.

`old_android` uses one value for both. `ContractBaseFragment.initView()` seeds
`dataModel.cntFreeJobCode` with `WOMEN_CONTRACT_CODE` / `STUDENT_CONTRACT_CODE` up front, and the
premium-range call passes exactly that (`InsuranceContractFragment.kt:928-931`):

```kotlin
mViewModel.getContractPremiumRate(
    mViewModel.dataModel.premiumRateCode,
    mViewModel.dataModel.cntFreeJobCode,
)
```

**Failure scenario:** a housewife reaches the premium step. The min/max band comes back for a job
code that is really her insurance number, so the slider offers a range that does not belong to the
housewife scheme; she picks an amount inside it and the contract is registered under a different
job code than the one the amount was calculated for.

> **مغایرت بیزینسی:** برای «زنان خانه‌دار» و «دانشجویی»، کد شغل قرارداد در نسخه‌ی قدیمی از ابتدا
> مقدار ثابت مخصوص همان نوع بیمه است و همان کد هم برای گرفتن بازه‌ی حق بیمه و هم برای ثبت قرارداد
> استفاده می‌شود. در کد جدید برای گرفتن بازه‌ی حق بیمه به‌اشتباه «شماره بیمه»ی کاربر فرستاده
> می‌شود، ولی موقع ثبت قرارداد کد شغل ثابت. یعنی مبلغی که به کاربر پیشنهاد می‌شود مربوط به قرارداد
> دیگری است.

**Suggested change:** resolve the lookup code the same way both places do — `fixedFreeJobCode`
first, then `selectedFreeJobCode` — and reuse `resolveCntFreeJobCode()` for it.

> **Round 2 — ✅ fixed.** `buildPremiumRangeParams()` now calls `resolveCntFreeJobCode()` — the same
> helper `buildMakeContractParams()` uses for submission — so the premium-range lookup and the
> actual contract registration always agree on the job code.

## 5. ViewModel events are never collected — online payment never offered — High

**File:** `feature/contractFlow/src/commonMain/kotlin/com/tamin/taminhamrah/feature/contractFlow/ui/ContractFlowScreen.kt:91-95`

```kotlin
val state by viewModel.uiState.collectAsState()

LaunchedEffect(Unit) {
    viewModel.sendIntent(ContractFlowIntent.LoadInitialData)
}
```

`ContractFlowEvent.ShowPaymentOption` and `ContractFlowEvent.ShowMessage` are declared
(`ContractFlowContract.kt:164-167`) and `ShowPaymentOption` is emitted after a successful
registration (`ContractFlowViewModel.kt:576-586`), but nothing in the screen subscribes to
`viewModel.events`. Both events are dropped.

`old_android` shows a two-action dialog right after the contract is registered — «پرداخت حق بیمه»
plus «متوجه شدم» — and hides the payment action only for Red Crescent / medical-student contracts
(`InsuranceContractFragment.kt:1178-1194`). That is exactly what `allowsOnlinePayment` in the state
is tracking, and it never reaches the UI.

Worth noting the contrast: `ContractsScreen.kt` in this same MR does this correctly, with
`collectWithLifecycleAware` and `LocalToaster` — the same treatment applied here would fix both this
item and item 8.

> **مغایرت بیزینسی:** در نسخه‌ی قدیمی بلافاصله بعد از ثبت موفق قرارداد، دیالوگی با شماره و تاریخ
> قرارداد باز می‌شود که دکمه‌ی «پرداخت حق بیمه» دارد و کاربر می‌تواند همان‌جا حق بیمه را آنلاین

**Suggested change:** collect `viewModel.events` with `collectWithLifecycleAware`, route
`ShowMessage` to the toaster, and expose `ShowPaymentOption` as a navigation callback out of
`ContractFlowScreen` the way `onBack` already is.

> **Round 2 — ✅ fixed.** `HandleContractFlowEvents` now collects `events` via
> `collectWithLifecycleAware` and routes `ShowMessage`/`ShowPaymentOption` to `onShowMessage`/
> `onShowPaymentOption` respectively. The payment option now surfaces through a proper
> `ContractSubmitResultDialog` (new in this round) rather than being dropped.

## 6. Guardian applicant type is selectable but has no effect — High

**File:** `core/core-ui/src/commonMain/kotlin/com/tamin/taminhamrah/ui/contractFlow/ContractApplicantStepContent.kt:29-50`,
`feature/contractFlow/src/commonMain/kotlin/com/tamin/taminhamrah/feature/contractFlow/ui/contract/ContractFlowContract.kt:77`

The «متقاضی قرارداد» step offers two radio buttons, `PERSONAL` and `GUARDIAN`. Picking `GUARDIAN`
stores `contractApplicantType` in the state and nothing else happens: `canGoNext` returns a flat
`true` for that step, no guardian fields are shown, and `contractApplicantType` is never read again
outside the radio group.

`old_android` treats the guardian case as a full sub-form (`ContractBaseFragment.kt:326-336, 511-545`):
national code, name, guardianship number (min 10 chars), guardianship date (min 7 chars) and a
guardianship image are all required before the step can be left, and submission goes to a
**different endpoint** — `makeContractByGuardian(…, ContractByGuardianRequest(dataModel))` instead of
`makeContract(…)` (`InsuranceContractFragment.kt:946-957`). The repository already exposes
`makeFreelanceContractByGuardian` / `makeOptionalContractByGuardian`; neither is wired here.

**Failure scenario:** a parent registering on behalf of a minor selects «قیم/ولی», walks through the
rest of the flow with no guardian details ever requested, and the contract is silently registered as
a personal contract in the parent's own name.

> **مغایرت بیزینسی:** در مرحله‌ی «متقاضی قرارداد» گزینه‌ی «قیم/ولی» قابل انتخاب است، ولی انتخابش
> هیچ اثری ندارد: نه فرم اطلاعات قیم (کد ملی، نام، شماره قیم‌نامه، تاریخ قیم‌نامه و تصویر قیم‌نامه)
> نمایش داده می‌شود، نه اعتبارسنجی می‌شود، و نه قرارداد از مسیر مخصوص قیم ثبت می‌شود — قرارداد به
> اسم خود کاربر ثبت می‌شود. در نسخه‌ی قدیمی همه‌ی این موارد الزامی است و سرویس ثبت قرارداد هم
> متفاوت است.

**Suggested change:** either implement the guardian branch end to end, or hide the `GUARDIAN` option
until it is implemented. Shipping a choice that silently does nothing is worse than not offering it.

> **Round 2 — still open.** `ContractFlowViewModel.handleSetContractApplicantType` still only
> updates `contractApplicantType` in state (`grep` confirms this is its entire body); no guardian
> form model (`GuardianFormPR.kt`, added this round, 26 lines) is ever read by the ViewModel, wired
> into `canGoNext`, or included in the submit request. The option is still selectable and still does
> nothing. This is the one High item from round 1 that received no attention this round.

## 7. Pre-flight contract-condition gates from `old_android` are missing — High

**File:** `feature/contractFlow/src/commonMain/kotlin/com/tamin/taminhamrah/feature/contractFlow/ui/ContractFlowViewModel.kt:138-163`

Before `old_android` even builds the stepper it runs a chain of checks and, on any of them, shows an
error and sends the user back (`ContractBaseFragment.kt:659-716`):

| Legacy check | Present here? |
|---|---|
| `insuranceIdState == null` → data-fetch error | no |
| overlap message (`chkRelolap != "1"`) → تداخل سابقه | no |
| `!insuranceIdState` → not registered yet | no |
| `selfIsuContStatCode == 1` → already has an active contract | no |
| age < 18 | no |
| `hasOtherContract(otherContract)` | no |
| `checkContractStatus == 2` → cancelled >20 days ago | no |
| `checkContractStatus == 4 or 5` → cancelled >3 months ago | no |
| women-only service vs. male applicant | yes (`requiresFemaleGender`) |

The new flow only implements the last one. `resolveEligibility()` reduces everything else to
`statusCode in 1..4`. Notably `insuranceIdValidity` — the legacy `insuranceIdState` — exists on
`RegistrationInfoDN` but is dropped by the mapper and is not even a field on `RegistrationInfoPR`,
so the "not registered" gate cannot be evaluated at all.

This gap was carried forward from the previous `studentInsuranceContract` implementation rather than
introduced here — but this MR extends the same engine to freelance, housewife and optional
insurance, so it now applies to four services instead of one.

**Failure scenario:** a user who already holds an active freelance contract opens the freelance flow,
is not stopped, fills in every step, and only finds out at the final submit — if the server happens
to reject it.

> **مغایرت بیزینسی:** در نسخه‌ی قدیمی، قبل از باز شدن مراحل قرارداد یک زنجیره شرط بررسی می‌شود و
> اگر هرکدام برقرار نباشد کاربر با پیام مناسب به صفحه‌ی قبل برمی‌گردد: نام‌نویسی نشده بودن، تداخل
> سابقه‌ی بیمه‌ای، داشتن قرارداد فعال، سن کمتر از ۱۸ سال، و ابطال قرارداد قبلی (بیش از ۲۰ روز یا
> بیش از سه ماه). در کد جدید فقط شرط «مخصوص بانوان بودن» پیاده شده و بقیه بررسی نمی‌شوند؛ یعنی
> کاربری که اصلاً واجد شرایط نیست تا آخرین مرحله جلو می‌رود.

**Suggested change:** carry `insuranceIdValidity`, the overlap message and the contract-status code
through to `RegistrationInfoPR` / `ContractPR`, and gate the flow on them before the stepper opens.
`ContractStatusCode` (added in this MR) is a good place for those codes.

## 15. The module split is on the wrong axis — Medium

**Files:** `feature/{student,housewife,freelance,optional}Contract/`, `settings.gradle.kts`

This is the one item here that is about direction rather than a defect, so it is worth settling now
— while it costs 262 lines to change — rather than after the rest of the contract surface lands.

The claim: **insurance type is data, not structure.** Encoding it as a module boundary is what
forces most of the friction below.

**The recommendation, up front: fold `:feature:contractFlow` and the four per-type modules into a
single `:feature:contracts`, and make insurance type a route argument instead of a module.** The
four config classes survive unchanged — they just become classes rather than modules. Concretely,
what that buys (every number below is measured or counted on this branch, and sourced in 15.4–15.5):

| | four per-type modules | one `:feature:contracts` |
|---|---|---|
| Gradle tasks for the contract domain | ~1,900 projected | **167** |
| Rebuild after a 1-line `ContractFlowConfig` change | 13.7 s | **7.1 s** |
| Deep link into a specific type | 4 URI patterns declared in 4 modules | **1 parameterised route** |
| Deep-link entry checks (auth, flag, eligibility) | live in `shared`, satellites bypassed | **one place, inside the feature** |
| List → edit / cancel / payment navigation | ~9 callbacks hoisted into `shared` (rule 4) | **direct, intra-feature** |
| Step composables shared between flows | pushed down into `core-ui` | **stay in the feature** |
| Cost of adding the 5th type (fraction, debt) | new module + `settings.gradle.kts` + `shared/build.gradle.kts` + `Koin.kt` + `FeatureNavigation.kt` + `TaminHamrahNavGraph.kt` | **one config class + one `when` branch** |
| Cost of adding the next operation (edit, cancel, pay) | new engine module + 4 more configs to register | **one package** |

The last two rows are the ones that matter most: with ~5,300 lines and nine flows still to port from
`old_android` (15.2), the question is not which shape is tidier today but which one makes the next
nine flows cheap. Everything below is the evidence for that table.

### 15.1 What the four modules hold today

| | LOC | files | Route | ViewModel | tests |
|---|---|---|---|---|---|
| `:feature:studentContract` | 66 | 3 | 1 | 0 | 0 |
| `:feature:housewifeContract` | 66 | 3 | 1 | 0 | 0 |
| `:feature:freelanceContract` | 65 | 3 | 1 | 0 | 0 |
| `:feature:optionalContract` | 65 | 3 | 1 | 0 | 0 |

Of those 66 lines, `Navigation.kt` (27) and the Koin module (10) are boilerplate — the only real
content is ~17 lines of config properties. Each module's fan-in is exactly **1**: nothing outside

```

                    di/Koin.kt, FeatureNavigation.kt, TaminHamrahNavGraph.kt
```

Three of those five are pure registration. A module whose only consumer is the app's own wiring
layer is not protecting a boundary.

### 15.3 The axis problem

In `old_android`, **nine fragments share one `ContractViewModel` and one `ContractDataModel`**
(`ContractBaseFragment`, `InsuranceContractFragment`, `OptionalContractFragment`,
`EditContractFragment`, `EditOptionalContractFragment`, `FractionContractFragment`,
`DeficitContractFragmen`, `CancelContractFragment`, plus the VM itself). Insurance type there is a
runtime parameter — `contractType: EnumInsuranceType` — and the decomposition axis is the
**operation**.

This MR splits on **type** instead. The two axes are orthogonal:

| Operation ↓ / Type → | student | freelance | housewife | optional | fraction | debt |
|---|---|---|---|---|---|---|
| Create | ← one fragment, 3 types → | | | separate | separate | separate |
| Edit | ← `EditContractFragment`, 3 types → | | | `EditOptional` | – | – |
| Cancel | ← `CancelContractFragment` — type-agnostic → | | | | – | – |
| Payment | ← `InsurancePaymentFragment` — type-agnostic → | | | | – | – |
| List | ← `ContractListFragment` — shows all five types at once → | | | | | |

**Four of the five operations cut across the module boundary.** Only "create" happens to line up
with it, which is why the split looks fine today and stops looking fine at the next flow.

### 15.4 What continuing this costs

**Build.** Every feature module costs exactly **167 Gradle tasks** regardless of size
(measured with `--dry-run`; identical for `:feature:studentContract` at 66 LOC and
`:feature:pensioner` at 8,494 LOC). Measured on this branch:

| | measured |
|---|---|
| Clean compile — 262 LOC across the 4 satellites | **19,752 ms** |
| Clean compile — 1,774 LOC in `:feature:contractFlow` alone | **10,435 ms** |
| Incremental — 1-line change in `ContractFlowConfig.kt`, 5 modules recompile | **13,718 ms** |
| Same change if it were one module | **7,080 ms** |

The four near-empty modules take about **twice** as long to build as a module holding seven times
more code, and they double the incremental feedback loop on the exact file that gets edited while
these flows are being finished. (Single-run timings on one machine — daemon noise applies, but the
2× gap is well outside it; the 167-task count is exact.)

Projected forward, with an edit wizard needing its own engine plus cancel / payment / fraction /
debt:

| | modules | LOC | Gradle tasks |
|---|---|---|---|
| `:feature:pensioner` (7 services, one module) | 1 | 8,494 | 167 |
| Contracts, continuing this approach | ~11–12 | ~7,600 | **~1,900** |

**Navigation.** `ContractListFragment` navigates to **seven** destinations — create, create-optional,
payment, payment list, edit, edit-optional, cancel. Per `CLAUDE.md` rule 4, navigation between two
feature modules must go through a callback. Keeping the split turns what is logically
*intra-feature* navigation into roughly nine callbacks hoisted into `shared`. Today it is one
(`onNavigateToService`).

**Leakage into `core-ui`.** When type is the module boundary, everything shared has to be pushed
downward — and this has already started. Of the ten contract composables now sitting in
`core-ui/ui/contractFlow/`, seven have exactly one consumer:

```
SelectableField                <- workshops                  ← genuinely shared
```

pattern turns `core-ui` into a warehouse for contract business UI.

### 15.5 Deep links

A deep link that opens a specific contract type is on the roadmap, and this is where encoding type
as structure bites hardest: **a deep link is a URL, and in a URL the contract type is a value.**

The project already has the pattern. `AgentDestination` documents it explicitly —

> *"The agent module must not depend on other feature modules, so it emits one of these ids ... and
> the host (nav graph) maps it to the real route."*

— and that list holds a single `CONTRACTS` id, not one per insurance type.

| | one module | current split |
|---|---|---|
| Route | `ContractFlowRoute(val type: ContractType)` — one parameterised route | four `data object` routes in four modules |
| URI pattern | `taminx://contract/{type}` — one | four separate patterns |
| `navDeepLink` declaration | one place, reviewable as a set | four modules, no central view of the URI space |
| `intent-filter` in `:androidApp` | one path | four paths to keep in sync with four modules |
| Koin qualifier | resolved from the route argument at runtime | four separate `named()` lookups |

The entry checks make this sharper. Landing from a deep link has to verify auth, that the service is
enabled (`FeatureFlag` / `ContractNewEntryFlags`), and the contract preconditions from item 7
(registration validity, history overlap, an already-active contract, age). **Those checks are
identical for all four types**, so they cannot live in the satellites — they belong in `shared` or
`contractFlow`. The deep-link path therefore bypasses the satellite modules completely, which
removes their last reason to exist.

And it multiplies: once `taminx://contract/{id}/edit` and `.../pay` exist, the current shape implies
four types × five operations = up to twenty URI patterns spread over a dozen modules, against one
route with two arguments.

### 15.6 Suggested change

Fold `:feature:contractFlow` and the four satellites into `:feature:contracts` as packages, and move
insurance type from the module boundary into the route:

```kotlin
@Serializable data class ContractFlowRoute(val type: ContractType)
@Serializable data class ContractEditRoute(val type: ContractType, val contractId: String)
@Serializable data class ContractCancelRoute(val contractId: String)
```

The Koin qualifiers already exist (`ContractFlowQualifiers`) and can be resolved from the route
argument; the four config classes stay exactly as they are, just as classes rather than modules.

This also matches how the rest of the codebase is organised — `:feature:pensioner` holds 7 routes,
`:feature:workshops` 9, `:feature:taminServices` 4, all in one module each. Nowhere else in the
project is there a module per service.

**Where the current split would be justified:** if an insurance type ever has to be excluded from a
build at the flavor level. If that is on the roadmap, say so and this item can be closed as
`➖ rejected` — `FeatureFlag` covers the runtime case, so it would need to be a real build-level
requirement.

> **Round 2 — ✅ fixed, taken exactly as recommended.** `settings.gradle.kts` now declares a single
> `:feature:contracts` (`grep -c` for the four old per-type module names returns zero); the four
> `*ContractFlowConfig` classes live inside it as plain classes, matched to a `ContractType` enum and
> resolved via `ContractFlowConfigs`, not as separate modules. `docs/vault/Modules.md` and
> `Dependency-Injection.md` were updated to match (the DI doc has its own small residual issue — see
> the same finding filed independently against MR !213/!215's copy of this file). This is the biggest
> single change in the round-2 diff and it's the right one — the projected Gradle-task and
> deep-link costs this item measured no longer apply.
