## 1. `CancellationException` swallowed at multiple sites — ✅ fixed (round 2)

**Verified** (`fd31a7f78`): both ViewModel flows (`loadData`, `handleSubmitConfirmed`) now rethrow
`CancellationException` before the general catch. In the data source, the shared `fetchData` helper
and `saveConflict`'s own try/catch were replaced with the existing `ErrorParser.safeCall(tag)` helper
(`NetworkUtils.kt`), which rethrows `CancellationException` and also classifies failures more
accurately than the old blanket `NO_CONNECTION_ERROR`. The same fix was applied to the
`history-objection` data source and both of its ViewModels, which were not part of this report.
Unit tests pass.

## 2. Legacy business-flow parity — ✅ done (round 2)

Checked against `old_android` (`ui/home/services/objectionInsuranceHistory/*`,
`ObjectionInsuranceHistoryResponse.kt`, `ServicesService.kt`):

- **Month slots — match.** `om*` is the registered value and `mm*` the edited one; index order is
  farvardin → esfand; no off-by-one and no swap. `withMonthEdits` writes month 0..11 to
  `newMonth1..12` correctly.
- **Edit validation — match.** Day caps (31 for months 1-6, 30 for 7-11, 29/30 for esfand) come from

  number → back on acknowledge. Legacy also does not require a description.
- **Active-request pre-check — match.** Same check, same message. Legacy left the user on an empty
  screen on dismiss; this MR navigates back, which is a reasonable improvement.
- **Multi-workshop years — match.** One card per year; one record opens the detail, several open a
  workshop picker.
- **Query — match on parameters** (page 0, limit 60, empty filter/sort). See item 4 for the paging
  difference.

## 3. `saveconflict` payload differs from legacy — Medium, needs confirmation

**Files:** `core/core-ui/.../mapper/objectionInsurance/ObjectionInsuranceMapper.kt`
(`toPresentation()` turns every null into `""`, `toDomain()` passes it straight back),
`feature/objectionInsurance/.../ui/mapper/ObjectionInsuranceUiMapper.kt:206-234` (`withMonthEdits`,
`buildEditedRecords`)

The record sent to `saveconflict` is the PR-layer record with the edited months written onto it.
Because the PR layer converts `null` to `""` on the way in and nothing converts it back, the payload
differs from legacy in ways the server may or may not care about:

- **Months the user did not edit** go out as the server's `mm` value, or `""` if it was null. Legacy
  seeded these as `"0"`.
- **`prow`, `reqno`, `reqtype`** go out as `""` (or the server value). Legacy's `setDefaultValue()`
  deliberately set them to `null` (and `isDeleted = false`, `userDesc = ""`) before saving.
- **`userDesc`** is `null` when the description is blank, which the JSON config omits entirely
  (`encodeDefaults` is off). Legacy always sent the text, `""` when blank.
- `confirmed` `null` becomes `false`.

I cannot tell from the client side how the backend treats `""` versus `null` versus `"0"`; legacy
setting them explicitly suggests it may matter. The likely symptoms are a rejected save, or a month
counted as something other than «no change».

> **سناریوی بیزینسی:** نسخه‌ی قدیمی قبل از ذخیره، فیلدهای `prow` و `reqno` و `reqtype` را عمداً
> خالی (null) می‌کرد و ماه‌هایی که کاربر دست نزده بود را با مقدار «۰» می‌فرستاد. نسخه‌ی جدید به‌جای
> آن‌ها رشته‌ی خالی می‌فرستد. اگر سرور بین «خالی» و «مقدار خالی‌رشته‌ای» فرق بگذارد، ممکن است
> ثبت اعتراض رد شود یا ماه‌های بدون تغییر اشتباه محاسبه شوند.

**Suggested change:** confirm with the backend team how `""` is treated for those fields; if it is not
identical to `null`/`"0"`, reproduce legacy's defaults in `buildEditedRecords`. Either way, add a test
that pins the serialized `saveconflict` body for a record with one edited month.

## 4. Only the first 60 records are loaded — Medium

**File:** `core/core-data/.../repository/objectionInsurance/ObjectionInsuranceRepositoryImpl.kt:12,22-26`

```kotlin
private const val CONFLICT_HISTORIES_PAGE_LIMIT = 60
...
emit(response.list.orEmpty().map { it.toDomain() })
```

Legacy requested the same first page (limit 60) but fed it through a paging source that kept
requesting pages until `total` was reached (`GeneralPagingSource.kt`). The new code makes one request
and ignores `total`, so anyone with more than 60 year/workshop records silently loses the rest — the
list just ends, with no indication that anything is missing. How many users that affects I cannot
tell; each row is one year per workshop, so someone with a long career across many employers could
reach it.

> **سناریوی بیزینسی:** در نسخه‌ی قدیمی، اگر تعداد ردیف‌های سوابق (سال × کارگاه) بیشتر از ۶۰ بود، بقیه
> هم صفحه‌به‌صفحه بارگذاری می‌شد. در نسخه‌ی جدید فقط ۶۰ ردیف اول نمایش داده می‌شود و بقیه بدون هیچ
> پیامی نمایش داده نمی‌شوند؛ کاربری با سابقه‌ی زیاد نمی‌تواند به سال‌های قدیمی‌تر اعتراض کند.

**Suggested change:** keep requesting pages until `total` (or an empty page) is reached, or raise the
limit with a comment on why it is safe.

## 5. Blank tracking number opens a success dialog — Low

**File:** `feature/objectionInsurance/.../ui/ObjectionInsuranceViewModel.kt:159-160`

`finalConfirmObjectionInsuranceConflictUseCase()` returns the tracking number as a `String`, and the
data source's `extractData()` only rejects `null`. If the server answers with an empty string, the
success dialog opens with a blank tracking number. Legacy checked for this and showed an error
instead (`ObjectionInsuranceHistoryFragment.kt:322-326`).

> **سناریوی بیزینسی:** اگر سرور شماره‌ی پیگیری خالی برگرداند، نسخه‌ی قدیمی پیام خطا نشان می‌داد.
> نسخه‌ی جدید پیام «ثبت شد» را با یک شماره‌ی پیگیری خالی نشان می‌دهد، و کاربر فکر می‌کند اعتراضش
> ثبت شده در حالی که چیزی برای پیگیری ندارد.

**Suggested change:** treat a blank tracking number like a failed confirmation and show the error.

## What was done well

- **The `CancellationException` fix was applied at the right layer** — replacing the hand-rolled
  `fetchData` with the shared `safeCall` removed the duplicated try/catch instead of patching it
  five times, and it was applied to the sibling `history-objection` code as well.
- **The month-slot mapping is correct** — the highest-risk area for this feature, with 24 positional
  fields (`om1`-`om12`/`mm1`-`mm12`). Checked field by field against legacy: no swap, no off-by-one.
- **Edit validation is as strict as legacy and slightly more consistent** (`hasRealEdit()` treats
  blank and 0 the same way everywhere).
- **The multi-workshop picker matches records by index**, where legacy matched on year + history
  type + workshop name — safer against duplicate names.
- **No hardcoded Persian strings, and the `FakeIOException` test bug does not appear.**
- **Test coverage at every layer**, and the suites pass across all affected modules.
