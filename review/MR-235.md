## 1. National-ID checksum validation is missing — High

**Files:** `feature/taminServices/src/commonMain/kotlin/com/tamin/taminhamrah/feature/taminServices/funeralAllowance/FuneralAllowanceViewModel.kt`,
`.../contract/FuneralAllowanceContract.kt:29`

`old_android`'s equivalent inquiry button runs the deceased's national code through Iran's
national-ID checksum before allowing the lookup:

```kotlin
// FuneralAllowanceFragment.kt (btnInquiryEligibility.onClick)
edNationalCode.getValueNationalCode()   // EditTextNationalCode → ValidationUtil.nationalCode(context, code)
```

The new code only checks digit count:

```kotlin
// FuneralAllowanceScreen.kt:236
enabled = uiState.deceasedNationalCode.length == 10
```

This isn't just a missing check — the evidence points at unfinished work rather than a deliberate
simplification:

- `FuneralAllowanceViewModel.kt:19` imports `com.tamin.taminhamrah.util.ValidationUtils`, but nothing
  in the file ever calls it.
- `FuneralAllowanceViewModel.kt:28` imports the string resource
  `funeral_allowance_error_invalid_national_id`, but it's never referenced.
- `FuneralAllowanceContract.kt:29` declares `deceasedNationalCodeError: String? = null` on the UI
  state, but no `PartialState`/`reduceState` branch ever sets it, and `FuneralAllowanceScreen.kt`
  never reads it.
- `core-ui/util/ValidationUtils.kt` doesn't have a national-ID checksum function at all yet — so even
  wiring the above up as-is wouldn't be enough; the checksum helper itself still needs to exist.

Net effect: a 10-digit but checksum-invalid national code is sent straight to
`shortterm/validateFuneral/{nationalCode}` with no client-side rejection, where legacy would have
stopped it with an inline error.

> **سناریوی بیزینسی جاافتاده:** در نسخه‌ی قدیمی، قبل از استعلام شرایط متوفی، کد ملی واردشده با
> الگوریتم چک‌سام کد ملی ایران اعتبارسنجی می‌شد و در صورت نامعتبر بودن، خطا نمایش داده می‌شد. در کد
> جدید این اعتبارسنجی انجام نمی‌شود و فقط طول ۱۰ رقمی بررسی می‌شود — یعنی یک کد ملی ۱۰ رقمی نامعتبر
> (با چک‌سام غلط) بدون خطا به سرور استعلام می‌شود. جالب اینکه import مربوط به ابزار اعتبارسنجی و
> رشته‌ی خطای «کد ملی نامعتبر» در کد اضافه شده‌اند ولی هیچ‌جا استفاده نمی‌شوند — به نظر می‌رسد این
> ولیدیشن قرار بوده اضافه شود ولی جا افتاده.

**Suggested change:** add a national-ID checksum helper to `ValidationUtils` (or reuse one if it
exists elsewhere under a different name — worth checking `core-domain`), wire it into
`onNationalCodeChanged`/the inquiry-button's enabled check, and set/clear
`deceasedNationalCodeError` accordingly, the way the unused string resource and state field already
anticipate.

> **Round 2 — ✅ fixed, verified** (`e0c43b086`). `ValidationUtils.isNationalCodeValid()` added,
> implementing the exact legacy checksum algorithm (weighted sum of the first 9 digits mod 11 vs.
> the 10th digit), and is now actually called from `FuneralAllowanceViewModel.kt:112` — the
> previously-dead import is live, and `deceasedNationalCodeError` is set/cleared through it.

## 2. Selected bank account is required to submit, but never sent — High

**Files:** `feature/taminServices/src/commonMain/kotlin/com/tamin/taminhamrah/feature/taminServices/funeralAllowance/contract/FuneralAllowanceContract.kt:43-44`,
`core/core-domain/src/commonMain/kotlin/com/tamin/taminhamrah/model/funeralAllowance/FuneralAllowanceModelsDN.kt:56-80`

```kotlin
// FuneralAllowanceContract.kt:43-44
val canSubmitRequest: Boolean
    get() = deceasedValidation?.isEligible == true && selectedBankAccount != null && isAccountConfirmed && !isSubmitting
```

The submit button stays disabled until the user picks a bank account from a new step-2 selector and
ticks a confirmation checkbox — an entire UI section
(`FuneralAllowanceSteps.kt:107-218`, `FuneralAllowanceBankAccountBottomSheet.kt`) built around this.
But the actual submit payload never carries it:

```kotlin
// FuneralAllowanceModelsDN.kt:56-65
data class SubmitFuneralAllowanceParamsDN(
    val deceasedNationalId: String,
    val branchCode: String,
    val branchName: String,
    val insuranceFirstName: String,
    val insuranceLastName: String,
    val mobileNumber: String,
    val nationalCode: String,
    val insuranceNumber: String,
    val requestHelpType: String = FUNERAL_ALLOWANCE_HELP_TYPE,
    // no bank-account field
)
```

`toSubmitParams()` never touches `selectedBankAccount`, and neither does
`FuneralAllowanceRequestDTO`/the API service. This is confirmed by the MR's own test —
`FuneralAllowanceViewModelTest.kt`'s "submits everything confirmed" test asserts
`deceasedNationalId`/`nationalCode`/`branchCode`/`requestHelpType` on the submitted params, never the
bank account — so this isn't a coverage gap masking a real send, it's genuinely dropped.

`old_android`'s equivalent submit call (`submitRequestFuneralAllowance`) sends only
`deadNationalId` + a `shorttermRequest` body with a hardcoded `requestHelpType="07"` — no bank-account
selection exists in the legacy flow at all (see item 3).

> **سناریوی بیزینسی جاافتاده:** در مرحله‌ی دوم فرم، انتخاب حساب بانکی و تیک تأیید آن اجباری شده
> (بدون آن دکمه‌ی «ثبت درخواست» فعال نمی‌شود)، اما این حساب انتخاب‌شده اصلاً در درخواست ارسالی به
> سرور قرار نمی‌گیرد. یعنی کاربر مجبور به انتخاب و تأیید یک حساب بانکی می‌شود که هیچ اثری در ثبت
> درخواست ندارد.

**Suggested change:** either add the selected bank account to `SubmitFuneralAllowanceParamsDN` and
the request DTO/API body (if the backend expects it and this is a genuine gap), or, if this step
was never meant to gate submission in the first place, confirm with product/backend what the
correct behavior is — this can't be resolved from the client code alone.

> **Round 2 — ✅ fixed, verified** (`e0c43b086`). The entire bank-account selection/confirmation
> step is removed — `selectedBankAccount`, `isAccountConfirmed`, `showBankAccountBottomSheet`,
> `SelectBankAccount`/`ToggleAccountConfirmation`/`ShowBankAccountBottomSheet` (state, intents, and
> the whole `FuneralAllowanceBankAccountBottomSheet.kt` file) are all gone. `canSubmitRequest` is now
> `deceasedValidation?.isEligible == true && !isSubmitting`, matching legacy's actual gate.

## 3. Pre-flight "no bank account" gate has no legacy equivalent — Medium, needs confirmation

**Files:** `feature/taminServices/src/commonMain/kotlin/com/tamin/taminhamrah/feature/taminServices/funeralAllowance/FuneralAllowanceViewModel.kt:67-85`,
`.../ui/components/NoBankAccountDialog.kt`

> "does the user have a bank account on file at all" gate, with nothing left half-wired. It still

> (not tied to any specific account) is an intended new requirement — but it's no longer the
> confusing, self-contradicting state round 1 found.

## 4. `CancellationException` swallowed at 9 sites — High

**Files:** `feature/taminServices/src/commonMain/kotlin/com/tamin/taminhamrah/feature/taminServices/funeralAllowance/FuneralAllowanceViewModel.kt`
(`checkBankAccountThenLoadInfo:72`, `loadInfo:91`, `validateDeceased:121`, `submitRequest:145`,
`confirmAccountCorrection:162`),
`core/core-network/src/commonMain/kotlin/com/tamin/taminhamrah/dataSource/funeralAllowance/FuneralAllowanceRemoteDataSourceImpl.kt`
(all 4 methods)

All five `catch (e: Exception)` blocks in the ViewModel, and all four in the remote data source,
catch broadly with no `CancellationException` rethrow first:

```kotlin
// FuneralAllowanceViewModel.kt:70-77 — one of five identical-shaped sites
val bankAccounts = try {
    getBankAccountListUseCase().first()
} catch (e: Exception) {
    emit(PartialState.CheckingBankAccount(false))
    ...
    return@flow
}
```

```kotlin
// FuneralAllowanceRemoteDataSourceImpl.kt:19-27 — one of four identical-shaped sites
override suspend fun getFuneralAllowanceInfo(): FuneralAllowanceInfoDTO = try {
    apiService.getFuneralAllowanceInfo().extractData()
} catch (e: TaminErrorUriException) {
    throw errorParser.parseGeneralError(e)
} catch (e: Exception) {
    throw errorParser.parseGeneralError(TaminErrorUriException(ErrorUri.NO_CONNECTION_ERROR))
}
```

This is a bug already correctly fixed elsewhere in this same codebase — e.g.
`feature/contractsAndPaymentAffair/.../ContractPremiumPaymentViewModel.kt:100-101`:

```kotlin
} catch (e: Exception) {
    if (e is CancellationException) throw e
    emit(PartialState.Error(e.toSingleLineMessage()))
}
```

(the same rethrow pattern is also used correctly by `CompleteEmployerInfoViewModel`,
`WorkersPaymentViewModel`, `InquiryEducationViewModel`, `HistoryViewModel`, and
`StoryViewerViewModel`). A user who navigates away from the funeral-allowance screen mid-request has
that cancellation caught and converted into a state update / a relabeled `NO_CONNECTION_ERROR`
instead of propagating normally, breaking structured concurrency — and in the data-source case,
mislabeling a routine navigation-away as a connectivity problem.

**Suggested change:** add `catch (e: CancellationException) { throw e }` before the general catch at
all 9 sites, matching the pattern already established in `ContractPremiumPaymentViewModel` and the
other ViewModels listed above.

> **Round 2 — ✅ fixed, verified** (`e0c43b086`). `catch (e: CancellationException) { throw e }`
> added before the general catch at all 9 sites (5 in the ViewModel, 4 in the remote data source).

## 5. Two positional-array response slots have no legacy accessor to verify — Low, needs confirmation

**File:** `core/core-network/src/commonMain/kotlin/com/tamin/taminhamrah/model/funeralAllowance/FuneralAllowanceDTO.kt`
(`DeceasedValidationDTO.fromPositional`)

The positional-array response from `shortterm/validateFuneral/{nationalCode}` is decoded well and
matches legacy exactly for the fields legacy actually reads: `[4]`=fullName, `[5]`=relationship,
`[6]`=eligibility flag, `[7]`=message, with the same `size >= 8` gate as
`old_android`'s `DeceasedInfoResponse.getDeceasedInfo()` — this part is thoroughly tested
(`DeceasedValidationDTOTest.kt` covers short lists, null lists, null entries, and the exact 8-entry
boundary).

But two additional slots are read that legacy never touches at all: `[9]` (`dependentStatus`) and
`[13]` (`deathDate`). `old_android`'s `DeceasedInfoResponse` never indexes past position 7, so there's
no legacy code to confirm these two indices against.

**Suggested change:** confirm slots `[9]` and `[13]` against the backend/API contract directly (not
derivable from the legacy client) — a wrong index here would silently show garbage instead of
failing loudly, since both fields are plain strings with no format validation.

> **Round 2 — ✅ fixed, verified** (`e0c43b086`). Rather than guessing at the two unconfirmed slots,
> `dependentStatus`/`deathDateRaw` were removed from `DeceasedValidationDTO` entirely — the decoder
> now matches legacy's `DeceasedInfoResponse` exactly (never reads past slot `[7]`), with a comment
> recording that choice explicitly.

## What was done well

- **The 4 endpoints match legacy exactly**: `GET funeral-no-presence/getFuneralNoPresenceLoadData`,
  `GET shortterm/validateFuneral/{nationalCode}`, `POST funeral-no-presence/saveShorttremFuneral`,
  `POST funeral-no-presence/confirmShorttremFuneral/{requestId}` — same paths, same HTTP methods.
- **The bank-account-issue correction flow (`hasBankAccountIssue`/backend `flag`) is a faithful
  port** of legacy's `onFuneralInfoResponse`/`btnCorrectedAccountNumber` — same fields
  (`partnerNationalId`, death date, `request.id`, `request.statusName`), same
  "re-submit via `confirmShorttremFuneral`" semantics.
- **The "not eligible" message fallback matches legacy exactly**:
  `message.ifBlank { getString(funeral_allowance_not_eligible) }` mirrors legacy's
  `list[7].ifEmpty { getString(R.string.not_eligible_funeral_allowance) }`.
- **No hardcoded Persian strings in production code** — the only literal Persian strings found are
  inside `@Preview` composables, the accepted exception already established elsewhere in this
  codebase.
- **No commented-out code anywhere in the new files.**
- **Test coverage is broad and genuinely useful where it exists**: the ViewModel test covers init
  (with/without bank account, error, retry), digit-filtering, eligible/ineligible/error
  validate-deceased, step navigation (forward, back-exits-on-step-1, back-from-step-2), bank-account
  select/confirm toggle, submit (happy path, blocked-until-confirmed, failure), account-correction
  re-submit, and the no-bank-account dialog. `DeceasedValidationDTOTest.kt` in particular is
  unusually thorough for a positional-array decoder — exactly the kind of edge-case coverage that
  class needs.
