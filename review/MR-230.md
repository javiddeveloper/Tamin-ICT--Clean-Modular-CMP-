## 1. Video keeps playing when the app is backgrounded — Medium

**Files:** `feature/stories/src/commonMain/kotlin/com/tamin/taminhamrah/feature/stories/ui/viewer/StoryViewerScreen.kt`,
`.../StoryVideoPlayer.android.kt`, `.../StoryVideoPlayer.ios.kt`

`isPaused` (the state that gates video playback) is driven only by three sources: touch-and-hold,
the comment field gaining focus, and the pager's scroll-in-progress state
(`StoryViewerScreen.kt:228-234`, `StoryViewerViewModel.setHold`). There is no lifecycle observer
anywhere in `feature/stories` keyed on `ON_STOP`/`ON_PAUSE` (or the iOS equivalent) — if the user
backgrounds the app (home button, switches apps, a phone call) while a video is playing, nothing
pauses it. On Android this means ExoPlayer keeps decoding and its audio track keeps playing while
the app has no visible UI; on iOS, `AVPlayer` behaves the same way.

Player *release* itself is correct — both platform actuals tear the player down properly in
`onDispose`, keyed on `url` (`StoryVideoPlayer.android.kt:76-79`: `player.release()`;
`StoryVideoPlayer.ios.kt:110-115`: pause + clear item) — so this is specifically about pausing on
backgrounding, not about a leak.

**Suggested change:** add a `DisposableEffect`/lifecycle observer in the viewer (or in
`StoryVideoPlayer` itself) that dispatches a pause intent on `ON_STOP`, and resumes (if the user was
actually watching, not mid-hold) on `ON_START`/`ON_RESUME`.

## 2. Saved-event card tap does nothing — Medium

**File:** `feature/profile/src/commonMain/kotlin/com/tamin/taminhamrah/feature/profile/ui/saveEvents/SaveEventsScreen.kt:148`

```kotlin
items(state.events) { event ->
    SaveEventCard(
        event = event,
        onClick = { /* handle */ },
        onToggleSave = { onIntent(SaveEventsIntent.ToggleSave(event.id)) }
    )
}
```

The whole point of a "saved events" list is presumably to re-open the story the user bookmarked —
`onToggleSave` (the bookmark/unsave button) is wired, but `onClick` (tapping the card itself) is a
literal no-op. Unlike the comment-sending stub elsewhere in this MR (explicitly documented as
intentional in `StoryViewerContract.kt`), nothing here says this is deliberate, and it's the primary
interaction on a screen this MR ships as complete.

**Suggested change:** wire `onClick` to navigate back into the story viewer at the saved event (or,
if that's genuinely out of scope for this iteration, say so explicitly with a comment so the next
reader doesn't have to guess).

## 4. Malformed deep link silently closes the viewer with no fallback — Low

**File:** `shared/src/commonMain/kotlin/com/tamin/taminhamrah/ui/navigation/TaminHamrahNavGraph.kt:527-551`

```kotlin
onOpenDeepLink = { link ->
    navController.popBackStack()
    ...
    } else {
        try {
            navController.navigate(link)
        } catch (e: Exception) {
            // Ignore or handle invalid deep link gracefully
        }
    }
},
```

`popBackStack()` runs unconditionally, before the link is validated at all. For a link that isn't
`http(s)://` or `tamin://feature/...`, `navController.navigate(link)` is tried as a raw route and,
on failure, the exception is swallowed by a catch block whose own comment
("Ignore or handle invalid deep link gracefully") reads as an undecided placeholder rather than a
deliberate choice. The net effect: a story's CTA that turns out to be malformed or point at a route
that doesn't exist closes the story viewer and does nothing else — no error toast, no staying on the
story, just a silent drop back to wherever the user was.

**Suggested change:** validate before popping — either keep the viewer open and only pop once a
target is confirmed reachable, or show a brief error/toast on the catch path instead of silently
swallowing it.

## 5. This MR's own playback fixes have no regression test — Low

**Files:** `feature/stories/src/androidMain/kotlin/com/tamin/taminhamrah/feature/stories/ui/viewer/StoryVideoPlayer.android.kt`,
`feature/stories/src/commonMain/kotlin/com/tamin/taminhamrah/feature/stories/ui/viewer/StoryViewerScreen.kt:228-234`

The most recent commit (`85d508251`, "improve video playback and loading state handling") fixes two
real bugs: a video built while the viewer was already paused used to start playing anyway
(`playWhenReady = true` → `playWhenReady = !isPaused`), and the pager's scroll-settle handler used to
resume playback on any page the pager passed through while swiping across several channels, not just
the one actually landed on (`else -> onIntent(Resume)` → gated on
`pagerState.currentPage == state.channelIndex`). Both are genuine logic fixes, not just symptom
patches — but neither has a test pinning the fixed behavior, despite `StoryViewerViewModelTest.kt`
(514 lines) otherwise covering the pause/resume state machine thoroughly via virtual time.

**Suggested change:** add a ViewModel-level test asserting `Resume` is only honored when
`pagerState.currentPage == channelIndex` (this part is testable without touching platform video
code), so a future refactor of the pager-settle logic doesn't silently reintroduce the
swipe-through-multiple-channels bug this commit just fixed.

## What was done well

- **MVI pattern followed correctly throughout.** Both `StoryRailViewModel` and
  `StoryViewerViewModel` extend `BaseViewModel<STATE, PARTIAL_STATE, EVENT, INTENT>`, and every UI
  interaction routes through `sendIntent` — no side effects fire directly from composables.
- **Player teardown is correct.** Despite item 1, releasing the player on dispose (and never holding
  more than one instance, keyed on `url`) is done correctly on both Android and iOS actuals.
- **`StoryViewerScreen.kt` (936 lines) is large but not a tangle** — it's already broken into
  well-named, well-documented private composables (`StoryMediaLayer`, `StoryTapZone`, `StoryHeader`,
  `StoryContent`, `StoryActions`, `StoryCommentField`), which makes it a reasonable candidate for a
  follow-up file split rather than a real SRP problem today.
- **`StoryViewerViewModelTest.kt` (514 lines) is genuinely thorough** — the segment clock, combined
  pause sources (hold + comment focus), video ready/ended/failed/watchdog-timeout paths, CTA
  dispatch (internal feature / external URL / absent), like/save toggling, and channel/item
  navigation edges are all covered using virtual time, with no flakiness risk.
- **The deep-link CTA architecture (`81567dc93`) is a deliberate, sound choice** — routing story CTAs
  through `tamin://feature/...` deep links rather than direct `FeatureFlag` references keeps
  `:feature:stories` decoupled from every feature it might link to, correctly following rule 4.
- **No hardcoded strings or magic-value comparisons anywhere in `:feature:stories` itself** — the one
  violation found (item 3) is confined to the newer, smaller profile-side screen.
- **`SaveEventsScreen`/`SaveEventsViewModel` reach stories data only through shared domain use cases**,
  never a direct cross-feature import — correct per rule 4. `storiesModule` is correctly registered
  in `sharedModules`.
