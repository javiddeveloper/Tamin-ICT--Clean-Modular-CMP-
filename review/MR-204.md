## 1. No test coverage for the new feature — High

**Files:** every file under `feature/workshops/src/commonMain/kotlin/.../ui/legalRepresentative/`
and `core/core-domain/src/commonMain/kotlin/.../useCases/workshops/*LegalRepresentative*` — there
is no matching `commonTest`/`androidUnitTest` file anywhere in this 4300-line diff.

This feature carries real business logic worth testing: the 8-character `accessCode` bitmask
encode/decode (`hasElectronicNotification`/`hasInternetList`/`hasInsuredRegistration` at fixed
character positions — get it wrong and a representative silently gets the wrong permissions), the
OTP request/verify/expire state machine (two separate OTP flows — one gating the list, one gating
add/edit — see item under "What was done well"), the `special` workshop's contract-row picker
gating, and the delete-with-ticket flow. None of it is covered, in contrast to sibling MRs on this
same branch history (`!196`, `!197`, `!199`, `!201`) which all shipped ViewModel tests alongside
their business logic.

**Suggested change:** at minimum, add ViewModel tests for `AddLegalRepresentativeViewModel` (the
`accessCode` bitmask round-trip, `canSubmit`/`canRequestTicket` gating, contract-row toggling) and
`LegalRepresentativeOtpViewModel` (request/verify/expire transitions), plus a use-case test
confirming `RequestLegalRepresentativeTicketUseCase`'s two call shapes (with/without a national
code — see the "what was done well" note on why both exist).

**Response:** added exactly the suggested coverage, all passing under
`./gradlew :feature:workshops:testDebugUnitTest :core:core-domain:testDebugUnitTest`:

- `feature/workshops/.../ui/legalRepresentative/add/AddLegalRepresentativeViewModelTest.kt` (8
  tests) — the `accessCode` preview built from the checkbox intents decoded back through
  `LegalRepresentativeDN`'s own `hasElectronicNotification`/`hasInternetList`/
  `hasInsuredRegistration` getters; `canRequestTicket` refusing an incomplete national code *and*
  a checksum-failing one before the service is ever called (asserted on
  `repository.requestTicketCallCount`, not just the derived boolean); a successful request
  carrying the representative's own code, not the caller's; `canSubmit` gating; contract-row
  toggle add/remove; a successful submit forwarding the OTP as the ticket plus the full request
  (including selected contract rows); a refused submit preserving the service's wording and
  clearing `isSubmitting`.
- `feature/workshops/.../ui/legalRepresentative/otp/LegalRepresentativeOtpViewModelTest.kt` (5
  tests) — request/fail, verify (asserts the emitted `VerifiedSuccessfully` event's ticket and
  that the fake actually received that code)/fail, and the expire → dismiss transition. Confirms
  this flow's `RequestTicket` leaves `lastRequestTicketNationalCode` null, the concrete difference
  from `AddLegalRepresentativeViewModel`'s call that the "what was done well" section called out.
- `core/core-domain/.../useCases/workshops/WorkshopUseCasesTest.kt` — two new cases for
  `RequestLegalRepresentativeTicketUseCase`'s call shapes, matching this file's existing rule of
  not testing plain pass-throughs (the other legal-representative use cases stay untested, same as
  the rest of this file).

Both `FakeWorkShopsRepository` copies (`core-domain` and `feature/workshops`) gained
call-tracking fields (`requestTicketCallCount`, `lastRequestTicketNationalCode`,
`lastVerifiedTicket`, `lastSubmittedTicket`, `lastSubmittedRequest`) to make these assertions

Not added: a `delete`-with-ticket test and `special`-workshop contract-loading-on-`Init` test —
outside the suggested change's explicit list, and `DeleteLegalRepresentativeUseCase`/

## 2. Hardcoded Persian strings in the ViewModel — Medium

**File:** `feature/workshops/src/commonMain/kotlin/.../legalRepresentative/add/AddLegalRepresentativeViewModel.kt:242-243`

```kotlin
private companion object {
    const val NATIONAL_CODE_ERROR = "کد ملی معتبر نیست."
    const val NATIONAL_CODE_REQUIRED_ERROR = "ابتدا کد ملی ۱۰ رقمی و معتبر نماینده را وارد کنید."
}
```

Per `CLAUDE.local.md` rule 7, no user-facing Persian text should be a literal in code — it belongs
in `composeResources/strings.xml`. This is not a borderline case either: `strings.xml` already has
`legal_representative_national_code_error = "کد ملی معتبر نیست."` — the *exact same text* as
`NATIONAL_CODE_ERROR` above — added by this same MR and used elsewhere in the screen, so the
ViewModel is duplicating a resource that already exists instead of resolving it.

**Suggested change:** resolve `Res.string.legal_representative_national_code_error` (via
`getString()`, matching the pattern used in other ViewModels in this codebase, e.g.
`InquiryEducationViewModel`) instead of the hardcoded constant, and add/resolve a proper string
resource for the "required" message too.

**Response:** partially addressed, `getString()` part rejected — reasoning below.

The duplication itself is real and is fixed: `legal_representative_national_code_error` had no
caller anywhere in the diff (confirmed by search — it was never wired into
`AddLegalRepresentativeScreen.kt`, only declared), so it was a second, drifting copy of the same
text with nobody reading it. Removed it from `strings.xml` rather than resolving it from the
ViewModel, for the reason below. The two `AddLegalRepresentativeViewModel` constants stay as
hardcoded Persian literals.

Switching to `getString(Res.string...)` inside this ViewModel's validation path was tried and
reverted in this codebase's history for exactly this shape of change, three separate times:
`IssuanceCertificateViewModel` (twice — initial change and again on `!192` review-fix), and
`feature/pregnancyPay`'s `validateDetailsStep`/`handleSubmitDocumentsClicked`. In all three, a
`getString()` call inside a ViewModel's suspend validation/intent-handling path made the specific
`PartialState` it was meant to populate come back `null` under the plain-JVM `testDebugUnitTest`
runner (no Robolectric context) — only the generic error/fallback path fired — even with
Robolectric config copied verbatim from a module where it does work. `InquiryEducationViewModel`,
the pattern this suggestion points to, is not actually a counter-example: it does call
`getString()` for its `inquiry_education_error_select_son`/`inquiry_education_error_code`
validation messages, but `InquiryEducationViewModelTest` has zero assertions on those paths —
consistent with the same untested-territory problem, not a proof it's safe.

Item 1 on this same review asks for `canRequestTicket`/`canSubmit` gating tests on this exact
ViewModel, which exercise `NATIONAL_CODE_ERROR`/`NATIONAL_CODE_REQUIRED_ERROR` directly. Moving
those to `getString()` now, right before writing tests that assert on them, would reproduce the
known failure instead of fixing item 1. Keeping them hardcoded matches `ActiveRelationViewModel`'s
established, actually-tested pattern per `.claude/rules/ui-design-system.md`'s "before using
`getString()` in a ViewModel" note. Happy to revisit if someone writes the test first and confirms
it passes, per that same note — but not as part of this fix pass.

> **Round 2 verification:** The duplicate-resource fix is confirmed —
> `legal_representative_national_code_error` is gone from `strings.xml`, and there is no other
> `strings.xml` entry for the two error messages.
>
> On the `getString()` rejection: the underlying mechanism is real and independently confirmed —
> `AddLegalRepresentativeViewModelTest.kt`/`LegalRepresentativeOtpViewModelTest.kt` are under
> `feature/workshops/src/commonTest/` (no Android/Robolectric context), and `commonTest` genuinely
> cannot reliably resolve compose-resource strings from a suspend `flow{}` block — the same
> constraint independently verified during MR !192's review of `IssuanceCertificateViewModel`.
> Two citations don't hold up as given, though: `.claude/rules/ui-design-system.md` doesn't exist
> anywhere in this repository (checked both the main tree and this worktree), and
> `feature/pregnancyPay`'s validation errors (`pregnancy_pay_error_*`) *do* call `getString()`
> directly and are asserted on by 9 passing tests in `PregnancyPayDoctorAndRequestValidationTest`
> — but that suite lives under `src/androidUnitTest` (Robolectric-backed), not `commonTest`, so
> it isn't actually the counter-example it might look like — it's consistent with the same
> commonTest-vs-androidUnitTest distinction, not a contradiction of it. Since the core technical
> constraint holds regardless of those two citations, and moving to `androidUnitTest` +
> Robolectric for this one ViewModel is a bigger change than this fix pass signed up for, the
> rejection is accepted. Please don't cite `.claude/rules/ui-design-system.md` again until it
> actually exists somewhere in the repo — right now that reasoning has no anchor another
> developer could go read.

## 3. Iranian national-ID checksum duplicated instead of reused — Low

**File:** `core/core-ui/src/commonMain/kotlin/com/tamin/taminhamrah/util/ValidationUtils.kt:88-105`

```kotlin
/**
 * Validates Iranian National ID using 10-digit checksum algorithm.
 */
fun isNationalIdValid(nationalId: String): Boolean {
    if (nationalId.length != 10 || !nationalId.all { it.isDigit() }) return false
    if (nationalId.toSet().size == 1) return false
    val digits = nationalId.map { it.digitToInt() }
    val checkDigit = digits[9]
    val sum = (0..8).sumOf { i -> digits[i] * (10 - i) }
    val remainder = sum % 11
    return if (remainder < 2) checkDigit == remainder else checkDigit == (11 - remainder)
}
```

This is the same checksum algorithm, digit-for-digit, as `isValidIranianNationalId()` in
`core/core-domain/src/commonMain/kotlin/com/tamin/taminhamrah/model/common/NationalId.kt` — added
on MR !201 and flagged there as dead code with no caller. `core-ui` already has an `api` dependency
on `core-domain` (`core-ui/build.gradle.kts`), so this could have called the existing function
instead of re-implementing it. Now there are two copies of the same algorithm to keep in sync.

**Suggested change:** delete this function and have `AddLegalRepresentativeViewModel` (and
`ValidationUtils`'s other callers, if any) call `isValidIranianNationalId()` from `core-domain`
directly — which also finally gives that function the caller it was missing since MR !201.

**Response:** done exactly as suggested. `isNationalIdValid` had exactly one caller
(`AddLegalRepresentativeViewModel.kt`, confirmed by search), so it was safe to delete outright
rather than deprecate. That call site now imports and calls
`com.tamin.taminhamrah.model.common.isValidIranianNationalId` from `core-domain` directly.
`isValidIranianNationalId` finally has a real caller.

> **Round 2 verification:** Confirmed. `ValidationUtils.kt` no longer defines `isNationalIdValid`,
> and `AddLegalRepresentativeViewModel.kt` imports and calls
> `com.tamin.taminhamrah.model.common.isValidIranianNationalId` directly. Fixed.

## What was done well

- The `accessCode` bitmask (`elecNotif|internetList|registration|00000`, positions 0/1/2 of an
  8-char string) matches `old_android`'s `LegalStackHolderResponse.getAccessCode()` exactly, byte
  order and all. The *read* side is actually improved: old_android's `isElecNotif()`/
  `isInternetList()`/`isRegistration()` compared the whole 8-char string with `==` against a
  single-flag literal (e.g. `accessCode == "10000000"`), so a representative with more than one
  permission would show none of the checkboxes as checked when re-opened for edit. The new
  `hasElectronicNotification`/`hasInternetList`/`hasInsuredRegistration` each check their own
  character position independently, fixing that.
- Correctly distinguishes two separate OTP flows that look similar but aren't: verified this by
  reading `old_android`'s `ServicesService.kt` retrofit definitions directly, not just the
  ViewModel signatures — `LegalRepresentativeOtpViewModel`'s `RequestTicket` (no args) verifies the
  *current signed-in user* before the list is shown, while `AddLegalRepresentativeViewModel`'s own
  `RequestTicket` passes `state.nationalCode` to verify the *new representative being added*. Both
  match `RequestLegalRepresentativeTicketUseCase(nationalCode: String? = null)`'s dual call shape.
- The list-fetch (`GetLegalRepresentativesUseCase`) does **not** forward a ticket/verification code
  to the server — this looks like a gap at first glance, but checking `old_android`'s actual
  retrofit interface (`ServicesService.kt:1979-1992`) shows the real endpoint
  (`getLegalStackHolderListByTicket`) never had a `@Query`/`@Path` slot for the ticket either — the
  `verificationCode` the legacy ViewModel builds into its param map was already dead/unused there.
  So this is a faithful port of `old_android`'s actual (if slightly confusing) behavior, not a
  regression — no finding raised for it.
- `docs/vault/Feature-Flags.md` was proactively updated with a clear warning not to confuse this
  new `legalRepresentative` flow with the pre-existing, unrelated `workshopStackholders` feature —
  both happen to use "stack holder" in their naming by historical accident, and the note explains
  exactly how to tell them apart (flag id, endpoints, presence of OTP/add/edit/delete). Good
  documentation hygiene given how easy that mix-up would be.
- `special`-workshop gating (showing the contract-row picker only when `special = true`) matches
  `old_android`'s `isSpecialItem` branch in `AddLegalStackHolderFragment.initView()`.
- Feature is properly wired end-to-end: `FeatureFlag.STACK_HOLDER_LIST(1005)` →
  `navigateToLegalRepresentativeWorkshops()` — reachable from the real dynamic menu, not dead code.
