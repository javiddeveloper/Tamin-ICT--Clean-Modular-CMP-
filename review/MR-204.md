## 1. No test coverage for the new feature — High

**Files:** every file under `feature/workshops/src/commonMain/kotlin/.../ui/legalRepresentative/`
and `core/core-domain/src/commonMain/kotlin/.../useCases/workshops/*LegalRepresentative*` — there
is no matching `commonTest`/`androidUnitTest` file anywhere in this 4300-line diff.

This feature carries real business logic worth testing: the 8-character `accessCode` bitmask
encode/decode (`hasElectronicNotification`/`hasInternetList`/`hasInsuredRegistration` at fixed
character positions — get it wrong and a representative silently gets the wrong permissions), the
OTP request/verify/expire state machine (two separate OTP flows — one gating the list, one gating
add/edit — see item under "What was done well"), the `special` workshop's contract-row picker
gating, and the delete-with-ticket flow. None of it is covered, in contrast to sibling MRs on this
same branch history (`!196`, `!197`, `!199`, `!201`) which all shipped ViewModel tests alongside
their business logic.

**Suggested change:** at minimum, add ViewModel tests for `AddLegalRepresentativeViewModel` (the
`accessCode` bitmask round-trip, `canSubmit`/`canRequestTicket` gating, contract-row toggling) and
`LegalRepresentativeOtpViewModel` (request/verify/expire transitions), plus a use-case test
confirming `RequestLegalRepresentativeTicketUseCase`'s two call shapes (with/without a national
code — see the "what was done well" note on why both exist).

## 2. Hardcoded Persian strings in the ViewModel — Medium

**File:** `feature/workshops/src/commonMain/kotlin/.../legalRepresentative/add/AddLegalRepresentativeViewModel.kt:242-243`

```kotlin
private companion object {
    const val NATIONAL_CODE_ERROR = "کد ملی معتبر نیست."
    const val NATIONAL_CODE_REQUIRED_ERROR = "ابتدا کد ملی ۱۰ رقمی و معتبر نماینده را وارد کنید."
}
```

Per `CLAUDE.local.md` rule 7, no user-facing Persian text should be a literal in code — it belongs
in `composeResources/strings.xml`. This is not a borderline case either: `strings.xml` already has
`legal_representative_national_code_error = "کد ملی معتبر نیست."` — the *exact same text* as
`NATIONAL_CODE_ERROR` above — added by this same MR and used elsewhere in the screen, so the
ViewModel is duplicating a resource that already exists instead of resolving it.

**Suggested change:** resolve `Res.string.legal_representative_national_code_error` (via
`getString()`, matching the pattern used in other ViewModels in this codebase, e.g.
`InquiryEducationViewModel`) instead of the hardcoded constant, and add/resolve a proper string
resource for the "required" message too.

## 3. Iranian national-ID checksum duplicated instead of reused — Low

**File:** `core/core-ui/src/commonMain/kotlin/com/tamin/taminhamrah/util/ValidationUtils.kt:88-105`

```kotlin
/**
 * Validates Iranian National ID using 10-digit checksum algorithm.
 */
fun isNationalIdValid(nationalId: String): Boolean {
    if (nationalId.length != 10 || !nationalId.all { it.isDigit() }) return false
    if (nationalId.toSet().size == 1) return false
    val digits = nationalId.map { it.digitToInt() }
    val checkDigit = digits[9]
    val sum = (0..8).sumOf { i -> digits[i] * (10 - i) }
    val remainder = sum % 11
    return if (remainder < 2) checkDigit == remainder else checkDigit == (11 - remainder)
}
```

This is the same checksum algorithm, digit-for-digit, as `isValidIranianNationalId()` in
`core/core-domain/src/commonMain/kotlin/com/tamin/taminhamrah/model/common/NationalId.kt` — added
on MR !201 and flagged there as dead code with no caller. `core-ui` already has an `api` dependency
on `core-domain` (`core-ui/build.gradle.kts`), so this could have called the existing function
instead of re-implementing it. Now there are two copies of the same algorithm to keep in sync.

**Suggested change:** delete this function and have `AddLegalRepresentativeViewModel` (and
`ValidationUtils`'s other callers, if any) call `isValidIranianNationalId()` from `core-domain`
directly — which also finally gives that function the caller it was missing since MR !201.

## What was done well

- The `accessCode` bitmask (`elecNotif|internetList|registration|00000`, positions 0/1/2 of an
  8-char string) matches `old_android`'s `LegalStackHolderResponse.getAccessCode()` exactly, byte
  order and all. The *read* side is actually improved: old_android's `isElecNotif()`/
  `isInternetList()`/`isRegistration()` compared the whole 8-char string with `==` against a
  single-flag literal (e.g. `accessCode == "10000000"`), so a representative with more than one
  permission would show none of the checkboxes as checked when re-opened for edit. The new
  `hasElectronicNotification`/`hasInternetList`/`hasInsuredRegistration` each check their own
  character position independently, fixing that.
- Correctly distinguishes two separate OTP flows that look similar but aren't: verified this by
  reading `old_android`'s `ServicesService.kt` retrofit definitions directly, not just the
  ViewModel signatures — `LegalRepresentativeOtpViewModel`'s `RequestTicket` (no args) verifies the
  *current signed-in user* before the list is shown, while `AddLegalRepresentativeViewModel`'s own
  `RequestTicket` passes `state.nationalCode` to verify the *new representative being added*. Both
  match `RequestLegalRepresentativeTicketUseCase(nationalCode: String? = null)`'s dual call shape.
- The list-fetch (`GetLegalRepresentativesUseCase`) does **not** forward a ticket/verification code
  to the server — this looks like a gap at first glance, but checking `old_android`'s actual
  retrofit interface (`ServicesService.kt:1979-1992`) shows the real endpoint
  (`getLegalStackHolderListByTicket`) never had a `@Query`/`@Path` slot for the ticket either — the
  `verificationCode` the legacy ViewModel builds into its param map was already dead/unused there.
  So this is a faithful port of `old_android`'s actual (if slightly confusing) behavior, not a
  regression — no finding raised for it.
- `docs/vault/Feature-Flags.md` was proactively updated with a clear warning not to confuse this
  new `legalRepresentative` flow with the pre-existing, unrelated `workshopStackholders` feature —
  both happen to use "stack holder" in their naming by historical accident, and the note explains
  exactly how to tell them apart (flag id, endpoints, presence of OTP/add/edit/delete). Good
  documentation hygiene given how easy that mix-up would be.
- `special`-workshop gating (showing the contract-row picker only when `special = true`) matches
  `old_android`'s `isSpecialItem` branch in `AddLegalStackHolderFragment.initView()`.
- Feature is properly wired end-to-end: `FeatureFlag.STACK_HOLDER_LIST(1005)` →
  `navigateToLegalRepresentativeWorkshops()` — reachable from the real dynamic menu, not dead code.
