## 1. `kindDoc` mapped with a raw-string `when` instead of an enum — Low

**File:** `core/core-ui/src/commonMain/kotlin/com/tamin/taminhamrah/mapper/workshop/WorkshopUiMapper.kt:269-274`

```kotlin
proceedingType = when (kindDoc.trim()) {
    "1" -> Res.string.article_42
    "2" -> Res.string.article_43
    "3" -> Res.string.article_44
    else -> null
},
```

`kindDoc` is a server type-code with a small, finite set of values ("1"/"2"/"3", each meaning a
specific ماده — no Persian text is hardcoded here, the labels correctly go through `strings.xml`).
No enum exists yet for this concept anywhere in the codebase (checked). Per the project's convention
for exactly this shape — a finite server code with no matching enum should get a *new* enum rather
than a `when (code)` mapper — this should be `enum class WorkshopKindDoc(val code: String)` with its
own `label` extension, the same pattern this MR itself uses correctly for
`ArticleSixteenRequestStatus.label` a few lines above in `WorkshopStatusTint.kt`.

**Suggested change:** introduce a small enum for `kindDoc`'s three values and switch on that instead
of the raw string, matching the pattern already used for `ArticleSixteenRequestStatus` in this same
MR.

## What was done well

- **The filing-window deadline math was checked against legacy and matches exactly**: legacy's
  `Utility.differenceBetweenShamsiDate` computes a real Gregorian-converted day count and truncates
  it to whole 365-day years (`diffDay / 365`), refusing once that count exceeds 1 — i.e. day 730 is
  the first refused day. `ArticleSixteenDN.kt`'s constants and `ManagementDebitViewModel.kt`'s check
  reproduce this precisely, including the counter-intuitive detail that day 729 is still accepted
  even though the refusal message reads «بیش از یک سال». The code's own comment correctly flags that
  the design spec's stated rule («یک روز») is wrong and should not be followed — a real discrepancy
  caught and resolved in the right direction, rather than faithfully implementing a wrong spec.
- **Directly tested at both boundaries**: `day 729 after the executive notice is still accepted` and
  `day 730 after the executive notice is refused` are both explicit tests in
  `ManagementDebitViewModelTest.kt`, along with the resubmission-past-deadline case.
- **The no-debt pre-check dialog matches legacy's `WorkshopInfoFragment`** (fetch debts before
  navigating, dialog instead of an empty screen when there are none) and **the resubmission notice's
  trigger matches legacy's `RequestArticle16Fragment`** (shown exactly on `DOCUMENT_DEFECT`/status
  "7", nothing else).
- **A real bug was fixed in the neighboring `ObjectionableDebitViewModel`**: every failure path used
  to `emit(reportFailure(it))`, which unconditionally replaced the whole debt list with an error
  screen — even when only a sub-action (downloading a PDF, checking a deadline) failed and the list
  itself had loaded fine. Now `reportFailure` always raises a toast instead, confirmed against
  `old_android`'s `DebitObjectionFragment` to be the more legacy-faithful behavior, not a new
  deviation.
- **`CancellationException` is never swallowed anywhere in this MR's new code** — every error path in
  `ManagementDebitViewModel`, `ArticleSixteenFormPage`, `WorkshopsViewModel.selectAction`, and
  `ObjectionableDebitViewModel` uses `Flow.catch {}` consistently, which never intercepts
  cancellation, unlike the raw `try/catch(Exception)` pattern found repeatedly elsewhere this cycle.
- **No hardcoded Persian strings** — the only Persian literals in the diff are `@Preview`-only sample
  data (workshop names, dates, amounts for the form's preview composables).
- **Document duplicate-detection is well isolated and tested**: `DocumentFingerprintTest.kt` covers
  re-picking the same file, a different file, a removed attachment no longer blocking, and a
  server-read document never accidentally matching.
- **Good status-code parity**: all six `ArticleSixteenRequestStatus` values and their string codes
  match legacy's `FilterRequestTypeEnumClass` one-to-one, confirmed independently.
