## 5. Round-2 business-validation tests removed instead of fixed — Medium

**File:** `feature/orotez-protez/src/androidUnitTest/kotlin/com/tamin/taminhamrah/feature/orotezprotez/ui/OrotezProtezDocumentUploadTest.kt`

I confirmed the underlying problem is real, not a false alarm: checking out the round-2 reviewed
commit (`cd3eccd27`) and running
`:feature:orotez-protez:testDebugUnitTest --tests "...OrotezProtezDocumentUploadTest"` fails —
5 of 5 tests time out:

```
OrotezProtezDocumentUploadTest > documentPicked_withNonJpegExtension_isRejectedAndStaysEmpty FAILED
    app.cash.turbine.TurbineAssertionError: No value produced in 3s
    Caused by: app.cash.turbine.TurbineTimeoutCancellationException: Timed out waiting for 3s
```

The same failure shape (Turbine's `awaitItem()` timing out after 3s under
`UnconfinedTestDispatcher`) hits all five tests: the two rejection-path tests, the duplicate-image
test, the missing-required-document test, and the full submit-success test. So the three "fix
test" commits on top of that were fixing a genuine, reproducible failure — not chasing a phantom.

What changed is *how* it was fixed. Rather than diagnosing why those specific `await`s hang (the
new code's own comment says it's because the rejection/validation code paths call
`getString(Res.string...)`, which it claims "can't be resolved without an Android context" in a
plain JVM unit test), the fix:

- Deleted the five tests asserting non-JPEG rejection, oversize rejection, duplicate rejection,
  missing-required-doc validation, and the full submit-success-and-navigate-back path.
- Kept only three tests: a valid-JPEG upload, an upload failure, and a document removal — none of
  which exercise the validation rules item 4 was originally about.
- Replaced Turbine's `ReceiveTurbine`/`awaitItem()` pattern with a plain
  `viewModel.uiState.first(predicate)` wrapped in `withContext(Dispatchers.Default) { withTimeout(5_000) { ... } }`
  for the tests that remain.

I did not verify the "`getString` needs an Android context" claim itself — worth noting because,
if it's accurate, it would mean the validation-message code paths were already silently
unverifiable by any of this project's JVM unit tests before this MR too (this repo has no
Robolectric per the new comment), which is a broader gap than this one file. If it's not accurate
and the real cause is something more specific to the test setup (e.g. `Dispatchers.IO` file
reads racing the 3s wallclock timeout, independent of `getString`), then the rejection paths may
be testable after all with a different fix (e.g. `Dispatchers.setMain` doesn't affect `Dispatchers.IO`
work inside the ViewModel, or Turbine's timeout could be raised the same way the remaining tests'
timeout was, or `getString` could be exercised once as a sanity check to see whether it actually
throws vs. hangs).

Either way, the net effect on this branch is the same as if item 4 had never been addressed: the
five business scenarios above have no passing test today.

**Suggested change:** before accepting the removal, confirm precisely why the deleted tests
hung (a compiling-but-hanging `getString` call behaves very differently from a call that throws,
and the fix should match which one it actually is), then restore equivalent coverage — either by
fixing the root cause so the original Turbine-based tests pass, or by porting them to the same
`uiState.first(predicate)` + `withTimeout` pattern already used successfully for the tests that
were kept.
