## 1. No confirmation dialog and no navigation away after a successful submission — High ✅

> **Round 2:** fixed. `OrotezProtezSubmitSuccessDialog` now shows `TaminConfirmationDialog` with
> `state.submittedResultMessage` (server message, matching old_android) on `hasSubmitted`;
> confirming it sends the new `OnSubmitSuccessAcknowledged` intent, which the ViewModel maps to
> `OrotezProtezEvent.NavigateBack` — the inline green text is gone. Covered by
> `submitDocuments_withBothRequiredDocuments_succeedsAndAcknowledgeNavigatesBack` in the new
> `OrotezProtezDocumentUploadTest.kt`. Verified by reading the code, not just the test name.

**File:** `feature/orotez-protez/src/commonMain/kotlin/com/tamin/taminhamrah/feature/orotezprotez/ui/OrotezProtezScreen.kt:751-759`, `.../OrotezProtezViewModel.kt:198-205`

```kotlin
// ViewModel
emit(PartialState.DocumentsReadyForSubmission)
emit(PartialState.Submitting(true))
try {
    val resultMessage = saveShortTermOrthosisUseCase(request).first()
    emit(PartialState.SubmitSucceeded(resultMessage))   // never sends NavigateBack
} catch (e: Exception) {
    emit(PartialState.SubmitFailed(e.toSingleLineMessage()))
}

// Screen
if (state.hasSubmitted) {
    Spacer(Modifier.height(Spacing.sm))
    Text(
        text = state.submittedResultMessage ?: stringResource(Res.string.orotez_protez_submit_success_fallback),
        style = MaterialTheme.typography.bodySmall,
        color = colors.greenText,
    )
}
```

`OrotezProtezEvent` has no "submitted" event, and `SubmitSucceeded` never triggers
`OrotezProtezEvent.NavigateBack` — the only place that does is the header back button and
`BackToPreviousStep` on the first step. After a successful submit, the user is simply left on the
same Documents screen: the submit button becomes permanently disabled
(`!state.hasSubmitted` in the `enabled` expression, with no way to reset it) and a small green
line of text appears at the top of the scrollable content, easy to miss if the user is scrolled
down near the button they just tapped.

`old_android/.../orotezProtez/OrotezProtezFragment.kt` (`onSendRequest`) does this differently on
success: it shows `DialogManagerMessageOfRequest` with the **server's own `resultMessage`**
(`result.data?.shorttermRequest?.resultMessage` — the very same field this MR's
`saveShortTermOrthosis()` already returns and stores in `submittedResultMessage`), and confirming
the dialog calls `requireActivity().onBackPressed()`, leaving the wizard entirely. The
infrastructure for a matching dialog already exists in this same MR —
`TaminConfirmationDialog` is used one file over, in `OrotezProtezHeader.kt`, for the help dialog —
it's just not reused for the success case.

> **مغایرت بیزینسی:** در نسخه‌ی قدیمی، وقتی درخواست اروتز و پروتز با موفقیت ثبت می‌شد، یک پیام
> تأیید (که متن آن از سرور می‌آمد) به‌صورت یک پنجره‌ی مجزا به کاربر نشان داده می‌شد و با تأیید آن،
> کاربر به‌طور خودکار از این فرم خارج می‌شد. در نسخه‌ی جدید، بعد از ثبت موفق، هیچ پنجره‌ای باز
> نمی‌شود و کاربر به‌طور خودکار از صفحه خارج نمی‌شود؛ فقط یک خط متن سبزرنگ کوچک در بالای فرم (جایی
> که ممکن است دیده نشود) اضافه می‌شود و کاربر روی همان صفحه‌ی بارگذاری مدارک باقی می‌ماند، بدون
> راه مشخصی برای فهمیدن این‌که «کارش تمام شده» یا رفتن به مرحله‌ی بعد.

**Suggested change:** on `SubmitSucceeded`, show a confirmation (`TaminConfirmationDialog` with
`state.submittedResultMessage`, matching old_android's server-driven message) and send
`OrotezProtezEvent.NavigateBack` when the user confirms it, the same way old_android returns to
the previous screen.

## 2. `serviceDateTimeStamp` is hardcoded to `0L` — Medium, needs confirmation

**File:** `core/core-data/src/commonMain/kotlin/com/tamin/taminhamrah/data/mapper/OrotezProtezMapper.kt:73`

```kotlin
request = ShortTermOrthosisRequestIdDTO(id = null),
requestFileList = requestFileList.map { it.toDTO() },
requestHelpType = SHORT_TERM_ORTHOSIS_HELP_TYPE,
risuid = risuid,
serviceDateTimeStamp = 0L,
```

`serviceDateTimeStamp` is a distinct field from `useTajTimeStamp`/`prescriptionDateTimeStamp` (the
prescription date, which *is* collected from the user and sent correctly). Nothing in the wizard
collects a second date for this field, so it's always sent as epoch `0`. I could not confirm from
`old_android`'s available files whether the legacy request also always sends `0`/omits this field
for a short-term orthosis submission, or whether it's meant to carry a real value (e.g. the date
of a related service) that this port is silently dropping.

**Suggested change:** confirm with backend/product whether `serviceDateTimeStamp` needs a real
value here; if `0` is the deliberate original behaviour, a short comment would save the next
reader the same question.

> **Author note (round 1):** deferred — not yet confirmed with backend/product. No code change
> made this round.

> **Round 2:** still open. The magic number was pulled into a named constant
> (`private const val SERVICE_DATE = 0L`), which is a readability improvement but doesn't answer
> the underlying question — still needs backend/product confirmation on whether `0` is correct.

## 3. Insured-persons list has no explicit page size or pagination — Low, needs confirmation

**File:** `core/core-data/src/commonMain/kotlin/com/tamin/taminhamrah/data/repository/orotezProtez/OrotezProtezRepositoryImpl.kt:23-27`, `feature/orotez-protez/.../OrotezProtezViewModel.kt:271`

```kotlin
override fun getInsuredPersons(query: ApiQueryParamDN?): Flow<List<InsuredPersonDN>> = flow {
    val effectiveQuery = query ?: apiQueryBuilder.defaultQuery()
    val response = orotezProtezRemoteDataSource.getInsuredPersons(effectiveQuery)
    emit(response?.list?.map { it.toDomain() } ?: emptyList())
}
```

`getInsuredPersonsUseCase()` is called once with `apiQueryBuilder.defaultQuery()` (an empty
`ApiQueryParamDN()`) and collected via `.first()` — a single page, whatever the server's default
page size is, with no "load more" in the `INSURED_PERSON` picker sheet. `old_android`'s dependants
list (`getDependantsResponse()`) was explicitly paged at page size 10. If the server's default page
size for this endpoint is smaller than a user's actual dependant count, some dependants would be
silently missing from the picker with no indication more exist.

I'm not confident this is a regression specific to this MR — the same "fetch once, no explicit
page size" pattern appears in other already-merged list screens in this codebase — so flagging as
needs-confirmation rather than a definite bug.

**Suggested change:** confirm the server's default page size for this endpoint is large enough to
never truncate a real user's dependant list; if not, pass an explicit page size or add pagination
to the picker.

> **Author note (round 1):** confirmed the server's default page size is sufficient for this
> endpoint — no truncation risk in practice. No code change made.

> **Round 2:** marked `➖ rejected` — the author checked the server's default page size for this
> endpoint and confirmed it's large enough that no real user's dependant list would be
> truncated. Accepting this; no code change needed.

## What was done well

- The document-validation rules are a faithful, detail-accurate port of
  `OrotezProtezFragment`/`OrotezProtezViewModel` in `old_android`: JPEG-only
  (`isJpegFileName`), 2MB max (`MAX_DOCUMENT_SIZE_BYTES`), duplicate-image rejection
  (`findDuplicateDocumentId`, byte-for-byte comparison), and the specific "both the prescription
  *and* the invoice image are mandatory, at least 2 documents total" submit gate
  (`missingRequired` + `MIN_REQUIRED_DOCUMENT_COUNT`) — this exactly matches old_android's
  `error_add_all_pic_orotez`/`error_select_image` rules, including the two optional hearing-aid
  documents not being gated.
- `risuid` in the submit payload is correctly sourced from the primary insured person's
  `mainInfo` regardless of which dependant is selected as the beneficiary — a subtle detail that
  matches `old_android`'s behaviour (`risuid` always comes from `mldUserInfo`, never from the
  selected dependant) rather than the more "obvious" but wrong choice of taking it from the
  selected person.
- Local temp files (camera/gallery picks) are cleaned up consistently: on removal
  (`OnDocumentRemoveClicked`), on replacement (picking a new image over an existing one), and on
  `onCleared()` for whatever's left — a reasonable equivalent to `old_android`'s
  `DCIM/tempImage` cleanup on `onDestroyView`.
- The `TaminJalaliDatePicker` refactor (extracting `JalaliDatePickerContent` and adding
  `TaminJalaliDatePickerBottomSheet`) is additive and doesn't touch the existing dialog-based
  callers' behaviour.
- The `androidApp/.../file_paths.xml` → `app_file_paths.xml` rename (needed to avoid a resource
  collision with a library's own `file_paths.xml`, most likely FileKit's) is applied consistently
  everywhere it's referenced.
