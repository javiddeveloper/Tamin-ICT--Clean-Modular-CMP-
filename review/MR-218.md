## 3. Gender derived by string-matching instead of using `genderCode`, plus hardcoded strings — Medium

**File:** `feature/pensioner/src/commonMain/kotlin/com/tamin/taminhamrah/feature/pensionInquiry/ui/disabilityPension/DisabilityPensionViewModel.kt:638, 725-730`

```kotlin
val genderTitle = if (personal?.genderDesc?.contains("زن") == true) {
    FEMALE_TITLE
} else {
    MALE_TITLE
}
```

```kotlin
private companion object {
    const val MALE_TITLE = "آقای"
    const val FEMALE_TITLE = "خانم"
    ...
    const val DISABILITY_DEMAND_TYPE_CODE = "01"
    const val HISTORY_OBJECTION_COMING_SOON_MESSAGE = "این امکان به‌زودی فعال می‌شود."
```

Two `CLAUDE.local.md` rule 7 violations in the same file:

1. **Gender is derived by substring-matching a free-text description** (`genderDesc.contains("زن")`)
   instead of the structured `genderCode` field that already exists on the same model
   (`DisabilityPersonalInfoDN.genderCode`) — and this exact pattern is done *correctly* two files
   away in the same feature: `DisabilityRelationClassifier.kt:33-34` defines
   `GENDER_MALE = "01"` / `GENDER_FEMALE = "02"` and branches on `genderCode`. A description string
   changing wording (a trailing space, "بانوان" instead of "زن", a locale variant) silently flips
   which title shows with no compile-time or runtime signal.
2. **Three Persian literals hardcoded as `const val` instead of `strings.xml` resources**
   (`MALE_TITLE`, `FEMALE_TITLE`, `HISTORY_OBJECTION_COMING_SOON_MESSAGE`) — despite this MR adding
   128 lines to `strings.xml` and this same feature's `DisabilityRelationClassifier` correctly using
   `Res.string.*` for its own gender-dependent titles.

Separately, `DISABILITY_DEMAND_TYPE_CODE = "01"` is a bare magic string used to filter registered
medical-commission records (`.filter { it.demandTypeCode == DISABILITY_DEMAND_TYPE_CODE }`) — a
finite type code compared as a raw string with no enum backing it, the same shape rule 7's own
worked example warns against. No `old_android` equivalent of this specific filter was found in the
reviewed legacy files, so it's not clear from the client side alone whether `"01"` is the only
demand type this screen should show — worth confirming while fixing the hardcoding.

**Suggested change:** branch on `genderCode` (`"01"`/`"02"`, matching `DisabilityRelationClassifier`)
instead of the description substring; move the three literals into `strings.xml`; and either confirm
`"01"` is the only relevant demand type and promote it to a small enum, or confirm the filter should
be broader.

> **Round 3 — 🔄 needs rework.** The three sub-parts of the original finding are each individually
> fixed correctly:
> - Gender now branches on `personal?.genderCode == "02"`, matching `DisabilityRelationClassifier`'s
>   `GENDER_FEMALE = "02"` convention.
> - `MALE_TITLE`/`FEMALE_TITLE`/`HISTORY_OBJECTION_COMING_SOON_MESSAGE` moved to
>   `Res.string.disability_pension_male_title` / `disability_pension_female_title` /
>   `disability_pension_history_objection_coming_soon`.
> - `DISABILITY_DEMAND_TYPE_CODE = "01"` replaced with a small `DisabilityDemandType` enum; the
>   now-dead `const val` was removed in the follow-up commit (`3a2d03f3a`).
>
> But the fix introduced a new, real regression: the two new `getString(...)` calls for the gender
> title are made directly inside `loadApplicantInfo()`'s flow body — a suspend function call, not
> behind `stringResource()` in a composable — and this code runs **unconditionally on every
> `DisabilityPensionViewModel` construction** (`init { sendIntent(DisabilityPensionIntent.Init) }` →
> `loadApplicantInfo()`). Running `:feature:pensioner:testDebugUnitTest` on this branch's current HEAD
> now fails **9 of 57 tests**, 6 of them in `DisabilityPensionViewModelTest` alone
> (`whenInitLoads_identityInfoAndAgeAreResolvedFromPersonalInfoAndUserAgeUseCase`,
> `whenAddDependentClicked_emitsNavigateToAddDependentEvent`,
> `whenSummaryConfirmedAndSubmitClicked_runsThreeCallChainAndShowsTrackingCode`,
> `whenSaveDisabilityUserInfoFails_showsToastAndStopsSubmitting`,
> `whenSaveDocumentDisabilityFails_showsToastAndStopsSubmitting`,
> `whenFinalConfirmDisabilityRequestFails_showsToastAndStopsSubmitting`), plus 3 timeouts in the new
> `DisabilityPensionDocumentUploadTest` (item 4's new file). The failure shapes are consistent with
> `getString()` throwing in the plain-JVM unit-test environment (no Compose resource loader
> initialized): the exception is swallowed by `handleIntent`'s `.catch { sendEvent(ShowToast(...)) }`
> wrapper, so `PartialState.IdentityLoaded` never emits (explaining
> `expected:<0019273648> but was:<null>` in the init test) and an extra, unasserted
> `ShowToast("مشکلی پیش آمده، لطفا بعدا سعی کنید")` event is left sitting in the events flow for every
> other test that constructs the ViewModel (explaining the `Unconsumed events found` failures — since
> `init` runs on construction, this fires before any test-specific intent is even sent).
>
> **سناریوی بیزینسی نیازمند بررسی:** این خرابی توی محیط تست پیش میاد، ولی چون کد واقعی هم همین‌جوری
> `getString` رو مستقیم و بدون شرط، همون لحظه‌ای که صفحه باز می‌شه صدا می‌زنه، نمی‌شه بدون بررسی دقیق‌تر
> مطمئن شد که این مشکل فقط مخصوص تسته و روی گوشی واقعی رخ نمی‌ده — چون این الگو (`getString` مستقیم
> توی یک متد غیر Composable که همیشه در لحظه‌ی ساخته‌شدن ViewModel اجرا می‌شه) جای دیگه‌ای از همین فایل
> یا این فیچر قبلاً استفاده نشده بود.
>
> **Suggested change:** move the gender-title resolution into the UI layer (resolve via
> `stringResource()` in the composable from the existing `genderCode`, the way
> `DisabilityRelationClassifier`'s title do), or confirm this exact `getString()`-in-`init`-flow
> pattern is verified safe at runtime (it's used elsewhere in the codebase, e.g. `PayRollViewModel`,
> but always behind an optional/lazy code path a test can choose not to exercise — this is the first
> place it runs unconditionally in `init`) and, at minimum, fix the 9 broken tests either way.

## 4. Submit-chain failure paths, document upload, and the objection branch are untested — Medium

**File:** `feature/pensioner/src/commonTest/kotlin/com/tamin/taminhamrah/feature/pensionInquiry/ui/disabilityPension/DisabilityPensionViewModelTest.kt`

The submit chain is three sequential calls — `saveDisabilityUserInfoUseCase` →
`saveDocumentDisabilityUseCase` → `finalConfirmDisabilityRequestUseCase` — matching `old_android`'s
`saveAndConfirmRequest()` status sequence (`"3"` → `"4"` → `"0"`) correctly. Only the **first** call's
failure is tested (`whenSaveDisabilityUserInfoFails_showsToastAndStopsSubmitting`); nothing tests
what happens when `saveDocumentDisabilityUseCase` or `finalConfirmDisabilityRequestUseCase` fails —
which matters specifically because by that point the backend has already written a record from the
earlier step(s), so a mid-chain failure is a different, likely worse, situation for the user than a
first-call failure (a half-submitted request) and is exactly the scenario most likely to need its
own recovery/retry handling.

Also untested: the entire document-upload flow (`handleDocumentImagePicked`, lines 229-271 — JPEG
extension check, the 2MB size cap, duplicate-content detection, and the upload-failure state), and
the "commission objection = yes" branch of the registered-commission step — only
`whenCommissionRecordAnsweredNo_advancesToDocumentsStep` exists; nothing proves answering "yes"
correctly keeps the user on the step or routes them differently.

> **سناریوهای بیزینسی جاافتاده:** فقط شکست‌خوردن مرحله‌ی اول زنجیره‌ی ثبت نهایی (ذخیره‌ی اطلاعات
> فردی) تست شده. اگه مرحله‌ی دوم (ذخیره‌ی مدارک) یا مرحله‌ی سوم (تایید نهایی) شکست بخوره — که دقیقاً
> جایی‌ست که چون مراحل قبلی موفق بودن، یک رکورد نیمه‌تکمیل توی بک‌اند وجود داره — هیچ تستی این حالت
> رو پوشش نمی‌ده. همچنین کل فلوی آپلود مدرک (بررسی پسوند JPEG، محدودیت حجم ۲ مگابایت، تشخیص مدرک
> تکراری، و حالت شکست آپلود) و حالتی که کاربر توی مرحله‌ی «سابقه‌ی کمیسیون پزشکی» اعتراض داره (پاسخ
> «بله» به‌جای «خیر») هیچ‌کدوم تست ندارن.

**Suggested change:** add failure tests for the second and third submit-chain calls, at least one
test for a successful document upload and one for each rejection reason (wrong extension, too large,
duplicate), and a test for the objection="yes" path staying on/blocking the step.

> **Round 3 — ✅ fixed, coverage-wise.** `whenSaveDocumentDisabilityFails_showsToastAndStopsSubmitting`,
> `whenFinalConfirmDisabilityRequestFails_showsToastAndStopsSubmitting`, and
> `whenCommissionRecordNextClickedWithObjection_staysOnStep` cover the previously-missing scenarios,
> and a new `DisabilityPensionDocumentUploadTest.kt` (Robolectric-based) covers all four document-upload
> outcomes (valid JPEG, wrong extension, oversized, duplicate content). All the new tests are
> well-targeted at exactly what was asked — but see item 3: 5 of these new/updated tests currently
> fail because of that round's regression, not because of a coverage gap.

## 5. Landline phone validation tightened to exactly 11 digits — Low, needs confirmation

**File:** `feature/pensioner/src/commonMain/kotlin/com/tamin/taminhamrah/feature/pensionInquiry/ui/disabilityPension/DisabilityPensionViewModel.kt:713`

```kotlin
LandlinePhoneError.InvalidLength.takeIf { value.length != LANDLINE_PHONE_LENGTH }
```

`old_android`'s equivalent gate (`DisabilityPensionFragment.kt:673`) only rejects `phone.length < 11`
— a number longer than 11 digits was accepted by the legacy client. The new code requires **exactly**
11. Real Iranian landline numbers (with the leading `0`) are always 11 digits, so this is likely a
correct tightening rather than a regression, but it is a stricter rule than what's being ported.

**Suggested change:** not blocking — confirm this was an intentional tightening (it reads like a
reasonable one) and this can be marked accepted.

## What was done well

- **The 7-step wizard and its submit chain are a genuinely accurate port.** Status codes `"3"`/`"4"`/
  `"0"` for save-info/save-document/final-confirm match `old_android`'s `DisabilityPensionDataModel`
  comments and `saveAndConfirmRequest()` exactly, and the call order is preserved.
- **`DisabilityRelationClassifier.kt` is a careful, well-documented port** of legacy
  `Utility.getTendencyResId`'s relation-title logic, using string resources and named gender-code
  constants correctly — worth pointing at as the model for fixing item 3.
- **The registered-medical-commission step correctly mirrors legacy's read-only, no-branching
  behavior** — `old_android`'s `RegisteredRequestFragment`/`RegisteredRequestAdapter` is a plain
  list with an empty click handler, and the new step matches that shape.
- **MVI and navigation conventions are followed correctly** — `DisabilityPensionViewModel` extends
  `BaseViewModel<UiState, PartialState, Event, Intent>` with all input through `sendIntent`, and
  navigation to the add-dependent feature goes through an `onNavigateToAddDependent` callback, not a
  direct cross-feature import.
- **No commented-out code anywhere in the diff**, and the temporary mock module used during
  development (`DisabilityPensionMockModule`) was correctly removed before submission.
- **Almost every Persian string in this large diff correctly goes through `strings.xml`** — the
  handful of literals in item 3 are the exception, not the pattern, and the ones in `@Preview` mock
  data (several step-content files) are the standard, accepted exception for preview fixtures.
