## 1. Every pension record is shown as an "active pensioner", regardless of `statusDesc` — High

**File:** `feature/pensionStatusInquiry/src/commonMain/kotlin/com/tamin/taminhamrah/feature/pensionStatusInquiry/ui/components/PensionStatusCard.kt:145-174`

```kotlin
@Composable
private fun StatusHeader() {
    val colors = LocalTaminColors.current
    Row(
        modifier = Modifier
            .fillMaxWidth()
            .background(colors.greenBg)
            ...
    ) {
        ...
        Text(
            text = stringResource(Res.string.pension_status_active_header),
            ...
            color = colors.springGreenText,
        )
        OrganizationBadge()
    }
}
```

`StatusHeader()` takes no parameters and unconditionally renders the green "active pensioner"
header + a green "verified" `OrganizationBadge()` for every card. `item.statusDesc` — present on
`PensionInquiryDN`/`PensionInquiryPR` and carried all the way from the DTO — is never read
anywhere in `PensionStatusCard.kt`, `PensionStatusInquiryScreen.kt`, or
`PensionStatusInquiryViewModel.kt`; I checked the full call chain (`PensionRepositoryImpl.getPensionInquiry`
→ `GetPensionInquiryUseCase` → the ViewModel's `handleLoad()`) and confirmed the list is never
filtered by status either — whatever the server returns is rendered as-is.

`old_android`'s `InquirePensionStatusAdapter` treats this as the screen's one conditional UI state:
`statusDesc == "01"` → active pensioner (green stamp/badge, "you are a pensioner"),
anything else → not a pensioner (red badge, different label). That distinction is completely
absent here.

**Concrete failure scenario:** a user whose pension record has a non-`"01"` `statusDesc` (e.g. a
suspended or terminated pension, or someone who queries a relation's record that isn't actually
active) opens this screen and sees a green "you are an active pensioner" badge anyway — the exact
opposite of what `old_android` would have shown them for the same data.

> **مغایرت بیزینسی:** در نسخه‌ی قدیمی، وضعیت هر رکورد مستمری بر اساس مقدار فیلد `statusDesc`
> تعیین می‌شد: اگر مقدار آن `"01"` بود، کاربر با یک نشان سبزرنگ «شما مستمری‌بگیر فعال هستید»
> مواجه می‌شد؛ در غیر این صورت (هر مقدار دیگری) نشان قرمزرنگ «شما مستمری‌بگیر نیستید» نمایش داده
> می‌شد. در نسخه‌ی جدید، این تفاوت به‌کلی حذف شده و مقدار `statusDesc` هیچ‌جا در نمایش کارت بررسی
> نمی‌شود — همه‌ی رکوردها، صرف‌نظر از وضعیت واقعی‌شان، با همان نشان سبز «مستمری‌بگیر فعال» نمایش
> داده می‌شوند. یعنی کاربری که در واقعیت مستمری‌بگیر فعال نیست هم پیام نادرستی مبنی بر فعال بودن
> وضعیتش می‌بیند.

**Suggested change:** branch `StatusHeader()` (and `OrganizationBadge()`'s copy/colors) on
`item.statusDesc == "01"`, matching `old_android`'s convention, with a distinct visual treatment
(e.g. red/neutral) for the non-active case.

> این حلقه‌ی گمشده هیچ تستی هم ندارد — هیچ‌کدام از تست‌های `PensionStatusInquiryViewModelTest.kt`
> مقدار `statusDesc` را متفاوت از «فعال» قرار نمی‌دهند، بنابراین نبود این شاخه از منطق در حین
> نوشتن تست هم دیده نشده است.

## 2. Send-certificate skips old_android's recipient-branch search step — Low, needs confirmation

**File:** `feature/pensionStatusInquiry/src/commonMain/kotlin/com/tamin/taminhamrah/feature/pensionStatusInquiry/ui/PensionStatusInquiryViewModel.kt:52-73`

```kotlin
private fun handleSendCertificate(item: PensionInquiryPR): Flow<PartialState> = flow {
    ...
    val filters = listOf(
        ApiFilterDN(FilterProperty.PENSIONER_ID, pensionerId, FilterOperator.EQUAL),
    )
    sendRequestInquirePensionCertificateUseCase(filters).collect { result -> ... }
}
```

Tapping "send certificate" fires the request immediately with just a `PENSIONER_ID` filter.
`old_android`'s equivalent (`CertificateToInboxInquireDialogFragment`) opens a bottom sheet where
the user searches for and picks a **recipient branch** first (`getBranchRequests`/autocomplete),
then calls `sendRequestInquirePensionCertificate(recipientName)` with that choice.

I'm flagging this as needs-confirmation rather than a definite bug: `SendRequestInquirePensionCertificateUseCase`
and its filter-based contract already existed before this MR (not part of this diff), and the same
pattern (`active_relation_send_certificate` string, no visible recipient picker) appears to be an
established convention elsewhere in this codebase already — so the recipient may now be resolved
server-side, making `old_android`'s manual branch search obsolete. I could not confirm either way
from what's in this MR.

**Suggested change:** confirm with backend/product whether the certificate's recipient is resolved
automatically now; if a recipient still needs to be chosen client-side, that step is missing here.

## What was done well

- The DN/DTO gained `pensionerId` and `pensionerTypeDesc` cleanly, with a `@JsonNames` fallback
  kept on `pensionerRisUid` for backward compatibility with the old serialized key — a careful
  touch for a field rename.
- `pensionerTypeLabel()`'s fallback mapping (`"101" -> "بازنشستگی"`) only kicks in when the server's
  own `pensionerTypeDesc` is blank, so it degrades gracefully rather than overriding real server
  data.
- The new `docs/vault/Theme.md` page and `HeaderDecoration` token in `Shape.kt` are a genuine
  addition to the design-token system (used by this screen's header), not just incidental noise —
  and `CLAUDE.md`'s table was updated to link it, per this repo's own "maintaining the vault" rule.
- Good breadth of ViewModel tests (`PensionStatusInquiryViewModelTest.kt`) covering load
  success/error, empty list, and the send-certificate success/error/blank-id paths.
- Deleting the old, already-stripped-down `feature/pensionInquiry` module in favor of a dedicated
  `feature/pensionStatusInquiry` matches this codebase's one-feature-per-module convention; the
  payroll/edict/personal-info/disability repository methods this module used to reference before
  its own earlier simplification are still present on `PensionRepository`, so nothing there looks
  lost — just not yet wrapped in their own feature module.
