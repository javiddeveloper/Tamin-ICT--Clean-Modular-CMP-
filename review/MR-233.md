## 1. History duration shown without carry-over normalization — Medium

**File:** `core/core-domain/src/commonMain/kotlin/com/tamin/taminhamrah/useCases/calculateWagePension/CalculateWagePensionUseCase.kt:36-38`

```kotlin
historyYears = firstItem?.historyYears ?: 0,
historyMonths = firstItem?.historyMonths ?: 0,
historyDays = firstItem?.historyDays ?: 0,
```

These three raw server fields are passed straight through to the UI
(`CalculateWagePensionScreen.kt:168-170` → the history-duration card), with no processing.

`old_android` never displays these raw fields directly — every call site runs them through
`Utility.normalizeHistoryDuration()` first:

```kotlin
// Utility.kt:1286-1306
fun normalizeHistoryDuration(historyYears: String?, historyMonths: String?, historyDays: String?): HistoryDuration {
    var years = historyYears?.toIntOrNull() ?: 0
    var months = historyMonths?.toIntOrNull() ?: 0
    val days = historyDays?.toIntOrNull() ?: 0

    months += days / 30
    val normalizedDays = days % 30

    years += months / 12
    val normalizedMonths = months % 12

    return HistoryDuration(years = years, months = normalizedMonths, days = normalizedDays)
}
```

```kotlin
// CalculateWagePensionFragment.kt:174-178 — the exact legacy screen this MR replaces
val normalizedDuration = Utility.normalizeHistoryDuration(
    list[0].historyYears, list[0].historyMonths, list[0].historyDays,
)
```

This function exists specifically because the server can return day/month values outside their
normal range (≥30 days, ≥12 months) — legacy always carries them over before display. The new code
skips this step entirely, so a server response like `historyMonths=13, historyDays=35` would show
literally "۱۳ ماه" and "۳۵ روز" to the user instead of the carried-over "۱ سال و ۱ ماه و ۵ روز" legacy
would have shown for the same data.

> **سناریوی بیزینسی جاافتاده:** نسخه‌ی قدیمی قبل از نمایش مدت سابقه (سال/ماه/روز)، همیشه این مقادیر را
> نرمال می‌کرد — اگر روزها به ۳۰ یا بیشتر می‌رسید به ماه تبدیل می‌شد، و اگر ماه‌ها به ۱۲ یا بیشتر
> می‌رسید به سال تبدیل می‌شد. نسخه‌ی جدید این مرحله را ندارد و دقیقاً همان عددی که سرور برمی‌گرداند را
> نشان می‌دهد. اگر سرور مقادیر ماه یا روز بزرگ‌تر از بازه‌ی معمول برگرداند (که طبق تابع نسخه‌ی قدیمی،
> این اتفاق واقعاً می‌افتاده)، کاربر عددی نادرست و گمراه‌کننده برای مدت سابقه‌اش می‌بیند.

**Suggested change:** port `normalizeHistoryDuration`'s carry-over logic into
`CalculateWagePensionUseCase` (or a shared utility, since it's a generic duration-normalization
concern) before setting `historyYears`/`historyMonths`/`historyDays` on the domain model.

## 2. Empty insurance history still calls the wage endpoint — Low, needs confirmation

**File:** `feature/calculateWagePension/src/commonMain/kotlin/com/tamin/taminhamrah/feature/calculateWagePension/ui/CalculateWagePensionViewModel.kt:68-78`

```kotlin
private suspend fun FlowCollector<PartialState>.loadCalculation() {
    if (uiState.value.isLoading) return
    emit(PartialState.Loading(true))
    val talfigh = getTalfighInfosUseCase()
    val dastmozd = getDastmozdInfosUseCase()
    val calculation = calculateWagePensionUseCase(talfigh, dastmozd).toPresentation()
    ...
}
```

Both use cases are always called, unconditionally.

`old_android`'s equivalent (`CalculateWagePensionFragment.kt:165-193`, `showResultCombinedList`)
returns immediately if the insurance-history list is empty — `getWageAndInsuranceHistory()` (the
`dastmozd`/wage-history call) is never reached in that case, and the screen simply shows nothing:

```kotlin
result.data?.list?.let { list ->
    if (list.isEmpty()) return   // non-local return — exits the whole function
    ...
}
...
mViewModel.getWageAndInsuranceHistory()   // never reached if list was empty
```

The new code has no equivalent short-circuit — a user with no insurance history at all will still
trigger the wage-history call. If that endpoint errors for a user with no history (plausible, since
legacy never exercised this path), the new screen shows an error toast where legacy silently showed
an empty page.

**Suggested change:** confirm whether an insured member can genuinely have zero `talfigh` history in
practice (if not, this is moot). If it can happen, consider adding an explicit empty-state guard
before calling `getDastmozdInfosUseCase`, mirroring legacy's short-circuit — or, if showing an error
in that case is an acceptable/intentional improvement, this can be marked accepted.

**File:** `feature/calculateWagePension/src/commonTest` (does not exist)

anywhere in this module. `CalculateWagePensionUseCaseTest.kt` (in `core-domain`, unchanged by this
MR) covers the calculation formula itself well, but nothing exercises
`CalculateWagePensionViewModel`'s intent handling. Untested, business-relevant behavior:

- The "concurrent multiple workshops" toggle's three distinct outcomes: the check result is "no"
  (shows the info dialog, restores the base amount), the check succeeds and recalculates
  (`DisplayedAmountChanged` should reflect the new amount), and a mid-flow failure (should disable
  the toggle and restore the base amount — the `catch` block at
  `CalculateWagePensionViewModel.kt:101-106` that does this has no test pinning it).
- Toggling the switch back off (`disableMultipleWorkshops`).
- The initial load path and its error/retry path.
- The empty-history scenario from item 2, once resolved.

> **سناریوهای بیزینسی جاافتاده:** برای سوییچ «اشتغال همزمان در چند کارگاه» هیچ تستی نوشته نشده — نه
> حالتی که کاربر واجد شرایط این حالت نیست (و باید دیالوگ اطلاع‌رسانی نشان داده و مبلغ به حالت پایه
> برگردد)، نه حالت موفق (که باید مبلغ مستمری را با مبلغ جدید جایگزین کند)، و نه حالتی که در میانه‌ی
> این فرآیند خطا رخ بدهد (که باید سوییچ خاموش شده و مبلغ به حالت پایه برگردد).

**Suggested change:** add a `CalculateWagePensionViewModelTest.kt` covering at minimum the load path
and all three multiple-workshops outcomes.
