## 2. «تاریخ تعهد» field choice — withdrawn (reviewer error)

**Round 1 claimed** the tile should read `commitmentDate` (`letDate`) instead of `startDate`, citing
`EmployerAgreementResponse.createKeyValueMain` in `old_android` (`KeyValueModel("تاریخ تعهد",
it.letDate ?: "-")`) as the legacy binding, and citing `EmployerWorkshopListFragment` as
**unreachable** in the legacy nav graph — which would have made that citation moot regardless.

**The developer's round-2 response, recorded in `ContractRowUiMapperTest.kt`, is correct, and both of

- `EmployerWorkshopListFragment` **is reachable.** `navigation_home.xml:1707-1711` declares

  that action. Round 1's "no incoming action at all" was a misreading of the nav graph.
- That fragment's own layout, `list_item_employer_workshop.xml:159-173`, binds the «تاریخ تعهد»
  label directly to `item.getLocalDate(item.startdate)` — **not** `letDate` — via live data binding
  (`EmployerWorkshopAdapter.bindItem` does nothing but `binding.item = item`, so this binding is what
  actually renders).
- By contrast, `EmployerAgreementResponse.createKeyValueMain(list)` — the function round 1 quoted —
  is dead code: `grep` across `ui/home/services/employer/` shows it is never called anywhere in
  `old_android`. Round 1's evidence came from a function the legacy app itself never executes.

So the reachable legacy screen that is the true equivalent of this tab reads `startdate` for «تاریخ
تعهد», matching what this MR already does. `EmployerInfoMapper.kt:84` (`letDate = commitmentDate…`),
which round 1 also cited as "elsewhere in the project", is a different screen (کارفرما اطلاعات) built
from a different DN and is not evidence about this one.

**Recorded as withdrawn, not rejected** — this was not a judgment call the developer disagreed with,
it was a factual error in the round-1 review. Thank you for checking rather than just complying with
the "fix" quietly.

## 3. Tab guessing — Medium → fixed

**File:** `feature/workshops/.../contractRows/ContractRowsViewModel.kt`

**Fix:** option (a) from round 1's suggestion, implemented as an automatic one-shot fallback rather
than a static preselection — which turns out to be the better of the two, since it also covers the
hand-typed-کد-کارگاه case round 1 called out as the one way a workshop *could* land in the
"wrong-category" guess:

- `loadPage(allowFallback = true)` on a first page that comes back empty re-requests the other
  service once (`tab.other()`), and only once — the fallback call itself passes `allowFallback =
  false`, so two genuinely empty services settle on the empty state instead of ping-ponging.
- A tab the user picks by hand (`selectTab`) passes `allowFallback = false`: a deliberate choice is
  final, never silently overridden.
- `didAutoSwitchTab` drives a small notice (`contract_rows_tab_switched` — «این کارگاه در دستهٔ
  دیگری ثبت شده است.») so the user is told the tab moved rather than discovering it by the heading
  having quietly changed.
- Tests: `an empty first tab falls back to the other one`, `both services empty settles without
  switching back`, `a deliberate tab choice does not fall back` — the three cases that matter.

Closed. See item 7 for a related concurrency defect this change's own mechanism opens up.

## What was found and fixed beyond the six original items

Two defects the developer's own device testing turned up, not part of round 1:

- **A failed list rendered as a blank empty page.** `PagedListState` had exactly three named states
  (`isFirstLoad`, `isEmpty`, loading-more) and no branch for "failed with nothing to show" — `error
  != null && items.isEmpty()` fell through to the empty-list rendering, so a 404 or a network error
  looked identical to "this workshop genuinely has no rows." Fixed by adding `isFailed` as an
  explicit fourth state, checked in `WorkshopListScaffold` before the empty branch, with its own
  `EmptyStateMessage` (warning icon, the service's own error text or a generic fallback, an optional
  retry action). `ContractRowsScreen` and `WorkshopsScreen` both now wire a retry intent through it.
- **The picker sheet had no scroll of its own.** `کارگاه‌های شما` can run to a full page of quick-pick
  rows, and on a short screen that pushed «مشاهدهٔ ردیف پیمان‌ها» past the visible area with nothing
  to scroll it into view. Fixed with `.verticalScroll(rememberScrollState())` on the sheet's column
  — a plain scroll rather than a lazy list, correctly reasoned in the inline comment: the content is
  bounded at one page, and a lazy list inside an already-scrolling sheet would nest two scrollers.

Both are good catches and both fixes are small and correctly scoped. No action needed on either.

## 7. Rapid tab switching can show stale rows under the wrong heading — Medium — new

**File:** `feature/workshops/src/commonMain/kotlin/com/tamin/taminhamrah/feature/workshops/ui/contractRows/ContractRowsViewModel.kt` (`selectTab`, `loadPage`) ·
`core/core-ui/.../base/BaseViewModel.kt:31` (`flatMapMerge`)

This is not something round 2 introduced — the same shape existed in round 1's code — but item 3's
fallback logic depends on the same mechanism, so it is reported here rather than as a separate note.

`BaseViewModel` dispatches intents through `flatMapMerge`, not `flatMapLatest`:

```kotlin
.flatMapMerge { intent -> handleIntent(intent) }
```

so two intents in flight run **concurrently**; a later one does not cancel an earlier one still
waiting on the network. `selectTab` does:

```kotlin
emit(PartialState.TabChanged(tab))
emitAll(loadPage(page = 0, filter = filter, tab = tab, allowFallback = false))
```

and the reducer for `PartialState.Loaded` is unconditional:

```kotlin
is PartialState.Loaded -> currentState.copy(list = partialState.list)
```

**Failure scenario:** the user taps «دارای تعهدنامه» then, before that request returns, taps «بدون
تعهدنامه». Both `loadPage` calls are now in flight. If the first (دارای تعهدنامه) request happens to
resolve *after* the second, its `Loaded` list overwrites the rows the second request already placed
on screen — the header still reads «بدون تعهدنامه» (`state.tab` was last set by the second
`TabChanged`), but the rows underneath belong to «دارای تعهدنامه». Nothing re-fetches to correct it;
the mismatch is permanent until the next tab switch or filter change.

The same race is reachable through the auto-fallback path in a narrower window: `loadPage`'s
recursive fallback call and a manual tab tap racing each other, though the one-shot `allowFallback =
false` on the recursive call limits how far that specific case can compound.

**Suggested change:** tag each `loadPage` emission with the tab (or a generation counter) it was
requested for, and drop it in the reducer if it no longer matches `currentState.tab`/the current
generation when it arrives — the same shape `didAutoSwitchTab` already uses to know which switch is
"current." Alternatively, route tab-changing intents through `flatMapLatest` specifically (most
ViewModels in this codebase that show this shape would benefit from the same fix, so this may be
worth raising as a `BaseViewModel`-level concern rather than a per-screen patch).

## 8. The row-count chip shows loaded-so-far, not the server's total — Low — new

**File:** `feature/workshops/.../contractRows/ContractRowsScreen.kt` (`contract_rows_count`) ·
`feature/workshops/.../model/PagedListState.kt`

```kotlin
stringResource(Res.string.contract_rows_count, list.items.size.toString().toPersianDigits())
```

`PagedListDN.total` — the server's grand total, already used by `hasMoreAfter()` to decide whether
another page exists — is never carried into `PagedListState` or surfaced to the UI. The chip reads
«N ردیف پیمان» using `items.size`, which only reflects what has been paged in so far. As the user
scrolls and more pages load, the number visibly climbs — which is more likely to read as "the count
was wrong at first" than as "you are seeing more of the total," since nothing distinguishes "N so
far" from "N total."

Not introduced by this round's fixes — the same field reference existed in round 1's code.

**Suggested change:** carry `total` through `PagedListState.loaded()` and either show it directly
(«N از M ردیف پیمان») once the first page lands, or drop the running count until all pages are in
if a partial number is not meant to be shown at all.

## 9. کارگاه‌های شما quick-pick never asks for a second page — Low — new

**File:** `feature/workshops/.../contractRows/ContractRowsViewModel.kt` (`loadMyWorkshops`)

```kotlin
val workshops = getMyWorkshops(WorkshopListQuery(page = 0))
```

`WORKSHOP_PAGE_SIZE` is 10. An employer holding more than 10 agreements will never see the 11th
onward in the «کارگاه‌های شما» quick-pick sheet — there is no follow-up request and no indication
that the list is partial. The two text fields still work for any workshop by number, so this is a
convenience gap rather than something the user is blocked by, which is why it is Low rather than
Medium — but for an employer with many workshops the "quick" pick quietly stops being complete.

**Suggested change:** either page it (the sheet already scrolls, per the round-2 fix above, so
appending is straightforward), or — cheaper — show a "و بیشتر…" affordance once `hasMoreAfter` would
be true, so the cap is visible rather than silent.
