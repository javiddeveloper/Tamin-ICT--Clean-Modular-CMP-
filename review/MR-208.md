## 1. کد شعبه is offered as optional, but it is a path segment — Medium

**File:** `feature/workshops/.../contractRows/ContractRowsViewModel.kt:173-188`,
`.../components/ContractRowPickerSheet.kt:181`

```kotlin
val workshopId = state.draftWorkshopId.trim()
if (workshopId.isBlank()) {
    emit(PartialState.WorkshopIdErrorChanged(isVisible = true))
    return@flow
}

val filter = ContractRowFilter(workshopId, state.draftBranchCode.trim())
```

Only کد کارگاه is validated. کد شعبه is labelled `contract_rows_branch_code_optional`
(«کد شعبه (اختیاری)») and a blank one is passed straight through to:

```kotlin
@GET(".../get-employer-agreement-by-workshop-id-and-branch-code/{workshopId}/{branchCode}")
@GET(".../contract-employer-workshop-info-with-workshop-and-branch-code/{workshopId}/{branchCode}")
```

Both take it as `@Path`, not `@Query`. The MR's own comments say exactly why that matters — twice:

- `ContractRowsViewModel.kt:169-172`: *"کد کارگاه is the one required field — it is a path segment,
  so a blank one would request a different route entirely."* The same sentence is true of کد شعبه.
- `WorkshopConstants.kt:27-34`: *"these two are **path segments** on both contract-row endpoints, so
  a value the wrong length does not narrow the request — it addresses a different route."*

The reasoning is applied to one of the two codes it was written about.

`old_android` requires both before it fetches anything — in both screens, identically
(`WorkshopContractListFragment.kt:42-51`, `EmployerWorkshopListFragment.kt:44-53`):

```kotlin
val workshopCode = arguments?.getString(mViewModel.ARG_WORKSHOP_ID)
val branchCode = arguments?.getString(mViewModel.ARG_BRANCH_CODE)
if (!workshopCode.isNullOrBlank() && !branchCode.isNullOrBlank()) { … }
```

**Failure scenario:** the user opens ردیف‌های پیمان from the services grid, types a کد کارگاه, leaves
the field the UI told them is optional empty, and taps «مشاهدهٔ ردیف پیمان‌ها». The request goes to
`…/get-employer-agreement-by-workshop-id-and-branch-code/9028212822/` — a trailing empty segment —
and the screen shows a network error rather than the rows.

The test at `ContractRowsViewModelTest.kt:164-179` codifies the current behaviour with the comment
*"The branch is optional — the service accepts the workshop on its own"*, but it only asserts
ViewModel state — it never checks that a well-formed request is produced, so it cannot support that
claim about the service.

> **مغایرت بیزینسی:** در نسخه‌ی قدیمی، لیست ردیف پیمان تا وقتی **هر دو** مقدار «کد کارگاه» و
> «کد شعبه» پر نباشند اصلاً درخواستی نمی‌فرستد — در هر دو صفحه‌ی معادل دقیقاً همین شرط گذاشته شده.
> در کد جدید «کد شعبه» به کاربر به‌عنوان فیلد اختیاری معرفی شده، ولی این مقدار بخشی از **آدرس**
> سرویس است نه یک فیلتر. یعنی اگر کاربر آن را خالی بگذارد، آدرس ناقصی ساخته می‌شود و به‌جای لیست
> ردیف پیمان‌ها خطا می‌بیند.

**Suggested change:** either require کد شعبه the same way کد کارگاه is required (and drop
«(اختیاری)» from the label), or — if the service really does accept the workshop alone — verify that
against the live endpoint and record the evidence in the test, since the current test does not
establish it. Marked `⬜ needs confirmation` for that reason; if the service rejects the call this
is High, because it is the normal path for the services-grid entry.

## 2. The «تاریخ تعهد» tile is filled from `startDate` — Medium

**File:** `core/core-ui/src/commonMain/kotlin/com/tamin/taminhamrah/mapper/workshop/WorkshopUiMapper.kt:85`

```kotlin
fun EmployerAgreementDN.toContractRow(): ContractRowPR = ContractRowPR(
    …
    commitmentDate = startDate.orDashDate(),
```

`EmployerAgreementDN` carries **both** dates:

```kotlin
val startDate: String = "",        // wire: startdate
val commitmentDate: String = "",   // wire: letDate
```

and the card labels the tile `contract_rows_commitment_date` = «تاریخ تعهد»
(`ContractRowCard.kt:98-101`). Elsewhere in the project, the تعهدنامه date is read from the other
field — `EmployerInfoMapper.kt:84`:

```kotlin
letDate = commitmentDate.ifBlank { workshop.approveDate }.toFormattedDate(),
```

while `startDate` is what feeds `WorkshopPR.startDate`, drawn as the workshop's own start date on
جزئیات کارگاه (`WorkshopUiMapper.kt:61`, `WorkshopDetailScreen.kt:145`).

So the same `EmployerAgreementDN` currently yields «تاریخ تعهد» from `letDate` on one screen and
from `startdate` on the other. One of the two is wrong.

The mapper test fixture (`ContractRowUiMapperTest.kt:20-31`) sets `startDate` and leaves
`commitmentDate` unset, then asserts the formatted `startDate` — so the choice is deliberate and
locked in by a test, but the test cannot tell the two apart either.

Note this applies only to the «دارای تعهدنامه» tab. On the lean endpoint there is no `letDate` at
all and `startDate` genuinely is تاریخ تعهد, as `WorkshopContractDN` documents — that mapping is
fine.

> **مغایرت بیزینسی:** روی تب «دارای تعهدنامه»، کاشی‌ای که برچسبش «تاریخ تعهد» است مقدارش را از
> «تاریخ شروع» می‌گیرد، نه از تاریخ تعهدنامه. سرویس هر دو تاریخ را می‌فرستد و در جای دیگر همین
> پروژه (صفحهٔ اطلاعات کارفرما) تاریخ تعهدنامه از فیلد درست خوانده می‌شود. نتیجه این‌که کاربر
> ممکن است تاریخی را به‌عنوان تاریخ تعهد ببیند که در واقع تاریخ شروع کارگاه است — عددی که کاملاً
> منطقی به نظر می‌رسد و به همین دلیل اشتباهش دیده نمی‌شود.

**Suggested change:** use `commitmentDate` for that tile (falling back to `startDate` only if the
service is known to leave `letDate` empty on this endpoint), and set both fields in the test fixture
so the assertion distinguishes them.

## 3. The two tabs make the user guess which service holds their rows — Medium

**File:** `feature/workshops/.../contractRows/contract/ContractRowsContract.kt:23-35`

The screen presents «دارای تعهدنامه» and «بدون تعهدنامه» as two tabs the user chooses between. A
given workshop is in exactly one of those categories, so one tab is always empty — and the empty
state says so out loud (`contract_rows_empty_none_body`):

> «برای این کارگاه در این دسته ردیف پیمانی ثبت نشده است. دستهٔ دیگر یا کد کارگاه دیگری را بررسی کنید.»

That is the design telling the user to try the other tab, which is work the app can do for them.
Concretely, for both of the ways into this screen the answer is already known:

- **Drill-down from جزئیات کارگاه** — the workshop list it comes from is
  `GetEmployerAgreementsUseCase` (کارگاه‌های کارفرما), i.e. workshops that *have* an agreement. The
  «بدون تعهدنامه» tab is therefore always empty on this path.
- **کارگاه‌های شما quick-pick** — the same use case (`ContractRowsViewModel.kt:35, 155`), so the same
  holds.

Only a hand-typed کد کارگاه can land in the other category.

`old_android` never asks. The tab is decided by where the user came from: the only live path is
`EmployerAgreementFragment` step 2, which lists workshops **without** a تعهدنامه and opens
`WorkshopContractListFragment` on the lean endpoint (`EmployerAgreementFragment.kt:295-315`). The
other screen, `EmployerWorkshopListFragment`, is declared in `navigation_home.xml:1769-1773` with no
incoming action at all — it is unreachable in the legacy app.

> **مغایرت بیزینسی:** یک کارگاه یا تعهدنامه دارد یا ندارد — نمی‌تواند هر دو باشد. در نسخه‌ی قدیمی
> کاربر هیچ‌وقت این را انتخاب نمی‌کرد؛ مسیر ورود مشخص می‌کرد کدام سرویس صدا زده شود. در کد جدید
> کاربر باید خودش حدس بزند و اگر تب اشتباه را انتخاب کند لیست خالی می‌بیند و باید تب دیگر را هم
> امتحان کند. بدتر این‌که در هر دو مسیر ورودِ فعلی (ورود از جزئیات کارگاه و انتخاب از «کارگاه‌های
> شما») کارگاه از فهرست کارگاه‌های دارای تعهدنامه می‌آید، یعنی تب «بدون تعهدنامه» همیشه خالی است.

**Suggested change:** two options, either is fine —
(a) keep one list and pick the endpoint from what is already known about the workshop, falling back
to the other when the first returns nothing; or
(b) keep the tabs but preselect the right one for the entry point, so the user only switches
deliberately. The `ContractRowTab` table is a good place for that decision to live.

## 4. The workshop-detail action ignores `FeatureFlag.CONTRACT_INFO` — Low

**File:** `feature/workshops/.../ui/detail/WorkshopDetailScreen.kt:198-201`

```kotlin
// Declaration order is menu order — see WorkshopAction.
WorkshopAction.entries.forEach { action ->
    WorkshopActionRow(action = action, onClick = { onAction(action) })
}
```

The services-grid entry goes through `FeatureFlag.CONTRACT_INFO`
(`FeatureNavigation.kt:40-41`), so the server can disable ردیف‌های پیمان there. The
workshop-detail row is rendered unconditionally, so the same service stays reachable from the other
entry point when the server has turned it off.

The pre-existing `PAYMENT_SHEETS` row has the same shape, so this is a pattern carried forward
rather than introduced here — but this MR is what makes it a two-entry-point feature with a flag
that only one of them honours.

**Suggested change:** filter `WorkshopAction.entries` by the feature flag each action maps to.

## 5. Drill-down navigates without checking `hasIdentity` — Low

**File:** `feature/workshops/.../ui/WorkshopsViewModel.kt:141-153`

```kotlin
private fun selectAction(action: WorkshopAction, workshop: WorkshopPR): Flow<PartialState> = flow {
    sendEvent(workshop.navigationEvent(action))
}
```

`WorkshopSummaryDN.hasIdentity` exists and is documented as *"Both halves present is the
precondition for every action on this workshop"*, but nothing checks it here. A row missing either
half opens ردیف‌های پیمان with a blank code — the same broken request as item 1, reached from the
other direction.

Carried forward from `PAYMENT_SHEETS`, not introduced by this MR.

**Suggested change:** guard on `hasIdentity` before sending the navigation event, or disable the
action rows for a workshop that lacks it.

## What was done well

This is a carefully built MR — the reasoning is written down where it is not obvious from the code,
and it is the kind of documentation that survives contact with the service.

- **The wire-name divergence is documented rather than tidied away.** `EmployerAgreementDTO` and
  `WorkshopContractDTO` describe the same concept under different spellings (`pymseq` vs
  `contractRow`, `startdate` vs `startDate`), and both classes say so explicitly, including *why*
  the two DTOs cannot be merged: the nested workshop object is a different shape on each endpoint
  (`character`/`workshopStatus` as bare strings on one, as objects on the other). That is exactly
  the note a future reader needs before "simplifying" them into one.
- **Two use cases instead of one with a boolean**, with the reasoning stated —
  *"they return different domain models, so a single entry point would have to hand back a union the
  caller unpacks anyway."*
- **The mapper folds both sources into one card model**, so nothing below the tab has to branch —
  and `ContractRowPR` documents the one deliberate asymmetry (mobile/email dash, address blank so
  its tile is dropped).
- **`WorkshopListScaffold` was extended, not forked** — one optional `empty` slot, defaulting to the
  existing behaviour for every current caller.
- **Test coverage is genuinely good**: 15 ViewModel tests covering pagination (first page, append,
  exhausted list), tab switching, the picker, and both error paths — including the deliberate
  "a failing کارگاه‌های شما must not fail the screen" case. The fake records `lastContractRowQuery`,
  so the pagination tests assert the page number that actually reaches the repository rather than
  just the resulting state. Plus 5 UI-mapper and 5 data-mapper tests, one of which specifically
  pins down that ردیف پیمان is read from the agreement and not from the workshop nested inside it.
- **Conventions followed throughout**: `@Immutable` on the state and PR models, `ImmutableList` for
  the quick-pick list, `toSingleLineMessage()` for errors, `PagedListState` reused rather than
  re-implemented, all copy in `strings.xml` with no hardcoded Persian in Kotlin, and no
  commented-out code anywhere in the diff.
- **Everything landed in `:feature:workshops`** — one module, packages for the new screen, matching
  how `:feature:pensioner` and `:feature:taminServices` are organised.
- The branch is already merged up with `develop`, so there is nothing to resolve before merge.
