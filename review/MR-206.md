## 1. Payment flow skips a ticket-activation call before opening the payment page — High, needs confirmation

**Files:** `core/core-domain/src/commonMain/kotlin/.../useCases/workshops/WorkshopDebitUseCases.kt:43-49`,
`core/core-data/src/commonMain/kotlin/.../mapper/WorkshopMapper.kt:182-190`

```kotlin
// WorkshopDebitUseCases.kt
class PayWorkshopDebitUseCase(private val repository: WorkShopsRepository) {
    suspend operator fun invoke(request: DebitPaymentRequestDN): DebitPaymentDN {
        val preCheck = repository.checkDebitPayment(request.debitNumber, request.branchCode)
        if (!preCheck.allowed) return DebitPaymentDN(succeeded = false)
        return repository.payWorkshopDebit(request)
    }
}

// WorkshopMapper.kt
private const val TFH_PAYMENT_PAGE = "https://tfh.tamin.ir/view/#/payment/"

fun DebitPaymentDTO.toDomain(): DebitPaymentDN {
    val ticket = paymentTicket?.takeIf { it.isNotBlank() }
    return DebitPaymentDN(
        ...
        paymentPageUrl = ticket?.let { TFH_PAYMENT_PAGE + it }.orEmpty(),
    )
}
```

`old_android`'s equivalent flow (`WorkshopInfoViewModel.kt:308-377`) is three network calls, not
two:

1. `checkPaymentStatus` → pre-check gate (matches `checkDebitPayment` here).
2. `normalDebitPayment` → returns a `paymentTicket`/`paymentURL`.
3. `normalDebitPaymentPreview` → takes that ticket and calls a **third, distinct endpoint**,
   `Constants.TFH_URL + "ticket/current-user/" + ticket` (`https://tfh.tamin.ir/api/v1.1/payment/ticket/current-user/{ticket}`)
   — a real round-trip to the TFH payment gateway itself, gated on `result.isSuccess` before the
   screen is allowed to open the payment page. Only *after* that call succeeds does the fragment
   build the final URL, `Constants.TFH_PAYMENT_VIEW_PAGE + ticket` (same-looking, but only reached
   past step 3).

This MR's `PayWorkshopDebitUseCase` stops after step 2 and builds `paymentPageUrl` straight from
`payWorkshopDebit`'s own `paymentTicket` — step 3 (`ticket/current-user/`) is never called
anywhere in this diff. If that endpoint does nothing but echo the ticket back, this is a harmless,
even beneficial, simplification (one fewer round-trip). But its URL path (`ticket/current-user/`)
reads like it *associates* the ticket with the currently signed-in user/session on the gateway
side — in which case a browser opened straight to `TFH_PAYMENT_PAGE + ticket` without that call
could be rejected by the TFH payment gateway as an unrecognized/unbound ticket. I can't tell which
from the client code alone.

> **یافته‌ی بیزینسی (فارسی):** برای پرداخت آنلاین بدهی، نسخه‌ی قدیمی بعد از گرفتن bilet پرداخت،
> یک درخواست سوم هم به درگاه TFH می‌زنه (`ticket/current-user/...`) و فقط اگه اون موفق باشه صفحه‌ی
> پرداخت رو باز می‌کنه. در پیاده‌سازی جدید این مرحله‌ی سوم اصلاً زده نمی‌شه و لینک پرداخت مستقیماً
> از تیکت مرحله‌ی دوم ساخته می‌شه. اگه این تماس سوم فقط برای «متصل کردن تیکت به کاربر جاری در
> درگاه» بوده، ممکنه با حذفش کاربر وقتی وارد صفحه‌ی پرداخت می‌شه با خطای «تیکت نامعتبر» یا مشابه
> مواجه بشه — این چیزیه که فقط با تست واقعی روی درگاه TFH قابل تأیید یا رد کردنه.

**Suggested change:** confirm with whoever owns the TFH payment integration whether
`ticket/current-user/{ticket}` has a required server-side side effect beyond echoing data back. If
it does, add it as a third step in `PayWorkshopDebitUseCase` before building `paymentPageUrl`. If
it's confirmed to be redundant against the current backend, leave a comment in
`PayWorkshopDebitUseCase` saying so explicitly (so the next reader doesn't have to re-derive this
from `old_android` again) and this can be marked rejected.

> **Round 2 — ✅ fixed.** `PayWorkshopDebitUseCase` now calls `repository.confirmPaymentTicket(payment.ticket)`
> as a third step after a payable `payWorkshopDebit` result, before returning. That call
> (`WorkShopsRemoteDataSourceImpl.confirmPaymentTicket`) hits
> `NetworkConstants.BASE_URL_TFH + NetworkConstants.TFH_TICKET_PATH + ticket` =
> `https://tfh.tamin.ir/api/v1.1/payment/ticket/current-user/{ticket}` — byte-for-byte the endpoint
> `old_android`'s `normalDebitPaymentPreview()` calls. It goes further than the suggestion asked:
> where the legacy fragment read `result.isSuccess` with no `else` (a refused ticket just left the
> pay button doing nothing), the new code throws on a refusal and the caller reports it like any
> other payment failure — a real improvement over the legacy behaviour, not just a port of it. The
> class's own KDoc documents this reasoning in place, so the next reader doesn't have to re-derive it
> from `old_android`.

## 2. New legal-person identity fields have no wiring test — Medium

**File:** `feature/workshops/src/commonTest/kotlin/com/tamin/taminhamrah/feature/workshops/ui/workshopDebit/WorkshopDebitViewModelTest.kt:55-56`

```kotlin
private fun open(viewModel: WorkshopDebitViewModel) =
    viewModel.sendIntent(WorkshopDebitIntent.Open(WORKSHOP_ID, BRANCH_CODE))
```

This round adds `characterCode`/`legalNationalId` to `WorkshopDebitIntent.Open` and
`WorkshopDebitUiState` (both default to `""`), threaded through so a legal-person (حقوقی) workshop's
own national ID reaches `DebitPaymentRequestDN.toDto()`
(`core-data/.../WorkshopMapper.kt:284-296`: `nationalId = legalNationalId.takeIf { characterCode == CHARACTER_LEGAL && it.isNotBlank() }`).
That mapper-level rule is well covered by `DebitPaymentMapperTest.kt`/`DebitPaymentRequestDTOTest.kt`
(both new this round, and thorough — see "What was done well"). But `open()`'s test helper never
passes the two new fields, so nothing in `WorkshopDebitViewModelTest` proves they actually survive
the trip: `Open` → `WorkshopDebitUiState` → the `DebitPaymentRequestDN` built in `pay()`
(`WorkshopDebitViewModel.kt:80-89`). Given the test file's own stated purpose is pinning exactly this
class of wiring bug (values that are correct in the model but don't reach where they're sent), the
two newest fields it adds a path for are the ones with no test on that path.

> **سناریوی بیزینسی جاافتاده:** اگر به هر دلیلی کد ملی یا نوع شخصیت کارگاه بین صفحه‌ی لیست و صفحه‌ی
> پرداخت گم بشه (مثلاً یک تغییر بعدی در ناوبری یا در state)، هیچ تستی این رگرسیون رو نمی‌گیره — یعنی
> ممکنه یک کارگاه حقوقی، درخواست پرداختش بدون کد ملی خودش (به‌جای `null` عمدی) به سرویس بره و سرویس
> طبق کامنت خودِ کد («یک درخواست بدون این فیلدها رد می‌شه») کل پرداخت رو رد کنه.

**Suggested change:** one test passing `characterCode = "02"`/`legalNationalId = "..."` to `Open`,
then triggering `PayDebit`, and asserting the fake repository received a `DebitPaymentRequestDN`
with those exact values.

## What was done well

- The pre-check/payment collapse into one `PayWorkshopDebitUseCase` call (rather than two separate
  ViewModel-level calls like `old_android`'s `checkPaymentStatus`/`normalDebitPayment`) is a real
  improvement with a documented reason: "splitting them across two callers is how the old client
  ended up able to pay without checking." Good catch, and worth keeping regardless of how item 1
  above resolves.
- Payment failures (both a refused pre-check and a transport error) are routed through one
  `reportPaymentFailure()` so neither path goes silent — and correctly kept out of the list's own
  error state, which would otherwise blank out the whole debt list over a single payment failure.
- Both new ViewModels avoid the `CancellationException`-swallowing pattern flagged on MR !191/!201
  — consistent `Flow.catch { }` use throughout.
- Real test coverage: `WorkshopDebitViewModelTest` (11 tests) and `DemandDocumentsViewModelTest`
  (6 tests), continuing the pattern established since MR !198's review (this codebase now
  consistently ships ViewModel tests with new workshop-service screens).
- `DemandDocuments` is correctly scoped as a debt-row drill-down rather than its own
  `WorkshopAction` menu entry, matching `old_android` (only reachable by tapping a row in the debt
  list, never from the workshop's top-level service menu).
- The PDF viewer's failure path (`DemandDocumentsIntent.ShowCalculationPdf`) reports to the viewer
  alone via `DownloadFailed` rather than the list's `Error` state, with a comment explaining why —
  same good instinct as the payment-failure routing above.
- **Round 2: the `pay-normal-debit` wire format is treated with real care.** `DebitPaymentRequestDTO`'s
  KDoc records the exact JSON shape the service team confirmed against the web client, names every
  gotcha (`encodeDefaults` dropping a default-valued field, the boolean-as-string requirement, the
  null-vs-empty-string distinction for `nationalId`/`peymanSequence`), and `DebitPaymentRequestDTOTest`
  asserts on the **serialized JSON string**, not the model — which is exactly the right level, since a
  model-level assertion would pass while the field silently vanished at encode time. This is the kind
  of subtle wire-format bug that's easy to reintroduce months later, and it's pinned down precisely.
- **Round 2: the legal-person national-ID rule is centralised in one place**
  (`WorkshopMapper.kt:284-296`'s `toDto()`), not duplicated at each call site, and uses one named
  constant (`CHARACTER_LEGAL`) rather than a magic `"02"` scattered around.
- **Round 2: `peymanSequence`'s rocky commit history resolved into a coherent, documented final
  state** rather than being left inconsistent — the divergence from `old_android`'s own historical
  wire behaviour (which omitted a null `peymanSequence`) was a deliberate, recorded choice confirmed
  against the current web client, not an oversight.
