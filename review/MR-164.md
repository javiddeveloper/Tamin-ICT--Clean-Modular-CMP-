## ۱. نگه‌داری `fileBytes` در State — شدت بالا

**فایل:** `feature/addDependent/.../ui/contract/AddDependentContract.kt:40-70`

```kotlin
@Immutable
data class UploadedDocument(
    val guid: String,
    val docType: String,
    val fileName: String,
    val fileBytes: ByteArray? = null
) {
    override fun equals(other: Any?): Boolean {
        // …
        if (!fileBytes.contentEquals(other.fileBytes)) return false
    }
    override fun hashCode(): Int {
        // …
        result = 31 * result + (fileBytes?.contentHashCode() ?: 0)
    }
}
```

override کردن `equals`/`hashCode` برای `ByteArray` درست انجام شده و این نکته‌ی مثبتی است. مشکل جای دیگری است:

این object داخل `AddDependentState` نگه داشته می‌شود و `AddDependentState` هم در یک `MutableStateFlow` است. `MutableStateFlow` قبل از هر emit، مقدار جدید را با `equals` مقایسه می‌کند.

نتیجه: **با هر تغییر state — از جمله هر کاراکتری که کاربر در فیلد کد تحصیلی تایپ می‌کند — یک مقایسه‌ی byte-by-byte روی تمام فایل‌های آپلودشده انجام می‌شود.** با ۳ سند و سقف `MAX_UPLOAD_SIZE_BYTES = 2_000_000`، این یعنی تا ۶ مگابایت مقایسه در هر keystroke. همان ۶ مگابایت هم تا پایان flow در حافظه می‌ماند.

این byteها فقط برای یک کار لازم‌اند: تشخیص تکراری بودن فایل در `uploadDocument`.

**پیشنهاد:** به‌جای خود byteها، یک hash نگه دارید:

```kotlin
@Immutable
data class UploadedDocument(
    val guid: String,
    val docType: String,
    val fileName: String,
    val contentHash: Int          // fileBytes.contentHashCode()
)
```

با این تغییر `equals`/`hashCode` دستی هم لازم نیست و `data class` پیش‌فرض کافی است. بررسی تکراری بودن هم می‌شود:

```kotlin
if (uiState.value.uploadedDocuments.any { it.contentHash == fileBytes.contentHashCode() })
```

## ۲. نبود guard برای double-submit — شدت متوسط

**فایل:** `feature/addDependent/.../ui/AddDependentViewModel.kt:292`

```kotlin
private fun submitFinalRequest(): Flow<PartialState> = flow {
    val state = uiState.value
    emit(PartialState.Loading(true))
    // …
    addNewDependentUseCase(requestPR.toDomain())
```

در `BaseViewModel`، intentها با `flatMapMerge` پردازش می‌شوند، یعنی **موازی** اجرا می‌شوند نه صف‌شده. اگر دو intent پشت سر هم برسند، هر دو `uiState.value` را قبل از ثبت شدن `Loading(true)` می‌خوانند و هر دو request را می‌فرستند.

`LoadingButton` با `enabled = enabled && !isLoading` بیشتر این حالت را پوشش می‌دهد، ولی فاصله‌ی بین `sendIntent` تا رسیدن `isLoading = true` به recomposition همچنان باز است. برای فرمی که رکورد رسمی «افراد تحت تکفل» ایجاد می‌کند، اتکا به guard سمت UI کافی نیست.

**پیشنهاد:** در ابتدای `submitFinalRequest` (و ترجیحاً `submitInquiryRegistry` و `uploadDocument`) یک بررسی اضافه شود:

```kotlin
private fun submitFinalRequest(): Flow<PartialState> = flow {
    val state = uiState.value
    if (state.isLoading) return@flow
    emit(PartialState.Loading(true))
    // …
}
```

## ۴. در `SON_MODE` دکمه‌ی بعدی مرحله را جلو نمی‌برد — نیاز به تأیید

**فایل:** `feature/addDependent/.../ui/AddDependentViewModel.kt:278`

```kotlin
StepperMode.SON_MODE -> if (state.needCallInquiryEducation)
    submitInquiryEducation().collect { emit(it) }
else
    emit(PartialState.StepChanged(STEP_DOCUMENTS))
```

`submitInquiryEducation()` فقط `EducationInquirySuccess` را emit می‌کند که `universityName` را ست و `needCallInquiryEducation` را `false` می‌کند — ولی `StepChanged` نمی‌فرستد.

یعنی کاربر در `SON_MODE` باید **دو بار** روی «بعدی» بزند: بار اول استعلام تحصیلی اجرا می‌شود، بار دوم به مرحله‌ی مدارک می‌رود.

اگر هدف این است که کاربر اول نام دانشگاه را ببیند و تأیید کند، رفتار درست است — فقط بهتر است متن دکمه در این حالت عوض شود (مثلاً «استعلام» به‌جای «بعدی») تا کاربر سردرگم نشود. اگر هدف این نبوده، بعد از موفقیت استعلام باید `StepChanged(STEP_DOCUMENTS)` هم emit شود.

## ۸. `emit` داخل `catch` به collector بیرونی می‌رود — شدت پایین

**فایل:** `feature/addDependent/.../ui/AddDependentViewModel.kt:189-191`

```kotlin
getFamilyRelationshipsFromProxyUseCase(...)
    .map { it.map { item -> item.toPresentation() } }
    .catch { emit(PartialState.Error(it.toSingleLineMessage())) }
    .collect { relationships -> … }
```

جریان بعد از `map` از نوع `Flow<List<FamilyRelationshipPR>>` است، ولی `PartialState.Error` در آن emit می‌شود. کد کامپایل می‌شود چون Kotlin در resolution به receiver بیرونی (`flow { }`) می‌رسد، و رفتار هم درست است — ولی خواندنش گمراه‌کننده است و هر تغییر بعدی در نوع flow می‌تواند بی‌سروصدا رفتار را عوض کند.

برای خوانایی بهتر است صریح نوشته شود:

```kotlin
.catch { e -> this@flow.emit(PartialState.Error(e.toSingleLineMessage())) }
```
