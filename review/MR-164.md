## 1. `fileBytes` kept in state — High

**File:** `feature/addDependent/.../ui/contract/AddDependentContract.kt:40-70`

```kotlin
@Immutable
data class UploadedDocument(
    val guid: String,
    val docType: String,
    val fileName: String,
    val fileBytes: ByteArray? = null
) {
    override fun equals(other: Any?): Boolean {
        // …
        if (!fileBytes.contentEquals(other.fileBytes)) return false
    }
    override fun hashCode(): Int {
        // …
        result = 31 * result + (fileBytes?.contentHashCode() ?: 0)
    }
}
```

Overriding `equals`/`hashCode` for `ByteArray` is correct and worth keeping in mind — the
problem is elsewhere.

This object is held inside `AddDependentState`, which lives in a `MutableStateFlow`.
`MutableStateFlow` calls `equals` on the whole value before every emission to decide whether
to publish it.

The result: **every state change — including each character the user types into the education
code field — triggers a byte-by-byte comparison over all uploaded documents.** With 3
documents and `MAX_UPLOAD_SIZE_BYTES = 2_000_000`, that is up to 6 MB compared per keystroke,
and the same 6 MB is retained in memory until the flow ends.

Those bytes are needed for exactly one thing: the duplicate check in `uploadDocument`.

**Suggested change** — store a hash instead of the bytes:

```kotlin
@Immutable
data class UploadedDocument(
    val guid: String,
    val docType: String,
    val fileName: String,
    val contentHash: Int          // fileBytes.contentHashCode()
)
```

With this, the hand-written `equals`/`hashCode` are no longer needed — the generated
`data class` implementations are enough. The duplicate check becomes:

```kotlin
if (uiState.value.uploadedDocuments.any { it.contentHash == fileBytes.contentHashCode() })
```

## 2. No guard against double submission — Medium

**File:** `feature/addDependent/.../ui/AddDependentViewModel.kt:292`

```kotlin
private fun submitFinalRequest(): Flow<PartialState> = flow {
    val state = uiState.value
    emit(PartialState.Loading(true))
    // …
    addNewDependentUseCase(requestPR.toDomain())
```

`BaseViewModel` processes intents through `flatMapMerge`, which means they run **concurrently**,
not sequentially. If two intents arrive close together, both read `uiState.value` before
`Loading(true)` has been reduced, and both send the request.

`LoadingButton` uses `enabled = enabled && !isLoading`, which closes most of this window, but
the gap between `sendIntent` and `isLoading = true` reaching recomposition is still open. For
a form that creates an official dependent record, a UI-side guard alone is not enough.

**Suggested change** — add an early return in `submitFinalRequest` (and ideally in
`submitInquiryRegistry` and `uploadDocument` as well):

```kotlin
private fun submitFinalRequest(): Flow<PartialState> = flow {
    val state = uiState.value
    if (state.isLoading) return@flow
    emit(PartialState.Loading(true))
    // …
}
```

## 4. In `SON_MODE` the next button does not advance the step — needs confirmation

**File:** `feature/addDependent/.../ui/AddDependentViewModel.kt:278`

```kotlin
StepperMode.SON_MODE -> if (state.needCallInquiryEducation)
    submitInquiryEducation().collect { emit(it) }
else
    emit(PartialState.StepChanged(STEP_DOCUMENTS))
```

`submitInquiryEducation()` only emits `EducationInquirySuccess`, which sets `universityName`
and flips `needCallInquiryEducation` to `false` — it never emits `StepChanged`.

So in `SON_MODE` the user has to press "next" **twice**: the first press runs the education
lookup, the second one moves to the documents step.

If the intent is for the user to see and confirm the university name first, the behaviour is
right — but the button label should change in that state (e.g. "lookup" instead of "next") so
the user is not left wondering. If that was not the intent, emit
`StepChanged(STEP_DOCUMENTS)` after a successful lookup.

```kotlin
if (uiState.value.uploadedDocuments.any { it.fileBytes?.contentEquals(fileBytes) == true }) {
    sendEvent(... error_image_duplicate)
```

## 8. `emit` inside `catch` resolves to the outer collector — Low

**File:** `feature/addDependent/.../ui/AddDependentViewModel.kt:189-191`

```kotlin
getFamilyRelationshipsFromProxyUseCase(...)
    .map { it.map { item -> item.toPresentation() } }
    .catch { emit(PartialState.Error(it.toSingleLineMessage())) }
    .collect { relationships -> … }
```

After `map` the flow is `Flow<List<FamilyRelationshipPR>>`, yet a `PartialState.Error` is
emitted into it. This compiles because Kotlin's overload resolution walks outward and lands on
the enclosing `flow { }` collector, and the runtime behaviour is correct — but it reads as if
the error goes into the inner flow, and any later change to the flow's element type could
shift the resolution silently.

**Suggested change** — make the receiver explicit:

```kotlin
.catch { e -> this@flow.emit(PartialState.Error(e.toSingleLineMessage())) }
```
