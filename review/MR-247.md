## 1. «سوابق تلفیقی» silently drops out of the «پرکاربرد» shortlist — Medium

**File:** `core/core-domain/src/commonMain/kotlin/com/tamin/taminhamrah/repository/home/HomeServiceMembership.kt:28`

```kotlin
val frequent: List<FeatureFlag> = listOf(
    FeatureFlag.CONTRACTS,
    FeatureFlag.PRESCRIPTION,
    FeatureFlag.PAY_ROLL,
    FeatureFlag.MERGE_HISTORY,   // ← id 90 now, no menu row
    ...
```

`MERGE_HISTORY` moved to id `90` and `MockMenuData` no longer has a row for it — the three history rows
were merged into «کلیه سوابق» (`COMBINED_RECORD`, id 3). `HomeRepositoryImpl` builds the cached
quick-access rows with `byId[flag.id]?.let { ... }`, so a flag with no menu row produces no row, and
`toHomeSections()` renders only cached rows. The shortlist therefore shrinks from seven services to
six with no error, and its history entry is gone. `COMBINED_RECORD` is only in the `history` list.

> **سناریوی بیزینسی:** در صفحه‌ی اصلی، بخش «پرکاربرد» قبلاً میان‌بر «سوابق تلفیقی» را داشت. با این
> تغییر، ردیف منو حذف شده ولی لیست «پرکاربرد» اصلاح نشده؛ در نتیجه آن میان‌بر بدون هیچ خطایی از
> صفحه‌ی اصلی ناپدید می‌شود و کاربر دیگر از بخش پرکاربرد به سوابق دسترسی سریع ندارد.

**Suggested change:** replace `MERGE_HISTORY` with `COMBINED_RECORD` in `frequent` (or state that the
shortlist is meant to lose it), and update the id comments in that file (item 4).

## 2. Ids renumbered to fix ordering, cutting them off from the server's — Medium, needs confirmation

**Files:** `core/core-domain/.../model/common/FeatureStatus.kt` (`FeatureFlag`),
`core/core-network/.../commonSource/MockMenuData.kt`,
`core/core-network/.../commonSource/CommonRemoteDataSourceImpl.kt:82-105`

The menu is currently served from `MockMenuData` (`getMainMenu` returns it with a
«Temporarily returning local data» comment; the real `menu_data_<version>.txt` call is commented out).
The MR's reasoning is sound as far as it goes: the list is stored in Room and read back
`ORDER BY sorting, id`, `sorting` is `null` for every mock row, so `id` silently decides the on-screen
order, and rows were written in one order and numbered in another.

The fix chosen is to renumber **every** `FeatureFlag` to match the display order. Before this MR the
ids were the legacy server's (`1`–`47`, `101`–`113`, `1001`–`1012`); now they are the app's own, and
the MR's own doc says so: *"if `menu_data_<version>.txt` is ever switched back on … the server
payload's ids will not line up — every `FeatureFlag` id has to be remapped."* Ordering could have been
fixed without touching identity, by giving the mock rows a `sorting` value — that is what the column is
for, and the DAO query already orders by it first.

Consequence to be aware of: the day the real menu returns, every `featureStatusOf(flag)` lookup reads
the wrong row (or none), so services are gated on, off or routed by the wrong row, with no compile or
runtime error. Deep links and assistant actions go through the same lookup.

> **سناریوی بیزینسی:** شناسه‌ی هر سرویس در نسخه‌ی قدیمی همان شناسه‌ای بود که سرور منو می‌فرستاد.
> حالا شناسه‌ها مال خود اپ شده‌اند و با سرور فرق دارند. تا وقتی منو از فایل محلی می‌آید مشکلی
> دیده نمی‌شود؛ اما روزی که منوی واقعی سرور دوباره فعال شود، وضعیت روشن/خاموش بودن و مسیر هر سرویس
> با ردیف اشتباه تطبیق داده می‌شود (مثلاً سرویسی که باید غیرفعال باشد فعال نشان داده شود).

**Suggested change:** confirm with the team that leaving the server's ids behind is intended and that
the remote menu will be remapped when it returns. If not, keep the original ids and set `sorting` on
the mock rows instead.

## 3. Cached home rows keep the old `flagId` — Low

**Files:** `core/core-database/.../entity/HomeContentEntity.kt:77,88,98`,
`core/core-data/.../mapper/HomeMapper.kt:76-78`

`CampaignEntity`, `QuickAccessEntity` and `SpecialServiceEntity` persist `flagId` and are turned back
into flags with `FeatureFlag.fromId(flagId)`. The database version is unchanged and there is no
migration, so after updating, a cached row saved as, say, id `18` (was «کمک هزینه کفن و دفن») now
resolves to `OBJECTION_INSURANCE_HISTORY`, still wearing the old title and icon, until the next sync
replaces the cache. The window is short when the sync succeeds, but a tap inside it routes to the
wrong screen, and offline users keep the wrong mapping until they reconnect.

**Suggested change:** clear the cached home content once after this change (or bump the cache
version), so nothing persisted under the old numbering is read back.

## 5. The new invariants and the DAO change have no tests — Low

The documentation now states rules the code relies on: every `FeatureFlag` id is unique, every id in
`MockMenuData` appears in the enum exactly once (`fromId` takes the first match, so a repeat routes a
row to the wrong feature), and the display order is the id order. I checked these by hand for this
round and they hold — 62 unique ids, 58 menu rows each with one flag, the four extra flags being the
documented `90`–`93` — but nothing enforces them, and the only test edited was a rename in
`AgentServiceKeyCoverageTest`. `replaceAllMenuItems` (the fix for removed rows lingering) has no test
either.

> **سناریوی بیزینسی:** اگر بعداً کسی دو سرویس را با یک شناسه تعریف کند، یکی از آن‌ها بی‌صدا روی
> سرویس دیگر نوشته می‌شود و از منو ناپدید می‌شود؛ و اگر ردیفی از منوی سرور حذف شود، تستی نیست که
> نشان دهد ردیف قدیمی از حافظه‌ی محلی هم پاک می‌شود.

**Suggested change:** add a small test that checks id uniqueness, the one-to-one match between
`MockMenuData` and `FeatureFlag`, and that a row missing from the next sync is gone from `menu_items`.

## What was done well

- **The id scheme is internally consistent**: no duplicate ids, every menu row maps to exactly one
  flag, and the four flags without a row are deliberately parked in a separate `90`–`93` band so they
  cannot shadow a real one in `fromId`. Checked by comparing the enum against `MockMenuData`.
- **`replaceAllMenuItems` fixes a real bug**: inserting alone never removed a service that had left
  the menu or changed id, so it stayed cached next to its replacement. Doing the delete and insert in
  one transaction also avoids observers seeing an empty table.
- **The `id ASC` tie-break is right**: with `sorting` null everywhere, SQLite was free to order equal
  keys arbitrarily; the DAO now has a deterministic order.
- **The audience split keeps existing routing intact**: the pensioner-only flags (`DESERVED_TREATMENT`,
  `DISABILITY_PENSION`, `REQUEST_PENSION_BY_SURVIVOR`, `CALCULATE_WAGE_PENSION`) each get their own
  `*_PENSIONER` flag routed to the same screen, and deep links / agent actions that used the old
  pensioner ids (`101`, `113`) were re-pointed at them.
- **The documentation names its own trap**: `Feature-Flags.md` explains that ids decide order, that the
  ids are no longer the server's, and that duplicate ids overwrite each other in Room — the warning for
  item 2 is already written down.
- **No cancellation or error-handling regressions** — the change adds no new catch blocks.
