## 1. Landline validation only checks length, not the area-code pattern — Medium

**File:** `core/core-ui/src/commonMain/kotlin/com/tamin/taminhamrah/util/ValidationUtils.kt:42-44`

```kotlin
fun isPhoneNumberValid(phone: String): Boolean {
    return phone.length == 11
}
```

`old_android`'s equivalent checked both length **and** format:

```kotlin
// Utility.kt:225-232
fun checkPhoneNumber(phoneNumber: String): Int {
    if (phoneNumber.length < 11) return R.string.error_input_length_phone
    if (!(Pattern.compile("^0[1-8][1-9]{2}\\d{7}$").matcher(phoneNumber).matches()))
        return R.string.error_input_phone
    return 0
}
```

`isPhoneNumberValid` (this MR is the first place it's actually wired into a form field, via
`UserInfoStepContent.kt`'s new `isPhoneError` check) only confirms the digit count. A value like
`09123456789` (a mobile number, not a landline) or `00000000000` now passes as "valid" where legacy
would have rejected both — the area code must start with a digit 1-8, which this check doesn't
enforce. `ValidationUtils.isMobileNumberValid` (used elsewhere) shows the pattern already exists in
this codebase for the mobile case (`^09\d{9}$`) — the landline case is just missing its own pattern.

**Suggested change:** add the `^0[1-8][1-9]{2}\d{7}$` pattern to `isPhoneNumberValid` (or a new
`isLandlineFormatValid`), matching legacy.

## 2. Blank `checkFractionMonthStatus` now shows a generic error — Low, needs confirmation

**File:** `feature/fractionContract/src/commonMain/kotlin/com/tamin/taminhamrah/feature/fractionContract/ui/contract/FractionContractContract.kt:160`

Legacy's equivalent hard-block check, when `checkFractionMonthStatus` is blank (and not `"1"`), shows
an error dialog with an **empty** message — a legacy bug. The new code shows
`fraction_contract_error_eligibility_unavailable` (a real, generic message) for the same case instead.

This reads like an intentional, reasonable fix rather than an accidental deviation — but since this
review's mandate is checking for faithful business-flow parity, it's worth an explicit confirmation
that showing a real message here (instead of matching legacy's blank-dialog bug) was a deliberate
choice.

**Suggested change:** no code change expected — just confirm this was intentional, and it can be
marked accepted.

## 3. New validation wired into a shared component silently changes an unrelated, already-shipped flow — Medium

**Files:** `core/core-ui/src/commonMain/kotlin/com/tamin/taminhamrah/ui/contractFlow/UserInfoStepContent.kt`,
`feature/contracts/src/commonMain/kotlin/com/tamin/taminhamrah/feature/contracts/flow/ui/ContractFlowScreen.kt`

`UserInfoStepContent` is a **shared** `core-ui` component with two consumers: this MR's new
`FractionUserInfoStep.kt`, and the pre-existing `ContractFlowScreen.kt` (the optional/housewife
insurance contract flow, already shipped, untouched by this MR otherwise). This MR adds real
zip-code and phone validation to that shared component:

```kotlin
val isZipComplete = userInfo.zipCode.length == 10 && ValidationUtils.isPostcodeValid(userInfo.zipCode)
val isZipError = userInfo.zipCode.isNotEmpty() && !isZipComplete
...
val isPhoneComplete = ValidationUtils.isPhoneNumberValid(userInfo.phoneNumber)
val isPhoneError = userInfo.phoneNumber.isNotEmpty() && !isPhoneComplete
```

`ValidationUtils.isPostcodeValid`/`isPhoneNumberValid` already existed in the codebase before this
MR but were unused by this component — this MR is the first to wire them in. The new `isZipError`/
`isPhoneError` checks are unconditional (not gated behind the new `hideMobileWhenEmpty` parameter this
MR does add for the mobile-field-visibility change), so `ContractFlowScreen.kt` — a screen this MR
doesn't otherwise touch or test — now shows new validation errors it never showed before, purely as
a side effect of building the fraction-contract feature.

This isn't necessarily wrong (the validation itself is reasonable), but it's an unscoped, untested
behavior change to a different, already-shipped feature bundled into this MR.

**Suggested change:** either confirm this is an intentional, desired improvement to the shared
optional/housewife-insurance flow too (and add a note/test for that flow), or gate the new validation
behind a parameter the way `hideMobileWhenEmpty` already is, so only the fraction-contract flow gets
the new behavior.

## What was done well

- **The four eligibility hard-block rules are a faithful, well-ordered port** of legacy's
  `onCheckContractCondition` (not insured → error, age < 18 → error, `checkFractionMonthStatus != "1"`
  → error, insurance-type-code `"38"` → error, else proceed) — same order, same conditions, and
  exhaustively unit-tested including the age-18 boundary.
- **The secondary "eligibility status 1-4" display gate correctly reuses the shared
  `ContractEligibilityReason` enum** rather than hardcoding per-status reason text — status 3's
  dynamic history+age breakdown and the fixed reasons for 1/2/4 both match legacy's
  `Utility.getEligibilityStatusList()` semantics, and this follows rule 7 correctly (no magic-string
  status comparison).
- **The `"38"` insurance-type-code check, submit body shape, PDF path, and payment hand-off**
  (`EnumInsuranceType.TYPE_FRACTION` → `FractionContractState.PREMIUM_TYPE_CODE`) are all ported
  correctly, and documented with genuinely useful `// Legacy ...` comments pointing at the exact old
  behavior being matched — not noise, actually helpful for the next reader.
- **No hardcoded Persian strings anywhere in the new diff** — all UI text goes through `strings.xml`
  (43 new keys).
- **`.catch {}` on `Flow`, not raw `try/catch(e: Exception)`,** is used consistently in the new
  ViewModel — the `CancellationException`-swallowing bug found elsewhere this review cycle doesn't
  apply here.
- **The `TaminTextField` max-length/delete-only-when-full change is a genuinely careful piece of
  Compose state handling** — keeping an internal `TextFieldValue` in sync with the caller's filtered
  `value` via `LaunchedEffect`, correctly handling the "over-length keystroke must not stick visually"
  edge case that a naive `value.take(n)` filter alone would get wrong.
