## 1. A test in this diff currently fails — High

**File:** `core/core-network/src/commonTest/kotlin/com/tamin/taminhamrah/dataSource/weddingPresent/WeddingPresentRemoteDataSourceImplTest.kt:107-113`

```kotlin
@Test
fun getWeddingPresentInfo_networkException_throwsNoConnection() = runTest {
    fakeApiService.shouldThrowException = RuntimeException("network")

    val exception = assertFailsWith<TaminApiException> {
        dataSource.getWeddingPresentInfo()
    }
    assertEquals(ErrorUri.NO_CONNECTION_ERROR, exception.getTaminErrorUri())
}
```

Running `:core:core-network:testDebugUnitTest` on this branch's current HEAD fails this exact test
(`AssertionError` at line 108). A plain `RuntimeException` is not classified as
`ErrorUri.NO_CONNECTION_ERROR` by `ErrorParserImpl` — only an IO-shaped exception is — so this test
doesn't actually verify what its name claims, and it fails outright rather than passing for the
wrong reason.

This is the exact same mistake already found and fixed on two sibling "Phase 1 data vertical"
MRs in this same family of work (`!229`, `!228` round 3) — both were corrected by throwing
`FakeIOException()` (already present in this codebase at
`core/core-network/src/commonTest/kotlin/com/tamin/taminhamrah/tools/FakeIOException.kt`) instead of
a bare `RuntimeException`.

**Suggested change:** replace `RuntimeException("network")` with `FakeIOException()`, matching the
fix already applied in `!229`/`!228`.

## 2. Main request-screen ViewModel has zero test coverage — Medium

**File:** `feature/weddingPresent/src/commonMain/kotlin/com/tamin/taminhamrah/feature/weddingPresent/ui/WeddingPresentViewModel.kt` (177 lines)

`WeddingPresentCalculateViewModel` (the estimate-calculation screen) got a full test file in the
self-review commit (`cbee204ef`), but `WeddingPresentViewModel` — the main request screen, with the
real submission gate — has no test file at all. Untested, money/eligibility-relevant logic:

- The submit validation order and rules (`submit()`, lines 98-137): marriage-date requiredness,
  partner national-code length + checksum (`isValidNationalCode`), and the commitment checkbox gate.
- `toAsciiDigitsOnly()` (lines 171-177), the Persian-to-ASCII digit normalization added in the same
  self-review commit for the national-code field — exactly the kind of input-sanitization logic
  that's easy to silently regress later.
- The `info == null` fallback branch (see item 3) — untested, which is likely why its wrong message
  wasn't caught before this review.
- The load-retry path (`ErrorStateView.onRetry` → re-dispatching `Load`).

**Suggested change:** add a `WeddingPresentViewModelTest.kt` mirroring the calculate ViewModel's
test structure — at minimum one test per validation rule (missing date, invalid code, unchecked
box) and one for the successful submit path.

## 3. Wrong error message when the initial info load failed — Low

**File:** `feature/weddingPresent/src/commonMain/kotlin/com/tamin/taminhamrah/feature/weddingPresent/ui/WeddingPresentViewModel.kt:122-124`

```kotlin
if (info == null) {
    emit(createErrorState(getString(Res.string.message_select_marriage_date)))
    return
}
```

`message_select_marriage_date` is «تاریخ عقد را وارد کنید» ("enter the marriage date") — the same
string used for the actual missing-date validation error a few lines above. If `loadedInfo` is
`null` at submit time (the initial `getWeddingPresentInfoUseCase()` load failed or hasn't finished,
but the user still reaches this point with a valid date and code filled in), this branch shows the
user a message telling them to do something they've already done correctly. The real problem —
the request info never loaded — isn't stated.

**Suggested change:** use a distinct message (e.g. a generic "please retry" or reuse the load-error
copy already shown by `ErrorStateView`), not the date-selection string.

## 4. Leftover unreachable `DismissError` intent — Low

**Files:** `feature/weddingPresent/src/commonMain/kotlin/com/tamin/taminhamrah/feature/weddingPresent/ui/contract/WeddingPresentContract.kt:54`,
`.../ui/WeddingPresentViewModel.kt:86`

The self-review commit (`cbee204ef`) changed the error dialog's dismiss action from
`{ onIntent(WeddingPresentIntent.DismissError) }` to `onBack` (`WeddingPresentScreen.kt:252`), but
left `WeddingPresentIntent.DismissError` declared in the contract and still handled in the
ViewModel. Nothing dispatches it anymore.

**Suggested change:** remove the now-dead `DismissError` intent and its handler, or wire something
to it if leaving the error dialog open (rather than navigating back) was actually the intent.

## What was done well

- **No placeholder/dummy default values anywhere** — the sibling "Phase 1 data vertical" MR (`!229`)
  had a real bug where a default parameter was a literal placeholder string reproduced across four
  layers; this MR's request-body chain (`WeddingPresentInfoDN` → `WeddingPresentMapper.toMarriageGiftRequestDTO`
  → `MarriageGiftRequestDTO`) was checked field-for-field against legacy `MarriageGiftReq.kt` and has
  no equivalent issue.
- **The calculation-response parsing rule is a precise, correct port.** Both the legacy AI-agent's
  `WeddingPresentCalculateUseCase.kt` and the new `WeddingPresentCalculateViewModel.kt` treat the
  response's first line as the average-salary figure and the second as the payable amount, with an
  identical "blank payable → show line 0 as the error message" fallback rule — matched exactly.
- **No hardcoded strings or magic-value comparisons anywhere in this diff** — every screen and both
  mappers route Persian copy through `strings.xml`/`Res.string.*`, and no status/type code is
  compared as a raw string.
- **Architecture is clean**: Koin module registered in `sharedModules`, navigation to the calculate
  screen goes through a callback (not a direct cross-feature import), and `WeddingPresentHeader.kt`
  composes existing `core-ui` components (`TaminTopAppBar`, `AnimatedRingHeaderIcon`,
  `DecorativeBackgroundCircle`) instead of duplicating them.
- **The self-review commit's other fixes are complete and correct**: the retry button on a load
  error, Persian-digit normalization on the national-code field, a hardcoded `Color.White` replaced
  with a theme token, and wiring the calculate screen's menu entry (`CALCULATE_MARRIAGE_ALLOWANCE`)
  into navigation — all verified working as claimed.
- **No commented-out code anywhere in the diff.**
