## 1. `Support` event ignores its own `phone` payload, produces a broken `tel:` URI — High

**File:** `feature/profile/src/commonMain/kotlin/com/tamin/taminhamrah/feature/profile/ui/ProfileScreen.kt:250-252`

```kotlin
is ProfileEvent.Support -> {
    onOpenUrl("tel:$1420")
}
```

`ProfileEvent.Support(val phone: String)` is emitted from the ViewModel as
`ProfileEvent.Support("1420")`, but the handler never reads `it.phone` — it interpolates the
literal token `$1420`. In Kotlin, `$` followed by a string that can't start a valid identifier
(digits aren't a legal identifier start) is *not* a compile error — it's kept as a literal `$`
character, so the resulting string is the literal text `"tel:$1420"`, not `"tel:1420"`. Old_android
built this exact same "call support" action correctly:
`"tel:" + getString(R.string.tel_1420)` (`old_android/.../ui/profile/ProfileFragment.kt:132`),
so this is a regression introduced fresh in this rewrite, not a carried-forward issue.

**Failure scenario:** user taps the new "پشتیبانی" (support) menu item; the dialer opens (or
fails to open) with the malformed number `$1420` instead of `1420`.

**Suggested change:**

```kotlin
is ProfileEvent.Support -> {
    onOpenUrl("tel:${it.phone}")
}
```

## 2. Hotline title/number alignment changed from `End` to `Start` — Low (needs confirmation)

**File:** `feature/profile/src/commonMain/kotlin/com/tamin/taminhamrah/feature/profile/ui/contactUs/components/HotlineCard.kt:118`

```kotlin
Column(
    horizontalAlignment = Alignment.Start   // was Alignment.End
) {
    Text(text = hotline.title, ...)
    Text(
        text = ...,
        style = ...,
        // textAlign = TextAlign.End,   // removed
    )
}
```

This flips the hotline title/number block from end-aligned to start-aligned, and drops the
explicit `TextAlign.End` on the number. Since `Alignment.Start`/`End` resolve relative to
`LayoutDirection` rather than to a fixed screen side, whether this reads as a genuine visual fix
or a regression depends on the app's RTL setup, which wasn't verified as part of this review.

**Suggested change:** confirm this was an intentional visual adjustment (e.g. a screenshot
before/after) rather than an incidental change while touching the file for the icon swap.

## What was done well

- The `SocialChannelType.BISPHONE → APARAT` rename is threaded correctly and completely through
  every layer that needs it: `ContactUsDN` (domain enum), `ContactUsPR` (presentation enum),
  `ContactUsUiMapper` (DN→PR mapping), `MockContactUsData` (DTO-level mock), and
  `SocialChannelsGrid`'s icon lookup — no layer was missed.
- `MockContactUsData`'s phone/fax/postal-code values were switched from Persian digits to plain
  ASCII digits, which is the right call for fields marked `canCopy = true` — copying a
  Persian-digit string as a phone number is far less useful than copying `1420` directly; display
  formatting (Persian digits) is a UI-layer concern (`toPersianDigits()`), not something to bake
  into the stored value.
- `shareText()` was added symmetrically on both platforms (`ExternalAppLauncher.android.kt` via
  `Intent.ACTION_SEND` + chooser, `ExternalAppLauncher.ios.kt` via `UIActivityViewController`),
  matching the existing `expect`/`actual` pattern used by the rest of the class rather than
  introducing a new one-off launcher.
