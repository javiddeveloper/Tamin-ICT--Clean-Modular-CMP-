## 1. ✕ button on the abandon dialog now goes back instead of home — High

**File:** `feature/history-objection/src/commonMain/kotlin/com/tamin/taminhamrah/feature/historyobjection/ui/stepper/HistoryObjectionStepperScreen.kt`

```kotlin
var showAbandonDialog by remember { mutableStateOf(false) }
// ✕ leaves to home; first-step back leaves via the nav back stack (same as OnBackClicked).
var abandonToHome by remember { mutableStateOf(true) }

val handleBack: () -> Unit = {
    if (state.currentStep == STEP_BRANCH) {
        abandonToHome = false
        showAbandonDialog = true
    } else {
        onIntent(HistoryObjectionStepperIntent.OnBackClicked)
    }
}
...
action = {
    TaminTopAppBarButton(
        icon = vectorResource(Res.drawable.ic_close),
        onClick = {
            abandonToHome = false   // was `true` before this MR's commit 109bed2c3
            showAbandonDialog = true
        },
        ...
    )
}
...
if (abandonToHome) onNavigateHome() else onNavigateBack()
```

Commit `109bed2c3` ("change close button navigation,fix back button size issue in bottombar")
flips the ✕ button's `abandonToHome` assignment from `true` to `false`. `onNavigateBack` and
`onNavigateHome` are genuinely different destinations (`TaminHamrahNavGraph.kt`):
`onNavigateBack = { navController.popBackStack() }` pops one step, while
`onNavigateHome = { navController.popBackStack(Route.Home, inclusive = false) }` pops the whole
stack to Home.

This is a revert of a deliberate, already-reviewed fix. Commit `e426d8b35`
("fix(ui): align form-abandon back handlers with DeferredInstallment") is exactly where
`abandonToHome = true` was added to the ✕ button's `onClick` (previously it had no explicit
assignment and relied on the declared-initial `true`). This MR's commit silently undoes that,
directly contradicting the code comment still sitting above the `abandonToHome` declaration
("✕ leaves to home"). After this MR, tapping ✕ on the abandon-confirmation dialog leaves the
user one step back inside the stepper instead of returning them to Home.

**Suggested change:**

```kotlin
onClick = {
    abandonToHome = true
    showAbandonDialog = true
},
```

## 3. Server-side city search replaced by client-side filtering — Medium, needs confirmation

**Files:** `feature/requestPaymentForIllDays/src/commonMain/kotlin/com/tamin/taminhamrah/feature/requestPaymentForIllDays/ui/wizard/IllDaysWizardViewModel.kt`, `IllDaysWizardContract.kt`

Commit `5fac80f7d` removes the `CitySearchQuery` intent entirely, along with the `searchCities()`
handler that called `getCitiesUseCase(cityName = query)` against the server:

```kotlin
// removed:
data class CitySearchQuery(val query: String) : IllDaysWizardIntent
// removed:
private suspend fun FlowCollector<PartialState>.searchCities(query: String) {
    try {
        val cities = getCitiesUseCase(cityName = query.takeIf { it.isNotBlank() })
            .first().toCityPresentation().toImmutableList()
        emit(PartialState.CitiesLoaded(cities))
    } catch (error: Throwable) {
        sendEvent(IllDaysWizardEvent.ShowToast(error.toSingleLineMessage()))
    }
}
```

The city picker now falls back to the generic `TaminSearchableListSheet` component's local
substring filter over whatever city list was already loaded, since `onSearchQueryChange` is no
longer passed to it. This is a real behavior change — the search box no longer queries the
server as the user types, it only filters the already-fetched page. Legacy
(`old_android/.../requestPaymentForillDays/RequestPaymentForillDaysViewModel.kt:32`) does have a
filterable `getCityList(cityName)` fetch, but whether it's actually wired to a live search box in
the legacy fragment wasn't conclusively confirmed. This should be confirmed with product/QA rather
than treated as a definite bug — if the full city list is always small enough to load in one page,
client-side filtering is a reasonable simplification; if not, users may not be able to find cities
outside the first page.

**Suggested change:** confirm whether the city list is always fully loaded up front on this
screen. If not, restore server-side search or document why client-side filtering is sufficient.

## What was done well

- **`loadProvinces()` cache/network fix is correct.** Commit `cd99f021c` changes
  `getProvincesUseCase().first()...` to `.collect { ... }`. `CityProvinceRepositoryImpl.getProvinces()`
  is a cache-then-network `flow{}` (emits the Room cache, refreshes from network, then
  `emitAll(...)` the reactive Room query) — `.first()` only ever saw the possibly-stale first
  emission; `.collect` is required to see the network-refreshed data. The sibling
  `loadInsuranceTypes()` correctly keeps `.first()`, since `CommonRepositoryImpl.getInsuranceTypes()`
  is a genuine single-emission flow.
- **`OrotezProtezScreen.kt`'s new `BackHandler`** (`aa1f868fe`) reuses the exact same `handleBack`
  lambda already wired to the visible step-back button, rather than duplicating the logic — the
  correct shared-handler pattern.
- **`MedicalRecordsScreen.kt`'s bottom-bar fix** (`0889776bb`) wraps `RecordsTotals` in
  `Modifier.navigationBarsPadding()`, a simple, safe fix for content being hidden behind the system
  nav bar.
- **This MR's `FeatureNavigation.kt` cleanup (`29d22fbf2`) happens to fix a `:shared` compile break
  present on `develop`'s current tip** (`FeatureFlag.OBJECTION_INSURANCE_HISTORY_45`, renamed to
  `OBJECTION_INSURANCE_HISTORY_LEGACY` by an earlier MR, was left referenced by its old name). This
  MR's own diff removes the stale reference as a side effect of unrelated cleanup, and the `when`'s
  `else -> return false` catch-all means the flag correctly gets no menu row either way — not a
  silently dropped feature.
- The `TaminServicesScreen.kt`/`HistoryJobInfoScreen.kt`/`CalculateWagePensionScreen.kt` top-area
  migrations all preserve their existing callbacks (`onBackClicked`, `onCopy`, `onIntent`, chart
  interactions) — only the scroll/collapse mechanism changed, moving from bespoke scroll-state
  calculations to the shared `TopAreaState`/`driveTopArea` system already used elsewhere.
