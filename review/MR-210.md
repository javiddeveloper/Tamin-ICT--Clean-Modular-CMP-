## 1. Persian display strings hardcoded in Kotlin — Medium

**File:** `feature/workshops/src/commonMain/kotlin/com/tamin/taminhamrah/feature/workshops/ui/objectionStatus/components/ObjectionLabels.kt:15-28`

```kotlin
internal fun WorkShopObjectionStatus.label(): String = when (this) {
    WorkShopObjectionStatus.SUBMITTED -> "ثبت درخواست"
    WorkShopObjectionStatus.CALCULATION_REVIEW -> "بازنگری محاسبات"
    …
}
```

Eleven user-facing Persian strings live as literals in Kotlin. The project convention is that every
string the user reads comes from `composeResources/values/strings.xml`
(`docs/vault/Typography.md`) — and this MR already adds fifty entries to that file for every other
label on these screens, so the mechanism is right there.

The KDoc gives a reason worth answering directly:

> Plain strings here rather than `stringResource` because both the list card and the summary header
> (list, sms, document packages) need them outside any one screen's composable.

Neither half of that holds. The cited precedent, `PaymentSheetStatus.labelRes`, keeps a **resource
id** on the enum rather than literal text — the opposite of what this file does. And every call site
of `label()` is inside a `@Composable` (`ObjectionRow`, `ObjectionSummaryHeader`, the document and
SMS screens), where `stringResource(...)` is available regardless of which package it is in;
Compose-Multiplatform resources are module-wide, not screen-scoped.

**Suggested change:** follow the `PaymentSheetStatus.labelRes` precedent exactly — put a
`StringResource` on the enum (or a `when` returning `Res.string.…`) and call `stringResource` at the
use site.

**Same file family:** `.../components/ObjectionSummaryHeader.kt:83` has `text = "شمارهٔ اعتراض"`
inline while the surrounding labels on that same header come from `Res.string`; move that one too.

> **Round 2 — ✅ fixed.** Both enums now expose a `labelRes: StringResource` property (11 new
> `strings.xml` entries), and every call site — `ObjectionRow`'s two labels and its detail-row value,
> `ObjectionSummaryHeader`'s type/status text — resolves through `stringResource(...)`.
> «شمارهٔ اعتراض» in the header also moved to `Res.string.objection_status_objection_number`.

## 3. `WorkshopListScaffold`'s two optional row lambdas — Low

**File:** `feature/workshops/src/commonMain/kotlin/com/tamin/taminhamrah/feature/workshops/ui/components/WorkshopListScaffold.kt:53-58,113`

```kotlin
indexedRow: (@Composable (index: Int, item: T) -> Unit)? = null,
row: (@Composable (T) -> Unit)? = null,
…
) { index, item -> indexedRow?.invoke(index, item) ?: row?.invoke(item) }
```

`row` used to be required. It is now optional, alongside a second optional lambda that does the same
job, and the two are mutually exclusive with nothing enforcing that either is supplied. A caller that
forgets both compiles cleanly and renders an empty list — on a shared component used by eight
screens, that is a trap worth closing.

**Suggested change:** keep one required parameter and let the non-indexed callers ignore the index:

```kotlin
row: @Composable (index: Int, item: T) -> Unit,
```

or, if the churn across the existing call sites is not wanted, keep `row` required as it was and add
`indexedRow` as the optional override.

> **Round 2 — ✅ fixed.** Exactly the first option: `indexedRow` is gone, `row` is now the single
> required `@Composable (index: Int, item: T) -> Unit`, and all four call sites
> (`WorkshopsScreen`, `PaymentSheetsScreen`, `ObjectionStatusScreen`, plus whichever already passed
> an index) were updated in the same commit. Confirmed by build: `:feature:workshops` compiles.

## 6. An unknown objection type requests the objection document — Low, needs confirmation

**File:** `.../objectionStatus/document/ObjectionDocumentViewModel.kt:48`

```kotlin
val pdf = if (state.objectionType == WorkShopObjectionType.ARTICLE_SIXTEEN) {
    getArticleSixteenReportPdf(state.seqNo)
} else {
    getDebitObjectionPdf(state.seqNo)
}
```

The legacy code branched on the three known codes only and did nothing at all for anything else:

```kotlin
when (objectionType) {
    "1","2" -> … downloadDebitObjectionPDF …
    "3"     -> … downloadDebitObjectionReportPDF …
}
```

So a row whose `objectionType` the service sends as something new (or omits) now issues a request the
old app would not have made. It fails harmlessly — the download error path is already handled — and
the row's button is arguably better than a button that does nothing at all. Flagging it only so the
choice is deliberate: if the intent is "unknown type ⇒ no document", `hasDocument` in `ObjectionRow`
should also require `objectionType != UNKNOWN`.

> **Round 2 — still open, but now a named, tested behaviour rather than a silent side-effect.**
> `hasDocument` still only checks `objection.seqNo != null`, and `ObjectionDocumentViewModel`'s
> routing is unchanged — an unknown type still reaches `getDebitObjectionPdf`. What changed is that
> `ObjectionDocumentViewModelTest` now has `an unknown objection type falls back to the debit
> objection endpoint`, naming this on purpose. That reads as "we looked at this and this is the
> intended behaviour" rather than an oversight, but no comment or commit message says so explicitly,
> so it is left as `⬜ needs confirmation` rather than closed — a one-line comment on the `else`
> branch confirming the choice would let this be marked fixed outright.

## What was done well

- **Two legacy defects were found and fixed rather than reproduced.** Both are the kind that only
  turn up by actually reading the old code:
  - The legacy search wrote the objection number into a map key named `branchCode`, while the legacy
    data source only ever looked for `seqNo` — so searching by شمارهٔ اعتراض in the old app silently
    did nothing. Here it goes through `FilterProperty.SEQ_NO`, with a repository test
    (`getWorkShopObjections_filtersObjectionNumberOnSeqNo`) pinning it.
  - `SmsMessageDTO` gained an `id`, and the test explains exactly why with a real captured response:
    three messages carrying identical text and status were being collapsed into one by the shared
    paged-list dedup, so a server total of 5 rendered as 3.
- **`voteTypeDesc`.** The wire key was verified against two independent legacy models rather than
  assumed, and the test says so — the previous `description` spelling deserialised to null on every
  real response.
- **Magic codes became enums.** `WorkShopObjectionType` and `WorkShopObjectionStatus` replace the
  legacy `when (item) { "1" -> … }` string comparisons, each case carrying the Persian meaning as a
  doc comment, and the KDoc explains why `WorkShopObjectionType` is deliberately separate from
  `ObjectionKind` instead of folding the two together.
- **Server-side filtering with real paging.** The three filters travel in the query and the list pages
  properly through `PagedListState`, rather than fetching one wide window and filtering it in memory.
- **PDF routing parity.** `debit-objection-reports/objection/{seqNo}` for types 1–2 and
  `.../comitte/{seqNo}` for type 3 match the legacy mapping exactly, and the status→colour mapping
  (1 neutral · 2 negative · 3 info · 4 warning) matches `gridStatusTypeColor` while giving codes 5
  and 6 the sensible tints the old `else` branch flattened.
- **The `drainBytesOrNull` / event-not-state fix.** The KDoc on `ObjectionDocumentEvent` records a
  genuine bug and its cause: a single-use byte channel kept in UiState replayed an already-drained
  read on recomposition and reported a false "no document" for a download that had succeeded.
- **Vault updated.** `TopArea-System.md` now lists the real consumers and states, with a threshold,
  when `straddlePreviousSibling` should stop being copied and get extracted.
