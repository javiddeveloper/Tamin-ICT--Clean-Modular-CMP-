## 1. Pensioner/anonymous-user access block is completely missing — High

**File:** `feature/taminServices/src/commonMain/kotlin/com/tamin/taminhamrah/feature/taminServices/sendHistoryToInstitutions/SendHistoryToInstitutionsViewModel.kt:32-36`

```kotlin
private fun handleLoadUserInfo(): Flow<PartialState> = flow {
    emit(PartialState.Loading(true))
    val userInfo = getUserInfosUseCase()
    emit(PartialState.UserInfoLoaded(userInfo.toPresentation()))
}
```

Old_android's equivalent (`MergeHistoryFragment.onPensionCheck`, driven by
`CheckInsuredInfoResponse.typeUser`) explicitly blocks two user categories before letting them
reach this feature at all:

```kotlin
EnumTypeUser.ANONYMOUS.title -> showAlertDialog(ERROR, error_recive_data, BACK_TO_PREVIOUS)
EnumTypeUser.PENSIONER.title -> showAlertDialog(
    ERROR, "کاربر گرامی؛ شما بازنشسته يا مستمري بگير مي باشيد؛ به همین دلیل مجوز دسترسی به سرویس فوق را ندارید",
    BACK_TO_PREVIOUS
)
EnumTypeUser.INSURED.title -> mViewModel.getHistoryInfo()   // only insured users proceed
```

The new `UserInfoDN`/`GetUserInfosUseCase` pulls plain identity fields (name, national ID,
birth date, etc.) — there is no `typeUser`/pensioner/anonymous concept anywhere in the new data
model, and nothing in `SendHistoryToInstitutionsViewModel`, the screen, or the navigation wiring
(`FeatureNavigation.kt`'s `FeatureFlag.SEND_INSURANCE_HISTORY_TO_INSTITUTION ->
navigateToSendInsuranceHistoryToInstitutions()`) checks user type before allowing access.

**Failure scenario:** a pensioner (retired/receiving a pension, not an actively insured worker)
opens this feature from the main menu and can complete the entire wizard and submit a
"send my insurance history to my personal fund" request, even though old_android explicitly
considered this an invalid operation for that user category and blocked it.

**Suggested change:** reintroduce the user-type check (via whatever endpoint now exposes it) and
block/redirect pensioner and anonymous users with an explanatory message, before `SelectTypeStep`
is reachable.

> **مغایرت بیزینسی:** در نسخه‌ی قدیمی، قبل از رسیدن به این سرویس، نوع کاربر بررسی می‌شد: کاربران
> بازنشسته/مستمری‌بگیر و کاربرانی که اصلاً بیمه‌شده نیستند، با یک پیام خطای صریح («شما بازنشسته یا
> مستمری‌بگیر می‌باشید؛ به همین دلیل مجوز دسترسی به سرویس فوق را ندارید») مسدود می‌شدند و به
> صفحه‌ی قبل برمی‌گشتند؛ فقط کاربران بیمه‌شده‌ی فعال اجازه‌ی استفاده از این سرویس را داشتند. در
> نسخه‌ی جدید این بررسی به‌کلی حذف شده و هر کاربری — حتی بازنشسته یا کسی که بیمه‌شده نیست — می‌تواند
> کل ویزارد را طی کند و درخواست ارسال سابقه ثبت کند.

## 2. Disclaimer promises a record review that never happens — Medium

**File:** `feature/taminServices/src/commonMain/kotlin/com/tamin/taminhamrah/feature/taminServices/sendHistoryToInstitutions/components/ReviewStep.kt`

The review step shows the disclaimer text carried over verbatim from old_android
(`send_history_disclaimer` = *"قبل از ارسال سابقه به صندوق شخصی برای اعلام سابقه، لطفاً تمامی
سوابق خود را مشاهده و بررسی نمایید و درصورت اطمینان از صحت سابقه، آن را ارسال فرمایید."* —
"before sending, please view and review all your records..."), but `ReviewStep` only renders
full name, insurance number, the selected type label, and the fixed destination ("صندوق شخصی").
No actual insurance-history records are shown anywhere in this wizard.

In old_android this same disclaimer/button lived directly on the `MergeHistoryFragment` screen,
*after* the user had already viewed their full combined-history chart and list on that exact
screen — so "review your records" had something concrete to point at. In the new standalone
wizard, the instruction is disconnected from any actual record data the user can review.

**Suggested change:** either link/show the relevant history records (or a summary of them) in
the review step, or adjust the disclaimer copy so it doesn't promise a review step that doesn't
exist in this flow.

## 3. `type1`/`type2`/`type3` — unlabeled booleans threaded through 4 layers — Medium

**Files:** `SendHistoryToInstitutionsViewModel.kt:38,53`, `SendToInstitutionUseCase.kt`,
`core/core-data/.../HistoryRepositoryImpl.kt`, `core/core-network/.../HistoryApiServices.kt`

```kotlin
private fun handleConfirmTypeSelection(type1: Boolean, type2: Boolean, type3: Boolean): ...
sendToInstitutionUseCase(state.isType1Selected, state.isType2Selected, state.isType3Selected)
```

These booleans mean "همه" (all), "دستمزد" (wages), "تلفیقی" (combined) — but that mapping only
exists as a `listOf(...)` of display strings built inside `SendHistoryToInstitutionsScreen.kt`
(`typeLabels`), matched purely by index. Every layer below the screen — ViewModel, use case,
repository, API service — passes three anonymous booleans with no semantic meaning attached.

**Suggested change:** replace the three booleans with a named type (e.g. an enum
`HistoryCertificateType { ALL, WAGES, COMBINED }` or a small value class), or at minimum name the
parameters/state fields after what they represent instead of a positional `type1/2/3`.

## 4. No test at the ViewModel/feature level for the wizard's logic — Medium

**File:** `feature/taminServices/src/commonTest/` (directory does not exist)

The domain/data layers are tested (`GetUserInfosUseCaseTest.kt`, `SendToInstitutionUseCaseTest.kt`,
`HistoryRepositoryImplReportTest.kt`), but nothing tests
`SendHistoryToInstitutionsViewModel` itself: step navigation (`GoToNextStep`/`GoToPreviousStep`),
type-selection state updates, or the send flow's success/error handling.

**Suggested change:** add a `SendHistoryToInstitutionsViewModelTest` covering step transitions,
type selection, and both the success and error paths of `SendToInstitution`.

> **سناریوی بیزینسیِ بدون تست:** این صفحه یک ویزارد چندمرحله‌ای است (انتخاب نوع سابقه → بازبینی →
> ارسال) که رفتار جابه‌جایی بین مراحل، انتخاب نوع سابقه، و ارسال نهایی (موفق یا ناموفق) هیچ‌کدام
> تست نشده‌اند؛ فقط لایه‌های زیرین (درخواست شبکه و use case) تست دارند، نه منطق واقعی صفحه.

## What was done well

- The success-message/destination copy ("صندوق شخصی") is carried over correctly from
  old_android, and the disclaimer text is preserved verbatim (see item 2 for the caveat about
  where it's shown).

  `TaminErrorUriException` from generic failures and routes both through `errorParser`, matching
  the pattern used elsewhere in this module.

  `SendToInstitutionUseCaseTest.kt`, and a thorough `HistoryRepositoryImplReportTest.kt` with
  real mock JSON fixtures for empty/success cases across all three history types.

  INTENT>`) and is wired through `sharedModules`/`FeatureFlag`-driven navigation rather than a
  direct cross-feature import.
- No commented-out code was found anywhere in the diff.
