## 1. Header count is the loaded rows, not the total — Low

**File:** `feature/workshops/src/commonMain/kotlin/com/tamin/taminhamrah/feature/workshops/ui/workshopMembers/WorkshopMembersScreen.kt:141`

```kotlin
WorkshopSectionHeader(
    title = stringResource(Res.string.workshop_action_members),
    count = state.list.items.size,
)
```

`PagedListState` carries the service's own `total`, and its KDoc says why: *"[items] only ever holds
what has arrived, so a count built from it climbs as the user scrolls and reads as though the first
number was wrong."* Legacy showed no count at all, so this figure is new in the KMP screen — and it is
the one place a staff list is most likely to be read as «how many people work here». Only
`ContractRowsScreen` uses `list.total`; every other list in the module, including this one, uses
`items.size`.

> **سناریوی بیزینسی:** کارگاهی با ۸۷ نفر کارمند را در نظر بگیرید. تا وقتی کاربر اسکرول نکرده،
> عنوان لیست «۱۰» را نشان می‌دهد؛ بعد از هر بار بارگذاری بیشتر به ۲۰ و ۳۰ می‌رسد. کاربر ممکن است
> تعداد را تعداد کل کارکنان کارگاه بخواند، در حالی که سرور ۸۷ نفر برگردانده است.

**Suggested change:** use `state.list.total`. The same one-line change applies to the sibling lists
(`WorkshopRecentlyAddedMembersScreen`, `PaymentSheetsScreen`, …); doing it here first is enough for
this MR.

## 2. A stale «load more» can land in a new search's list — Low

**Files:** `feature/workshops/.../workshopMembers/WorkshopMembersViewModel.kt:52-71`,
`feature/workshops/.../ui/model/PagedListState.kt` (`loaded`)

`loadPage` builds its `PartialState.Loaded` from `uiState.value.list` *at the moment the response
arrives*, and `BaseViewModel` merges intent flows rather than switching between them, so applying a new
search does not cancel a request that is already in flight. If the user is scrolling (a page-`N`
request is out), then applies a search, and the page-`N` response comes back *after* the new page-0
response, `loaded(result, isFirstPage = false)` appends the old search's rows onto the new search's
list and advances `receivedCount` with them. The request also used the old `applied` search, because
that value is read when `loadMore` is called.

This is the shared paging convention of the whole module (the sibling ViewModels are written the same
way), so it is noted here rather than blamed on this MR; the new ViewModel and its tests simply copy it.
None of the 13 tests in `WorkshopMembersViewModelTest` runs a search while a page is loading.

> **سناریوی بیزینسی:** کاربر لیست کارکنان را اسکرول می‌کند و همزمان با بارگذاری صفحه‌ی بعد، کد ملی
> یک نفر را جستجو می‌کند. اگر جواب صفحه‌ی قبلی دیرتر از جواب جستجو برسد، افراد جستجوی قبلی به
> انتهای نتیجه‌ی جستجوی جدید اضافه می‌شوند و کاربر کسانی را می‌بیند که به کد ملی او ربطی ندارند.

**Suggested change:** drop a page result whose `search` (and workshop identity) no longer equals the
current `applied` when it arrives, or cancel the in-flight page when a new search is applied. Fixing it
in `PagedListState`/a shared helper covers every list at once. Add a test that applies a search while
a page-1 request is suspended.

## What was done well

- **The data-layer mapping is right, and it was checked against legacy rather than assumed**:
  `INSURANCE_ID` / `INSURANCE_NATIONAL_ID` go to `insurance.id` / `insurance.nationalId` exactly as the
  legacy members query does, so a national code is never sent as an insurance number.
- **A note on the commit message.** It says the old stakeholder screen "crossed the two over and
  filtered on the wrong column". In legacy the call site did cross them
  (`WorkshopStackHolderListFragment` passes `(…, nationalCode, insuranceNumber)` into parameters named
  `(…, insuranceId, nationalId)`), but the stakeholder data source reads only its `workshopId.*` keys, so
  the search values were dropped and the search never filtered on any column. The members screen was
  never affected. Harmless for this MR; worth correcting in the message if it is quoted elsewhere.
- **No `CancellationException` risk**: every error path uses `Flow.catch {}`, which does not intercept
  cancellation, and there is no `try/catch(Exception)` or `runCatching` in the new code.
- **No hardcoded Persian strings** in production code — every label goes through `strings.xml`; the
  only literals are the sample rows inside `@Preview` composables.
- **The employed/left rule is derived from data, not text**: `isEmployed = leavingWorkDate.isBlank()`
  (green vs red) rather than comparing against the word «اشتغال», and it has mapper tests, including a
  person whose status text says working but who has a leaving date.
- **No list `key` on purpose**, with the reason written next to it: a person who left and was taken on
  again produces two rows with the same insurance number and national id, and a repeated key would crash
  the list.
- **Solid ViewModel tests** — 13 cases covering first load, re-open not refetching, the missing identity
  failing without a request, paging, both search fields, blank fields being omitted, clear, removing one
  chip, error, retry and a half-missing name not rendering `null`.
- **Also fixes a legacy blemish**: legacy rendered «null null» for a person with a missing name half.
