## 2. Database version — High, still open

**Files:** `core/core-database/src/commonMain/kotlin/com/tamin/taminhamrah/data/local/TaminHamrahDatabase.kt:106`,
`core/core-database/schemas/com.tamin.taminhamrah.data.local.TaminXDatabase/4.json`

`ConstructionFileEntity` is still added at `version = 4`; this branch now also carries a `4.json` that
contains the new table. Meanwhile `develop` moved to `version = 5` (MR !247). The branch does not touch the
`version` line, so a merge takes `develop`'s `5` without any conflict — and the result is a build whose
version is `5` but whose schema (with `construction_files`) is not the schema `develop`'s version 5 was
created from. Room accepts an existing database only when version *and* schema hash match, and
`fallbackToDestructiveMigration` only runs for a *lower* stored version, so any install that already ran
`develop`'s version 5 refuses to open the database after updating (the "Room cannot verify the data
integrity" failure) until app data is cleared. I did not run it on a device; it follows from how Room
validates the schema. Note also that `develop` holds no `4.json`/`5.json` at all, while this branch adds a
`4.json` that no longer matches the version it will end up with.

**Suggested change:** after merging `develop`, set `version = 6` (re-check the number at the time), export
`6.json`, and drop or regenerate the `4.json` this branch added so the schema history is consistent.

## 4. Issuing a payment sheet — the guard does not hold — Medium, needs rework

**Files:** `feature/taminServices/.../paymentSheet/ui/PaymentSheetViewModel.kt:120`,
`.../installmentAndPaymentSheet/ui/InstallmentManagementViewModel.kt:88`

What was fixed: after issuing, the screen no longer toasts and leaves — it shows the legacy «the system is
processing, wait a few minutes» notice and stays; cancellation is rethrown. What was not:

```kotlin
private fun issuePaymentSheet(): Flow<PartialState> = flow {
    if (uiState.value.isIssuing) return@flow     // ← reads reduced state
    emit(PartialState.IssuanceFailed(false))
    emit(PartialState.IssuanceLoading(true))
    ...
```

The KDoc above it says a second confirm "must be rejected here". But `BaseViewModel` applies partial
states in a separate collector, so a second `IssuePaymentSheet` that starts before `isIssuing = true` has
been reduced still reads `false`. I ran this on a `StandardTestDispatcher` (which orders work like a real
main thread): two `IssuePaymentSheet` intents in a row reached the repository **twice** (expected 1, got 2).
The existing test for it uses `UnconfinedTestDispatcher`, which runs every step eagerly, so it cannot see the
problem. `InstallmentManagementViewModel` has the same guard. (The scratch test was removed; the worktree is
clean.) This is the same defect found in MR !249, where the fix was a plain `isSubmitting` field.

> **سناریوی بیزینسی:** کاربر در پنجره‌ی تأیید، دکمه‌ی «صدور برگه پرداخت» را دو بار پشت‌سرهم لمس
> می‌کند. انتظار این است که فقط یک برگه صادر شود؛ ولی در شرایط واقعی هر دو درخواست به سرور می‌رسد
> و برای یک بدهی دو بار برگه‌ی پرداخت صادر می‌شود (عملیاتی که قابل برگشت نیست). تست فعلی این حالت
> را نمی‌گیرد، چون در محیط تست همه‌چیز پشت‌سرهم و بدون تأخیر اجرا می‌شود.

**Suggested change:** keep the guard in a plain field set before the first suspension (`private var
isIssuing = false`, checked and set at the top, cleared in `finally`) in both ViewModels, and run the
double-issue test on a `StandardTestDispatcher` so it fails without the field.

## 11. Empty first emission shows «موردی یافت نشد» while loading — Medium

**Files:** `core/core-data/.../ConstructionInsuranceRepositoryImpl.kt:43-45`,
`.../viewDetail/ui/ViewDetailRequestViewModel.kt:62`, `.../viewDetail/ui/ViewDetailRequestScreen.kt:169`

```kotlin
val matchingLocalFiles = constructionFileDao.getConstructionFiles().first().filter { it.matches(search) }
emit(matchingLocalFiles.map { it.toDomain() })          // empty list when nothing is cached
```

The cache only ever holds the file(s) from the last detail search (the paged list does not write to it), so
for any file that was not just opened the local list is empty and that empty list is emitted first. The
ViewModel maps every emission to `Loaded`, which sets `isLoading = false`, and the screen renders
`EmptyStateMessage` when `file == null && !isLoading`. The empty state therefore stays up for the whole
network call. This existed before the fix for the first-ever open; the fix makes it the normal case, since
it removed the stale rows that used to fill the screen instead.

> **سناریوی بیزینسی:** کاربر روی یک پرونده می‌زند تا جزئیاتش را ببیند. تا وقتی جواب سرور نرسیده،
> به‌جای حالت «در حال بارگذاری» پیام «موردی یافت نشد» نمایش داده می‌شود و بعد از چند ثانیه اطلاعات
> جای آن می‌آید؛ کاربر ممکن است فکر کند پرونده وجود ندارد.

**Suggested change:** emit the local list only when it is not empty (the skeleton then stays until the
network answers), and add a repository test that an empty cache emits nothing before the remote result.

## 12. The per-installment «issue payment sheet» button issues the whole debit's sheet — Medium, needs confirmation

**Files:** `installmentAndPaymentSheet/ui/InstallmentManagementViewModel.kt:80-100`,
`installmentAndPaymentSheet/ui/InstallmentManagementScreen.kt`

The KDoc says it plainly: "the old app only ever issues a payment sheet per whole debit …; there is no
per-installment endpoint, so the per-row button in the new design triggers the same call as
`PaymentSheetViewModel.issuePaymentSheet`". In legacy, `InstallmentManagementFragment` is a read-only paged
list — its issue and certificate buttons are commented out — and issuing lived only on the payment-sheet
screen. The new list puts an issue button on every installment row, but tapping it issues the sheet for the
whole debit.

> **مغایرت بیزینسی:** در نسخه‌ی قدیمی، در صفحه‌ی «مدیریت اقساط» فقط فهرست اقساط دیده می‌شد و صدور
> برگه‌ی پرداخت جای دیگری (صفحه‌ی برگه‌ی پرداخت) انجام می‌شد. در نسخه‌ی جدید کنار هر قسط دکمه‌ی
> «صدور برگ پرداخت» هست، ولی با لمس آن برگه‌ی پرداخت کل بدهی صادر می‌شود، نه برگه‌ی همان قسط. کاربر
> فکر می‌کند برای یک قسط برگه گرفته، در حالی که برای کل بدهی صادر شده است، و صدور قابل برگشت نیست.

**Suggested change:** confirm with product that issuing from this list is wanted. If it is, the button
belongs once at the top (labelled for the whole debit), not on each row; if not, remove it and keep the list
read-only as in legacy.
