## 1. The detail screen can show another file's data — High

**Files:** `core/core-data/.../repository/constructionInsurance/ConstructionInsuranceRepositoryImpl.kt:35-58`,
`feature/taminServices/.../viewDetail/ui/ViewDetailRequestViewModel.kt:52-68`,
`.../viewDetail/contract/ViewDetailRequestContract.kt:22`

```kotlin
// ConstructionInsuranceRepositoryImpl.getConstructionFiles(search)
val localFiles = constructionFileDao.getConstructionFiles().first()   // whole table, search ignored
emit(localFiles.map { it.toDomain() })
try {
    val remoteFiles = remoteDataSource.getConstructionFiles(buildQuery(search)).list.orEmpty()
    constructionFileDao.replaceAll(remoteFiles.map { it.toEntity() })  // table := this search's result
} catch (e: Exception) {
    if (localFiles.isEmpty()) throw e                                   // otherwise: silently keep the cache
}
```

```kotlin
// ViewDetailRequestContract.kt
val file: ConstructionFilePR? get() = items.firstOrNull()
```

The only consumer of this flow is the detail screen, which asks for exactly one file by
`fileNo`/`reqNo`. But the cache is one shared table with no notion of «which search produced it»:

- **Every open shows the previous file first.** The first emission is the whole table (the last file
  that was opened), and `Loaded` clears the skeleton, so the screen paints file A's amounts, address,
  deadline and debit number under file B's header until the network answers.
- **A failed network call keeps file A on screen permanently**, with no error, because the catch
  rethrows only when the cache is empty.
- The test `getConstructionFiles should first emit local data then remote data` asserts precisely
  this: cache holds file `1`, the search returns file `2`, and the first emission is expected to be
  `[1]`. `getConstructionFiles should not throw when local data exists and remote fails` asserts the
  stale file stays.

Legacy had no cache for this feature at all (`getConstructionFilesWhitOutPaging` went straight to the
server), so this is new behaviour rather than a port.

> **سناریوی بیزینسی:** کاربر پرونده‌ی «الف» را باز می‌کند و بعد پرونده‌ی «ب» را. تا وقتی جواب
> سرور نرسیده، صفحه‌ی جزئیات پرونده‌ی «ب» مبالغ، آدرس، سررسید و شماره‌ی بدهی پرونده‌ی «الف» را
> نشان می‌دهد؛ و اگر اینترنت قطع باشد، همان اطلاعات اشتباه بدون هیچ خطایی روی صفحه می‌ماند.
> کاربر ممکن است مبلغ بدهی یا شماره‌ی بدهی یک پرونده‌ی دیگر را به‌جای پرونده‌ی خودش بخواند و
> پرداخت کند.

**Suggested change:** either drop the cache (legacy had none, and the paged list already bypasses
it), or key it by file/request number and filter the local read by the same search before emitting.
Either way, change the two tests above to assert the *correct* behaviour, and add one where the cache
holds a different file than the one requested.

## 2. New Room entity without a database version bump — High

**File:** `core/core-database/src/commonMain/kotlin/com/tamin/taminhamrah/data/local/TaminHamrahDatabase.kt:106`

`ConstructionFileEntity` and `ConstructionFileDao` are added to `TaminXDatabase`, but `version = 4`
is unchanged — identical to `develop`, where version 4 was set when the home-content entity was
added. The setup relies on `fallbackToDestructiveMigration(dropAllTables = true)`, which only runs
when the stored version is *lower* than the code's. With the same version and a different schema
hash, Room refuses to open the existing database (`Room cannot verify the data integrity... forgot to
update the version number`) instead of rebuilding it.

Consequence: any install that already ran a build at version 4 — every developer and tester on
current `develop`, and every user if that version has shipped — fails at the first database access
after updating to this branch, until app data is cleared. Fresh installs are unaffected. I did not
run this on a device; it follows from how Room validates the schema hash. No schema JSON for the new
version is exported either.

**Suggested change:** bump `version` to 5 and export the schema. Since `develop` is 73 commits ahead,
re-check the number at merge time in case another branch has already taken 5.

## 3. `CancellationException` swallowed — Medium

**Files:** `core/core-network/.../ConstructionInsuranceRemoteDataSourceImpl.kt:76`,
`core/core-data/.../ConstructionInsuranceRepositoryImpl.kt:47`,
`feature/taminServices/.../paymentSheet/ui/PaymentSheetViewModel.kt:97,116`

```kotlin
private suspend fun <T> call(block: suspend () -> T): T = try {
    block()
} catch (e: TaminErrorUriException) {
    throw errorParser.parseGeneralError(e)
} catch (e: Exception) {
    throw errorParser.parseGeneralError(TaminErrorUriException(ErrorUri.NO_CONNECTION_ERROR))
}
```

None of the four sites rethrows `CancellationException` (there is no reference to it anywhere in the
new production code). In the data source this turns a cancelled call into a fake «no connection»
error and hides the cancellation from the caller; in the two ViewModel sites (certificate download and
**issue payment sheet**) a user leaving the screen surfaces an error toast and a `Failed` state.

`call {}` is also a private copy of `ErrorParser.safeCall(tag)` in `NetworkUtils.kt`, which already
rethrows cancellation and classifies failures properly instead of labelling everything «no
connection».

**Suggested change:** replace `call {}` with `errorParser.safeCall(...)`, and add
`catch (e: CancellationException) { throw e }` before the general catch at the other three sites.

## 4. Issuing a payment sheet: no in-flight guard, and different post-issue behaviour — Medium

**Files:** `PaymentSheetViewModel.kt:107-118`, `PaymentSheetScreen.kt:140-145,358-392`

button (`enabled = !isIssuing`) are UI-level only; the button is disabled after the ViewModel has
processed the first intent, and `handleIntent` has no `if (isIssuing) return`. Because intents are

After success the screen does:

```kotlin
state.issuanceMessage?.let { message ->
    LaunchedEffect(message) { toaster.success(message); onBackClicked() }
}
```

Legacy (`IssuanceAndManagementPaymentSheetFragment.kt`) showed a fixed notice —
«متقاضی محترم، سامانه درحال پردازش اطلاعات می‌باشد. لطفاً دقایقی منتظر بمانید تا پس از انجام عملیات،
برگ پرداخت صادر شده در لیست نمایش داده شود» — and stayed on the screen. Neither version refreshes the
list.

> **سناریوی بیزینسی:** در نسخه‌ی قدیمی بعد از صدور برگه‌ی پرداخت، به کاربر گفته می‌شد که سامانه
> در حال پردازش است و باید چند دقیقه صبر کند تا برگه در لیست دیده شود. در نسخه‌ی جدید فقط پیام
> سرور (که ممکن است خالی باشد) به‌صورت toast نشان داده می‌شود و صفحه بلافاصله بسته می‌شود؛ کاربر
> برگه‌ی جدید را نمی‌بیند و نمی‌داند باید صبر کند، و ممکن است دوباره درخواست صدور بدهد.

**Suggested change:** add an `isIssuing` early return in the ViewModel, show the legacy wait message
(from `strings.xml`) and stay on the screen. Add tests for a repeated `IssuePaymentSheet` intent and
for the success path.

## 5. Payment-sheet screen differs from legacy — Medium, needs confirmation

**File:** `feature/taminServices/.../paymentSheet/ui/PaymentSheetScreen.kt:198-201,247-254`

Compared with `IssuanceAndManagementPaymentSheetFragment` / `PaymentSheetAdapter`:

- **Certificate button always visible.** Legacy hid it when the file has no issued sheets
  (`btnPaymentCertificate.gone()`), since there is nothing to certify. The new bar always renders it,
  so with no sheets the user can request a certificate that can only fail.
- **Request-summary block missing.** Legacy shows an expandable block at the top (amount, deadline,
  file/request number, workshop, branch, debit). `ConstructionFilePR.getRequestInfoIssuancePaymentSheet()`
  exists but is never called.
- **Status.** Legacy compares `status == "1"` → «پرداخت شده» (green), anything else → «پرداخت نشده»
  (red). The new code prints the server's `status` string as-is and picks a colour by looking for
  «پرداخت شده» / «انتظار» / «منقضی» / «باطل» inside it. The test fixture uses the text
  «پرداخت شده», legacy compares against the code `"1"`; I cannot tell from the client which one the
  live service sends. If it is the code, the user sees a bare «1» with a neutral colour.

> **سناریوی بیزینسی:** در نسخه‌ی قدیمی، وقتی هیچ برگه‌ای صادر نشده بود دکمه‌ی «گواهی پرداخت» پنهان
> بود و بالای صفحه خلاصه‌ی درخواست (مبلغ، سررسید، شماره‌ی پرونده و درخواست، کارگاه و شعبه) دیده
> می‌شد. در نسخه‌ی جدید دکمه همیشه هست و خلاصه‌ی درخواست نمایش داده نمی‌شود. وضعیت برگه هم در
> قدیمی فقط «پرداخت شده» (سبز) یا «پرداخت نشده» (قرمز) بود؛ در جدید بستگی دارد سرور متن بفرستد یا
> کد.

**Suggested change:** hide the certificate button when the list is empty, render the request summary
(the helper already exists), and confirm with the backend team whether `status` is a code or a
description; map it explicitly to paid/unpaid the way legacy did.

## 6. Beneficiaries list keyed by `nationalCode` — Medium

**File:** `feature/taminServices/.../beneficiaries/ui/BeneficiariesScreen.kt:186-188`

```kotlin
items(..., key = { it.nationalCode ?: it.hashCode() }) { beneficiary -> ... }
```

The service returns one row per beneficiary *role* (owner «01» / applicant «02»). A builder who is
both owner and applicant of the same file yields two rows with the same national code, and
`LazyColumn` throws `IllegalArgumentException: Key ... was already used` when it lays them out. Legacy
used a plain adapter, which has no such constraint. I could not confirm that the live service returns
the same national code for both roles, but it is the natural shape of the data.

**Suggested change:** key on a combination that is unique per row (national code + owner type, or the
list index), or drop the key.

## 9. Magic codes and hardcoded Persian used as logic — Low

- **`"51"`** (installment debit status) is compared as a bare string in `ConstructionFilePR.kt:165`,
  and as two separate copies of `INSTALLMENT_DEBIT_STATUS_CODE` in `ConstructionFileCard.kt:206` and
  `ConstructionActionsSheet.kt:29`. The meaning matches legacy; the problem is three independent
  copies of a type code with no enum.
- **Status colouring by Persian substring:** `paymentStatusTint` matches «پرداخت شده» / «انتظار» /
  «منقضی» / «باطل», and the installment screen matches «معوق» / «پرداخت شده»
  (`STATUS_KEYWORD_*`). The code comments say no status code exists on these models, so an enum is
  not possible today — but the literals are still Persian text driving behaviour, and a rewording on
  the server silently loses the colour. Worth confirming with the backend whether a code is sent.
- **`"ریال"`** is hardcoded as `RIAL_UNIT` in both `ConstructionFilePR.kt:39` and
  `ConstructionFileCard.kt:61`; it belongs in `strings.xml`.

**Suggested change:** one `DebitStatus` enum in `core-domain` for `"51"`; move `"ریال"` to a string
resource; for the substring matching, ask for a code and map it to an enum.

## What was done well

- **The data vertical is a faithful port**: endpoint (`bld-request-services/building-workshops/normal`),
  DTO `SerialName`s, the four filter properties (`fileNo`, `reqNo`, `workshop.workshopId`,
  `workshop.branchCode`) with EQ semantics and blank-field skipping, page size, and «request/file
  number of 0 is skipped» all match legacy.
- **Screen-to-screen arguments are correct** — the classic source of swapped-parameter bugs here:
  payment sheet gets `(debitNumber, brhCode)`, installment letters get `(workshopId, brhCode)`,
  beneficiaries get `(requestNumber, fileNumber, requestDate)`, exactly as in legacy's fragment.
- **The operations-menu rule matches legacy**: status `"51"` shows «مدیریت پرداخت اقساط» instead of
  «صدور و مدیریت برگه پرداخت», beneficiaries always offered.
- **Fee rows keep legacy's order and the total comes from the server's `totalPayment`** instead of
  being re-derived, and beneficiaries send `requestDate` unconverted, as legacy does.
- **No mock or sample data remains in production code** — the earlier «remove mock data» commits did
  their job; the only hardcoded names, ids and dates are in `@Preview` composables.
- **Very broad test coverage**: API service, remote data source, repository, every use case, and all
  five ViewModels have tests, with JSON fixtures for the responses; the whole suite passes. The
  certificate-PDF state was moved into the ViewModel, which is the right place for it.
- **DI and navigation are wired correctly**: five `viewModelOf` registrations in
  `TaminServicesModule`, the routes in the nav graph, and the entry goes through the
  `FeatureFlag.CONSTRUCTION_INSURANCE` gate.
