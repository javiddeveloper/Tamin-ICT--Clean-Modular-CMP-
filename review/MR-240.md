## 1. Dispatcher and network layer re-swallow `CancellationException` that inner code correctly rethrows — High

**Files:** `feature/agent/src/commonMain/kotlin/com/tamin/taminhamrah/feature/agent/service/AgentActionDispatcher.kt:109`,
`core/core-network/src/commonMain/kotlin/com/tamin/taminhamrah/dataSource/agent/AgentRemoteDataSourceImpl.kt`
(`checkChatAllowed`, `sendServicePrompt`, and three more methods)

Every individual `AgentService` implementation in `feature/agent/service/impl/` (12 files —
`AverageWageAgentService`, `DastmozdInfosAgentService`, `EdictAgentService`, etc.) does this
correctly:

```kotlin
} catch (e: CancellationException) {
    throw e
} catch (e: Exception) {
    AgentServiceResult.Error(...)
}
```

But the dispatcher that calls into all of them does not:

```kotlin
// AgentActionDispatcher.kt:109
return try {
    val result = handler.execute(...)   // one of the correctly-rethrowing services above
    ...
} catch (e: Exception) {
    AgentServiceResult.Error(message = e.message ?: "Service execution error", cause = e)
}
```

A `CancellationException` correctly rethrown by `handler.execute()` gets caught right back here,
converted into an `AgentServiceResult.Error`, and never reaches the coroutine machinery that's
supposed to see it. The exact same shape repeats in `AgentRemoteDataSourceImpl.kt` — e.g.:

```kotlin
// AgentRemoteDataSourceImpl.kt:56-64
override suspend fun checkChatAllowed(): ChatAllowedDTO {
    return try {
        agentApiService.checkChatAllowed()
    } catch (e: TaminErrorUriException) {
        throw errorParser.parseGeneralError(e)
    } catch (e: Exception) {
        throw errorParser.parseGeneralError(TaminErrorUriException(ErrorUri.NO_CONNECTION_ERROR))
    }
}
```

— here a cancelled coroutine (e.g. the user leaves the assistant screen mid-request) doesn't just
have its cancellation swallowed, it gets actively **relabeled** as a connection error, which could
surface a confusing toast on a screen that's already being torn down. The same pattern repeats at
4 more call sites in this file (`sendServicePrompt`, and others using the identical
`catch (TaminErrorUriException) { ... } catch (Exception) { ... }` shape).

The fact that `catch (e: ChatTokenExpiredException) { throw e }` already exists as a dedicated
rethrow branch in `sendServicePrompt` (right next to the `TaminErrorUriException` catch) shows the
pattern for "rethrow this specific type before the general catch" is already known and used in this
same file — it just wasn't extended to `CancellationException`.

**Suggested change:** add `catch (e: CancellationException) { throw e }` before the general
`catch (e: Exception)` at all 6 locations (1 in `AgentActionDispatcher.kt`, 5 in
`AgentRemoteDataSourceImpl.kt`).

**Author response:** fixed as suggested at all 6 sites.

## 2. `CancellationException` also swallowed by `runCatching {}` on every prompt send — High

**Files:** `core/core-network/src/commonMain/kotlin/com/tamin/taminhamrah/apiService/agent/AiChatTokenPlugin.kt:29`,
`core/core-domain/src/commonMain/kotlin/com/tamin/taminhamrah/useCases/agent/GetAgentPersonalInfoUseCase.kt:34,47`

```kotlin
// AiChatTokenPlugin.kt:28-29 — inside a Ktor Send-hook, itself a suspend context
val body = if (response.status == HttpStatusCode.OK || response.status == HttpStatusCode.BadRequest) {
    runCatching { response.bodyAsText() }.getOrDefault("")
} else { "" }
```

```kotlin
// GetAgentPersonalInfoUseCase.kt:34
val identity = runCatching { userRepository.getIdentityInfo().firstOrNull() }.getOrNull()
...
// :47-48
val id = runCatching { pensionRepository.getPensionerId().firstOrNull()?.firstOrNull()?.pensionerId }
    .getOrElse { return null }
```

`runCatching` catches `Throwable`, `CancellationException` included, and its own doc comment
explicitly warns about this ("this function... should not be used for a Job's cancellation" is the
standard caveat for this exact API). `GetAgentPersonalInfoUseCase`'s own doc comment says this runs
on **every** assistant prompt (`personal_info` is attached to every request) — so this isn't an edge
case, it's on the hot path for the entire assistant feature.

Contrast with `ResolveDeepLinkUseCase.kt` (same MR, different half of the diff), which gets this
exactly right: `catch (e: CancellationException) { throw e }` before its generic catch, at both of
its two call sites.

**Suggested change:** replace `runCatching { ... }` with an explicit `try { ... } catch (e:
CancellationException) { throw e } catch (e: Exception) { ... }`, matching `ResolveDeepLinkUseCase`'s
pattern already present elsewhere in this same MR.

**Author response:** fixed as suggested in both files (3 sites).

## 3. Voice recorder's `stop()` can block the main thread for up to 1 second — Medium, needs confirmation

**Files:** `feature/agent/src/androidMain/kotlin/com/tamin/taminhamrah/feature/agent/audio/VoiceAudio.android.kt:106-116`,
`feature/agent/src/commonMain/kotlin/com/tamin/taminhamrah/feature/agent/ui/AgentViewModel.kt:989-993`

```kotlin
// VoiceAudio.android.kt
private const val WRITER_JOIN_TIMEOUT_MS = 1_000L
...
override fun stop() {
    ...
    runCatching { writer?.join(WRITER_JOIN_TIMEOUT_MS) }
    ...
}
```

```kotlin
// AgentViewModel.kt:989-993
override fun onCleared() {
    ...
    voiceRecorder.stop()
    ...
    super.onCleared()
}
```

`ViewModel.onCleared()` runs synchronously as part of ViewModel lifecycle teardown, which the
platform invokes on the main thread. If the writer thread is mid-`AudioRecord.read()` when the user
navigates away from the assistant screen while recording, `stop()`'s `Thread.join(1000)` can hold the
main thread for up to a full second, which would show as a visible UI freeze during navigation.

The code comment nearby explains *why* the join exists (the WAV header must be finalized before
anything tries to upload the file), which is a real constraint — this may be an accepted trade-off
rather than an oversight.

**Suggested change:** not necessarily a required fix — confirm whether this was a deliberate
trade-off. If not, consider moving the `stop()` call off the main thread (e.g. dispatch it in
`onCleared()` via a non-cancellable background scope) so the join can't block navigation.

**Author response:** not an accepted trade-off — fixed. `VoiceRecorder.stop()` is now `suspend` and waits
for the WAV header on `Dispatchers.IO`; a new non-blocking `cancel()` is what `onCleared()` calls. It
drops the recording without waiting: the writer thread releases `AudioRecord` itself and deletes the
file. iOS follows the same interface (`AVAudioRecorder.deleteRecording()` on cancel).

## 4. Some legacy externally-reachable deep-link hosts have no equivalent intent filter — Low, needs confirmation

**File:** `androidApp/src/main/AndroidManifest.xml:33-69`

Legacy (`old_android/app/src/main/AndroidManifest.xml:101-147`) registered `mytamin://` intent
filters for several bare hosts as external entry points: `callback_freelance`, `callback_optional`,
`callback_fraction`, `callback`, `workers_payment_callback`, `workers_payment_info`,
`edit_phone_number`, `prescription_detail`, in addition to `login`/`logout`. The new manifest only
registers `login`, `logout`, `payment_callback`, and `feature`. The various payment-callback hosts are
correctly consolidated into the one `payment_callback` host (matches legacy
`MainActivity.showCallbackResponse`, which treated them identically) — but `workers_payment_info`,
`edit_phone_number`, and `prescription_detail` were separate, externally-browsable links in legacy,
and no equivalent intent filter for their bare-host shape was found in the new manifest.

I could not confirm any external sender (push notification, SMS, backend-generated link) that still
emits the old bare-host shape — no FCM/notification deep-link construction was found in `old_android`
— so this may well be moot. But if something outside the app still sends
`mytamin://prescription_detail?...` (not wrapped in `/feature/...`), Android will no longer route it
to the app at all — no matching intent filter means the OS shows "no app can handle this" rather than
even an in-app "blocked" message.

**Suggested change:** confirm with the backend/notification team whether any external channel still
generates links in the old bare-host shape for these three cases. If not, this is fine as-is.

**Author response:** made safe without waiting for that answer. `mytamin://prescription_detail?…` and
`mytamin://workers_payment_info` have intent filters again and go through the same flag gate
(`DeepLinkParser` accepts a known key as the host; `MainActivity` and iOS `handleIncomingUrl` route
them). `edit_phone_number` is left out: there is no `FeatureFlag`/screen for it in this codebase yet.

## 5. No test for concurrent prompts racing on token refresh — Low

**Files:** `core/core-domain/src/commonMain/kotlin/com/tamin/taminhamrah/useCases/agent/SendAgentPromptUseCase.kt:77`,
`core/core-domain/src/commonTest/kotlin/com/tamin/taminhamrah/useCases/agent/SendAgentPromptUseCaseTest.kt`

`SendAgentPromptUseCase` uses a shared `Mutex` (`refreshLock`) specifically so that if two prompts
are in flight and both hit an expired token, only one refresh call happens and both requests proceed
with the newly-refreshed token — a real, deliberate concurrency guard. Nothing in
`SendAgentPromptUseCaseTest.kt` exercises two prompts racing against an expired token to confirm this
actually holds (only one `checkChatAllowed()` call, both requests succeed with the fresh token).

> **سناریوی بیزینسی جاافتاده:** اگر کاربر هم‌زمان چند پیام به دستیار بفرستد درحالی‌که توکن چت منقضی
> شده، طبق کد باید فقط یک‌بار توکن تازه گرفته شود و همه‌ی پیام‌ها با همان توکن جدید ارسال شوند — این
> رفتار (که یک قفل مخصوصاً برایش نوشته شده) هیچ تستی ندارد.

**Suggested change:** add a test that launches two concurrent `SendAgentPromptUseCase` calls against
a fake that reports the token expired, and asserts `checkChatAllowed()`/refresh happens exactly once.

**Author response:** the test found a real bug — the `Mutex` only serialised the refreshes, so every
waiting prompt still called `chat-allowed`. Fixed: inside the lock, a token newer than the one that
failed is reused. Tests: three concurrent prompts → one check, all resend with the new token; a refused
refresh → the waiting prompt asks again.

## What was done well

- **The deep-link gate matches its own documented contract precisely.** `DeepLinkParser`,
  `DeepLinkKey`, `ResolveDeepLinkUseCase`, and `DeepLinkDispatcher` correctly handle every format
  `docs/vault/Deep-Links.md` describes (`@key`, `mytamin://feature/key`, `tamin://feature/FLAG_NAME`,
  `agent://nav/key`, `agent://prompt?text=`, host-restricted `https://` for agent-originated links),
  and `CancellationException` is correctly rethrown in `ResolveDeepLinkUseCase` itself — the exact
  pattern items 1-2 above are asking for, already present elsewhere in this same MR. Test coverage
  (`DeepLinkParserTest`, `ResolveDeepLinkUseCaseTest`) is thorough: enabled/disabled/temporary/
  web-view/enabled-with-error/missing-from-menu/unreadable-menu/assistant-permission-gating are all
  covered.
- **`PrescriptionDetailLink` correctly ports legacy's argument semantics** — the `"0"` sentinel for
  "no id"/"no child", and the `ARG_REQUEST_TYPE`-vs-`PRES_TYPE` fallback, verified against
  `old_android`'s `ElectronicPrescriptionDetailFragment`.
- **The `DeepLinkKey` catalog's apparent gaps aren't actually gaps** — every legacy nav key missing
  from the new enum (`add_dependent`, `edit_phone_number`, `insurance_registration`, etc.) corresponds
  to a feature that doesn't have a `FeatureFlag` entry in this codebase yet at all, so none of them
  could be added regardless of this MR.
- **Token caching/refresh logic faithfully follows the documented contract**
  (`AI-Agent-API-Contract.md` §2-3): token cleared before each `chat-allowed` check, permission
  survives transport failures, one-shot refresh-and-resend on `ChatTokenExpiredException`, token read
  fresh at send time rather than cached on the screen. Well-tested (refresh-once,
  double-rejection-fails, refusal-during-refresh, per-prompt personal-info/user-type resolution).
- **WAV format is exactly what the server requires** (16kHz mono 16-bit PCM, 44-byte RIFF header) —
  matches `AI-Agent-API-Contract.md`'s explicit warning that anything else gets a silent 403 from the
  server firewall.
- **Server-coded fields go through enums, not magic strings** (`PensionerStatusDN`,
  `PayRollItemKindDN`, `GenderCodeDN`, `DependentRelationDN`, etc.) — this MR is precisely what
  introduces that discipline for the assistant's service adapters, correctly following rule 7.
- **No hardcoded Persian strings anywhere in the diff.**
