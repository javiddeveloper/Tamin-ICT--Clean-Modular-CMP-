## 1. Stats strip now pages through every agreement, untested — Medium

**File:** `feature/workshops/src/commonMain/kotlin/com/tamin/taminhamrah/feature/workshops/ui/WorkshopsViewModel.kt:99-135`

```kotlin
private fun countStats(firstPage: PagedListState<WorkshopPR>): Flow<PartialState> = flow {
    var all = firstPage
    while (all.hasMore) {
        val next = getEmployerAgreements(WorkshopListQuery(page = all.nextPage))
        all = all.loaded(next, isFirstPage = false) { it.toPresentation() }
    }
    emit(PartialState.StatsLoaded(all.items.toStats()))
    // A later page failing still leaves the figures of what did arrive, counted the same way.
}.catch { emit(PartialState.StatsLoaded(firstPage.items.toStats())) }
```

Before this MR, the stats strip (total + active count on the workshops list) cost exactly two
requests regardless of list size: the first page load, plus one request with
`WORKSHOP_STATS_PAGE_SIZE = 1` just to read the server's `total` for `status = ACTIVE`. This MR
removes `WORKSHOP_STATS_PAGE_SIZE` entirely and instead loops `getEmployerAgreements` at the normal
page size (10) until `hasMore` is false, folding every page through `PagedListState.loaded` so a
workshop repeated across several agreements is only counted once. The reasoning is sound — the
server's own `total` double-counts those repeats, which is exactly the `distinctTotal` bug this same
commit fixes for list headers — but the fix for the *stats strip* specifically requires reading every
row's `status`, which can't be done from a single `total` figure, so it resorts to full pagination
instead. The code's own comment says as much: *"an employer with hundreds of agreements pays that on
opening. Ask for a server-side distinct count if that ever shows."*

No test covers `countStats`: not the loop itself, not that a failure partway through still emits the
partial figures gathered so far (the `.catch` fallback), and not that the numbers it produces are
actually deduplicated the way `distinctTotal` is (which does have its own five tests).

> **سناریوی بیزینسی مهمی که تست ندارد:** کارفرمایی با تعداد زیادی قرارداد/کارگاه (مثلاً چند صد
> مورد) صفحه‌ی «کارگاه‌های من» را باز می‌کند. سیستم برای نمایش عدد «تعداد کل» و «تعداد فعال» بالای
> لیست، باید تک‌تک تمام صفحه‌ها را پشت‌سرهم از سرور بگیرد تا بتواند شمارش درستی انجام دهد — که هم
> باز شدن صفحه را کند می‌کند و هم اگر یکی از این درخواست‌ها وسط راه با خطا مواجه شود، هیچ تستی
> تضمین نمی‌کند که حداقل عددهای تا همان‌جا محاسبه‌شده درست نمایش داده شوند.

**Suggested change:** if the backend can offer a distinct/deduplicated count directly (as the code's
own comment suggests), use that instead of paginating client-side. Short of that, add tests for the
loop — multi-page aggregation, the partial-failure fallback, and that duplicate workshops across
pages are not double-counted — so a regression here is caught rather than only discovered by a large
employer's slow load.

## What was done well

- **The national-ID search fix is a real correctness improvement, not just a rename.** Commit
  `2b54d5640` traced the stakeholder endpoint's actual filter property (`nationalId`, flat — not
  nested under `workshopId.*`, which answers 500) and pinned it with a repository test. Legacy's own
  search on this screen sent the filter to a property the server silently dropped, so this MR's
  version is the first one that actually filters.
- **`StakeHolderRole` is exactly the pattern rule 7 asks for**: a four-value enum keyed by the
  server's code, each mapped to a `StringResource`, with an explicit fallback (show the raw
  `stackType`) for a code outside the known set — matching legacy's own `getStackTypeDescription()`
  one-for-one, cited directly in the KDoc rather than reverse-engineered.
- **The stale-page race is correctly guarded.** `WorkshopStackholdersViewModel` claims a `latestLoad`
  token before each request goes out and checks it before emitting, so a slow answer to a superseded
  search or page can't be appended to a list it no longer belongs to — the exact class of bug found
  (unguarded) in a sibling MR's members screen.
- **The list is immune to the duplicate-key crash** a sibling beneficiaries screen hit:
  `WorkshopListScaffold` keys each row by `"$index:${keyOf(item)}"`, so two stakeholders sharing a
  national ID (two roles for the same person) can never collide.
- **No hardcoded Persian strings in production code** — the only literals are `@Preview` sample data.
- **Broad test coverage on the new screen**: `WorkshopStackholdersViewModelTest.kt` (291 lines) and
  `WorkshopStackHolderUiMapperTest.kt` cover the role mapping, search, paging and the stale-load
  guard directly.
