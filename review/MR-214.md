## 1. Job search fallback and retry paths are untested — Medium

**File:** `feature/taminServices/src/commonTest/kotlin/com/tamin/taminhamrah/feature/taminServices/inspection/InspectionViewModelTest.kt`

The generic append/replace paging mechanics are already covered separately by
`core/core-domain/src/commonTest/.../paging/PaginatorTest.kt`, so this is not about re-testing
`Paginator` itself — it's about the two pieces of business logic this ViewModel adds on top of it
that have no coverage at all:

```kotlin
/** `jobDescription LIKE "*query*"`, or `LIKE "*"` (match all) when [query] is blank. */
private fun jobBaseQuery(query: String): ApiQueryParamDN = ApiQueryParamDN(
    filters = listOf(
        ApiFilterDN(
            FilterProperty.JOB_DESCRIPTION,
            query.trim().takeIf { it.isNotEmpty() }?.let { "*$it*" } ?: "*",
            FilterOperator.LIKE,
        )
    )
)
```

`searchBranches_addsNameLikeFilter` exists and tests exactly this shape for branches, but there is
no `searchJobs_...` counterpart — the fallback-to-`"*"` case (ported correctly from
`SubmitInspectionRequestViewModel.getJob`, per the file header) is exactly the kind of detail a
future "clean up the filter builder" pass could quietly break, on the one list where a blank filter
would otherwise return nothing.

Separately, `handleRetrySource` — the per-source error-clearing dispatch for
`USER_INFO`/`BRANCHES`/`JOBS` — has no test for any of its three branches, so nothing proves a retry
on the branch picker doesn't also clear the job picker's error (or vice versa).

**Suggested change:** one test mirroring `searchBranches_addsNameLikeFilter` for the job list's
blank-query case, and one retry test per source (branch error → retry → only the branch error
clears, job error untouched).

> **Round 2 — ✅ fixed, and more thorough than asked.** `searchJobs_blankQuery_sendsMatchAllLikeFilter`
> and `searchJobs_nonBlankQuery_wrapsQueryInLikeWildcards` cover the exact blank/non-blank shapes
> suggested. For retry, all **three** sources got a dedicated test (the suggestion only asked for
> branch/job): `retrySource_branches_...`, `retrySource_jobs_...`, and
> `retrySource_userInfo_clearsOnlyUserInfoErrorAndLeavesPickerErrors` — each asserts the retried
> source's error clears while the other two remain, which is exactly the isolation property that
> mattered.

## What was done well

- **The two legacy filter rules that actually mattered were checked and preserved**, not just
  carried over by copy-paste luck: branches still require `type=1`/`status=1`, and a blank job
  search still sends `LIKE "*"` rather than an absent filter (which would have silently returned
  zero results on the one field the old app deliberately worked around).
- **Per-source error isolation carried forward correctly.** `InspectionRequestErrorSource` gives the
  branch picker, job picker, and step-1 profile fetch independent retryable errors — retrying one
  doesn't touch the others, matching the shape already established elsewhere in this codebase
  (`EmployerOnlineServicesErrorSource`, `WorkshopsUiState`'s per-action gating).
- **`InspectionSelectionSheet` is a clean, single generic component** for both the branch and job
  pickers — debounced server search, shared `OnLoadMore`/`PagingFooter` primitives, distinct
  loading/error/empty states, and a stable `key = { it.id }` — rather than two near-duplicate sheets.
- **The old, now-redundant client-side search UI was deleted outright**
  (`InspectionSearchSheet.kt`, `InspectionFilterChipRow.kt`, `InspectionSearchEmptyState.kt`,
  `InspectionSearchValidation.kt`), not left dead alongside the new server-side search.
- **The keyboard/padding fix is a real simplification, not a patch.** Removing the outer
  `Scaffold`'s `imePadding()` and switching to `.padding(padding)` (both edges from the scaffold)
  instead of `padding(top = ...)` plus a manual bottom `Spacer` collapses three overlapping padding
  mechanisms into one, applied consistently across all six occurrence steps and the matching
  inspection steps.
- **Round 2: both fixes landed in one focused commit** with test coverage that went beyond what was
  asked (three retry-isolation tests instead of the two suggested), rather than the minimum needed to
  close the items.
