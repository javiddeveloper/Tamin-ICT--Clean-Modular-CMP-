## 1. No unit tests for the feature's ViewModels — High

**Files:** everything under
`feature/requestPaymentForIllDays/src/commonMain/kotlin/.../ui/{wizard,intro,calculate}/` — there
is no `commonTest`/`androidUnitTest` source set anywhere in this module.

`IllDaysWizardViewModel` alone carries a large amount of business logic ported from the legacy
fragment: date-range validation (start ≤ end, ≤365-day span), the covid auto-fill-vs-manual-dates
branch, document format/size/duplicate/max-count checks, and the final request-assembly mapping
(`illnessKind`, `workStatus` codes). `IllDaysCalculateViewModel` has its own date/marital-status
validation and two-line result parsing. None of it is covered by a test — contrast with the rest
of this MR, where the data layer (`RequestPaymentForIllDaysMapperTest`,
`RequestPaymentForIllDaysRepositoryImplTest`, `RequestPaymentForIllDaysApiServiceTest`,
`RequestPaymentForIllDaysRemoteDataSourceImplTest`, `RequestPaymentForIllDaysUseCasesTest`,
`RequestPaymentForIllDaysUiMapperTest`) is well tested, and with sibling MRs (!196, !197) that do
include a `*WizardViewModelTest`/`*ViewModelTest` for their own feature module.

> **یافته‌ی تست (فارسی):** مهم‌ترین بخش این فیچر — یعنی ویزارد ثبت درخواست غرامت دستمزد ایام
> بیماری — اصلاً تست واحد ندارد. سناریوهای بیزینسی مهمی مثل «تاریخ پایان زودتر از شروع»، «بازه‌ی
> استعلام بیش از ۱۲ ماه»، «انتخاب کووید و دریافت خودکار بازه‌ی زمانی از سرور در مقابل ورود دستی
> تاریخ»، «حداکثر ۵ مدرک و رد کردن فرمت/حجم/مدرک تکراری»، و «ساخت درخواست نهایی برای ارسال به
> سرور» هیچ‌کدام تست ندارند. اگر رفتار این ویزارد در آینده به‌اشتباه تغییر کند، هیچ تستی نیست که
> این تغییر را گزارش بدهد.

**Suggested change:** add at least a `IllDaysWizardViewModelTest` covering the validation/covid/
document-upload/submit paths, mirroring the coverage style already used in `InquiryEducationViewModelTest`
(MR !197) or `PensionSurvivorViewModelTest` (MR !196).

> **Round 2 (commit `d7e51f877`):** Fixed. Added `IllDaysWizardViewModelTest` (covering single-vs-

## 2. First branch/workshop is auto-selected regardless of how many exist — Medium

**File:** `feature/requestPaymentForIllDays/src/commonMain/kotlin/.../ui/wizard/IllDaysWizardViewModel.kt:166-169`

```kotlin
val branches = info.branchWorkshops.toImmutableList()
val selected = branches.firstOrNull()
emit(PartialState.BranchesLoaded(branches = branches, selected = selected))
```

This unconditionally pre-selects `branches.firstOrNull()`, so `canGoNextFromStep1` is satisfied
without any user interaction as soon as there is at least one branch — including when there are
several.

> **یافته‌ی بیزینسی (فارسی):** در `old_android` (`RequestPaymentForillDaysFragment.showBranchResult`)
> فقط وقتی بیمه‌شده دقیقاً یک شعبه/کارگاه ثبت‌شده داشته باشد آن مورد به‌صورت خودکار انتخاب می‌شود؛
> اگر چند شعبه/کارگاه داشته باشد، فیلد انتخاب شعبه خالی می‌ماند و کاربر مجبور است از یک لیست
> صراحتاً یکی را انتخاب کند (و اگر انتخاب نکند، ارسال درخواست با پیام خطا مسدود می‌شود). در
> پیاده‌سازی جدید این تمایز وجود ندارد: حتی وقتی چند شعبه/کارگاه ثبت‌شده باشد، اولین مورد از لیست
> به‌طور خودکار و بدون تأیید کاربر انتخاب می‌شود و کاربر می‌تواند بدون توجه به این انتخاب ادامه
> دهد — درحالی‌که این شعبه/کارگاه ممکن است شعبه‌ی درستی برای این درخواست نباشد.

**Suggested change:** only auto-select when `branches.size == 1`, leaving `selectedBranch = null`
(and `canGoNextFromStep1` unsatisfied) when there is more than one, matching old_android's
single-vs-multiple distinction.

> **Round 2 (commit `d7e51f877`):** Fixed — `branches.firstOrNull()` → `branches.singleOrNull()`,
> the exact minimal change, matching `old_android`'s single-vs-multiple distinction exactly. Both
> the single-branch auto-select and the multiple-branch no-auto-select cases now have a dedicated
> test.

  matching `old_android`'s `diffDayStartAndEndRest > 365` check.

  `bimKind`/`groupSelectDate`/`groupReciveDate` state machine.
- `illnessKind`/`workStatus` code values (`"1"`/`"2"`) match the legacy `bimKind`/`bimWkstatus`
  values sent to the server.
- Data-layer test coverage (mapper, repository, API service, remote data source, use cases) is
  thorough and present for every layer that does have tests.
- DI and navigation wiring for the new module are correctly registered.
