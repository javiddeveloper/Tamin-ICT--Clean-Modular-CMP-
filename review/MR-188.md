## 1. `Paginator` locks pagination forever after any first-page offline fallback — High

**File:** `core/core-domain/src/commonMain/kotlin/com/tamin/taminhamrah/paging/Paginator.kt:104-109`

```kotlin
private fun isEndReached(page: PageDN<T>, loadedCount: Int): Boolean {
    val total = page.total
    return page.items.isEmpty() ||
        page.items.size < config.pageSize ||
        (total != null && loadedCount >= total)
}
```

Both new offline-first repositories that feed this `Paginator` set `total = cached.size` when the first page's remote call fails and a local cache exists (`PersonalInboxRepositoryImpl.getInboxItemsPage:69`, mirrored by the `getCitiesByProvince`/`getProvinces` cache-fallback shape). Because `total` then equals `loadedCount` exactly, `isEndReached` returns `true` and the paginator sets `endReached = true` in its state.

**Failure scenario:** user opens My Inbox while offline (or during a transient network blip). The first page is served from cache with `total = cached.size`, and `endReached` becomes permanently `true` for that generation. When connectivity returns, `OnLoadMore` is a no-op (`Paginator.load` early-returns while `endReached`), so the user can never page past whatever was cached — the inbox looks artificially short until they trigger a full `RefreshInbox`.

**Suggested change:** don't report a `total` on the offline-fallback path (leave it `null`), or introduce a separate flag (e.g. `isFromCache`) that `isEndReached` treats as "not yet known," so pagination can resume once the network is available again.

## 2. Edit mode never reloads the cities/branches lists for the restored province/city — High

**File:** `feature/history-objection/src/commonMain/kotlin/com/tamin/taminhamrah/feature/historyobjection/ui/stepper/HistoryObjectionStepperViewModel.kt:351-369, 381-414`

```kotlin
private fun loadInitialData(editRequestNumber: String?, editRowIndex: String?): Flow<PartialState> = flow {
    emit(PartialState.ModeInitialized(...))
    emit(PartialState.Loading(true))
    try {
        emitAll(merge(loadProvinces(), loadInsuranceTypes()))
        if (editRequestNumber != null) {
            loadEditModeData(editRequestNumber, editRowIndex)?.let { emit(it) }
        }
    } catch (e: Exception) {
        emit(PartialState.Error(e.toSingleLineMessage()))
    }
    emit(PartialState.Loading(false))
}
```

`loadEditModeData` (line 381) restores `selectedProvince`/`selectedCity`/`selectedBranch` directly from the saved record via `EditModeDataLoaded`, but only provinces and insurance types are ever fetched (`loadProvinces()`, `loadInsuranceTypes()`). `getCitiesByProvinceUseCase`/`getBranchesUseCase` are only invoked from `handleProvinceSelected`/`handleCitySelected` (lines 248-276), which fire on user *selection*, not on state restore.

**Failure scenario:** the user opens "edit" on an existing not-exist-history request. Province, city and branch are shown as already selected (their names come straight from the saved record), but `state.cities`/`state.branches` are still empty lists. `OnShowCityPicker`/`OnShowBranchPicker` (lines 118-174) only guard on `selectedProvince`/`selectedCity` being non-null, not on the lists being populated — so if the user taps "change city" or "change branch" to correct a mistake, the bottom sheet opens empty instead of showing the real options.

**Suggested change:** after (or as part of) `loadEditModeData`, also kick off `getCitiesByProvinceUseCase(provinceCode)` and `getBranchesUseCase(cityCode)` so `state.cities`/`state.branches` are populated before the user can open either picker.

## 3. Pensioner/anonymous eligibility gate from `old_android` not ported — High, needs confirmation

>
> در کد جدید هیچ بررسی مشابهی برای نوع کاربر پیدا نشد — نه در `HistoryObjectionViewModel`، نه در مسیر ناوبری. یعنی هر کاربری (از جمله بازنشسته یا کاربر مهمان، اگر چنین مفهومی هنوز در برنامه‌ی جدید معنا داشته باشد) می‌تواند وارد این فیچر شود و درخواست ثبت کند، در حالی که این سرویس اساساً برای بازنشستگان کاربردی ندارد.

I could not find a `userType`/`insuredType` concept anywhere yet in `core-domain`/`core-data` of this codebase, so this gate may simply not exist yet as shared infrastructure in the KMP rewrite and could be intentionally out of scope for this particular ticket (a separate, app-wide eligibility mechanism). Flagging as `needs confirmation` rather than a definite bug — please confirm whether this check belongs in this MR or is deliberately deferred to another task.

## 4. Remote fetch errors are silently swallowed once a local cache exists — Medium

**File:** `core/core-data/src/commonMain/kotlin/com/tamin/taminhamrah/data/repository/CityProvinceRepositoryImpl.kt:68-84, 92-108`

```kotlin
override fun getCitiesByProvince(provinceCode: String): Flow<List<CityDN>> = flow {
    val localCities = cityProvinceDao.getCitiesByProvinceCode(provinceCode).first()
    emit(localCities.map { it.toDomain() })

    try {
        val response = commonRemoteDataSource.getCitiesByProvince(CityByProvinceQuery.build(provinceCode))
        cityProvinceDao.replaceCitiesForProvince(provinceCode, response.list.map { it.toEntity() })
    } catch (e: Exception) {
        if (localCities.isEmpty()) throw e
    }

    emitAll(...)
}.distinctUntilChanged()
```

Both `getCitiesByProvince` and `getProvinces` are new in this MR. When the remote call fails but a local cache is non-empty, the exception is discarded and the flow silently re-emits stale cached data — no error state ever reaches `HistoryObjectionStepperViewModel`. This mirrors the pre-existing `getInboxItems` offline-first pattern in this codebase, so it's a consistent style choice, not an isolated one-off — but unlike `PersonalInboxRepository`, nothing here surfaces "this data may be stale" to the UI.

**Failure scenario:** server call for cities/provinces fails (expired token, 500, timeout) while a stale local cache exists from a previous session. The province/city picker silently shows the old list with no error banner and no retry affordance; a user submitting a request based on outdated province/city data has no way to know.

**Suggested change:** either keep swallow-on-cache-hit as intentional and add a lightweight staleness indicator in the picker, or propagate the exception as a non-fatal warning event so the ViewModel can show a dismissible "showing cached data" message.

## 7. `GetCitiesByProvinceUseCase` duplicates `GetCitiesUseCase(provinceCode=...)` — Low

**File:** `core/core-domain/src/commonMain/kotlin/com/tamin/taminhamrah/useCases/common/GetCitiesByProvinceUseCase.kt`

```kotlin
class GetCitiesByProvinceUseCase(
```

`GetCitiesUseCase` already accepts an optional `provinceCode` (`repository.getCities(cityName, provinceCode)`, remote-fetch + client-side filter). **Suggested change:** if the offline-first behavior is the one going forward, consider migrating other callers of `GetCitiesUseCase(provinceCode=...)` onto `GetCitiesByProvinceUseCase` and documenting when each should be used, or note the intentional split if there's a reason (e.g., search-by-name vs. by-province needing different caching).
