## 1. Lab-result/prescription download buttons now keyed on record category instead of the per-record `flagSata` flag — High

**File:** `feature/treatment/src/commonMain/kotlin/com/tamin/taminhamrah/feature/treatment/ui/records/RecordDetailScreen.kt:230`, `feature/treatment/src/commonMain/kotlin/com/tamin/taminhamrah/feature/treatment/ui/model/RecordTab.kt:42,96`

```kotlin
// RecordTab.kt
val hasLabResult: Boolean get() = this == PARACLINIC
fun String.hasLabResult(): Boolean = RecordType.fromId(this)?.hasLabResult == true

// RecordDetailScreen.kt
if (type.hasLabResult()) TaminTopAppBarButton(
    icon = vectorResource(Res.drawable.ic_tamin_print),
    contentDescription = stringResource(Res.string.prescription_lab_result_cd),
    onClick = { showing = TreatmentRecordPdfExport.LAB_RESULT },
)
```

`old_android/.../electronicPrescription/adapter/ElectronicPrescriptionAdapter.kt:28-36` and
`ElectronicPrescriptionListFragment.kt:80-95` decide this **per record**, from the `flagSata`
field the record itself carries — not from its category:

```kotlin
btnDownload.isVisible = item.flagSata != "1"        // hidden entirely when "1"
if (item.flagSata == "2") { /* fetch lab result */ } else { /* fetch prescription PDF */ }
```

`flagSata` still flows all the way through the new stack (`ElectronicPrescriptionPR.flagSata`)
but is **not consulted** for either button's visibility here. Instead:
- The "دریافت نسخهٔ الکترونیک" button is now shown unconditionally, regardless of `flagSata` —
  the old app hid it entirely when `flagSata == "1"`.
- The "دریافت جواب آزمایش" button is now shown for the whole PARACLINIC category, regardless of
  whether that specific record's `flagSata` is actually `"2"`.

**Failure scenario:** a PARACLINIC record whose lab result isn't ready yet (`flagSata` not
`"2"`) still shows the "دریافت جواب آزمایش" button; tapping it calls
`downloadLabResultPdfUseCase`, which hits a distinct backend endpoint with nothing to return for
that record — a button that can only fail, on exactly the class of records this MR's own code
comment says it was trying to fix. Conversely, records where the old app hid the download
entirely (`flagSata == "1"`) now always show an active button.

**Suggested change:** gate both buttons on `record.flagSata` (hide when `"1"`, choose the
lab-result endpoint only when `"2"`) as old_android did, or confirm with product/backend that
`flagSata` is genuinely redundant with category before dropping it from this decision.

> **مغایرت بیزینسی:** در نسخه‌ی قدیمی، نمایش/عدم‌نمایش دکمه‌ی «دریافت نسخه» و تشخیص اینکه دکمه
> باید «دریافت نسخه الکترونیک» باشد یا «دریافت جواب آزمایش»، بر اساس یک فیلد مخصوص همان
> رکورد تعیین می‌شد؛ یعنی این تصمیم به ازای هر نسخه/رکورد جداگانه گرفته می‌شد، نه بر اساس نوع
> کلی سربرگ (مثلاً پاراکلینیک بودن). در کد جدید این تصمیم فقط بر اساس نوع سربرگ گرفته می‌شود و
> آن فیلد مخصوص رکورد دیگر در این تصمیم استفاده نمی‌شود. نتیجه این است که ممکن است برای یک رکورد
> پاراکلینیک که هنوز جواب آزمایشش آماده نیست، دکمه‌ی دریافت جواب آزمایش نمایش داده شود و با کلیک
> خطا بدهد؛ و همچنین دکمه‌ی دریافت نسخه که در نسخه‌ی قدیم گاهی به‌طور کامل مخفی می‌شد، در نسخه‌ی
> جدید همیشه نمایش داده می‌شود.

## 3. No test covers the concurrency fix itself — Medium

**File:** `feature/treatment/src/commonTest/kotlin/com/tamin/taminhamrah/feature/treatment/ui/prescriptions/PrescriptionsViewModelTest.kt`

This file was not touched by the MR despite its core claim being a concurrency-bug fix in
`PrescriptionsViewModel`. The fix itself is real and well-targeted (confirmed:
`BaseViewModel.handleIntent` merges intents via `flatMapMerge`, so the old per-intent `flow{}`
really did leak concurrent in-flight requests writing into shared state; moving to a persistent
`flatMapLatest` pipeline driven by a replay-1 `MutableSharedFlow<RecordListQuery>` closes it
correctly). But the existing tests only send a single `LoadList` intent per test, never
repeated/rapid ones, so nothing in the suite would catch a regression of the exact bug this MR
fixes.

**Suggested change:** add a test sending two `LoadList` intents in quick succession with
different `requestTypeIds`/repository responses that resolve out of order, asserting the final
state reflects only the second query.

> **سناریوی بیزینسیِ بدون تست:** وقتی کاربر به‌سرعت بین تب‌های سوابق درمانی جابه‌جا می‌شود یا چند
> بار پشت‌سرهم جستجو/فیلتر می‌کند، باید همیشه فقط نتیجه‌ی آخرین درخواست روی صفحه نمایش داده
> شود، نه نتیجه‌ی یک درخواست قدیمی‌تر که دیرتر برمی‌گردد. این رفتار الان در کد پیاده شده ولی
> هیچ تستی وجود ندارد که نشان دهد وقتی دو یا چند درخواست پشت‌سرهم و هم‌زمان ارسال می‌شود، فقط
> نتیجه‌ی آخری در نهایت روی صفحه می‌ماند.

## 4. Title-centering fix doesn't scale past one action button — Low

**File:** `core/core-ui/src/commonMain/kotlin/com/tamin/taminhamrah/ui/components/TaminTopAppBar.kt:113-116`

```kotlin
Box(
    modifier = Modifier
        .fillMaxWidth()
        .padding(horizontal = HEADER_BUTTON_SIZE + Spacing.sm),
) { /* title */ }
```

The comment above this block says the bug being fixed was "give one side a second action and a
title laid out between them slides off center" — but the fix still reserves a fixed,
single-button width of padding on both sides, regardless of how many buttons actually sit in the
end caps. `RecordDetailScreen.kt` (this same MR) now puts up to three buttons (share, download,
conditional lab-result) in the action slot, so a long enough title can render underneath the 2nd
and 3rd action icons — the reserved clearance doesn't scale with the real cap width.

**Suggested change:** measure each header slot's actual width (e.g. via `SubcomposeLayout` or
`onSizeChanged` feeding into the title's padding) instead of assuming one fixed button width per
side.

## What was done well

- **`PersianTextSearch.kt` is genuinely solid**: correctly folds Arabic/Persian letter variants
  (ي/ك/ة/ؤ, alef forms), strips tatweel/diacritics, treats ZWNJ/ZWJ as word breaks, folds
  Arabic-Indic and Persian digits to ASCII, and is order/spacing tolerant. Its test file covers
  all claimed character classes plus negative cases and an empty-query case. No equivalent
  client-side search existed in `old_android` for this screen, so this is new value with nothing
  being dropped.
- **The `PrescriptionsViewModel` concurrency fix is real and well-targeted** — see item 3 for the
  technical detail. The reasoning is well-documented in code comments.
- The second, same-titled commit is not a no-op — it's a real, small follow-up fixing
  `Uri.parse(...)` → `.toUri()` in `ExternalAppLauncher.android.kt`.
- `TreatmentSurface.kt` is a thin, `internal`, additive wrapper around the existing
  `taminSurface`/`core-ui` primitives, not a duplicate reimplementation — the component-reuse
  rule was respected.
- `CopyIconButton`/`PlainTextClipEntry`/`ExternalAppLauncher.shareText`/`openUrl` are wired
  consistently through both Android and iOS actuals and genuinely adopted (not dead code) in
  `RecordDetailComponents.kt`, `TaminPrimitives.kt`'s `DetailRow`, and most of `BankAccountScreen.kt`.
- No commented-out code was found anywhere in the diff.
- `StatTileStyle`/`CostSplitTiles` consolidation removes real duplication — three near-identical
  `StatTile` rows collapsed into one shared composable used by the timeline, detail screen, and
  per-item card.
