## 2. Hardcoded OAuth client secret ships in the release binary — High, needs confirmation

**File:** `feature/developerOptions/src/commonMain/kotlin/com/tamin/taminhamrah/feature/developerOptions/debugLogin/BackToBackCredentials.kt`

```kotlin
/**
 * Hardcoded at explicit request and accepted risk: `feature:developerOptions` ships unminified in
 * every build, so both values are readable in the release APK/IPA by anyone who extracts it.
 * Reaching the screens that use them is gated on `AppConfig.isDebug`, but that gate does not strip
 * the string literals themselves.
 */
internal object BackToBackCredentials {
    const val CLIENT_ID = "442e832b206822656b5f816f6a630383"
    const val CLIENT_SECRET = "04136b343832526014771644295c43636e4323051a805f4e1c3b192589820373"
}
```

The KDoc already states the risk accurately and precisely — this echoes MR !211's item 2 finding on
this same module (`isMinifyEnabled = false` on the release build type means nothing here is
stripped). The `AppConfig.isDebug` gate only blocks the *app's own screens* from reaching these
constants; it does nothing to stop someone who has extracted the release APK/IPA from reading the
literal and calling the account server's `client_credentials` token endpoint directly with it,
bypassing the app and its debug gate entirely. A mobile client can never truly keep a secret, but
shipping one that's reachable in a *release* binary (rather than, say, a `debug`-only source set or
BuildConfig field that's excluded from release) is the avoidable part.

Not marking this a definite bug — the comment suggests this was a deliberate, informed trade-off —
but it needs to be an *explicit, recorded* one, not something a reviewer discovers reading the diff.

**Needs confirmation:** was this accepted by whoever owns the account/auth server side (since the
real exposure is server-side: anyone with this secret can call the gateway directly)? If yes, say so
here and it'll be recorded as `➖ rejected (with reason)`. If not, the cheapest fix mirroring MR
!211's resolution is to keep `BackToBackCredentials` out of the release binary the same way
`BaseUrlPresets` was fixed there — a `debug`-only source set, or deriving the values from a
`BuildConfig` field that's empty/absent in release.

## 4. Active slot doesn't reset after a real login while a debug slot is active — Low

**Files:** `core/core-datastore/.../TokenStoreManagerImpl.kt` ·
`core/core-network/.../repository/authRepository/AuthRepositoryImpl.kt`

Debug-build-only edge case: if a tester switches the active slot to `BACK_TO_BACK` via Token
Manager, then performs a fresh real PKCE login without explicitly signing out first, the new token is
correctly written to the `USER` slot — but `switchTokenSlot` is only called from
`DebugClientCredentialsLoginUseCaseImpl` and `TokenManagerViewModel`, never from the PKCE login path,
so `activeSlot` stays on `BACK_TO_BACK`. The app keeps sending the stale back-to-back bearer on every
request until the tester manually re-activates `USER` in Token Manager — confusing to debug, though
confined to `AppConfig.isDebug` builds so not a shipped-app risk.

**Suggested change:** have the real PKCE login path call `switchTokenSlot(TokenSlot.USER)` (or
equivalent) unconditionally on success, the same way logout already resets slot-related state.

## 6. Persian-numeral input erases what was already typed — High

**File:** `feature/payment/src/commonMain/kotlin/com/tamin/taminhamrah/feature/payment/ui/checkout/PaymentCheckoutViewModel.kt:57`

```kotlin
is PaymentCheckoutIntent.PayerIdentifierChanged -> flow {
    val digits = intent.identifier.filter { it in '0'..'9' }
```

The field's displayed value is rendered through `.toPersianDigits()`
(`PaymentCheckoutScreen.kt:199`), so what the user sees — and what a Persian-numeral keyboard types
back into the field — is Persian digit glyphs (۰-۹), not ASCII. The filter here keeps only ASCII
`'0'..'9'`, so it silently drops every Persian digit already in the field on each keystroke. This
also contradicts `PayerType.kt`'s own doc comment, which says to *fold* Persian digits to ASCII
before validating, not discard them.

> **سناریوی بیزینسی:** کاربری که برای شخص دیگری (نه خودش) در حال پرداخته و باید کد ملی طرف مقابل را
> تایپ کند، اگر روی صفحه‌کلید فارسی/اعداد فارسی تایپ کند، عملاً هیچ‌وقت نمی‌تواند بیشتر از یک رقم
> وارد کند — هر رقم جدید، ارقام قبلی را پاک می‌کند چون فیلتر فقط ارقام انگلیسی را نگه می‌دارد. این
> دقیقاً همان چیزی است که کامنت خودِ کد در `PayerType.kt` می‌گوید باید «تبدیل» شود، نه «حذف».

**Suggested change:** fold Persian digits to ASCII before filtering (e.g. via the existing
`toEnglishDigits()`/equivalent used elsewhere in the codebase), the same direction `PayerType.kt`'s
doc comment already prescribes.

## 7. "Pay for myself" can submit with an empty national code — Medium

**File:** `feature/payment/src/commonMain/kotlin/com/tamin/taminhamrah/feature/payment/ui/checkout/contract/PaymentCheckoutContract.kt:38-41`

```kotlin
val canSubmit: Boolean
    get() = !isLoading && !isSubmitting && !isExpired && !hasOpenedGateway &&
        preview.isPayable &&
        (!payerType.needsIdentifier || (payerIdentifier.isNotBlank() && !identifierError))
```

For `PayerType.CURRENT_USER`, `needsIdentifier` is `false`, so `canSubmit` never checks
`currentUserNationalCode`. That value comes from `GetCurrentUserNationalCodeUseCase`, which swallows
any failure and returns `null` (`GetCurrentUserNationalCodeUseCaseImpl.kt:19-22`) — in that case
`currentUserNationalCode` stays `""` and the pay button is still enabled. `PayClicked`
(`PaymentCheckoutViewModel.kt:75-78`) then sends `createPaymentLink(ticket, CURRENT_USER, "")` — an
empty identifier reaches the gateway instead of the user being told the app couldn't verify who they
are.

> **سناریوی بیزینسی جاافتاده:** اگر به هر دلیلی (خطای شبکه، خطای سرور و…) اپ نتواند کد ملی کاربر
> لاگین‌شده را بخواند، دکمه‌ی پرداخت غیرفعال نمی‌شود و کاربر می‌تواند با کد ملی خالی درخواست پرداخت
> بفرستد، به‌جای اینکه پیام خطا ببیند و دوباره تلاش کند.

**Suggested change:** include `currentUserNationalCode.isNotBlank()` in `canSubmit` for
`PayerType.CURRENT_USER`, and/or surface an error state when the load fails instead of leaving it
silently blank.

## 8. Debug-only concerns wired permanently into shared production logic — Medium

**Files:** `core/core-domain/.../useCases/agent/CheckChatAllowedUseCase.kt` ·
`core/core-network/.../repository/authRepository/AuthRepositoryImpl.kt:31-36`

Two places in this MR thread a debug-only concept into code every build/user runs:

- `CheckChatAllowedUseCase` — the AI-chat gate every user hits — now also writes the token into
  `TokenSlot.AGENT` on every successful check, purely so the debug Token Manager screen has something
  to show. This use case's job is "is chat allowed," not "keep the debug token screen in sync."
- `AuthRepositoryImpl.isLoggedIn`, the app-wide login gate, is now `combine`d with
  `activeSlotFlow()` — a flow that only changes value in debug builds — so every user's login check
  permanently carries a debug-only re-evaluation trigger it will never actually need.

Both are commented as intentional and are release-safe as written (the combine is a no-op in release
per the comment, and the slot write doesn't change chat-gating behavior), so this is a design/altitude
note rather than a functional bug: shared, always-on infrastructure now carries logic whose only
reason to exist is a debug screen. A cleaner shape would have the debug screen pull/observe the token
and slot from wherever the debug feature already needs it, without the production use case/repository
having to know the debug feature exists.

## 9. Payment mock-mode gate doesn't match the pattern it claims to follow — Low

**File:** `core/core-datastore/src/commonMain/kotlin/com/tamin/taminhamrah/core/datastore/DeveloperOptionsRepositoryImpl.kt:60-61`

```kotlin
/**
 * Guarded exactly like [getEffectiveBaseUrl]: a release build must never answer a payment call
 * from a fake, whatever a previous debug install left in shared app storage.
 */
override fun getPaymentMockMode(): PaymentMockMode =
    if (AppConfig.isDebug) _paymentMockMode.value else PaymentMockMode.DISABLED
```

`getEffectiveBaseUrl()` right above it gates on the constructor-injected `isDebug` field (so tests can
control it without touching the real `AppConfig`), but `getPaymentMockMode()` gates on the global
`AppConfig.isDebug` directly — not what the doc comment says. Harmless in production (the constructor
defaults `isDebug` to `AppConfig.isDebug` anyway), but it means this method can't be exercised the
same way `DeveloperOptionsRepositoryImplTest.kt` already tests the base-URL override, and it's an
inconsistency inside the same class between two methods described as working "exactly" alike.

**Suggested change:** use the injected `isDebug` field, matching `getEffectiveBaseUrl()`.

## What was done well

- **The payment module matches its own design doc precisely** — every claim in `Payments.md` about
  gateway-URL confinement, ticket release, the `PayerType` enum, the unconfirmed-payment UX, and
  `VERIFYING`-counts-as-settled parity with `old_android` was independently verified true. This is
  the strongest review outcome seen across this feature's family of MRs.
- **The highest-risk scenario in the payment flow has a direct test.** `PaymentCheckoutViewModelTest`
  covers both "running out of time releases the ticket" and "backing out of a live ticket asks first,
  then releases it" — the exact scenario the doc calls out as the one that must not regress (an
  abandoned ticket blocking the next attempt on the same debt).
- **The mock gateway's "every run gets a fresh ticket" fix is documented as a real bug that was
  caught and fixed**, not silently corrected — `Payments.md` records it so it doesn't get
  reintroduced.
- **`isPaidButUnconfirmed` is treated as the distinct, dangerous state it is** — separate visual
  treatment from a plain failure, with a reference number and a pointer to a branch, matching the
  doc's explicit statement that telling an already-paid user to pay again is the worst outcome this
  screen could produce.
- **The debug-only nature of the token-slot feature is consistently gated** through the same
  `AppConfig.isDebug` pattern already established for base-URL overrides and the payment mock — no
  new gating mechanism was invented, and no leak path from a debug slot into a real user's request
  was found anywhere in `AuthRepositoryImpl`/the Ktor bearer provider.
- **UI strings are properly externalized** across both halves of this MR — `strings.xml` gained the
  relevant entries and both feature areas read through `stringResource(...)`, with the payment mock's
  debug-only raw Persian payloads and the token screens' raw diagnostic strings being reasonable,
  clearly-scoped exceptions rather than oversights.
