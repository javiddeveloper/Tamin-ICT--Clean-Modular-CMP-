("superpowers") — per-task status reports ("Status: DONE", file-change tables, self-review
checklists, `gradlew` verification transcripts) and a separate design/scope doc. None of them
follow this project's actual documentation convention (`docs/vault/`, Obsidian-style), and this MR
did add a `.gitignore` entry for a *different* local-only folder
(`feature/pensionSurvivor/src/localMocks/`) in the same commit — suggesting the intent was to keep
working files local, but these five slipped through.

**Failure scenario:** nothing breaks functionally, but these files accumulate in the repo history
as noise unrelated to the shipped feature, and a future contributor searching `docs/` for real
project documentation has to first figure out `docs/superpowers/specs/...` isn't part of the
`docs/vault/` system this project actually uses.

**Suggested change:** remove these five files from the branch (or add `.superpowers/` and
`docs/superpowers/` to `.gitignore` if this tooling is used repo-wide and its output is meant to
stay local, matching how `review/` and `CLAUDE.local.md` are already excluded).

> **Round 1 response (user, 2026-08-26):** confirmed intentional — not a problem, no change
> needed. Marked `➖ rejected (with reason)`.

## What was done well

- The survivor relation-classification rules (`SurvivorRelationClassifier.kt`) — tendency-code
  groupings, the "adult son ≥ 19" / "adult daughter ≥ 16" age thresholds, gender-aware child
  classification, and the age-from-birthdate formula (`diffDays / 365`, defaulting to 20 on a
  blank/invalid DOB) — were checked line-by-line against `old_android`'s
  `SurvivorInfoFragment.getRelationType()` / `Utility.getTendencyResId()` / `Utility.getAge()` and
  match exactly, including the special-case `"124"` tendency code and the step-child codes.
- The commit history shows real, self-caught fixes before this even reached review: a debugging
  commit that temporarily commented out the deceased-document upload gate was later explicitly
  reverted ("restore deceased upload gates") — verified directly in the current code that
  `areDeceasedDocumentsComplete` still gates both the Step 2 "next" button
  (`PensionSurvivorScreen.kt`) and the ViewModel's own guard (`PensionSurvivorViewModel.kt:317`),
  so the temporary bypass did not leak into the final diff.
- The legacy rules PDF (`rulesAndRegulationsHtmlFile/rule_pension_survivor.pdf`) was tracked down
  and bundled as a real resource (`files/rule_pension_survivor.pdf`) rather than left as the
  placeholder toast an earlier task report describes — the rules step is fully functional, not a
  stub.
- `requestId` selection (`loadSurvivorInfo`/wherever the final confirmed-survivors list is loaded)
  correctly handles the case of multiple confirmed final requests: picks the highest non-null id
  via `mapNotNull { it.request?.id }.maxOrNull()` rather than assuming exactly one, and emits a
  warning when more than one is returned — a real edge case handled deliberately, not ignored.
- No hardcoded Persian strings found in any ViewModel/Contract file in the feature.
- DI (`pensionSurvivorModule` registered in `shared/.../di/Koin.kt`) and navigation
  (`TaminHamrahNavGraph.kt`/`FeatureNavigation.kt` switched to the new module, the old
  `feature/pensioner` stub fully removed rather than left dangling) are both correctly wired.
- This branch's own test-only `FakeUserRepository` for the inspection feature already has the
  `getWageCertificateReport` override — the exact interface-implementation gap found on MR !194's
  branch after a `develop` merge — so no fallout from that here.
- Good test coverage: `PensionSurvivorViewModelTest`, `SurvivorInfoViewModelTest`, and a dedicated
  `SurvivorRelationClassifierTest` (116 lines) exercising the classification rules directly.
