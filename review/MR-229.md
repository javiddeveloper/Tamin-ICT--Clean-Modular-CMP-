## 1. Default `premium` value is a literal placeholder string, not real data — High

**Files:**
`core/core-network/src/commonMain/kotlin/com/tamin/taminhamrah/model/fractionContract/MakeFractionContractRequestDTO.kt`
`core/core-domain/src/commonMain/kotlin/com/tamin/taminhamrah/repository/fractionContract/FractionContractRepository.kt`
`core/core-domain/src/commonMain/kotlin/com/tamin/taminhamrah/useCases/fractionContract/MakeFractionContractUseCase.kt`
`core/core-network/src/commonMain/kotlin/com/tamin/taminhamrah/dataSource/fractionContract/FractionContractRemoteDataSource.kt`

```kotlin
/** Body matches legacy `FractionRequestDataModel` — literal premium string. */
@Serializable
data class MakeFractionContractRequestDTO(
    @SerialName("premium") val premium: String = "this.premium",
)
```

```kotlin
interface FractionContractRepository {
    fun checkAgeAndHistory(): Flow<FractionEligibilityDN?>
    fun makeFractionContract(premium: String = "this.premium"): Flow<FractionContractResultDN>
}

class MakeFractionContractUseCase(...) {
    operator fun invoke(premium: String = "this.premium"): Flow<FractionContractResultDN> = ...
}

interface FractionContractRemoteDataSource {
    suspend fun makeFractionContract(
        request: MakeFractionContractRequestDTO = MakeFractionContractRequestDTO(),
    ): FractionContractResultDTO
}
```

This is a real defect that predates this MR: `old_android`'s own model
(`ui/home/services/contracts/model/FractionRequestDataModel.kt:3`) has the identical bug —
`data class FractionRequestDataModel(val premium: String = "this.premium")` — and its one call site,
`ContractViewModel.makeFractionContract(req: FractionRequestDataModel = FractionRequestDataModel())`,
sits next to a `/* fake data */` comment, strongly suggesting this whole legacy flow was never
actually wired to a real caller. So this isn't something this MR introduced — it's a faithful port of
a pre-existing placeholder that was apparently never fixed because it was never really exercised.

The reason it's still worth a High-severity item **now**, in this MR specifically: this MR pins the
literal into **four** separate declarations across three architectural layers (request DTO,
repository interface, use case, remote-data-source interface) — multiplying a single old bug into
four places a future fix has to touch — and, more importantly, **the tests actively assert it as
correct behavior** rather than flagging it:

```kotlin
// FractionContractUseCasesTest.kt:78
assertEquals("this.premium", repository.lastPremium)

// FractionContractRepositoryImplTest.kt:93
assertEquals("this.premium", fake.lastRequest?.premium)

// FractionContractRemoteDataSourceImplTest.kt:94
assertEquals("this.premium", fakeApiService.lastRequest?.premium)
```

All three tests call the use case/repository/data-source with **no** `premium` argument and then
assert that the literal string reached the wire. If Phase 2 wires a real caller that also forgets to
pass a real premium (an easy mistake with a default this innocuous-looking), the request body will
contain the literal text `"this.premium"` as the amount, and these three tests will keep passing —
they'd need to be *changed* to catch that, not just left alone.

**Suggested change:** drop the default entirely (make `premium` a required parameter with no default
at every layer), so a Phase-2 caller that forgets to pass it fails to compile instead of silently
sending placeholder text. Update the three tests to pass an explicit, realistic premium value.

> **Round 2 — ✅ fixed, exactly as suggested.** `premium: String` is now a required parameter with no
> default at all four sites (`MakeFractionContractRequestDTO`, `FractionContractRepository`,
> `MakeFractionContractUseCase`, `FractionContractRemoteDataSource`) — a Phase-2 caller that forgets
> to pass it now fails to compile rather than silently sending placeholder text. All three tests that
> previously asserted `"this.premium"` now pass an explicit `premium = "1500000"` and assert that
> value reaches the wire instead.

## 2. `makeFractionContract`'s error paths are untested — Low

**Files:**
`core/core-network/src/commonTest/kotlin/com/tamin/taminhamrah/dataSource/fractionContract/FractionContractRemoteDataSourceImplTest.kt`
`core/core-network/src/commonTest/kotlin/com/tamin/taminhamrah/apiService/fractionContract/FractionContractApiServiceTest.kt`

`checkAgeAndHistory` gets three scenarios in the data-source test (success, null-data, error-status)
plus a network-exception case, and two in the API-service test (success, null-data). `makeFractionContract`
gets exactly one test in each file — the success path only. Nothing exercises what happens when
`makeFractionContract` hits an HTTP error status, the `hasProblems` branch in
`extractData`/`extractNullableData`, or a network exception — even though `checkAgeAndHistory` right
next to it in the same class is held to that standard.

**Suggested change:** mirror `checkAgeAndHistory`'s error-path tests for `makeFractionContract` —
at minimum an HTTP-error-status case and a network-exception case.

> **Round 2 — ✅ fixed.** `makeFractionContract_errorStatus_throws` and
> `makeFractionContract_networkException_throwsNoConnection` were added to the data-source test,
> mirroring `checkAgeAndHistory`'s coverage; `makeFractionContract_nullData_isAllowed` was added to
> the API-service test. A follow-up commit (`e80dc3c5d`) also caught and fixed a real test-correctness
> bug in the new network-exception case (and the pre-existing `checkAgeAndHistory` one next to it): a
> plain `RuntimeException` doesn't actually get classified as `NO_CONNECTION_ERROR` by
> `ErrorParserImpl` — only an IO-shaped exception does — so both tests now throw `FakeIOException()`
> instead, which is what makes them meaningful rather than accidentally-passing.

## 3. Address-joining logic tested only at the extremes — Low

**File:** `core/core-ui/src/commonTest/kotlin/com/tamin/taminhamrah/mapper/fractionContract/FractionContractUiMapperTest.kt`

`toPresentation()`'s `branchAddress` builder has real conditional logic — a comma is inserted between
province/city and between city/address only when both neighboring parts are non-blank:

```kotlin
if (resolvedProvince.isNotBlank()) append(resolvedProvince)
if (resolvedProvince.isNotBlank() && resolvedCity.isNotBlank()) append(", ")
if (resolvedCity.isNotBlank()) append(resolvedCity)
if (resolvedCity.isNotBlank() && resolvedAddress.isNotBlank()) append(", ")
if (resolvedAddress.isNotBlank()) append(resolvedAddress)
```

The two existing tests cover "all three present" and "all three absent" — the two cases where the
conditional comma-insertion logic can't actually produce a wrong answer (no comma either way). None
of the partial combinations (province only; city only; province + address but no city; etc.) are
tested, which is exactly where a stray leading/trailing/double comma would show up if this logic
regresses later.

**Suggested change:** add one or two cases with exactly one or two of the three fields blank, e.g.
province blank + city/address present, asserting no leading comma and no double comma.

> **Round 2 — ✅ fixed.** Three new tests cover each single-field-blank case
> (`provinceBlank_noLeadingComma`, `cityBlank_noDoubleComma`, `addressBlank_noTrailingComma`). One is
> worth flagging even though it isn't a new bug: `cityBlank_noDoubleComma` asserts
> `"تهرانشعبه,۱"` — when the *middle* field (city) is blank, province and address run together with
> **no** separator at all, not just "no double comma" as the test name implies. Checked against
> `old_android`'s `ContractViewModel.loadBranchInfo():589-601` — this exact three-way
> append-with-conditional-comma shape, including this same no-separator-when-middle-blank behavior,
> is a byte-for-byte match with the legacy builder. So the test now correctly documents a faithfully
> ported quirk rather than a regression; not reopening as a new item since it matches source behavior
> and wasn't part of this item's original scope (untested logic, not wrong logic). Separately, the new
> code's `organizationAddress.replace("-", ",")` is applied correctly here — legacy's equivalent line
> (`ContractViewModel.kt:588`, `address.replace("-", ",")`) discards the replace's result without
> reassigning it, a no-op bug in the original that this port fixes rather than reproduces.

## What was done well

- **The data-layer wiring is correct end-to-end** — repository, use case, API service, and remote
  data source are all registered in the right core module (`dataKoinModule`, `domainModule`,
  `ApiClientsModule`, `remoteModule`), following the existing pattern exactly, even though the
  feature-level Koin module is (correctly, for a Phase-1 stub) empty.
- **The legacy field-name swap bug is caught and documented rather than silently reproduced.**
  `FractionEligibilityDTO.kt` notes that the wire fields `provinceCode`/`provinceName` are
  transposed in the legacy service response and maps them to the correctly-named domain fields with
  an explicit comment — exactly the kind of subtlety a rewrite could easily get backwards.
  (`old_android`'s own `CheckAgeAndHistoryResponse` has the same swap, unremarked.)
- **Naming conventions are followed precisely** across all four layers (`*DTO.kt`, `*DN.kt`, `*PR.kt`,
  `core-data/data/mapper/*Mapper.kt`, `core-ui/mapper/*Mapper.kt`), and the placeholder screen is
  clearly labeled as such in its own KDoc rather than left to look finished.
- **No hardcoded strings, no commented-out code, no stray `review/` files.**
- **Test coverage is present for every new layer** (mapper, repository, use cases, API service, remote
  data source) even at this early phase — items 2-3 are about coverage gaps within that testing, not
  an absence of it.
- **Round 2: the fix went further than the letter of the request.** Beyond the four items, the
  follow-up commit caught and fixed a real bug in how the network-exception tests classified their
  fake exception (`RuntimeException` vs. `FakeIOException`) — something that would have kept both the
  new and a pre-existing `checkAgeAndHistory` test passing for the wrong reason.
- **Round 2: the newly-added edge-case tests were checked against `old_android`, not just written to
  pass.** The address-builder's no-separator-when-blank quirk was traced back to a byte-for-byte
  matching legacy implementation rather than assumed to be a new bug, and the dash-to-comma
  replacement was confirmed to *fix* a no-op bug present in the legacy source.
