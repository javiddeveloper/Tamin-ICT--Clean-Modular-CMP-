## 1. Duplicate `TaminOptionSheetItem` — module does not compile — High

**File:** `core/core-ui/src/commonMain/kotlin/com/tamin/taminhamrah/ui/components/bottomsheet/TaminSearchableListSheet.kt:55`

```
e: TaminSearchableOptionSheet.kt:52:12 Redeclaration:
data class TaminOptionSheetItem : Any
```

This MR adds a brand-new file, `TaminSearchableListSheet.kt`, declaring its own
`data class TaminOptionSheetItem(...)` in the same package
(`com.tamin.taminhamrah.ui.components.bottomsheet`) as the existing
`TaminSearchableOptionSheet.kt:52`, which already declares a class of the same name. Two classes
with the same fully-qualified name in the same module is a hard Kotlin compile error —
`:core:core-ui:compileDebugKotlinAndroid` fails, which in turn fails every module that depends on
`core-ui`, including `:feature:contracts` itself. **This branch cannot be built.**

`TaminSearchableOptionSheet` (`fb78eb5a7`, already on `develop` from MR !193/EM-2593's ill-days
wizard) and the new `TaminSearchableListSheet` do almost the same job — "search and pick one item
from a list" — with about 80% overlapping code (dimensions, filtering, the item model). This is
exactly the case `CLAUDE.md` rule 5 exists for: *"Search `core-ui/ui/components/` before building a
new component"*. The new component was not just added redundantly — this MR also migrated two
**unrelated** existing features onto it (`IssuanceCertificateRecipientSheet.kt` in `:feature:pensioner`
and `RecipientsBottomSheet.kt` in `:feature:profile`, both rewritten in this diff to call
`TaminSearchableListSheet`), while a third caller (`IllDaysWizardScreen.kt`) was left on the old
`TaminSearchableOptionSheet` — so even once the name collision is fixed, the app will carry two
near-identical searchable-list sheets with call sites split across them.

**Suggested change:** don't add a second component. Extend `TaminSearchableOptionSheet` with
whatever `TaminSearchableListSheet` needed that it didn't have (its own domain model for callers
that don't want the key-value default, external search delegation, etc.), delete
`TaminSearchableListSheet.kt`, and point `SelectableField.kt` (this MR's own new caller) and the two
migrated screens at the one component.

## 2. Rules bottom sheet hardcoded to student content, used for every contract type — High

**File:** `core/core-ui/src/commonMain/kotlin/com/tamin/taminhamrah/ui/contractFlow/ContractRulesBottomSheet.kt`

```kotlin
fun ContractRulesBottomSheet(
    onDismiss: () -> Unit,
    title: String = stringResource(Res.string.contract_rules_sheet_title_student),
    ...
) {
    ...
    Text(text = stringResource(Res.string.contract_rules_sheet_student_p1), ...)
    // section1_item1..4, section2_item1..3 — all `..._student_...`
```

This is a brand-new, shared `core-ui` component this MR adds. Every one of its default parameters
and every body string is named `..._student_...`, and there is no parameter for which contract
type's rules to show. `strings.xml` has **no** `contract_rules_sheet_freelance_*`,
`_housewife_*`, or `_optional_*` entries at all — the student wording is the only wording that
exists.

The call site in `ContractFlowScreen.kt` — the **shared** screen used by all four
`ContractFlowConfig`s — calls it unconditionally with no arguments:

```kotlin
if (showRulesSheet) {
    ContractRulesBottomSheet(onDismiss = { showRulesSheet = false })
}
```

So a freelancer, a housewife, or an optional-insurance applicant who taps «قوانین» will be shown
the student insurance eligibility rules (age 18–50, student-certificate requirement, etc.) — legal
text describing a contract they are not signing. `ContractFlowConfig.rulesPdfPath` already exists
as a per-type field (`"rules.pdf"` for freelance/housewife/student, `"rules2.pdf"` for optional,
matching the legacy app's own `InsuranceContractFragment`/`OptionalContractFragment` split) but it
is declared and never read anywhere — the design clearly intended per-type content, it just was not
wired through to this sheet.

**Impact today vs. tomorrow:** if `FreelanceContractFlowConfig`/`HousewifeContractFlowConfig`/
`OptionalContractFlowConfig` are not yet reachable behind their feature flags, no real user hits
this today. But this is a shared `core-ui` file the sibling `EM-2612`/`EM-2613` (freelance) branches
will also compile against, so the landmine is set for whichever of those merges next — worth fixing
here rather than in whichever MR discovers it first.

**Suggested change:** parameterize the sheet by `ContractFlowConfig` (or by an explicit set of
string resources passed in), the same way `screenTitleRes`/`insuranceTypeLabelRes` already are, and
add the missing `strings.xml` entries for the other three types before their flows go live.

## 4. `ContractFlowViewModel` has no tests — Medium

**File:** `feature/contracts/src/commonMain/kotlin/com/tamin/taminhamrah/feature/contracts/flow/ui/ContractFlowViewModel.kt` (1,137 lines)

The only test in `:feature:contracts` for this entire flow is `ContractPreflightGateTest.kt` — pure
function tests for the eligibility gate. The ViewModel itself, which this MR adds and substantially
extends, has none. It is not a thin dispatcher: it holds the special-free-job branching (هلال احمر
day-limit check + eligibility call, دانشجوی پزشکی status check, each with its own locked premium
rate and `hidePremiumSlider`/`allowsPayment` side-effects), premium-rate/range selection per config,
file-upload validation, step-navigation, and submit handling — the kind of logic a future change to
any *one* contract type's flow can silently break for the other three, since they all share this
one ViewModel.

> **سناریوهای بیزینسی جاافتاده:** برای فلوی مشترک بین چهار نوع قرارداد، هیچ تستی مطمئن نمی‌شود که
> تغییری در فلوی یک نوع بیمه (مثلاً دانشجویی) رفتار سه نوع دیگر را خراب نمی‌کند. مهم‌ترین سناریوهایی
> که الان بدون محافظت هستند: انتخاب شغل خاص «هلال احمر» باید هم محدودیت روز ماه را چک کند و هم
> وضعیت صلاحیت کاربر را از سرویس بگیرد، و اگر هرکدام رد شود کاربر نباید بتواند ادامه دهد؛ انتخاب
> شغل خاص «دانشجوی پزشکی» باید وضعیت را از سرویس جداگانه بگیرد و رد شود اگر وضعیت مجاز نباشد؛ و
> برای هر دوی این حالت‌ها نرخ حق‌بیمه باید قفل شود و اسلایدر نرخ مخفی شود، تا کاربر نتواند نرخ
> دلخواه انتخاب کند.

**Suggested change:** at minimum, cover the two special-free-job branches above (success and
rejection for each), one premium-range/rate selection per relevant config, and the submit
success/failure paths — `ContractPreflightGateTest.kt`'s structure and the project's existing
`FakeContractsRepository` give a ready starting point.

## What was done well

- **The module consolidation itself is the right call.** Four near-identical Fragment/ViewModel
  pairs in `old_android` (`InsuranceContractFragment` covering freelance/housewife/student,
  `OptionalContractFragment` separately) become one config-driven flow with one shared screen and
  ViewModel — `ContractFlowConfig` names exactly the axes that differ between them (steps, whether a
  free-job step exists, whether gender is required, which premium-type code and rules doc apply),
  which is a real reading of the legacy business rules, not a mechanical copy.
- **The legacy `rules.pdf` / `rules2.pdf` split was preserved correctly** — `InsuranceContractFragment`
  and `OptionalContractFragment` in `old_android` serve different rule documents, and
  `ContractFlowConfig.rulesPdfPath` keeps that distinction (even though it is not wired through yet
  — see item 2).
- **`ContractPreflightGate` is a small, pure, well-tested function** — `resolvePreflightBlock` takes
  data in and returns an enum out, with `ContractPreflightGateTest.kt` covering not-registered,
  under-age, each contract-status code, and the cross-type "another active contract" case. This is
  exactly the shape the rest of the flow's business logic should have been given (see item 4).
- **The old `:feature:studentInsuranceContract` module was fully removed**, not left dangling
  alongside the new flow — `settings.gradle.kts`, `shared/build.gradle.kts`, `Koin.kt`, and
  navigation all had their references dropped together, and `grep` found no orphaned imports.
- **`MakeFreelanceContractUseCase` was cleanly retired** in favour of a generalized
  `MakeContractUseCase`, with the old use case, its DI registration, and its dedicated test all
  removed together rather than left as dead code.
